### 前言
一种应用程序编程接口（API 或 Web API），遵循一组关于应用程序如何使用 HTTP 方法相互通信的架构规则。 RESTful Web 服务使用 REST API 协议，因此有时也称为 RESTful API。所以RESTful API 是一种基于 **REST（Representational State Transfer）** 架构风格设计的 Web 服务接口。它强调 **资源（Resource）** 为核心，通过标准的 **HTTP 方法（GET, POST, PUT, DELETE 等）** 对资源进行操作，并使用 **URI（统一资源标识符）** 来唯一标识资源。

### 一、核心原则
 - 1、以资源为中心：
    1. 将系统中的数据或服务抽象为资源（例如：用户、订单、产品）。
    2. 一切操作都围绕资源的增删改查（CRUD）展开。
 - 2、统一接口：
    1. 资源标识： 使用 URI 唯一标识资源。https://api.example.com/users/123
    2. 资源操作： 使用标准的 HTTP 方法（动词）来操作资源：
        - GET： 检索资源（安全且幂等）
        - POST： 创建新资源（非幂等）。
        - PUT： 更新整个现有资源（幂等）
        - PATCH： 部分更新现有资源（非幂等）。
        - DELETE： 删除资源（幂等）。
    3. 自描述消息： 请求和响应的消息体（如 JSON、XML）应清晰描述资源状态或操作信息。使用 Content-Type 头明确媒体类型。
    4. HATEOAS (Hypermedia as the Engine of Application State - 可选但推荐)： 在响应中提供指向相关资源的超链接，指导客户端如何导航和操作 API。客户端无需硬编码 URI 结构。
- 3、无状态
  1. 每个请求必须包含处理该请求所需的所有信息。服务器不应在请求之间存储客户端会话状态（认证信息除外，通常通过 Token 或 API Key 在请求头中传递）。
  2. 状态保存在客户端或资源本身中。
- 4、可缓存：
  1. 明确标识响应是否可缓存（使用 HTTP 缓存头如 Cache-Control, Expires, ETag, Last-Modified）。
  2. 减少服务器负载，提高性能。
- 5、分层系统：
    1. 客户端通常不知道直接连接的是最终服务器还是中间层（如代理、网关、负载均衡器）。这提高了可扩展性和安全性。
### 二、设计最佳实践
- 1、URI 设计:
    1. 使用名词（复数形式）： 表示资源集合。/users, /orders, /products
    2. 层级表示关系： 使用路径表示资源间关系。/users/{userId}/orders (用户的所有订单) /orders/{orderId}/items (订单的所有商品项)
    3. 简洁清晰： 避免过长、深层次的嵌套。
    4. 使用小写字母和连字符： 保持 URI 可读性和一致性。/user-preferences (而不是 /userPreferences 或 /user_preferences)
    5. 避免动词： 操作由 HTTP 方法表示，URI 只标识资源。GET /users (获取用户列表) POST /users (创建新用户) PUT /users/123 (更新用户 123) DELETE /users/123 (删除用户 123) - *错误示例*： GET /getUsers, POST /createUser
    6. 避免文件扩展名： 使用 Content-Type 头指定格式。/users/123 (而不是 /users/123.json)

- 2、HTTP 方法使用:
    1. 严格遵循语义：
        - GET： 只读，永不改变资源状态。幂等。
        - POST：创建新资源或执行可能不直接映射到 CRUD 的操作（如搜索 /search）。非幂等。
        - PUT：替换整个资源（提供所有字段）。幂等（多次调用效果相同）。
        - PATCH： 部分更新资源（仅提供需要修改的字段）。非幂等（取决于实现）。
        - DELETE：删除资源。幂等（删除一次或多次，结果都是资源不存在）。
    2. 幂等性和安全性： 理解并正确利用幂等性（多次执行相同请求效果相同）和安全性（不改变资源状态）对客户端重试和缓存很重要。
- 3、状态码：
  1. 使用标准的 HTTP 状态码 清晰传达请求结果：
    - 2xx 成功： 200 OK (成功), 201 Created (资源创建成功，响应头 Location 包含新 URI), 202 Accepted (请求已接受处理，但未完成), 204 No Content (成功但无返回体，如 DELETE)。
    - 3xx 重定向： 301 Moved Permanently, 304 Not Modified (缓存有效)。
    - 4xx 客户端错误： 400 Bad Request (请求语法错误/无效), 401 Unauthorized (需要认证), 403 Forbidden (认证成功但无权限), 404 Not Found (资源不存在), 405 Method Not Allowed (不允许的 HTTP 方法), 409 Conflict (资源状态冲突，如更新旧版本)。
    - 5xx 服务器错误： 500 Internal Server Error (通用服务器错误), 503 Service Unavailable (服务暂时不可用)。
### 三、总结
    设计良好的 RESTful API 的关键在于深刻理解并始终遵循其核心原则（资源、统一接口、无状态等），
    并在 URI 设计、HTTP 方法使用、状态码选择、数据格式、版本控制、安全性和文档化等方面应用最佳实践。
    保持 API 的 简洁性、一致性、可预测性和易用性 是提升开发者体验和 API 成功的关键。
    使用 OpenAPI (Swagger) 等工具进行设计和文档化可以大大提高效率和质量。

### 四、网络协议丨安全与幂等
关于HTTP请求方法有两个比较重要的概念：安全与幂等。

###### 安全
在 HTTP 协议里，所谓的“安全”是指请求方法不会“破坏”服务器上的资源，即不会对服务器上的资源造成实质的修改。即HTTP 方法不会修改服务器资源的状态（只读操作）。多次调用安全方法不会对资源产生副作用。
按照这个定义，只有 GET 、 HEAD和OPTIONS 方法是“安全”的，因为它们是“只读”操作，无论 GET 和 HEAD 操作多少次，服务器上的数据都不会受到影响
而 POST/PUT/DELETE 操作会修改服务器上的资源，增加或删除数据，所以是“不安全”的。所以后两个方法现在很多服务器直接不支持或不处理。

###### 幂等
“幂等”实际上是一个数学用语，被借用到了 HTTP 协议里，意思是多次执行相同的操作，结果也都是相同的，即多次“幂”后结果“相等”。比如1的3次幂还是1。

安全和幂等并不冲突，比如GET、OPTIONS 和 HEAD（ **GET 类似，但不返回响应体（用于检查资源是否存在**） 既是安全的也是幂等的，因为不管请求多少次，服务器的资源永远没有变化，结果相同。DELETE 可以多次删除同一个资源，效果都是“资源不存在”，所以也是幂等的。

POST 和 PUT 的幂等性质就略费解一点。
按照 RFC 里的语义，POST 是“新增或提交数据”，多次提交数据会创建多个资源，所以不是幂等的；而 PUT 是“替换或更新数据”，多次更新一个资源，资源还是会第一次更新的状态，所以是幂等的。
POST是新增，会导致资源增加，所以不是幂等。
PUT是替换，替换不会增加，1替换成了另一个1，结果还是1，所以PUT是幂等。
用数据库来理解，POST是INSERT，PUT是UPDATE，会更加清晰。
**幂等性的重要性**
- 1、 网络不可靠性：
    客户端超时后可自动重试（如 PUT、DELETE），无需担心重复生效。
- 2、分布式系统：
    服务间调用失败重试时，幂等性防止数据不一致。
- 3、用户体验：
    用户误操作（如多次点击）不会导致数据错误。
###### 最佳实践
- 优先使用幂等方法（GET/PUT/DELETE）。
- 对 POST 和 PATCH 设计幂等机制（如唯一请求 ID、版本控制）。
- 在文档中明确接口的幂等性保证，指导客户端正确处理重试逻辑。

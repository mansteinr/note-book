# 一、集合框架

## 1.1 ArrayList 和 LinkedList 的区别是什么？

核心区别对比表

| 对比维度   | ArrayList                                                | LinkedList                          |
| ------ | -------------------------------------------------------- | ----------------------------------- |
| 底层结构   | 动态数组（`Object[] elementData`）                             | 双向链表（`Node` 节点，含 prev/next/item）    |
| 查询性能   | O(1)，基于下标随机访问                                            | O(n)，需从头/尾遍历                        |
| 增删性能   | 尾插 O(1) 均摊；中间插入 O(n) 需移动元素                               | 头尾插入 O(1)；中间插入需先定位 O(n)，但插入本身 O(1)  |
| 内存占用   | 连续内存，紧凑；有扩容浪费（1.5 倍）                                     | 每个节点额外存储 prev/next 指针，开销大           |
| 是否实现接口 | `List`, `RandomAccess`                                   | `List`, `Deque`, `Queue`（可当队列/双端队列） |
| 初始容量   | 默认 10（首次 add 时创建）                                        | 无初始容量概念，按需创建节点                      |
| 扩容机制   | `newCapacity = oldCapacity + (oldCapacity >> 1)`，即 1.5 倍 | 无需扩容                                |

ArrayList 原理详解

```java
// ArrayList 核心字段
transient Object[] elementData;   // 存储元素的数组
private int size;                 // 实际元素个数

// add 流程
public boolean add(E e) {
    ensureCapacityInternal(size + 1);  // 1. 检查容量，必要时扩容
    elementData[size++] = e;            // 2. 赋值后 size++
    return true;
}

// 扩容核心：1.5 倍
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);  // 1.5 倍
    if (newCapacity < minCapacity)
        newCapacity = minCapacity;
    elementData = Arrays.copyOf(elementData, newCapacity);  // 复制数组
}
```

LinkedList 原理详解

```java
// LinkedList 双向链表节点
private static class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;

    Node(Node<E> prev, E element, Node<E> next) {
        this.item = element;
        this.next = next;
        this.prev = prev;
    }
}

// 头插 O(1)
private void linkFirst(E e) {
    final Node<E> f = first;
    final Node<E> newNode = new Node<>(null, e, f);
    first = newNode;
    if (f == null) last = newNode;  // 空链表
    else f.prev = newNode;
    size++;
}
```

选型建议

- 读多写少、随机访问频繁  ：用 `ArrayList`（如配置表、字典数据）。
- 频繁头尾增删、队列场景  ：用 `LinkedList` 或更优的 `ArrayDeque`。
- 实际开发中 90% 用 `ArrayList`；`LinkedList` 因节点开销大、缓存不友好，实际性能优势场景有限。

## 1.2 HashMap 的底层原理是什么？

JDK 1.8 的 HashMap 结构

：数组 + 链表 + 红黑树

```Java
HashMap 结构示意
┌─────────────────────────────────────────┐
│  table[]（Node 数组，长度为 2 的幂）        │
├────┬────┬────┬────┬────┬────┬────┬───────┤
│ 0  │ 1  │ 2  │ 3  │ 4  │ ...│ 14 │ 15    │
└─┬──┴────┴─┬──┴────┴────┴────┴────┴───────┘
  │         │
  ▼         ▼
 Node      Node → Node → Node → Node（链表，长度 ≤ 8）
            │
            ▼ 当链表长度 ≥ 8 且数组长度 ≥ 64
          TreeNode（红黑树，查找 O(log n)）
```

核心字段

```java
public class HashMap<K,V> extends AbstractMap<K,V> {
    transient Node<K,V>[] table;      // 哈希桶数组
    transient int size;               // 元素个数
    int threshold;                    // 扩容阈值 = capacity * loadFactor
    final float loadFactor;           // 负载因子，默认 0.75
    static final int DEFAULT_INITIAL_CAPACITY = 1 << 4;   // 默认容量 16
    static final int TREEIFY_THRESHOLD = 8;               // 链表转红黑树阈值
    static final int UNTREEIFY_THRESHOLD = 6;             // 红黑树退化阈值
    static final int MIN_TREEIFY_CAPACITY = 64;            // 转树前最小表容量
}
```

put 流程（JDK 1.8）

```java
public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}

static final int hash(Object key) {
    int h;
    // 高 16 位异或低 16 位，让高位也参与桶定位，减少碰撞
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;
    // 1. 表为空或长度 0 → resize() 初始化
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;
    // 2. 计算桶下标 (n-1) & hash，桶为空直接放入
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);
    else {
        // 3. 桶不为空，分情况
        Node<K,V> e; K k;
        // 3.1 桶首元素 key 相同 → 替换
        if (p.hash == hash && ((k = p.key) == key || (key != null && key.equals(k))))
            e = p;
        // 3.2 是红黑树节点 → 红黑树插入
        else if (p instanceof TreeNode)
            e = ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);
        else {
            // 3.3 链表遍历
            for (int binCount = 0; ; ++binCount) {
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);  // 尾插
                    if (binCount >= TREEIFY_THRESHOLD - 1)       // 链表长度 ≥ 8
                        treeifyBin(tab, hash);                   // 转红黑树
                    break;
                }
                if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
                    break;  // 找到相同 key
                p = e;
            }
        }
        if (e != null) {  // 替换旧值
            V oldValue = e.value;
            if (!onlyIfAbsent || oldValue == null)
                e.value = value;
            afterNodeAccess(e);
            return oldValue;
        }
    }
    ++modCount;
    // 4. 超过阈值 → 扩容
    if (++size > threshold)
        resize();
    afterNodeInsertion(evict);
    return null;
}
```

扩容机制 resize()

- 触发条件：`size > threshold`（threshold = capacity \* 0.75）。
- 新容量 = 旧容量 × 2，新阈值 = 旧阈值 × 2。
- JDK 1.8 优化元素迁移：因容量为 2 的幂，扩容后元素位置要么不变，要么 = 原位置 + 旧容量。
  - 判断依据：`if ((e.hash & oldCap) == 0)` → 留原位；否则 → 原位 + oldCap。

## 1.3 HashMap 为什么是线程不安全的？

线程不安全的三大场景

| 场景         | JDK 1.7 问题     | JDK 1.8 问题           |
| ---------- | -------------- | -------------------- |
| 并发 put     | 链表成环导致死循环（头插法） | 数据覆盖（两线程同时判断桶空）      |
| 并发 put/get | get 死循环        | get 可能返回 null（可见性问题） |
| 并发扩容       | 链表成环 + 数据丢失    | 数据丢失 + size 计数不准     |

JDK 1.7 死循环根因（头插法）

```java
// JDK 1.7 transfer() 扩容时迁移元素（头插法）
void transfer(Entry[] newTable) {
    for (Entry<K,V> e : table) {
        while (e != null) {
            Entry<K,V> next = e.next;  // 记录下一个
            int i = indexFor(e.hash, newTable.length);
            e.next = newTable[i];      // 头插：新节点指向桶首
            newTable[i] = e;           // 桶首更新为新节点
            e = next;
        }
    }
}
```

并发扩容时，两线程相互覆盖 `next` 指针，可能形成环形链表。后续 get 遍历该链表 → 死循环 → CPU 100%。

JDK 1.8 改用尾插法

避免了死循环，但仍不安全：

- 两线程同时 `put`，都判断 `tab[i] == null`，都执行 `tab[i] = newNode`，后写入的覆盖先写入的 →   数据丢失  。
- `size++` 非原子操作，并发下计数不准。

线程安全方案

- `Hashtable`：方法级 synchronized，性能差，已淘汰。
- `Collections.synchronizedMap`：包装同步，粒度粗。
- `ConcurrentHashMap`  ：推荐方案，分段锁 / CAS + synchronized。

## 1.4 ConcurrentHashMap 如何实现线程安全？

JDK 1.7：分段锁 Segment

```
ConcurrentHashMap (JDK 1.7)
├── Segment[]（默认 16 个，继承 ReentrantLock）
│   └── HashEntry[]（每个 Segment 一张小表）
│       └── HashEntry 链表
```

- 每个 Segment 是一把锁，锁粒度 = Segment，最多 16 个线程并发写。
- get 无锁：volatile 读 HashEntry 的 value。

JDK 1.8：CAS + synchronized

```java
// JDK 1.8 ConcurrentHashMap 结构与 HashMap 一致：数组 + 链表 + 红黑树
// 锁粒度细化到桶首节点

final V putVal(K key, V value, boolean onlyIfAbsent) {
    // ... 省略 hash 计算
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        // 1. 桶为空 → CAS 写入（无锁）
        if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;
        }
        // 2. 桶首节点 hash = MOVED(-1) → 协助扩容
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);
        else {
            // 3. 桶非空 → synchronized 锁桶首节点
            synchronized (f) {
                if (tabAt(tab, i) == f) {  // 二次确认
                    // 链表或红黑树插入
                    if (fh >= 0) { ... }
                    else if (f instanceof TreeBin) { ... }
                }
            }
            if (binCount != 0) {
                if (binCount >= TREEIFY_THRESHOLD)
                    treeifyBin(tab, i);  // 链表转树
                break;
            }
        }
    }
    addCount(1L, binCount);  // 基于 LongAdder 思想的并发计数
    return null;
}
```

JDK 1.8 并发安全机制

| 操作      | 机制                                               |
| ------- | ------------------------------------------------ |
| 空桶写入    | CAS（无锁）`casTabAt`                                |
| 桶非空写入   | `synchronized(桶首节点)`，锁粒度细                        |
| size 计数 | `baseCount` + `CounterCell[]` 分段累加（LongAdder 思想） |
| 扩容      | 多线程协助迁移，每个线程负责一段区间                               |
| get     | 完全无锁，volatile 读 Node 的 val 和 next                |

## 1.5 HashSet 和 TreeSet 的区别是什么？

| 对比维度      | HashSet                              | TreeSet                                   |
| --------- | ------------------------------------ | ----------------------------------------- |
| 底层结构      | 基于 `HashMap`（value 固定为 `PRESENT` 对象） | 基于 `TreeMap`（红黑树）                         |
| 元素顺序      | 无序（哈希散列）                             | 有序（自然排序或 Comparator）                      |
| 是否允许 null | 允许 1 个 null                          | 不允许 null（会 NPE，因为要比较）                     |
| 查询性能      | O(1) 平均                              | O(log n)                                  |
| 插入性能      | O(1) 平均                              | O(log n)，需维护红黑树平衡                         |
| 元素要求      | 重写 `hashCode` / `equals`             | 实现 `Comparable` 或传 `Comparator`           |
| 应用场景      | 去重、快速判存在                             | 排序、范围查询（`headSet` / `tailSet` / `subSet`） |

HashSet 源码

```java
public class HashSet<E> extends AbstractSet<E> {
    private transient HashMap<E,Object> map;
    private static final Object PRESENT = new Object();  // 固定占位 value

    public HashSet() { map = new HashMap<>(); }

    public boolean add(E e) {
        return map.put(e, PRESENT) == null;  // key 不存在返回 null → true
    }

    public boolean contains(Object o) {
        return map.containsKey(o);
    }
}
```

TreeSet 范围查询示例

```java
TreeSet<Integer> set = new TreeSet<>();
set.add(5); set.add(2); set.add(8); set.add(1); set.add(9);

System.out.println(set);                  // [1, 2, 5, 8, 9]（自然排序）
System.out.println(set.headSet(5));       // [1, 2]（<5）
System.out.println(set.tailSet(5));       // [5, 8, 9]（≥5）
System.out.println(set.subSet(2, 8));     // [2, 5]（[2,8)）
System.out.println(set.first());          // 1（最小）
System.out.println(set.last());           // 9（最大）
System.out.println(set.floor(6));         // 5（≤6 的最大）
System.out.println(set.ceiling(6));       // 8（≥6 的最小）
```

## 1.6 为什么 HashMap 的容量是 2 的幂？

核心原因：用位运算替代取模，提升性能

```java
// 桶下标计算
int index = (n - 1) & hash;
// 等价于
int index = hash % n;  // 当 n 是 2 的幂时两者等价
```

为什么

&#x20;

`hash & (n-1)`

&#x20;

等价于

&#x20;

`hash % n`（当 n 是 2 的幂）

设 n = 16 = 2⁴，则 n - 1 = 15 = `0000 1111`。

```
hash       = 1010 1101 0011 1010
n - 1      = 0000 0000 0000 1111
──────────────────────────────────
hash & n-1 = 0000 0000 0000 1010 = 10

hash % n   = 同样等于 10
```

位运算的优势

| 维度     | `hash % n`       | `hash & (n-1)` |
| ------ | ---------------- | -------------- |
| CPU 指令 | 除法指令（约 20-40 周期） | 与指令（1 周期）      |
| 性能     | 慢                | 快约 5-10 倍      |
| 分布均匀性  | 相同               | 相同（n 为 2 幂时）   |

扩容时的优势

扩容后容量翻倍（仍是 2 的幂），元素位置只需判断最高位：

```java
// JDK 1.8 扩容迁移优化
if ((e.hash & oldCap) == 0) {
    // hash 高位为 0，新位置 = 原位置
} else {
    // hash 高位为 1，新位置 = 原位置 + oldCap
}
```

- 若 `oldCap = 16 = 0001 0000`，`e.hash & oldCap` 判断 hash 的第 4 位。
- 第 4 位为 0 → 新位置仍是原 index；第 4 位为 1 → 新位置 = 原位 + 16。
- 无需重新计算 `hash & (newCap-1)`，迁移高效。

# 二、JVM

## 2.1 JVM 的内存结构是什么？

JVM 运行时数据区分为线程私有和线程共享两部分：

```
┌─────────────────────────────────────────────────────────────┐
│                      JVM 运行时数据区                        │
├──────────────────────┬──────────────────────────────────────┤
│   线程私有            │           线程共享                    │
├──────────────────────┼──────────────────────────────────────┤
│ 1. 程序计数器(PC)     │ 4. 堆(Heap)                          │
│ 2. 虚拟机栈(VM Stack) │ 5. 方法区(Method Area) / 元空间      │
│ 3. 本地方法栈         │                                      │
└──────────────────────┴──────────────────────────────────────┘
```

各区域详解

| 区域    | 作用                        | 异常类型                              | 线程性 |
| ----- | ------------------------- | --------------------------------- | --- |
| 程序计数器 | 记录当前线程执行字节码行号             | 唯一不会 OOM 的区域                      | 私有  |
| 虚拟机栈  | 存栈帧（局部变量表、操作数栈、动态链接、方法出口） | StackOverflowError / OOM          | 私有  |
| 本地方法栈 | 为 native 方法服务             | StackOverflowError / OOM          | 私有  |
| 堆     | 存对象实例和数组，GC 主战场           | OutOfMemoryError: Java heap space | 共享  |
| 方法区   | 存类信息、常量、静态变量、JIT 编译后的代码   | OutOfMemoryError: Metaspace       | 共享  |

JDK 1.8 内存结构变化

```
JDK 1.7 之前                  JDK 1.8 之后
┌────────────┐               ┌────────────┐
│ 堆          │               │ 堆          │
├────────────┤               ├────────────┤
│ 方法区      │  ──> 移除     │ 元空间      │  使用本地内存
│ (Perm Gen) │               │ (Metaspace) │
└────────────┘               ├────────────┤
                             │ 堆外内存    │  Direct Memory
                             └────────────┘
```

移除永久代的原因

1. 字符串常量池在永久代中容易 OOM（`PermGen space`）。
2. 类元数据大小难以预估，永久代固定上限易触发 Full GC。
3. 方便与其他 JVM（如 JRockit）融合。

堆内存分代结构

```
堆(Heap)
├── 新生代(Young) = 1/3 堆
│   ├── Eden = 8/10 新生代
│   ├── Survivor 0 (S0) = 1/10
│   └── Survivor 1 (S1) = 1/10
└── 老年代(Old) = 2/3 堆
```

JVM 参数：`-Xms`（堆初始）、`-Xmx`（堆最大）、`-Xmn`（新生代大小）、`-XX:SurvivorRatio=8`。

## 2.2 堆和栈有什么区别？

| 对比维度  | 栈(Stack)                 | 堆(Heap)                           |
| ----- | ------------------------ | --------------------------------- |
| 存储内容  | 栈帧、局部变量、对象引用、基本类型        | 对象实例、数组                           |
| 线程隔离  | 线程私有，每个线程一个栈             | 线程共享                              |
| 生命周期  | 方法调用结束自动释放               | 由 GC 管理                           |
| 存取速度  | 快，仅移动栈指针                 | 慢，需分配+寻址                          |
| 空间大小  | 小，默认 512KB-1MB           | 大，受物理内存限制                         |
| 异常    | StackOverflowError（递归过深） | OutOfMemoryError: Java heap space |
| 是否 GC | 不参与 GC                   | GC 主战场                            |

栈帧结构

```
栈帧(Stack Frame)
├── 局部变量表(LVT)：基本类型 + 对象引用 + returnAddress
├── 操作数栈(OS)：执行字节码运算的中转站
├── 动态链接：指向运行时常量池中方法的引用
└── 方法返回地址：方法退出后恢复上层执行位置
```

```java
    }
}
```

## 2.3 垃圾回收算法有哪些？

四大基础 GC 算法

### 1. 标记-清除(Mark-Sweep)

```
步骤：
  1. 从 GC Roots 开始可达性分析，标记存活对象
  2. 清除未被标记的对象

缺点：
  - 产生内存碎片，大对象分配可能失败
  - 效率不稳定，存活对象多时清除慢
```

### 2. 复制(Copying)

```
步骤：
  1. 将内存分两块，只用一块
  2. GC 时把存活对象复制到另一块，顺序排列
  3. 清空原块，交换指针

优点：无碎片，分配快
缺点：可用内存减半
应用：新生代（Eden + S0 + S1，浪费 10%）
```

### 3. 标记-整理(Mark-Compact)

```
步骤：
  1. 标记存活对象
  2. 把存活对象向一端移动，清理边界外内存

优点：无碎片，无内存浪费
缺点：移动对象慢，STW 时间长
应用：老年代
```

### 4. 分代收集(Generational)

```
┌─────────────────────────────────────────┐
│         堆(分代)                         │
├──────────────────┬──────────────────────┤
│  新生代(频繁GC)   │   老年代(较少GC)      │
│  复制算法         │   标记-整理           │
│  Minor GC        │   Major GC / Full GC │
└──────────────────┴──────────────────────┘

对象晋升流程：
  Eden → S0/S1 → (年龄 ≥ 15) → 老年代
  大对象 → 直接进老年代(-XX:PretenureSizeThreshold)
```

GC Roots 类型

- 虚拟机栈中引用的对象
- 方法区中类静态属性引用的对象
- 方法区中常量引用的对象
- 本地方法栈 JNI 引用
- JVM 内部引用（如基本类型 Class）
- 同步锁 synchronized 持有的对象

## 2.4 CMS 和 G1 有什么区别？

| 对比维度   | CMS(Concurrent Mark Sweep)               | G1(Garbage-First)                 |
| ------ | ---------------------------------------- | --------------------------------- |
| 目标     | 低停顿（响应时间优先）                              | 可预测停顿 + 高吞吐                       |
| 内存布局   | 分代：新生代 + 老年代                             | Region 分区：Eden/Surv/Old/Humongous |
| 算法     | 老年代：标记-清除                                | Region：复制 + 标记-整理                 |
| 碎片     | 有（标记-清除产生）                               | 几乎无（复制整理）                         |
| 停顿时间   | 不可控，随堆增大而变长                              | 可设置目标（`-XX:MaxGCPauseMillis`）     |
| 适用堆大小  | ≤ 8GB                                    | 8GB-64GB                          |
| 回收过程   | 初始标记 → 并发标记 → 重新标记 → 并发清除                | 初始标记 → 并发标记 → 最终标记 → 筛选回收         |
| 并发回收   | 并发清除（不移动对象）                              | 筛选回收（复制存活到空 Region）               |
| 是否浮动垃圾 | 有                                        | 有                                 |
| 失败模式   | Concurrent Mode Failure → 退化为 Serial Old | 类似但概率低                            |
| JDK 版本 | JDK 9 标记废弃，JDK 14 移除                     | JDK 9+ 默认                         |

CMS 回收流程

```
1. 初始标记(STW)        标记 GC Roots 直接关联对象，速度快
2. 并发标记             从 GC Roots 遍历对象图，与用户线程并发
3. 重新标记(STW)        修正并发标记期间引用变化，时间短
4. 并发清除             清除未标记对象，与用户线程并发
```

G1 Region 布局

```
┌─────────────────────────────────────────┐
│  E  E  S  O  O  E  E  H  H  O  E  S  O  │
│  ─────────────────────────────────────  │
│  每个 Region 独立分配角色，可动态切换      │
│  E=Eden  S=Survivor  O=Old  H=Humongous │
│                                         │
│  回收价值 = Region 垃圾占比 / 预计耗时      │
│  优先回收价值高的 → Garbage-First          │
└─────────────────────────────────────────┘
```

G1 可预测停顿原理

- 用户设置 `MaxGCPauseMillis=200`（默认 200ms）。
- G1 维护每个 Region 的回收成本模型。
- 每次回收时按"性价比"排序，在目标时间内回收尽可能多垃圾。

## 2.5 为什么会发生 Full GC？

Full GC 触发条件汇总

| 触发场景                        | 具体原因                              | 应对策略                                    |
| --------------------------- | --------------------------------- | --------------------------------------- |
| 老年代空间不足                     | 大对象进老年代 / 晋升过快                    | 增大老年代 / 调大 `-XX:MaxTenuringThreshold`   |
| 永久代/元空间不足                   | 加载类过多、CGLIB 动态代理                  | `-XX:MaxMetaspaceSize` 调大               |
| `System.gc()`               | 代码显式调用                            | `-XX:+DisableExplicitGC` 禁用             |
| CMS Concurrent Mode Failure | 老年代空间不够容纳浮动垃圾                     | 调大 `-XX:CMSInitiatingOccupancyFraction` |
| 空间分配担保失败                    | Minor GC 前检查老年代连续空间 < 历次晋升平均      | 调大老年代                                   |
| 大对象直接进老年代                   | 对象大于 `-XX:PretenureSizeThreshold` | 优化代码避免大对象                               |
| 内存泄漏                        | 对象无法回收，堆积                         | 排查泄漏点                                   |

晋升流程与 Full GC 触发

```
对象分配流程
├── 优先 TLAB(线程本地分配缓冲) → 快速无锁
├── Eden 区分配
├── 大对象 → 老年代(避免 Eden↔Survivor 来回复制)
└── Minor GC 时
    ├── 存活对象年龄 < 15 → 复制到 Survivor，年龄+1
    ├── 年龄 ≥ 15 → 晋升老年代
    └── Survivor 空间不足 → 担保晋升到老年代

Minor GC 前检查：
  老年代可用连续空间 < 历次晋升平均大小 →
    1. 检查 -XX:+HandlePromotionFailure
    2. 允许担保失败 → 风险承担，Minor GC 继续
    3. 不允许 → 触发 Full GC
```

生产案例：CGLIB 动态代理导致元空间 Full GC

```java
// 问题代码：每次调用生成新代理类，元空间膨胀
for (int i = 0; i < 100000; i++) {
    Enhancer enhancer = new Enhancer();
    enhancer.setSuperclass(UserService.class);
    enhancer.setCallback(new MethodInterceptor() { ... });
    UserService proxy = (UserService) enhancer.create();
    // proxy 未释放 → 代理类 Class 元数据无法卸载 → 元空间 Full GC
}
```

## 3.1 synchronized 和 ReentrantLock 的区别是什么？

| 对比维度 | synchronized                          | ReentrantLock                           |
| ---- | ------------------------------------- | --------------------------------------- |
| 性质   | JVM 关键字（monitorenter/monitorexit 字节码） | JDK API 类（`java.util.concurrent.locks`） |
| 锁释放  | 自动释放（退出同步块/异常）                        | 必须手动 `unlock()`，通常放 finally             |
| 锁获取  | 非公平（不可配置）                             | 可公平可非公平（构造函数传参）                         |
| 可中断  | 不可中断（等锁时不响应 interrupt）                | `lockInterruptibly()` 可响应中断             |
| 超时获取 | 不支持                                   | `tryLock(timeout)` 支持                   |
| 条件变量 | 1 个（`wait` / `notify`）                | 多个 `Condition`，可精确唤醒                    |
| 锁绑定  | 对象 / 类                                | Lock 对象                                 |
| 性能   | JDK 6+ 优化后接近 ReentrantLock            | 略优，功能更强                                 |
| 是否独占 | 均为独占锁                                 | 均为独占锁（有 ReentrantReadWriteLock）         |

synchronized 锁升级过程

```
无锁 → 偏向锁 → 轻量级锁 → 重量级锁(不可逆)

1. 偏向锁：首次进入，对象头 Mark Word 记录线程 ID，下次无竞争直接进入
2. 轻量级锁：多线程交替进入(无竞争)，CAS 自旋等待
3. 重量级锁：真竞争，CAS 失败 → monitor 阻塞 → 操作系统互斥量 → 上下文切换
```

ReentrantLock 可中断示例

```java
ReentrantLock lock = new ReentrantLock();
Thread t = new Thread(() -> {
    try {
        lock.lockInterruptibly();   // 可被中断
        try {
            // 临界区
        } finally {
            lock.unlock();
        }
    } catch (InterruptedException e) {
        System.out.println("被中断，放弃获取锁");
    }
});
t.start();
Thread.sleep(1000);
t.interrupt();  // 主线程中断 t
```

Condition 多条件变量

```java
ReentrantLock lock = new ReentrantLock();
Condition notFull = lock.newCondition();
Condition notEmpty = lock.newCondition();

// 生产者：队列满 → 在 notFull 等待，放入后唤醒 notEmpty
// 消费者：队列空 → 在 notEmpty 等待，取出后唤醒 notFull
```

## 3.2 volatile 的作用是什么？

volatile 三大语义

### 1. 可见性

```
线程工作内存(寄存器/CPU 缓存)     主内存
   ┌──────────┐                  ┌──────────┐
   │ flag = 0 │  <── 读          │ flag = 0 │
   └──────────┘     写 ──>       └──────────┘
                   volatile      ↑
                                其他线程可见
```

- volatile 写：刷新到主内存，并使其他线程工作内存的副本失效。
- volatile 读：从主内存读，保证看到最新值。

### 2. 禁止指令重排序

通过\*\*内存屏障(Memory Barrier)\*\*实现：

| 屏障类型       | 作用                   |
| ---------- | -------------------- |
| LoadLoad   | 读读屏障：前面的读完成才能执行后面的读  |
| StoreStore | 写写屏障：前面的写完成才能执行后面的写  |
| LoadStore  | 读写屏障：前面的读完成才能执行后面的写  |
| StoreLoad  | 写读屏障：最全屏障，volatile 用 |

### 3. 不保证原子性

```java
volatile int count = 0;

// 10 个线程各 ++ 1000 次
// count = i+1  分为：读 i、加 1、写回
// volatile 只保证每次读到最新值，但读-改-写非原子
// 最终 count < 10000，丢失更新
```

应用场景：DCL 单例

```java
public class Singleton {
    // volatile 防止指令重排
    // new Singleton() 分三步：①分配内存 ②初始化 ③引用赋值
    // 重排成 ①③② → 其他线程拿到未初始化对象 → NPE
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一次检查(无锁)
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二次检查
                    instance = new Singleton();   // 安全发布
                }
            }
        }
        return instance;
    }
}
```

volatile vs synchronized

| 维度  | volatile | synchronized        |
| --- | -------- | ------------------- |
| 原子性 | 不保证      | 保证                  |
| 可见性 | 保证       | 保证                  |
| 有序性 | 保证(禁止重排) | 保证( happens-before) |
| 阻塞  | 不阻塞      | 可能阻塞                |
| 性能  | 轻量       | 较重                  |

## 3.3 CAS 是什么？

CAS(Compare-And-Swap)

：无锁原子操作，比较并交换。

```
CAS(V, Expected, New)
  V：内存地址
  Expected：期望值
  New：新值

if (V == Expected) {
    V = New;
    return true;
}
return false;
```

底层实现

：CPU 的 `cmpxchg` 指令（x86）/ `LL/SC`（ARM）。

Java 中的 CAS：Unsafe 类

```java
// AtomicInteger 的 incrementAndGet
public final int incrementAndGet() {
    return U.getAndAddInt(this, VALUE, 1) + 1;
}

// Unsafe.getAndAddInt
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);   // 读最新值
    } while (!compareAndSwapInt(o, offset, v, v + delta));  // CAS 失败重试
    return v;
}
```

CAS 三大问题

### 1. ABA 问题

```
线程1：读 A → 准备 CAS(A, B)
线程2：A → B → A      // 中间值变化，但线程1看不到
线程1：CAS 成功(以为没变)
```

解决

：版本号 `AtomicStampedReference`

```java
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);

// 线程2 修改
ref.compareAndSet(100, 200, 0, 1);  // 期望值100，期望版本0，新值200，新版本1
ref.compareAndSet(200, 100, 1, 2);  // ABA，但版本变了

// 线程1 CAS 失败(版本号不匹配)
ref.compareAndSet(100, 50, 0, 3);   // false
```

### 2. 自旋开销

CAS 失败后自旋重试，竞争激烈时 CPU 空转。

### 3. 只保证一个变量原子

```java
// 多个变量需原子 → AtomicReference 包装成对象
AtomicReference<Point> ar = new AtomicReference<>(new Point(0, 0));
Point old = ar.get();
Point neu = new Point(old.x+1, old.y+1);
ar.compareAndSet(old, neu);
```

应用：原子类

| 类                              | 作用         |
| ------------------------------ | ---------- |
| `AtomicInteger` / `AtomicLong` | 整数原子操作     |
| `AtomicBoolean`                | 布尔原子       |
| `AtomicReference`              | 引用类型原子     |
| `AtomicStampedReference`       | 带版本号解决 ABA |
| `LongAdder`                    | 高并发计数，分段累加 |
| `AtomicIntegerFieldUpdater`    | 反射更新字段     |

## 3.4 ThreadLocal 的原理是什么？

核心原理

：每个线程独立持有变量副本，互不干扰。

```
Thread                         ThreadLocalMap
┌─────────────────┐           ┌─────────────────────────┐
│ Thread.currentThread()      │ Entry[] table           │
│   └─ threadLocals ──────────┤ Entry 0: key=tl1, val=v1│
│                             │ Entry 1: key=tl2, val=v2│
└─────────────────┘           └─────────────────────────┘

ThreadLocalMap key 为 ThreadLocal 对象(弱引用)
              value 为实际值(强引用)
```

源码核心

```java
public class Thread {
    ThreadLocal.ThreadLocalMap threadLocals = null;
}

public class ThreadLocal<T> {
    public void set(T value) {
        Thread t = Thread.currentThread();
        ThreadLocalMap map = getMap(t);  // 获取当前线程的 ThreadLocalMap
        if (map != null)
            map.set(this, value);       // key=this(ThreadLocal)
        else
            createMap(t, value);
    }

    public T get() {
        Thread t = Thread.currentThread();
        ThreadLocalMap map = getMap(t);
        if (map != null) {
            ThreadLocalMap.Entry e = map.getEntry(this);
            if (e != null) return (T) e.value;
        }
        return setInitialValue();
    }

    // Entry 继承 WeakReference，key 为弱引用
    static class Entry extends WeakReference<ThreadLocal<?>> {
        Object value;
        Entry(ThreadLocal<?> k, Object v) {
            super(k);   // key 弱引用
            value = v;  // value 强引用
        }
    }
}
```

内存泄漏原理

```
ThreadLocal ref       Entry key(弱引用)   Entry value(强引用)
   ↓                       ↓                    ↓
 ThreadLocal 对象  ←─弱─  key             value(大对象)
                                                  ↑
                                                  │ 强引用链
Thread.threadLocals ──> Entry[] ──> Entry ────────┘

线程销毁 → threadLocals 被回收 → 无泄漏
线程池复用 → 线程不销毁 → value 一直强引用 → 泄漏
```

解决

：用完务必 `remove()`

```java
ThreadLocal<UserContext> context = new ThreadLocal<>();
try {
    context.set(new UserContext());
    // 业务逻辑
} finally {
    context.remove();   // 必须清理
}
```

应用场景

- 用户会话上下文（UserContext）
- 数据库连接（Connection）
- 事务管理（TransactionSynchronizationManager）
- 简单日期格式化（`SimpleDateFormat` 非线程安全）

## 3.5 什么是线程池？

线程池

：预先创建并管理一组线程，复用线程避免频繁创建销毁。

核心优势

1. 降低资源消耗  ：复用线程，避免创建/销毁开销。
2. 提高响应速度  ：任务到达直接用现有线程执行。
3. 便于管理  ：统一调优、监控、限流。

Executor 框架

```
Executor
  └─ ExecutorService
       └─ AbstractExecutorService
            └─ ThreadPoolExecutor    ← 核心实现
                 ├─ newFixedThreadPool     固定线程数
                 ├─ newCachedThreadPool   可缓存(0~Integer.MAX_VALUE)
                 ├─ newSingleThreadExecutor 单线程
                 └─ newScheduledThreadPool 定时/周期
```

任务提交流程

```
execute(Runnable task)
  │
  ├─ 当前线程数 < corePoolSize → 新建核心线程执行
  │
  ├─ 核心线程满 → 进入工作队列(BlockingQueue)
  │
  ├─ 队列满 → 新建非核心线程(不超过 maximumPoolSize)
  │
  └─ 线程数达 maximumPoolSize → 触发拒绝策略
```

拒绝策略

| 策略                    | 行为                             |
| --------------------- | ------------------------------ |
| `AbortPolicy`(默认)     | 抛 `RejectedExecutionException` |
| `CallerRunsPolicy`    | 由提交任务的线程执行                     |
| `DiscardPolicy`       | 直接丢弃                           |
| `DiscardOldestPolicy` | 丢弃队列最老任务，重试                    |

***

## 3.6 线程池的核心参数有哪些？

`ThreadPoolExecutor`

&#x20;

七大参数

```java
public ThreadPoolExecutor(
    int corePoolSize,                  // 1. 核心线程数
    int maximumPoolSize,               // 2. 最大线程数
    long keepAliveTime,                // 3. 非核心线程空闲存活时间
    TimeUnit unit,                     // 4. 时间单位
    BlockingQueue<Runnable> workQueue, // 5. 工作队列
    ThreadFactory threadFactory,      // 6. 线程工厂
    RejectedExecutionHandler handler  // 7. 拒绝策略
)
```

参数详解

| 参数              | 说明                                           | 推荐值                                                          |
| --------------- | -------------------------------------------- | ------------------------------------------------------------ |
| corePoolSize    | 常驻线程数，即使空闲也不回收(除非设 `allowCoreThreadTimeOut`) | CPU 密集型：N+1；IO 密集型：2N                                        |
| maximumPoolSize | 线程池最大线程数                                     | 根据任务类型和资源定                                                   |
| keepAliveTime   | 非核心线程空闲超时时间                                  | 60s                                                          |
| unit            | 时间单位                                         | `TimeUnit.SECONDS`                                           |
| workQueue       | 任务队列                                         | 见下表                                                          |
| threadFactory   | 创建线程的工厂，可自定义命名                               | `new ThreadFactoryBuilder().setNameFormat("biz-%d").build()` |
| handler         | 拒绝策略                                         | `CallerRunsPolicy` / 自定义                                     |

常用队列对比

| 队列                      | 特点                                | 适用                            |
| ----------------------- | --------------------------------- | ----------------------------- |
| `LinkedBlockingQueue`   | 无界(默认 `Integer.MAX_VALUE`)，可能 OOM | Executors.newFixedThreadPool  |
| `ArrayBlockingQueue`    | 有界，需指定容量                          | 生产推荐                          |
| `SynchronousQueue`      | 不存储，直接交付                          | Executors.newCachedThreadPool |
| `PriorityBlockingQueue` | 优先级排序                             | 任务有优先级                        |
| `DelayedWorkQueue`      | 延迟队列                              | 定时任务池                         |

为什么不推荐 Executors 工具方法？

```java
// 风险代码
ExecutorService pool1 = Executors.newFixedThreadPool(10);
// 队列 LinkedBlockingQueue 无界 → 任务堆积 OOM

ExecutorService pool2 = Executors.newCachedThreadPool();
// maximumPoolSize = Integer.MAX_VALUE → 创建大量线程 OOM
```

阿里巴巴推荐

：手动 `new ThreadPoolExecutor`，明确队列容量和最大线程。

线程数配置公式（Brian Goetz）

```
线程数 = CPU 核数 × (1 + 等待时间/计算时间)
      = CPU 核数 × (1 + I/O 时间/CPU 时间)

CPU 密集型(N+1)：多 1 个用于在某个线程偶尔缺页时顶替
I/O  密集型(2N)：I/O 等待时切换其他线程
```

生产配置示例

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8,                                   // 核心线程数(8 核 CPU)
    16,                                  // 最大线程数
    60L, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),      // 有界队列 1000
    new ThreadFactoryBuilder()
        .setNameFormat("order-pool-%d")
        .setUncaughtExceptionHandler((t, e) -> log.error("异常", e))
        .build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // 拒绝时由调用方执行(背压)
);
```

# 四、Spring IOC

## 4.1 什么是 IOC？

IOC(Inversion of Control，控制反转)

：对象创建和依赖关系的管理权从程序代码转移给外部容器。

```
传统开发：
  类 A { A a = new A(); }   ← 程序主动创建对象

IOC 模式：
  容器创建 A → 注入到使用方   ← 容器被动管理
  类 B { @Autowired A a; }  ← 容器注入
```

核心思想

：好莱坞原则（Don't call us, we'll call you）。

***

## 4.2 Spring IOC 是什么？

Spring IOC 是 Spring 框架对 IOC 的实现，核心容器负责：

1. 对象创建  ：通过反射实例化 Bean。
2. 依赖注入  ：通过 `@Autowired` / `@Resource` / XML 配置。
3. 生命周期管理  ：从创建到销毁的全过程。
4. 作用域管理  ：单例、原型等。

核心组件

| 组件                       | 作用                      |
| ------------------------ | ----------------------- |
| `BeanFactory`            | IOC 容器根接口（懒加载）          |
| `ApplicationContext`     | 扩展 BeanFactory，预加载+企业特性 |
| `BeanDefinition`         | Bean 的元数据（类名、作用域、依赖）    |
| `BeanDefinitionRegistry` | 注册 BeanDefinition       |
| `BeanPostProcessor`      | Bean 创建时的扩展点            |

***

## 4.3 Spring IOC 的实现原理是什么？

核心流程：`refresh()`

&#x20;

12 步

```java
public void refresh() throws BeansException, IllegalStateException {
    // 1. 准备刷新：设置启动时间、活跃标志、初始化属性源
    prepareRefresh();

    // 2. 获取 BeanFactory：创建 DefaultListableBeanFactory，加载 BeanDefinition
    ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();

    // 3. BeanFactory 准备：配置类加载器、注册后置处理器、忽略指定接口
    prepareBeanFactory(beanFactory);

    // 4. 子类扩展：模板方法，如 Web 容器注册 scope
    postProcessBeanFactory(beanFactory);

    // 5. 调用 BeanFactoryPostProcessor：修改 BeanDefinition
    invokeBeanFactoryPostProcessors(beanFactory);

    // 6. 注册 BeanPostProcessor：Bean 创建时的扩展点
    registerBeanPostProcessors(beanFactory);

    // 7. 初始化 MessageSource：国际化
    initMessageSource();

    // 8. 初始化事件广播器
    initApplicationEventMulticaster();

    // 9. 子类扩展：如 SpringBoot 启动嵌入式 Tomcat
    onRefresh();

    // 10. 注册监听器
    registerListeners();

    // 11. 实例化非懒加载的单例 Bean（核心）
    finishBeanFactoryInitialization(beanFactory);

    // 12. 发布刷新完成事件
    finishRefresh();
}
```

Bean 实例化流程（第 11 步详解）

```
getBean(name)
  │
  ├─ 1. 转换 beanName（别名 → 真实名 / 去掉 & 前缀）
  ├─ 2. getSingleton() 查缓存（三级缓存）
  │     一级 singletonObjects：完整 Bean
  │     二级 earlySingletonObjects：早期暴露的半成品
  │     三级 singletonFactories：ObjectFactory
  ├─ 3. 缓存命中 → 返回
  ├─ 4. 缓存未命中 → createBean()
  │     ├─ 4.1 resolveBeforeInstantiation：InstantiationAwareBeanPostProcessor
  │     │         (AOP 代理提前返回机会)
  │     ├─ 4.2 doCreateBean：实际创建
  │     │     ├─ createBeanInstance：反射实例化(构造器注入)
  │     │     ├─ applyMergedBeanDefinitionPostProcessors：@Autowired/@Value
  │     │     ├─ addSingletonFactory：放入三级缓存(解决循环依赖)
  │     │     ├─ populateBean：属性注入(@Autowired)
  │     │     └─ initializeBean：初始化
  │     │           ├─ invokeAwareMethods：BeanNameAware 等
  │     │           ├─ applyBeanPostProcessorsBeforeInitialization
  │     │           │     (@PostConstruct 在此触发)
  │     │           ├─ invokeInitMethods：InitializingBean.afterPropertiesSet + init-method
  │     │           └─ applyBeanPostProcessorsAfterInitialization
  │     │                 (AOP 代理在此生成)
  │     └─ 4.3 注册到 singletonObjects
  └─ 5. 返回 Bean
```

循环依赖解决（三级缓存）

```
A 依赖 B，B 依赖 A：

1. 创建 A：实例化 → 半成品 A 放入 singletonFactories(三级)
2. 填充 A 属性：需要 B → 创建 B
3. 创建 B：实例化 → 半成品 B 放入 singletonFactories
4. 填充 B 属性：需要 A → 查缓存
   ├─ 一级空 ├─ 二级空 ├─ 三级有 A 的 ObjectFactory
   ├─ 调用 ObjectFactory.getObject() → 提前 AOP → 半成品 A
   └─ 半成品 A 放入 earlySingletonObjects(二级)，移除三级
5. B 填充完成 → B 初始化 → 完整 B 放入一级
6. 回到 A 填充：拿到完整 B → A 填充完成 → A 初始化 → 放入一级
```

## 4.5 Bean 的生命周期是什么？

完整 9 步生命周期

```
1. 实例化(Instantiation)
   └─ 反射调用构造器创建对象

2. 属性赋值(Populate Properties)
   └─ @Autowired / @Value 注入

3. Aware 接口回调
   ├─ BeanNameAware.setBeanName()
   ├─ BeanClassLoaderAware.setBeanClassLoader()
   └─ BeanFactoryAware.setBeanFactory()

4. BeanPostProcessor.postProcessBeforeInitialization
   └─ @PostConstruct 在此触发(CommonAnnotationBeanPostProcessor)

5. 初始化方法
   ├─ InitializingBean.afterPropertiesSet()
   └─ @Bean(initMethod="xxx") 自定义方法

6. BeanPostProcessor.postProcessAfterInitialization
   └─ AOP 代理生成(AbstractAutoProxyCreator)

7. 使用中(Ready for Use)

8. DisposableBean.destroy()

9. @Bean(destroyMethod="xxx") 自定义销毁
```

代码示例

```java
@Component
public class MyBean implements BeanNameAware, InitializingBean, DisposableBean {

    @Value("${app.name}")
    private String appName;

    @Autowired
    private UserService userService;

    @Override
    public void setBeanName(String name) {
        System.out.println("3. Aware: name=" + name);

    public void init() {
        System.out.println("4. @PostConstruct");
    }

    @Override
    public void afterPropertiesSet() {
        System.out.println("5. afterPropertiesSet");
    }

    @PreDestroy
    public void cleanup() {
        System.out.println("8. @PreDestroy");
    }

    @Override
    public void destroy() {
        System.out.println("9. destroy");
    }
}
```

## 4.6 Bean 是如何创建的？

核心方法

：`AbstractAutowireCapableBeanFactory.createBean()`

```java
protected Object doCreateBean(final String beanName, final RootBeanDefinition mbd) {
    // 1. 实例化：instantiateBean() 或 resolveConstructorOrFactoryMethod()
    BeanWrapper instanceWrapper = createBeanInstance(beanName, mbd, args);
    Object bean = instanceWrapper.getWrappedInstance();

    // 2. 提前暴露半成品(放入三级缓存)
    //    只有单例 + 允许循环依赖 + 正在创建中
    boolean earlySingletonExposure = (mbd.isSingleton() &&
        this.allowCircularReferences && isSingletonCurrentlyInCreation(beanName));
    if (earlySingletonExposure) {
        addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean));
    }

    // 3. 属性填充：populateBean()
    //    - 解析 @Autowired、@Resource
    //    - 调用 InstantiationAwareBeanPostProcessor.postProcessProperties
    populateBean(beanName, mbd, instanceWrapper);

    // 4. 初始化：initializeBean()
    Object exposedObject = initializeBean(beanName, exposedObject, mbd);

    // 5. 注册 disposableBean
    registerDisposableBeanIfNecessary(beanName, bean, mbd);

    return exposedObject;
}
```

实例化策略

：`SimpleInstantiationStrategy`

- 无参构造：`Constructor.newInstance()` 反射调用。
- 有参构造：`resolveConstructorArguments()` 解析参数 → 反射调用。

## 4.7 @Autowired 的底层原理是什么？

核心组件

：`AutowiredAnnotationBeanPostProcessor`

流程

```
1. BeanDefinition 加载阶段
   └─ AutowiredAnnotationBeanPostProcessor.postProcessMergedBeanDefinition()
      └─ 扫描字段/方法上的 @Autowired，缓存到 InjectionMetadata

2. 属性填充阶段
   └─ AutowiredAnnotationBeanPostProcessor.postProcessProperties()
      └─ InjectionMetadata.inject()
         └─ resolveDependency()  查找依赖
            ├─ DefaultListableBeanFactory.resolveDependency()
            ├─ 先按类型 findAutowireCandidates()
            ├─ 多个候选 → @Qualifier / @Primary / 优先级 / 字段名匹配
            └─ 最终确定一个 Bean → 反射注入
```

核心源码简化

```java
public class AutowiredAnnotationBeanPostProcessor {

    // 属性注入入口
    public PropertyValues postProcessProperties(PropertyValues pvs, Object bean, String beanName) {
        InjectionMetadata metadata = findAutowiringMetadata(beanName, bean.getClass());
        metadata.inject(bean, beanName, pvs);   // 注入
        return pvs;
    }

    class InjectionMetadata {
        void inject(Object target, String beanName, PropertyValues pvs) {
            for (InjectedElement element : this.injectedElements) {
                element.inject(target, beanName, pvs);
            }
        }
    }

    class AutowiredFieldElement extends InjectedElement {
        protected void inject(Object bean, String beanName, PropertyValues pvs) {
            Field field = (Field) this.member;
            Object value = beanFactory.resolveDependency(
                new DependencyDescriptor(field, true), beanName);
            field.setAccessible(true);
            field.set(bean, value);   // 反射注入
        }
    }
}
```

类型冲突解决

```java
// 多个实现类时，按优先级选择
interface Animal { }
@Component class Dog implements Animal {}
@Component class Cat implements Animal {}

// 方案1：@Qualifier
@Autowired @Qualifier("dog") Animal a;

// 方案2：@Primary 标记优先
@Primary
@Component class Dog implements Animal {}

// 方案3：字段名匹配 beanName
@Autowired Animal dog;  // 按字段名 dog 匹配
```

# 五、Spring AOP

## 5.1 什么是 AOP？

AOP(Aspect-Oriented Programming，面向切面编程)

：将横切关注点（日志、事务、安全）从业务逻辑中分离。

核心概念

| 术语             | 说明               | 示例                          |
| -------------- | ---------------- | --------------------------- |
| Aspect(切面)     | 横切逻辑的模块化         | `@Aspect` 事务切面              |
| JoinPoint(连接点) | 可被增强的点           | 方法执行、异常抛出                   |
| Pointcut(切入点)  | JoinPoint 的表达式筛选 | `execution(* com..*.*(..))` |
| Advice(通知)     | 在切点上执行的逻辑        | @Before / @After / @Around  |
| Target(目标对象)   | 被代理的原始对象         | UserService                 |
| Proxy(代理)      | 织入切面后的对象         | UserService$Proxy           |
| Weaving(织入)    | 创建代理的过程          | 运行时(动态代理)                   |

五种通知类型

```java
@Aspect
public class LogAspect {

    @Pointcut("execution(* com.example.service.*.*(..))")
    public void servicePointcut() {}

    @Before("servicePointcut()")
    public void before(JoinPoint jp) { /* 方法前 */ }

    @After("servicePointcut()")
    public void after(JoinPoint jp) { /* 方法后(无论成功失败) */ }

    @AfterReturning(value = "servicePointcut()", returning = "result")
    public void afterReturning(JoinPoint jp, Object result) { /* 成功返回后 */ }

    @AfterThrowing(value = "servicePointcut()", throwing = "ex")
    public void afterThrowing(JoinPoint jp, Exception ex) { /* 抛异常后 */ }

    @Around("servicePointcut()")
    public Object around(ProceedingJoinPoint pjp) throws Throwable {
        // 方法前逻辑
        Object result = pjp.proceed();  // 执行目标方法
        // 方法后逻辑
        return result;
    }
}
```

***

## 5.2 Spring AOP 是什么？

Spring AOP 是基于于于动态代理于于的 AOP 实现，与 IoC 容器集成，为 Bean 提供声明式服务（事务、缓存、异步等）。

特点

- 运行时织入（非编译时）。
- 仅支持方法级 JoinPoint（不支持字段级）。
- 与 AspectJ 互补：复杂场景可用 AspectJ 静态织入。

***

## 5.3 Spring AOP 的实现原理是什么？

核心组件

| 组件                                       | 作用                                        |
| ---------------------------------------- | ----------------------------------------- |
| `AnnotationAwareAspectJAutoProxyCreator` | BeanPostProcessor，扫描 @Aspect 创建代理         |
| `AopProxy`                               | 代理接口，有 JdkDynamicAopProxy 和 CglibAopProxy |
| `AdvisedSupport`                         | 持有切面配置(Advice、Pointcut)                   |
| `ReflectiveMethodInvocation`             | 责任链执行拦截器                                  |

代理创建流程

```
1. Spring 扫描 @Aspect 类，解析为 Advisor 列表
2. BeanPostProcessor.postProcessAfterInitialization()
   └─ AbstractAutoProxyCreator.wrapIfNecessary()
      ├─ findEligibleAdvisors()  找出适用当前 Bean 的 Advisor
      │   └─ aspectJAdvisors 遍历匹配 Pointcut
      ├─ createProxy()  创建代理
      │   ├─ 有接口 → JdkDynamicAopProxy
      │   └─ 无接口 → CglibAopProxy
      └─ 返回代理对象(替换原 Bean)
```

责任链执行

```java
// 代理方法调用时
public Object intercept(Object proxy, Method method, Object[] args) {
    List<Object> chain = advised.getInterceptorsAndDynamicInterceptionAdvice(method);
    if (chain.isEmpty()) {
        return method.invoke(target, args);   // 无切面直接调用
    }
    // 创建责任链
    CglibMethodInvocation invocation = new CglibMethodInvocation(
        proxy, target, method, args, targetClass, chain);
    return invocation.proceed();  // 依次执行拦截器
}

// 责任链递归
public Object proceed() throws Throwable {
    if (currentInterceptorIndex == interceptors.size - 1) {
        return invokeJoinpoint();  // 执行目标方法
    }
    Object interceptor = interceptors.get(++currentInterceptorIndex);
    return ((MethodInterceptor) interceptor).invoke(this);
}
```

原理

```java
@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration { }

// AutoConfigurationImportSelector
public class AutoConfigurationImportSelector implements DeferredImportSelector {

    public String[] selectImports(AnnotationMetadata metadata) {
        // 1. 加载 META-INF/spring.factories (Spring Boot 2.x)
        //    或 META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (3.x)
        List<String> configurations = getCandidateConfigurations(metadata);

        configurations = removeDuplicates(configurations);

        configurations = filter(configurations, autoConfigurationMetadata);

        return configurations.toArray(new String[0]);
    }
}
```

## 7.2 InnoDB 和 MyISAM 的区别是什么？

| 对比维度      | InnoDB          | MyISAM       |

| 事务        | 支持(ACID)        | 不支持          |

```
└──────────────────────────┘

二级索引(name)
```

```
└──────────┘           └──────────┘

```

## 7.3 主键索引和普通索引有什么区别？

| 维度        | 主键索引(Primary) | 普通索引(Secondary)     |
| --------- | ------------- | ------------------- |
| 唯一性       | 必须唯一且非空       | 可重复可空               |
| 数量限制      | 一表 1 个        | 多个                  |
| InnoDB 存储 | 聚簇索引(存行数据)    | 存主键值，需回表            |
| 查询性能      | 一次 B+ 树查找     | 二次查找(二级索引→主键索引→行数据) |
| 是否自动创建    | 是             | 需显式                 |

查询对比

```sql
-- 表结构
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    phone VARCHAR(20),
    INDEX idx_name (name)
);

-- 主键查询：直接走聚簇索引
SELECT * FROM user WHERE id = 1;
-- 流程：B+ 树定位主键 = 1 → 返回行数据(1次查找)

-- 普通索引查询
SELECT * FROM user WHERE name = 'Tom';
-- 流程：
--   1. idx_name B+ 树查到 name='Tom' 的主键值 = 1
--   2. 回表：主键索引 B+ 树查 id=1 的行数据(2次查找)

-- 覆盖索引优化(避免回表)
SELECT id, name FROM user WHERE name = 'Tom';
-- 流程：idx_name 叶子节点已含 id 和 name，无需回表
```

## 7.4 B+Tree 为什么适合数据库？

B+ 树特点

```
                    [30 | 60]                    ← 非叶子节点(仅存索引)
                   /     |     \
        [10|20]         [40|50]          [70|80]   ← 非叶子节点
        /    \           /    \           /    \
[10]→[20]→[30]→[40]→[50]→[60]→[70]→[80]→[90]   ← 叶子节点(存数据)
   ←── 双向链表 ──→
```

对比其他数据结构

| 数据结构 | 查找       | 范围查询     | 磁盘 IO |
| ---- | -------- | -------- | ----- |
| 二叉树  | O(log n) | 差(需遍历)   | 高(树深) |
| 红黑树  | O(log n) | 差        | 高(树深) |
| B 树  | O(log n) | 一般       | 中     |
| B+ 树 | O(log n) | 极好(叶子链表) | 低(矮胖) |
| Hash | O(1)     | 不支持      | -     |

B+ 树优势

### 1. 矮胖结构 → 磁盘 IO 少

- InnoDB 页大小 16KB，假设主键 BIGINT 8B + 指针 6B = 14B。
- 一页可存 `16384/14 ≈ 1170` 个索引项。
- 3 层 B+ 树可存 `1170 × 1170 × 16 ≈ 2000 万` 行数据。
- 查询任意数据仅需 3 次磁盘 IO。

### 2. 叶子节点链表 → 范围查询高效

```sql
SELECT * FROM user WHERE id BETWEEN 100 AND 200;
-- 定位 id=100 叶子节点 → 沿链表向后扫描到 id=200
```

### 3. 非叶子节点不存数据 → 节点能存更多索引

- 同样页大小，B+ 树扇出更大 → 树更矮 → IO 更少。

### 4. 数据有序 → 排序、分页高效

```sql
SELECT * FROM user ORDER BY id LIMIT 100000, 10;
-- B+ 树叶子节点有序 → 顺序读取 → 快
```

## 7.5 联合索引的最左匹配原则是什么？

联合索引

：`(a, b, c)` 在 B+ 树中按 a → b → c 顺序排序。

```
索引 (a, b, c)
├─ (1, 1, 1)
├─ (1, 1, 2)
├─ (1, 2, 1)
├─ (2, 1, 1)
├─ (2, 1, 3)
└─ (2, 2, 2)
排序规则：先按 a，a 相同按 b，b 相同按 c
```

最左匹配原则

```sql
-- 建索引
CREATE INDEX idx_abc ON t (a, b, c);

-- 能走索引的查询
WHERE a = 1                       ✅ 用到 a
WHERE a = 1 AND b = 2             ✅ 用到 a, b
WHERE a = 1 AND b = 2 AND c = 3   ✅ 用到 a, b, c
WHERE a = 1 AND c = 3             ⚠️ 只用到 a，c 无法用索引(中间断 b)
WHERE a = 1 AND b > 2 AND c = 3   ⚠️ a, b 用索引；b 是范围查询，c 失效

-- 无法走索引(缺少最左前缀 a)
WHERE b = 2                       ❌
WHERE b = 2 AND c = 3             ❌
WHERE c = 3                       ❌

-- MySQL 优化器会自动调整顺序
WHERE b = 2 AND a = 1             ✅ 优化为 a=1 AND b=2
```

范围查询截断

```sql
-- a 用索引，b 是范围 → c 失效
WHERE a = 1 AND b > 2 AND c = 3
-- 实际用到的索引列：a, b（b 之后的 c 失效）

-- a 是范围 → b, c 都失效
WHERE a > 1 AND b = 2 AND c = 3
-- 实际用到的索引列：a
```

索引下推(ICP, 5.6+)

```sql
-- 联合索引 (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age > 18;

-- 无 ICP：
--   1. 索引找到 name LIKE '张%' 的所有记录(可能很多)
--   2. 逐条回表，再过滤 age > 18
-- 5.6+ ICP：
--   1. 索引找到 name LIKE '张%' 的记录
--   2. 直接在索引层过滤 age > 18(索引中有 age)
--   3. 仅对满足条件的记录回表
-- 减少 80%+ 回表次数
```

## 7.6 什么情况下索引会失效？

九大常见失效场景

### 1. 函数操作

```sql
-- ❌ 对索引列用函数
WHERE YEAR(create_time) = 2024        -- 失效
WHERE LEFT(name, 1) = '张'            -- 失效
WHERE DATE(create_time) = '2024-01-01' -- 失效

-- ✅ 改写
WHERE create_time >= '2024-01-01' AND create_time < '2024-01-02'
```

### 2. 运算操作

```sql
-- ❌
WHERE id + 1 = 10          -- 失效
WHERE id * 2 = 20          -- 失效

-- ✅
WHERE id = 10 - 1          -- 不失效
```

### 3. 隐式类型转换

```sql
-- ❌ phone 是 VARCHAR，传入数字 → 隐式转换
WHERE phone = 13800138000           -- 失效(转字符串函数)

-- ✅
WHERE phone = '13800138000'          -- 走索引
```

### 4. 隐式字符编码转换

```sql
-- ❌ 表 A 是 utf8，表 B 是 utf8mb4，JOIN 时编码不同 → 函数转换
SELECT * FROM A JOIN B ON A.code = B.code WHERE B.id = 1;

-- ✅ 统一编码
ALTER TABLE A CONVERT TO CHARACTER SET utf8mb4;
```

### 5. LIKE 以 % 开头

```sql
-- ❌
WHERE name LIKE '%张'      -- 失效(无法用 B+ 树前缀)
WHERE name LIKE '%张%'     -- 失效

-- ✅
WHERE name LIKE '张%'      -- 走索引(前缀匹配)
```

### 6. OR 连接非索引列

```sql
-- 假设 name 有索引，status 无索引
-- ❌ OR 两侧必须都有索引才走
WHERE name = 'Tom' OR status = 1     -- 全表扫描

-- ✅ 都有索引 OR 可走 index_merge
WHERE name = 'Tom' OR age = 18      -- 都有索引可走
```

### 7. 不符合最左匹配

见 7.5。

### 8. != / NOT IN / NOT EXISTS

```sql
-- ❌ 通常导致全表扫描
WHERE status != 1
WHERE id NOT IN (1, 2, 3)

-- 特殊情况：覆盖索引时可能走
SELECT name FROM t WHERE name != 'Tom'   -- 可能走 idx_name
```

### 9. 优化器认为全表扫描更快

- 表数据量小(几百条)。
- 索引区分度低(如性别，只有 2 个值)。
- 大量数据需要回表，优化器算成本后选择全表。

EXPLAIN 查看是否走索引

```sql
EXPLAIN SELECT * FROM user WHERE name = 'Tom';
-- type: ref 走索引，ALL 全表扫描
-- key: 实际使用的索引名
-- rows: 估算扫描行数
```

## 7.7 SQL 优化的策略有哪些？

优化金字塔

```
         少做事(最高效)
            ↑
       建合适的索引
            ↑
       只取需要的列
            ↑
       优化 SQL 写法
            ↑
       表结构设计合理
```

15 条实战优化建议

### 1. 避免全表扫描

```sql
-- ❌ SELECT *
SELECT * FROM user WHERE age > 18;

-- ✅ 只取需要的列
SELECT id, name, phone FROM user WHERE age > 18;
```

### 2. 用 LIMIT 1 加速已知唯一查询

```sql
SELECT name FROM user WHERE phone = '13800138000' LIMIT 1;
```

### 3. WHERE 替代 HAVING

```sql
-- ❌ HAVING 过滤(聚合后过滤)
SELECT dept, COUNT(*) FROM emp GROUP BY dept HAVING dept = 'IT';

-- ✅ WHERE 过滤(聚合前过滤)
SELECT dept, COUNT(*) FROM emp WHERE dept = 'IT' GROUP BY dept;
```

### 4. JOIN 顺序：小表驱动大表

```sql
-- 小表(过滤后行数少)放前面
SELECT * FROM small_table s JOIN big_table b ON s.id = b.sid WHERE s.status = 1;
```

### 5. 用 EXISTS 替代 IN(子查询)

```sql
-- ❌ IN 子查询
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE vip = 1);

-- ✅ EXISTS
SELECT * FROM orders o WHERE EXISTS (
    SELECT 1 FROM users u WHERE u.id = o.user_id AND u.vip = 1
);
```

### 6. 批量插入

```sql
-- ❌ 循环单条
INSERT INTO t VALUES (1);
INSERT INTO t VALUES (2);

-- ✅ 批量
INSERT INTO t VALUES (1), (2), (3);

-- 大批量用 load data
LOAD DATA INFILE '/data.csv' INTO TABLE t;
```

### 7. 避免大事务

```sql
-- ❌
BEGIN;
-- ... 10 万行更新
COMMIT;

-- ✅ 分批
BEGIN;
UPDATE t SET ... WHERE id BETWEEN 1 AND 1000;
COMMIT;
```

### 8. 避免深分页

```sql
-- ❌ 深分页扫描大量数据
SELECT * FROM t LIMIT 1000000, 10;

-- ✅ 游标/延迟关联
SELECT * FROM t WHERE id > 1000000 ORDER BY id LIMIT 10;

-- ✅ 延迟关联
SELECT * FROM t WHERE id IN (
    SELECT id FROM t ORDER BY id LIMIT 1000000, 10
);
```

### 9. 避免大表 LIKE

```sql
-- 全文索引替代
ALTER TABLE article ADD FULLTEXT INDEX ft_content (content);
SELECT * FROM article WHERE MATCH(content) AGAINST('Java' IN NATURAL LANGUAGE MODE);
```

见 7.6。

### 11. 用 UNION ALL 替代 UNION

```sql
-- ❌ UNION 去重(消耗大)
SELECT name FROM user1 UNION SELECT name FROM user2;

-- ✅ UNION ALL 不去重
SELECT name FROM user1 UNION ALL SELECT name FROM user2;
```

### 12. 使用 EXPLAIN 分析


### 13. 索引区分度

## 7.8 什么是事务？ACID 是什么？

事务

：一组操作要么全部成功，要么全部失败，是一个不可分割的工作单元。

ACID 四大特性

| 特性 | 全称              | 说明             | 实现机制             |
| -- | --------------- | -------------- | ---------------- |
| A  | Atomicity 原子性   | 事务内操作要么全做要么全不做 | undo log(回滚)     |
| C  | Consistency 一致性 | 事务前后数据状态一致     | 业务约束 + A + I + D |
| I  | Isolation 隔离性   | 并发事务互不干扰       | 锁 + MVCC         |
| D  | Durability 持久性  | 提交后永久保存        | redo log         |

事务示例

```sql
-- 转账事务
START TRANSACTION;
UPDATE account SET balance = balance - 100 WHERE id = 1;   -- A 扣 100
UPDATE account SET balance = balance + 100 WHERE id = 2;   -- B 加 100
COMMIT;  -- 或 ROLLBACK
```

事务并发问题

| 问题    | 说明              | 示例                                   |
| ----- | --------------- | ------------------------------------ |
| 脏读    | 读到其他事务未提交的数据    | A 改 B 余额，B 回滚，但 A 读到了改动              |
| 不可重复读 | 同一事务两次读同一行结果不同  | A 读余额 100，B 改为 200 提交，A 再读 200       |
| 幻读    | 同一事务两次范围查询结果集不同 | A 查 count=10，B 新增 1 条提交，A 查 count=11 |

四种隔离级别

| 隔离级别             | 脏读 | 不可重复读 | 幻读 | 性能           |
| ---------------- | -- | ----- | -- | ------------ |
| READ UNCOMMITTED | √  | √     | √  | 高            |
| READ COMMITTED   | ×  | √     | √  | 中(Oracle 默认) |
| REPEATABLE READ  | ×  | ×     | √  | 低(MySQL 默认)  |
| SERIALIZABLE     | ×  | ×     | ×  | 最低           |

## 7.9 什么是 MVCC？

MVCC(Multi-Version Concurrency Control)

：多版本并发控制，通过数据快照实现非阻塞读。

核心组件

| 组件                 | 作用              |
| ------------------ | --------------- |
| 隐藏字段 `DB_TRX_ID`   | 最近修改的事务 ID      |
| 隐藏字段 `DB_ROLL_PTR` | 指向 undo log 的指针 |
| 隐藏字段 `DB_ROW_ID`   | 隐含主键(无主键时)      |
| undo log           | 旧版本数据链(版本链)     |
| ReadView           | 读视图，决定能看到哪个版本   |

ReadView 结构

```
ReadView {
    m_ids:        当前活跃事务 ID 列表(未提交)
    min_trx_id:   活跃事务最小 ID
    max_trx_id:   下一个将分配的事务 ID
    creator_trx_id: 创建 ReadView 的事务 ID
}
```

可见性判断规则

```
对某条记录的某个版本：
  if trx_id == creator_trx_id:
      可见(自己修改的)
  elif trx_id < min_trx_id:
      可见(事务已提交)
  elif trx_id >= max_trx_id:
      不可见(事务在 ReadView 创建后才开始)
  elif trx_id in m_ids:
      不可见(事务未提交)
  else:
      可见(事务已提交)
```

RC vs RR 的 MVCC 差异

| 隔离级别            | ReadView 生成时机           | 效果                 |
| --------------- | ----------------------- | ------------------ |
| READ COMMITTED  | 每次 SELECT 都生成新 ReadView | 能读到已提交的最新数据(不可重复读) |
| REPEATABLE READ | 事务第一次 SELECT 时生成，后续复用   | 始终读同一快照(可重复读)      |

版本链示例

```
当前事务 A(id=100) 读取数据：

行记录：name='Tom', trx_id=90, roll_ptr→undo
                                    ↓
                            undo: name='Jerry', trx_id=80
                                    ↓
                            undo: name='Jack', trx_id=70

活跃事务列表 m_ids=[95, 105]
A 读取流程：
  1. 当前版本 trx_id=90，90 < 95(min)，可见 → 返回 'Tom'
  2. 若 90 在 m_ids 中 → 顺 roll_ptr 找上一版本
  3. 直到找到可见版本
```

## 7.10 什么是幻读？

幻读

：同一事务内执行两次相同的范围查询，第二次出现了第一次没有的行(其他事务 INSERT)。

与不可重复读的区别

| 类型    | 原因                 | 操作类型  |
| ----- | ------------------ | ----- |
| 不可重复读 | 其他事务 UPDATE/DELETE | 修改现有行 |
| 幻读    | 其他事务 INSERT        | 新增行   |

RR 隔离级别如何解决幻读

### 1. 快照读(普通 SELECT) - MVCC

```sql
-- 事务 A
SELECT * FROM user WHERE age > 18;   -- 第一次：10 行
-- 事务 B 插入 1 条并提交
SELECT * FROM user WHERE age > 18;   -- 第二次：10 行(MVCC 快照不变)
-- 不会幻读
```

### 2. 当前读(SELECT ... FOR UPDATE / UPDATE / DELETE) - 间隙锁

```sql
-- 事务 A
SELECT * FROM user WHERE age > 18 FOR UPDATE;
-- 锁定 age > 18 的所有行 + 间隙(age > 18 的范围)
-- 事务 B 尝试 INSERT(age=20) → 阻塞(间隙锁)
```

间隙锁(Gap Lock)

```
假设有数据：age = [10, 20, 30]
索引结构：(-∞, 10), (10, 20), (20, 30), (30, +∞)

执行：SELECT * FROM t WHERE age > 15 FOR UPDATE;
锁范围：(15, 20), [20, 30], (30, +∞)  ← 包括记录锁 + 间隙锁

其他事务无法在这些间隙插入 → 避免幻读
```

仍可能幻读的场景

```sql
-- 事务 A
BEGIN;
SELECT * FROM user WHERE id = 1;          -- 快照读，不存在
-- 事务 B 插入 id=1 并提交
UPDATE user SET name = 'Tom' WHERE id = 1; -- 当前读，更新成功(特殊场景)
SELECT * FROM user WHERE id = 1;           -- 现在能读到了(幻读)
```

避免

：事务开始时用 `SELECT ... FOR UPDATE` 锁定范围。

## 8.1 Redis 为什么这么快？

六大原因

| 原因             | 说明                |
| -------------- | ----------------- |
| 1. 内存存储        | 数据全在内存，读写无磁盘 IO   |
| 2. 单线程模型       | 避免多线程上下文切换和锁竞争    |
| 3. IO 多路复用     | epoll 单线程处理大量连接   |
| 4. 高效数据结构      | SDS / 压缩列表 / 跳表等  |
| 5. 通信协议简单      | RESP 协议解析快        |
| 6. 6.0+ 多线程 IO | 命令执行仍单线程，IO 读写多线程 |

单线程为何快

```
传统多线程：
  ┌─────┐ ┌─────┐ ┌─────┐
  │ 线程1│ │ 线程2│ │ 线程3│   ← 上下文切换开销
  └──┬──┘ └──┬──┘ └──┬──┘
     └────────┴────────┘
              ↓
           共享数据(加锁)        ← 锁竞争
              ↓
            串行执行

Redis 单线程：
  epoll 监听所有连接
       ↓
  事件队列(命令按序执行)
       ↓
  内存操作(O(1) / O(log n))
       ↓
  返回结果
```

Redis 6.0 多线程 IO

```
单线程：                多线程 IO：
  连接1 →               连接1 →┐
  连接2 →  命令执行          ├─ IO 线程池(读/写)
  连接3 →  (串行)          └─→ 命令执行(单线程串行)
  连接4 →                         ↓
                              返回 IO 线程写回
```

## 8.2 Redis 有哪些数据结构？

五大基础类型 + 底层编码

| 类型     | 编码(底层实现)                          | 应用场景             |
| ------ | --------------------------------- | ---------------- |
| String | int / embstr / raw(SDS)           | 计数器、缓存 JSON、分布式锁 |
| List   | quicklist(3.2+)                   | 消息队列、最新列表        |
| Hash   | ziplist(小) / hashtable(大)         | 对象存储(hget/hset)  |
| Set    | intset(纯整数) / hashtable           | 去重、标签、共同好友       |
| ZSet   | ziplist(小) / skiplist + hashtable | 排行榜、延迟队列         |

底层结构详解

### SDS(Simple Dynamic String)

```c
struct sdshdr {
    int len;      // 已使用长度
    int free;     // 剩余空间
    char buf[];   // 字符数组
};
// 优势：O(1) 获取长度、二进制安全、预分配减少扩容
```

### 跳表(SkipList)

```
Level 3:  HEAD ──────────────→ 30 ──────────────→ 50 → NULL
Level 2:  HEAD ──────→ 10 ──→ 30 ──→ 40 ────────→ 50 → NULL
Level 1:  HEAD → 5 → 10 ──→ 20 → 30 → 40 ──→ 45 → 50 → NULL

查询 40：
  Level 3: HEAD → 30(<40) → 50(>40) 退回 30
  Level 2: 30 → 40(=40) 找到
```

为什么 ZSet 用跳表而非红黑树

- 范围查询天然支持(层 1 是链表)。
- 实现简单，无旋转操作。
- 并发扩展性好。

### 压缩列表(ziplist)

```
连续内存：<zlbytes><zltail><zllen><entry1><entry2>...<entryN><zlend>
优势：紧凑省内存(小数据时)
缺点：插入/删除需 memmove；连锁更新 prevlen
```

## 8.3 Redis 和 MySQL 如何保证数据一致性？

问题本质

：缓存与数据库是两个系统，无法做原子操作。

常见方案对比

| 方案              | 流程             | 问题              |
| --------------- | -------------- | --------------- |
| 先更新 DB 再更新缓存    | DB→Cache       | 并发更新顺序错乱、缓存计算浪费 |
| 先更新缓存再更新 DB     | Cache→DB       | DB 失败导致不一致      |
| 先删缓存再更新 DB      | Cache→DB→Cache | 并发读回填旧值         |
| 先更新 DB 再删缓存(推荐) | DB→Cache       | 并发读旧值(概率极低)     |

方案 1：Cache Aside(旁路缓存)推荐

```
写：UPDATE DB → DEL cache
读：GET cache → 未命中 → GET DB → SET cache
```

问题：先删缓存再更新 DB 的并发问题

```
线程 A：DEL cache → UPDATE DB(耗时)
线程 B：GET cache 未命中 → GET DB(旧值) → SET cache(旧值)
结果：缓存是旧值，DB 是新值 → 不一致
```

解决：延迟双删

```
1. DEL cache
2. UPDATE DB
3. sleep 500ms(读旧值的时间窗口)
4. DEL cache 再次删除

代码：
redis.del(key);
db.update(...);
Thread.sleep(500);
redis.del(key);
```

方案 2：订阅 binlog 异步删缓存(最终一致)

```
MySQL binlog → Canal → MQ → 消费者 → DEL cache
                       │
                       └─ 重试保证最终删除成功
```

方案 3：消息队列重试

```
DB 更新后发 MQ → 消费者删缓存 → 失败重试
```

强一致性方案

- 2PC(两阶段提交) - 性能差，少用。
- 加分布式读写锁 - 适用于金融场景。

## 8.4 缓存穿透是什么？

定义

：查询不存在的数据，缓存和 DB 都没有，每次都打到 DB。

```
恶意请求：GET user?id=9999999(不存在)
  → 缓存未命中
  → DB 查询(null)
  → 不缓存
  → 每次都打 DB
```

解决方案

### 1. 缓存空值

```java
Object value = cache.get(key);
if (value == null) {
    value = db.query(key);
    if (value == null) {
        cache.set(key, "NULL", 60);   // 缓存空值，短过期
    } else {
        cache.set(key, value);
    }
}
```

### 2. 布隆过滤器(BloomFilter)

```
请求 → 布隆过滤器判断
  ├─ 不存在 → 直接返回(绝不存在)
  └─ 可能存在 → 查缓存 → 查 DB
```

```java
BloomFilter<Long> filter = BloomFilter.create(
    Funnels.longFunnel(), 1000000, 0.01);  // 100万容量，1% 误判率

// 启动时加载所有 key
users.forEach(u -> filter.put(u.getId()));

// 查询时
if (!filter.mightContain(id)) {
    return null;   // 一定不存在
}
```

### 3. 接口限流 + 参数校验

- 非法参数(负 id、超大 id)直接拒绝。

## 8.5 缓存击穿是什么？

定义

：热点 key 突然过期，大量并发请求同时打到 DB。

```
热点 key 过期瞬间：
  1000 个请求同时查缓存 → 未命中 → 1000 个查 DB → DB 压力激增
```

解决方案

### 1. 互斥锁(推荐)

```java
Object value = cache.get(key);
if (value == null) {
    // 加锁，只让一个线程查 DB
    if (lock.tryLock()) {
        try {
            value = cache.get(key);   // 双重检查
            if (value == null) {
                value = db.query(key);
                cache.set(key, value);
            }
        } finally {
            lock.unlock();
        }
    } else {
        Thread.sleep(50);
        return get(key);   // 重试
    }
}
```

### 2. 逻辑过期(不设 TTL)

```java
// 数据中存逻辑过期时间
{
    "data": "...",
    "expireTime": 1690000000
}

Object value = cache.get(key);
if (value.expireTime < now()) {
    // 异步线程更新 DB→Cache
    asyncUpdate(key);
    // 当前线程返回旧值(允许短暂不一致)
}
return value.data;
```

### 3. 热点 key 永不过期

- 适合少量确定的热点(如首页推荐)。

## 8.6 缓存雪崩是什么？

定义

：大量 key 同时过期或 Redis 宕机，请求全打到 DB。

两种场景

| 场景          | 原因         |
| ----------- | ---------- |
| 大量 key 同时过期 | 缓存设置相同过期时间 |
| Redis 宕机    | 节点故障，整体不可用 |

解决方案

### 1. 过期时间加随机值

```java
// ❌ 相同过期时间
cache.set(key, value, 3600);

// ✅ 加随机值
int ttl = 3600 + random.nextInt(300);  // 3600-3900 秒
cache.set(key, value, ttl);
```

### 2. 多级缓存

```
请求 → 本地缓存(Caffeine) → Redis → DB
                ↓
            命中返回
```

### 3. Redis 高可用

- 主从 + 哨兵
- Redis Cluster 分片
- 限流降级：DB 压力大时返回降级数据

### 4. 服务熔断降级

```java
// Sentinel/Hystrix 熔断
@SentinelResource(value = "getUser", fallback = "getUserFallback")
public User getUser(Long id) {
    return userService.getById(id);
}

public User getUserFallback(Long id) {
    return new User(id, "默认用户");   // 降级
}
```

## 8.7 Redis 如何实现分布式锁？

基础实现

```java
// 加锁：SET key value NX EX 30
String result = jedis.set(lockKey, requestId, "NX", "EX", 30);
if ("OK".equals(result)) {
    try {
        // 业务逻辑
    } finally {
        // 释放锁：Lua 脚本保证原子性
        String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                     "  return redis.call('del', KEYS[1]) " +
                     "else return 0 end";
        jedis.eval(lua, Collections.singletonList(lockKey),
                   Collections.singletonList(requestId));
    }
}
```

SET NX EX 三大保证

- `NX`：不存在才设置(互斥)
- `EX`：设置过期时间(防死锁)
- 原子性：单条命令保证

Lua 脚本释放锁的原因

```
不加 Lua：
  if (get(key) == requestId) {   ← 线程 A 判断成功
      // GC 停顿或网络延迟
      del(key);                  ← 但此时锁已过期被 B 拿到，A 误删 B 的锁
  }

加 Lua：判断+删除原子执行
```

问题：锁过期但业务未完成

```
线程 A：持锁 30s，业务执行 35s → 锁过期 → 线程 B 拿到锁 → A 完成后误删 B 的锁
```

解决 1：看门狗续期(Redisson)

```java
RLock lock = redisson.getLock("myLock");
lock.lock();   // 默认 30s，每 10s 续期一次
try {
    // 业务
} finally {
    lock.unlock();
}
```

解决 2：RedLock 算法(多节点)

```
1. 向 5 个独立 Redis 实例加锁
2. 超过半数(3 个)成功 → 加锁成功
3. 总耗时 < 锁过期时间 → 有效
4. 否则向所有节点释放锁
```

生产推荐：Redisson

```java
Config config = new Config();
config.useClusterServers()
      .addNodeAddress("redis://192.168.1.1:6379")
      .addNodeAddress("redis://192.168.1.2:6379");
RedissonClient redisson = Redisson.create(config);

RLock lock = redisson.getLock("orderLock");
try {
    if (lock.tryLock(10, 30, TimeUnit.SECONDS)) {
        // 加锁成功
    }
} finally {
    if (lock.isHeldByCurrentThread()) {
        lock.unlock();
    }
}
```

分布式锁对比

| 方案        | 优点           | 缺点       |
| --------- | ------------ | -------- |
| Redis 单机  | 简单、性能高       | 单点故障     |
| RedLock   | 高可用、防脑裂      | 复杂、有争议   |
| Redisson  | 功能全(可重入、看门狗) | 依赖 Redis |
| ZooKeeper | 强一致(CP)      | 性能低      |
| etcd      | 强一致、租约       | 运维复杂     |

微服务核心组件

```
┌────────────────────────────────────────────────┐

└────────────────────────────────────────────────┘
        ↓            ↓            ↓            ↓
   ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐

      │           │           │           │
   ┌──┴───┐    ┌──┴───┐    ┌──┴───┐    ┌──┴───┐
   │MySQL │    │MySQL │    │MySQL │    │MySQL │
   └──────┘    └──────┘    └──────┘    └──────┘

横切关注点：
  - 服务注册发现(Nacos/Eureka)
  - 配置中心(Nacos Config)
  - 熔断降级(Sentinel/Hystrix)
  - 链路追踪(SkyWalking/Zipkin)
  - 分布式事务(Seata)
  - 消息队列(RocketMQ/Kafka)
```

## 9.2 为什么要拆分微服务？

六大驱动因素

### 1. 业务复杂度

单体应用代码量膨胀(百万行)，开发维护困难。

### 2. 团队规模

- 单体：团队冲突多(合并代码、发布协调)。
- 微服务：服务自治，团队独立。

### 3. 独立部署

- 单体：改一行代码全量发布。
- 微服务：只发布变更的服务。

### 4. 技术异构

- 不同服务选最合适技术：Java 做交易，Go 做网关，Python 做数据分析。

### 5. 弹性扩容

- 双 11：只扩容订单/支付服务，用户服务不扩。

### 6. 故障隔离

- 单体：一个 bug 导致整体崩溃。
- 微服务：支付服务挂不影响商品浏览。

拆分原则

| 原则     | 说明                  |
| ------ | ------------------- |
| 单一职责   | 每个服务只做一件事           |
| 限界上下文  | 按业务领域划分(DDD)        |
| 服务自治   | 独立开发、部署、数据存储        |
| 高内聚低耦合 | 服务内功能聚合，服务间接口清晰     |
| 合适粒度   | 不宜过细(管理成本)或过粗(失去意义) |

拆分时机

- 业务复杂、团队 > 50 人、需要独立扩容 → 拆分。
- 业务简单、团队小 → 不必微服务。

## 9.3 服务注册与发现是什么？

核心问题

：服务实例动态变化(扩容、宕机、迁移)，调用方如何知道实例地址？

两种模式

### 1. 客户端发现

```
服务提供者启动 → 注册到注册中心
服务调用者：
  1. 从注册中心拉取服务列表(本地缓存)
  2. 客户端负载均衡选实例
  3. 直接调用

代表：Eureka、Nacos
```

### 2. 服务端发现

```
服务提供者启动 → 注册到注册中心
服务调用者：
  → 请求负载均衡器(Consul Template / Kubernetes Service)
  → 转发到实例

代表：K8s Service、AWS ALB
```

Nacos 注册中心示例

```yaml
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: dev
```

```java
@Service
public class OrderService {
    @Autowired
    private RestTemplate restTemplate;

    public User getUser(Long id) {
        // 服务名调用，自动负载均衡
        return restTemplate.getForObject(
            "http://user-service/user/" + id, User.class);
    }
}
```

健康检查

- 心跳续约：服务定期向注册中心发心跳。
- 失效剔除：超过一段时间未心跳 → 标记为下线。
- 自我保护：Eureka 15 分钟内心跳失败比例 > 85% → 进入保护，不剔除(防网络抖动误删)。

## 9.5 为什么需要消息队列？

三大核心作用

### 1. 异步解耦

```
同步调用：
  用户注册 → 写 DB → 发邮件 → 发短信 → 送优惠券
  总耗时 = 50 + 100 + 100 + 100 = 350ms

异步消息：
  用户注册 → 写 DB → 发 MQ(立即返回)
                    ↓
            消费者各自处理邮件/短信/优惠券
  总耗时 = 50 + 5 = 55ms
```

### 2. 流量削峰

```
秒杀场景：
  10 万请求 → MQ 缓冲 → 系统按能力消费(1000/s)→ 写 DB
  避免 DB 被压垮
```

### 3. 服务解耦

```
订单服务 → MQ → 物流服务
              → 积分服务
              → 推送服务
新增下游服务无需改订单服务代码
```

常见 MQ 对比

| 特性   | Kafka  | RocketMQ | RabbitMQ |
| ---- | ------ | -------- | -------- |
| 吞吐量  | 百万级    | 十万级      | 万级       |
| 延迟   | 毫秒     | 毫秒       | 微秒       |
| 可靠性  | 高      | 高(金融)    | 高        |
| 顺序消息 | 分区有序   | 严格顺序     | 不保证      |
| 事务消息 | 弱      | 支持       | 不支持      |
| 适用   | 日志/大数据 | 金融/电商    | 企业应用     |

## 9.6 如何保证消息不丢失？

消息丢失的三个环节

```
生产者 → MQ Broker → 消费者
   ①           ②          ③
丢失        丢失          丢失
```

### 1. 生产者端丢失

```java
// Kafka：确认机制
props.put("acks", "all");  // 0/1/all
// 0：发送即忘
// 1：leader 确认(默认)
// all：所有副本确认(最安全)

// RocketMQ：同步发送 + 重试
producer.send(msg);   // 同步等待响应
// 失败重试：retryTimesWhenSendFailed=2

// 本地消息表：先写 DB 再发 MQ
db.save(localMessage);   // 本地消息表
mq.send(message);
// 定时任务扫描未发送的消息重发
```

### 2. Broker 端丢失

```java
// Kafka：副本机制
// 副本数 > 1，acks=all
min.insync.replicas=2   // 至少 2 个副本同步

// 持久化配置
log.flush.interval.messages=1   // 每条消息刷盘(性能低)
// 或用副本代替刷盘

// RocketMQ：同步刷盘
flushDiskType=SYNC_FLUSH   // 异步 ASYNC_FLUSH(默认，性能高)
```

### 3. 消费者端丢失

```java
// 手动 ACK(关闭自动提交)
// Kafka
consumer.commitSync();   // 处理完手动提交 offset

// RocketMQ
consumer.registerMessageListener((msgs, context) -> {
    try {
        process(msgs);              // 业务处理
        return ConsumeStatus.CONSUME_SUCCESS;
    } catch (Exception e) {
        return ConsumeStatus.RECONSUME_LATER;   // 失败重试
    }
});
```

完整方案

| 环节 | Kafka         | RocketMQ    |
| -- | ------------- | ----------- |
| 生产 | acks=all + 重试 | 同步发送 + 重试   |
| 存储 | 副本 + 刷盘       | 同步刷盘 + 主从同步 |
| 消费 | 手动提交 offset   | 返回状态 + 重试   |

## 9.7 如何避免重复消费？

重复消费原因

- 消费者处理完成但 ACK 失败 → Broker 重发。
- 网络抖动导致重试。
- Rebalance 时 offset 未提交。

解决方案：幂等性

### 1. 数据库唯一约束

```sql
-- 订单号唯一
INSERT INTO orders(order_no, ...) VALUES(...);
-- 重复插入报错 → 已处理
```

### 2. Redis 去重

```java
String key = "msg:processed:" + msgId;
if (redis.setIfAbsent(key, "1", 24, HOURS)) {
    // 首次处理
    process(message);
} else {
    // 已处理，跳过
}
```

### 3. 业务状态机

```java
// 订单状态：待支付 → 已支付 → 已发货
if (order.status == OrderStatus.UNPAID) {
    order.pay();   // 业务方法内判断状态
}
// 重复消费时 status 已变 → 不会重复支付
```

### 4. 乐观锁(版本号)

```sql
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;
-- 重复消费时 version 已变 → 影响 0 行
```

### 5. 全局唯一 ID + 去重表

```sql
-- 去重表
CREATE TABLE msg_consume_log(
    msg_id VARCHAR(64) PRIMARY KEY,
    consume_time DATETIME
);

-- 消费时
INSERT INTO msg_consume_log VALUES(?, now());
-- 成功 → 首次，继续业务
-- 主键冲突 → 已消费，跳过
```

## 10.1 Docker 和虚拟机有什么区别？

| 对比维度 | Docker 容器  | 虚拟机         |
| ---- | ---------- | ----------- |
| 隔离级别 | 进程级(共享内核)  | 操作系统级(独立内核) |
| 启动速度 | 秒级         | 分钟级         |
| 资源占用 | MB 级       | GB 级        |
| 并发密度 | 单机数百容器     | 单机数十 VM     |
| 性能   | 接近原生       | 有虚拟化损耗      |
| 镜像大小 | MB         | GB          |
| 隔离性  | 弱(共享内核)    | 强           |
| 安全性  | 较弱(逃逸风险)   | 高           |
| 跨平台  | Linux 内核特性 | 任意 OS       |

架构对比

```
虚拟机架构：                     Docker 架构：
┌────┬────┬────┐                 ┌────┬────┬────┐
│App│App│App│                 │App│App│App│
├────┼────┼────┤                 ├────┼────┼────┤
│Bins│Bins│Bins│                 │Bins│Bins│Bins│
├────┼────┼────┤                 ├────┴────┴────┤
│Guest OS│Guest OS│             │  Docker 引擎  │
├────┼────┼────┤                 ├──────────────┤
│  Hypervisor  │                 │  Host OS     │
├──────────────┤                 ├──────────────┤
│   硬件        │                 │   硬件        │
└──────────────┘                 └──────────────┘
```

Docker 核心概念

- 镜像(Image)  ：只读模板，包含应用+依赖+环境。
- 容器(Container)  ：镜像运行的实例，可读写。
- 仓库(Registry)  ：镜像存储分发(Docker Hub / 私有仓库)。
- Dockerfile  ：镜像构建脚本。

## 10.2 如何构建镜像？

Dockerfile 示例

```dockerfile
# 基础镜像
FROM openjdk:8-jdk-alpine

# 维护者
LABEL maintainer="harry@example.com"

# 工作目录
WORKDIR /app

# 复制 jar 包
COPY target/myapp.jar /app/myapp.jar

# 时区
ENV TZ=Asia/Shanghai

# 暴露端口
EXPOSE 8080

# JVM 参数
ENV JAVA_OPTS="-Xms512m -Xmx512m -XX:+UseG1GC"

# 启动命令
ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar /app/myapp.jar"]
```

多阶段构建(减小镜像)

```dockerfile
# Stage 1: 构建
FROM maven:3.8-openjdk-8 AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn clean package -DskipTests

# Stage 2: 运行(最终镜像小)
FROM openjdk:8-jdk-alpine
WORKDIR /app
COPY --from=builder /build/target/myapp.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

构建命令

```bash
# 构建镜像
docker build -t myapp:1.0.0 .

# 查看镜像
docker images

# 推送到仓库
docker login registry.example.com
docker tag myapp:1.0.0 registry.example.com/myapp:1.0.0
docker push registry.example.com/myapp:1.0.0
```

镜像分层原理

```
Dockerfile 每条指令 = 一层(只读)

FROM openjdk:8-jdk-alpine      ← 基础层(120MB)
  ↓
WORKDIR /app                   ← 配置层
  ↓
COPY target/myapp.jar ...      ← 应用层(20MB)
  ↓
EXPOSE 8080                    ← 元数据层
  ↓
ENTRYPOINT ["java", "-jar"]    ← 启动层

容器运行时：
  镜像层(只读) + 容器层(可读写)
```

镜像优化建议

- 选择小基础镜像(`alpine` / `distroless`)。
- 合并 RUN 指令减少层数。
- 使用 `.dockerignore` 排除无关文件。
- 多阶段构建：构建与运行分离。

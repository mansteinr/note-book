# ChatBI / AI Agent 项目面试回答

## 一、项目整体介绍

### 面试官：介绍一下你的 ChatBI / AI Agent 项目

> 这个项目主要是一个面向企业内部数据分析场景的 ChatBI 系统，用户可以通过自然语言直接查询业务数据。
>
> 例如用户可以输入“查询昨天南京地区的流量情况”或者“帮我看一下最近 7 天 PCDN 流量趋势”。
>
> 系统会先理解用户问题，然后结合当前用户权限、历史上下文以及业务语义模型，对问题进行补全和标准化。之后通过 Agent 调用 Dataset Tool、Plugin Tool 等工具完成数据查询或者其他业务操作。
>
> 在 Text2SQL 场景中，我们不会直接把用户原始问题交给大模型生成 SQL，而是先进行场景识别、实体和属性抽取、问题改写，再结合指标、维度以及实体关系等业务语义信息生成 SQL。
>
> 同时在整个链路中增加了权限校验、状态管理和异常处理机制，避免用户越权访问企业数据，并保证多轮对话和工具调用过程的稳定性。

# 三、实现权限校验、状态管理和异常处理机制，如何回答？

## 推荐面试回答

> 在 ChatBI 项目中，数据安全是比较重要的部分，因为用户最终是通过自然语言查询企业内部数据。
>
> 所以我们不能让用户的问题直接转换成 SQL 后访问数据库，而是在整个查询链路中增加权限控制。
>
> 第一是在请求进入系统时进行用户身份和角色校验；第二是在 Agent 或 Text2SQL 生成查询之前，根据用户的数据权限自动注入数据范围；第三是在 SQL 执行之前再次进行 SQL 安全校验，防止出现越权查询或者危险 SQL。
>
> 例如用户只拥有南京地区的数据权限，即使用户输入“查询全国流量数据”，最终生成的查询也会自动增加南京地区的数据过滤条件。
>
> 同时我们对多轮对话进行了状态管理，例如保存 conversationId、用户上下文、已识别参数和当前任务状态。
>
> 在异常处理方面，我们对大模型调用失败、工具调用失败、SQL 生成失败和数据库查询超时进行了统一异常处理，并返回可理解的错误信息，避免整个 Agent 链路直接中断。

# 五、如何实现数据权限隔离？

## 推荐回答

> 数据权限我们没有完全依赖前端传递查询条件，而是在后端根据当前用户身份自动生成数据过滤条件。
>
> 例如当前用户只拥有南京地区的数据权限，那么即使用户通过自然语言询问全国数据，我们在最终执行 SQL 之前，也会自动增加对应的数据范围条件。
>
> 这样可以避免用户通过修改参数绕过前端权限控制。

原始 SQL：

```sql
SELECT
    province,
    SUM(upload_traffic)
FROM traffic_hour
GROUP BY province;
```

江苏用户最终执行：

```sql
SELECT
    province,
    SUM(upload_traffic)
FROM traffic_hour
WHERE province = '江苏'
GROUP BY province;
```

南京用户：

```sql
WHERE province = '江苏'
  AND city = '南京'
```

# 六、为什么权限不能只依赖 Prompt？

> Prompt 可以作为辅助约束，但不能作为最终的数据安全机制。
>
> 因为 Prompt 本身不能保证百分之百可靠，大模型可能出现理解偏差或者受到 Prompt Injection 影响。
>
> 所以真正的数据权限必须在程序和数据库查询层进行强制控制。
>
> Prompt 负责辅助理解，后端负责真正的安全控制。

# 十、异常处理机制

## 推荐回答

> Agent 项目的异常处理和普通 Web 项目不太一样，因为一次请求可能涉及大模型调用、上下文管理、Tool 调用、SQL 生成以及数据库查询。
>
> 所以我们对不同阶段分别进行异常处理。

主要包括：

```text
LLM 调用异常
Tool 调用异常
参数解析异常
Text2SQL 异常
SQL 安全校验异常
数据库查询异常
超时异常
上下文异常
```

例如：

```text

```

处理方式：

```text
重试
+
超时控制
+

+

```

## 2. Tool 调用异常

例如：


# 十一、管理 ChatBI 多轮对话流程，如何回答？

## 推荐回答

> ChatBI 中多轮对话的核心是上下文管理和参数补全。
>
> 我们不会把所有历史对话无差别地发送给大模型，而是维护结构化的对话状态。
>
> 系统会保存上一轮已经识别出来的指标、时间、地区等参数。
>
> 当用户下一轮修改其中某一个条件时，我们只更新对应参数，再重新生成标准问题。
>
> 例如第一轮用户问“查询昨天南京的流量”，系统识别出时间是昨天、地区是南京、指标是流量。
>
> 第二轮用户说“改成苏州”，系统会结合上下文，把问题补全为“查询昨天苏州的流量”。
>
> 这样能够减少上下文 Token，同时提高多轮理解的准确性。

# 十四、基于 Prompt Engineering 设计场景识别、属性抽取和问题改写流程，如何回答？

## 推荐回答

> 在自然语言理解阶段，我们没有直接让模型一步完成所有任务，而是把整个过程拆成多个步骤。
>
> 首先进行场景识别，判断用户属于数据查询、趋势分析、指标排名还是其他业务场景。
>
> 然后进行属性抽取，识别用户问题中的时间、地区、指标、维度等关键信息。
>
> 最后结合上下文进行问题改写，把用户口语化的问题转换成标准问题。
>
> 通过这种分阶段 Prompt 的方式，可以减少单个 Prompt 的复杂度，提高模型输出的稳定性和准确性。

```text

   ↓

```

容易出现：

```text

```

因此采用：

```text
用户问题
   ↓

   ↓

   ↓
上下文补全
   ↓
问题改写
   ↓
标准问题
   ↓
Text2SQL
```

优势：

> 每个阶段职责更单一，更容易调试，也方便定位模型问题。

# 十八、结合业务语义模型优化 Text2SQL，如何回答？

## 推荐回答

> Text2SQL 最大的问题是大模型并不了解企业内部数据库的业务语义。
>
> 例如数据库里面可能只有字段名 traffic_value，但是模型并不知道它具体代表总流量、上行流量还是下行流量。
>
> 所以我们引入业务语义模型，把指标、维度、实体以及实体关系提供给模型。
>
> 模型生成 SQL 时，不只是依赖数据库表结构，而是结合业务语义进行理解。
>
> 例如“流量”对应哪些指标，“南京”对应哪个地区维度，以及指标和哪些事实表关联。
>
> 这样可以减少模型猜测字段的问题，提高 SQL 生成准确率。

# 二十一、参与 Agent 架构设计，实现 Dataset Tool、Plugin Tool 等工具调用能力，如何回答？

## 推荐回答

> 在 Agent 架构中，我们采用 Tool Calling 的方式，让大模型负责理解用户意图和选择工具，而具体的数据查询和业务操作由 Tool 来执行。
>
> 例如用户的问题属于数据查询场景，Agent 会选择 Dataset Tool。
>
> 如果用户需要调用其他业务能力，例如外部插件或者系统功能，则选择 Plugin Tool。
>
> 我们对 Tool 做了统一抽象，包括工具名称、描述、参数 Schema 和执行接口。
>
> 大模型根据 Tool 的 Description 和参数定义决定调用哪个工具，后端负责真正执行工具并把结果返回给 Agent。
>
> 这样可以把 LLM 的推理能力和传统系统的确定性执行能力结合起来。

# 二十三、Dataset Tool

> Agent 调用企业内部数据集进行查询的工具。

```text

      ↓

      ↓

```

```json

```

> 多轮对话方面，我们维护结构化的 Conversation State，保存当前问题、历史上下文以及已经识别出的时间、地区、指标等参数。用户下一轮修改某一个条件时，可以基于已有状态进行参数更新和问题补全。
>
> 在自然语言理解方面，我们把 Prompt 拆成场景识别、属性抽取和问题改写几个阶段，避免让模型一次完成过多任务，提高输出稳定性。
>
> Text2SQL 方面，我们结合企业业务语义模型，把指标、维度、实体关系等信息提供给模型，让模型不仅看到数据库 Schema，还能理解业务含义，从而提高 SQL 生成准确率。
>
> Agent 架构方面，我们采用 Tool Calling 的方式，让 LLM 负责理解用户意图和选择工具，具体的数据查询和业务执行交给 Dataset Tool、Plugin Tool 等工具完成。
>
> 整体上，我们通过权限控制、结构化上下文、分阶段 Prompt、业务语义增强和 Tool Calling，提升了 ChatBI 系统的数据安全性和自然语言查询准确率。

# 二十八、30 秒精简回答

> 我主要参与 ChatBI 的多轮对话和 Agent 能力建设。系统通过结构化 Conversation State 管理上下文和参数补全，通过场景识别、属性抽取和问题改写提高自然语言理解准确率。
>
> 在 Text2SQL 方面，我们引入指标、维度和实体关系等业务语义模型，减少 LLM 对字段和表的猜测。
>
> 同时 Agent 通过 Dataset Tool、Plugin Tool 等工具完成确定性的数据查询和业务调用。数据安全方面，权限控制最终落在后端和 SQL 执行层，而不是只依赖 Prompt，保证用户只能查询自己权限范围内的数据。

# ChatBI 输入理解规则总览

更新时间：2026-06-16

这份文档按当前代码行为总结规则，目的是方便你逐条对照业务要求。它覆盖主流程、场景识别、属性抽取、权限归一、分组推断、最终问题生成和 203 确认修改。

涉及核心文件：

- `main.py`：主状态机和编排入口
- `service/primary_scene_classification.py`：一级场景识别
- `service/scene_classification_service.py`：二级场景识别
- `service/third_scene_classification_service.py`：三级场景识别
- `service/attribute_extraction_service.py`：属性抽取、补参合并、缺失判断
- `service/permission_service.py`：权限校验和本端/对端视角归一
- `service/query_dimension_service.py`：分组维度推断
- `service/fill_template_pipeline_service.py`：最终标准问题生成
- `service/attribute_correction_service.py`：203 确认后的修改/纠正识别

## 1. 总体链路

一次请求大致按下面顺序执行：

1. 校验输入，如 IP 格式。
2. 做权限预校验。请求带了历史属性时，先用历史本端/对端判断是否越权。
3. 判断是否能力咨询或闲聊。
4. 判断当前输入是新任务还是延续上一轮。
5. 根据状态码进入不同流程。
6. 识别一级场景、二级场景、三级场景。
7. 抽取属性。
8. 按权限归一本端/对端视角。
9. 推断分组方式。
10. 检查必要属性是否缺失。
11. 生成最终标准问题。
12. 返回 203，让用户确认。

## 2. 状态码规则

| 状态码 | 含义 | 典型触发 |
| --- | --- | --- |
| 100 | 首轮新任务 | 前端首次请求 |
| 101 | 主动重置后的新任务 | 用户明确换个问题、重新开始 |
| 200 | 场景识别中间完整状态 | 二级场景识别完整 |
| 201 | 二级场景阶段缺本端/对端 | 场景能识别，但端点不完整 |
| 202 | 属性缺失补问 | 缺本端、对端或时间范围 |
| 203 | 最终问题生成，等待确认 | 已生成标准问题 |
| 204 | 用户修改上一轮问题 | 203 后用户说“对端错了”“时间改成...” |
| 205 | 三级场景不确定，等待用户确认 | 无法在候选三级场景中确定 |
| 400 | 非业务问题或输入错误 | 闲聊、IP 格式错误 |
| 403 | 权限不足 | 本端和对端都不在权限范围内 |
| 500 | 未知状态或异常 | 未处理状态码、异常 |

## 3. 新任务和续接判断

### 3.1 明确新任务

如果用户输入含有强新任务信号，会重置上下文，例如：

- `换个问题`
- `重新开始`
- `新问题`
- `再查一个`

例子：

- 上一轮已经 203，用户说：`换个问题，查询昨天南京到北京流量`
- 处理：清空上一轮属性，按新任务重新走 100/101 流程。

### 3.2 203 确认态

203 后分三类：

1. 用户确认：
   - `确认`
   - `对`
   - `好的`
   - `可以`
   - 处理：继续返回当前 203 内容，不改属性。

2. 用户发完整新问题：
   - 例：上一轮是南京到北京，用户直接说 `查询昨天上海到杭州流量`
   - 处理：判为新任务，避免和上一题混淆。

3. 用户修改上一题：
   - 例：`对端错了，应该是上海`
   - 例：`时间改成过去三个月`
   - 处理：进入 204 修改流程，用属性纠正服务修改已有属性，再重新生成最终问题。

### 3.3 202 补参态

如果上一轮缺属性，用户短输入更像参数补充，则续接：

- 缺时间，用户说：`昨天`
- 缺对端，用户说：`省外`
- 缺本端，用户说：`南京`

如果用户输入是一条完整新问题，则按新任务处理。

### 3.4 205 三级场景补充

如果上一轮 205，用户只回答候选三级场景，例如：

- `地市`
- `省际`
- `客户`
- `IP`
- `端口`

则作为三级场景补充，不判新任务。

## 4. 一级场景识别

一级场景主要是规则，不依赖大模型。

### 4.1 异常流量分析

最高优先级。命中以下关键词直接识别为 `异常流量分析`：

- `PCDN`
- `pcdn`
- `拉流`
- `被拉流`
- `CDNType`
- `访问域名`
- `域名数`
- `被拉流IP`

例子：

- `查询杭州被拉流TOPIP及对应的CDNType`
- 一级场景：`异常流量分析`

### 4.2 流量成分分析

命中以下关键词时识别为 `流量成分分析`：

- `占比`
- `成分`
- `结构`
- `组成`
- `终端用户`

例外：

- `结算详情`
- `结算数据`

这两个不归为流量成分分析，继续按流量流向分析处理。

例子：

- `top20客户-终端用户流出流量占比详情`
- 一级场景：`流量成分分析`

### 4.3 流量流向分析

默认场景。命中以下关键词也会识别为 `流量流向分析`：

- `查询`
- `统计`
- `流量`
- `流速`
- `流入`
- `流出`
- `流向`
- `ip`
- `客户`
- `地域`
- `地市`
- `省份`
- `IDC`
- `MAN`
- `城域网`
- `专线`
- `结算详情`
- `结算数据`
- `细分`
- `剔除`

例子：

- `查询昨天北京流入至南京的IDC流量`
- 一级场景：`流量流向分析`

## 5. 二级场景识别

二级场景先用规则识别本端/对端和关键词，再用规则分类；规则失败时才用大模型兜底抽取端点。

### 5.1 二级场景列表

一级 `流量流向分析` 下：

- `地域流量分析`
- `客户流量分析`
- `IP流量分析`

一级 `流量成分分析` 下：

- `流量成分分析`

一级 `异常流量分析` 下：

- `PCDN流量分析`
- `IP流量分析`
- `客户流量分析`

### 5.2 二级场景优先级

1. 异常流量：
   - 有 `PCDN` -> `PCDN流量分析`
   - 有 `拉流` 且有客户/账号 -> `客户流量分析`
   - 有 `拉流` 且没有客户/账号 -> `IP流量分析`

2. 客户类：
   - `客户`
   - `客户id`
   - `气象局`
   - `公安局`
   - `【客户名称】`
   - 如果同时出现 `端口`，优先改为 `IP流量分析`

3. 账号类：
   - `账号`
   - `家企宽账号`
   - `企宽账号`
   - `宽带账号`
   - `账号id`
   - 如果同时出现 `端口`，优先改为 `IP流量分析`

4. IP 类：
   - 具体 IP 地址
   - `IP`
   - `地址`
   - `网段`
   - `端口`
   - `路由器`

5. 地域类：
   - `地域`
   - `地市`
   - `省份`
   - `省际`
   - `结算详情`
   - `各个地市`
   - 默认兜底也是地域流量分析

例子：

- `模糊匹配公安局在过去三个月流量情况`
  - 二级：`客户流量分析`
- `查询172.56.3.33省外流出`
  - 二级：`IP流量分析`
- `查询省内各地市结算详情数据`
  - 二级：`地域流量分析`

## 6. 三级场景识别

三级场景先按当前一级/二级场景限制候选，再规则打分；低置信或不合法时用大模型兜底。

### 6.1 候选范围

`流量流向分析 / 地域流量分析`：

- `地市`
- `省际`

`流量流向分析 / 客户流量分析`：

- `客户`
- `账号`

`流量流向分析 / IP流量分析`：

- `IP`
- `端口`
- `网段`

`异常流量分析 / PCDN流量分析`：

- `账号`

`异常流量分析 / IP流量分析`：

- `IP`

`异常流量分析 / 客户流量分析`：

- `客户`

### 6.2 高优先级规则

1. `客户id` 优先三级 `客户`。
2. `端口`、`下行口`、`上行口`、`路由...详情` 优先三级 `端口`。
3. 多个 IP 地址优先三级 `IP`。
4. `账号` 相关优先三级 `账号`。
5. `AS` 或 `地市路由` 归为三级 `地市`。
6. `结算详情` 或 `结算数据` 归为三级 `地市`。
7. IP 二级场景下：
   - 有端口词 -> `端口`
   - 有网段词或 CIDR -> `网段`
   - 否则 -> `IP`
8. `省际`、`跨省`，或同时出现 `省外` 和 `省内`，倾向三级 `省际`。

### 6.3 置信度和补问

规则打分最高候选分数超过阈值 0.5，则选中三级场景。

如果未达到阈值，或选中的三级场景不在当前二级场景允许列表里，会尝试大模型重判。

仍然无法确定，则返回 205：

```text
无法精确判断三级场景。请确认您是否关注以下之一：地市, 省际？
```

## 8. 大模型参与点

当前代码中，大模型主要参与这些点：

1. 核心属性抽取：
   - 本端
   - 对端
   - 时间
   - 失败或结果不可信时回退规则。

2. 二级场景端点兜底：
   - 二级场景本端/对端规则失败时，会用 LLM 尝试补充端点。

3. 三级场景兜底：
   - 规则无法确定或候选不合法时，用 LLM 在有效候选中选择。

4. 流量组合抽取：
   - 多组合、细分、分别统计、对比类问题，优先用 LLM 抽结构化组合。
   - LLM 失败时用旧规则回退。

5. 分组维度推断：
   - 候选维度由规则生成。
   - 是否选择候选维度由 LLM 判断。
   - LLM 失败时规则回退。

6. 203 确认后的属性纠正：
   - 用户说“对端错了”“时间改成...”时，用纠正服务理解修改意图。

不再使用大模型判断的点：

- 结算类型当前已改为确定性规则。

## 9. 本端/对端抽取规则

### 9.1 核心 LLM 抽取规则

大模型只抽：

- 本端
- 对端
- 时间

并且必须遵守：

1. 不得猜测。
2. 端点不能包含业务类型。
3. 时间必须是用户原文连续子串。
4. `26年` 不能改成 `2026年`。
5. `近3个月` 不能改成 `最近3个月`。
6. `江苏各地市` 不能缩成 `各地市`。
7. `江苏南京` 不能缩成 `南京`。

例子：

- 原文：`查询26年江苏MAN到省外IDC的流入流出流量`
- 时间应该抽：`26年`
- 不应该抽：`2026年`

### 9.2 方向句式

以下句式按链路端点抽取：

- `A到B`
- `A流出到B`
- `A流入到B`
- `A流出至B`
- `A流入至B`
- `A流至B`
- `A流向B`

规则：

- 本端先抽 A。
- 对端先抽 B。
- 流入/流出不在这里交换端点。
- 端点视角交换在权限归一阶段做。

例子：

- `北京流入至南京`
  - 初始本端：北京
  - 初始对端：南京
  - 初始流向：流出，因为链路是北京 -> 南京
  - 江苏权限归一后：本端南京，对端北京，流向流入

### 9.3 来自/从...来

以下句式表示 B -> A：

- `A来自B`
- `A的流量来自B`
- `A从B来的流量`

规则：

- 初始本端：B
- 初始对端：A

例子：

- `江苏省各地市来自外省MAN的流入流量`
  - 初始本端：省外
  - 初始对端：江苏省各地市
  - 初始本端业务类型：MAN
  - 江苏权限归一后：
    - 本端：江苏省各地市
    - 对端：省外
    - 对端业务类型：MAN
    - 流向：流入

### 9.4 显式角色

用户明确说角色时优先：

- `本端是南京`
- `源端为IDC`
- `对端是省外`
- `目的端为MAN`
- `南京作为本端`

注意：

- `源端` 是输入别名，输出字段仍是 `本端`。
- `目的端/目标端/对端` 都统一理解为 `对端`。

### 9.5 各地市/各省

含有集合范围时保留完整范围：

- `江苏各地市`
- `江苏各个地市`
- `省内各地市`
- `全国各省`

例子：

- `查询江苏各地市IDC省内流出流入的月均流量`
  - 本端：江苏各地市
  - 本端业务类型：IDC
  - 对端：省内

当前有保护逻辑：

- 如果本端已经是 `江苏各个地市`，流量组合 LLM 返回 `江苏`，不会用粗粒度 `江苏` 覆盖细粒度 `江苏各个地市`。

### 9.6 单端查询

一些查询围绕单一对象取属性或详情，不要求对端：

- 结算详情
- 路由端口详情
- PCDN 域名
- AI 对应 IP
- 账号最新 IP+username

例子：

- `查询2026.1.1到2026.5.29剔除天翼云后省内各地市结算详情数据`
  - 本端：省内各地市
  - 对端：空
  - 返回字段：结算详情
  - 结算类型：默认省间结算、省内结算

## 10. 时间规则

### 10.1 时间必须来自原文

核心原则：

- 不补全。
- 不换算。
- 不把短年份改成长年份。

例子：

- `26年` -> `26年`
- `去年` -> `去年`
- `近3个月` -> `近3个月`
- `2026.1.1到5.29` -> 保留原文范围口径

### 10.2 支持的时间表达

支持：

- 单日：`昨天`、`今天`、`前天`
- 周/月/季度/年：`本周`、`上月`、`本季度`、`今年`
- 相对时间：`最近三个月`、`过去两个月`、`近一年`
- 年：`2026年`、`26年`
- 日期：`2026.1.1`
- 日期范围：`2026.1.1到2026.5.29`
- 月范围：`3月到5月`、`3-8月`
- 号范围：`3号到9号`、`3-9号`
- 季度：`第三季度`、`1-3季度`

### 10.3 时间粒度

时间粒度独立于指标定义：

- `按月`、`每月`、`月均` -> `月`
- `按天`、`每天`、`日均` -> `天`
- `逐时`、`按小时`、`每小时`、`小时均` -> `逐时`
- `按季度`、`季度统计` -> `季度`

例子：

- `月均流量`
  - 时间粒度：月
  - 指标定义：均值流速
  - 不再输出 `指标定义：月均流速`

## 11. 业务类型规则

### 11.1 业务类型词

识别：

- `IDC`
- `MAN`
- `城域网`，归一为 `MAN`
- `IDC+MAN`

### 11.2 没提业务类型时默认空

当前规则：

- 所有场景，只要用户没明确提业务类型，本端业务类型和对端业务类型都保持空。
- 不再因为地域场景默认 `IDC+MAN`。

例子：

- `查询昨天南京到北京流量`
  - 本端业务类型：空
  - 对端业务类型：空

### 11.3 显式本端/对端业务类型

优先识别：

- `本端业务类型是IDC`
- `本端为MAN`
- `源端类型IDC`
- `对端业务类型MAN`
- `目的端为IDC`

例子：

- `查询南京到北京流量，本端为IDC，对端为MAN`
  - 本端业务类型：IDC
  - 对端业务类型：MAN

### 11.4 紧邻端点绑定

业务类型紧邻哪个端点，就绑定哪个端点：

- `南京IDC到南通MAN`
  - 南京：IDC
  - 南通：MAN

- `IDC南京到MAN南通`
  - 南京：IDC
  - 南通：MAN

- `外省城域网流入到江苏各地市IDC`
  - 外省：MAN
  - 江苏各地市：IDC

### 11.5 “A到B的IDC流量”归源端

已有规则：

- `A到B的IDC流量`
- `A流入至B的IDC流量`
- `A流出到B的IDC流量`

这里 `的IDC流量` 归语义源端 A。

例子：

- `直询昨天北京流入至南京的IDC流量`
  - 初始本端：北京
  - 初始对端：南京
  - IDC 属于北京
  - 江苏权限归一后：
    - 本端：南京
    - 对端：北京
    - 本端业务类型：空
    - 对端业务类型：IDC
    - 流向：流入

### 11.6 客户/IP 不做默认业务类型

客户、账号、IP、网段对象：

- 只有明确说业务类型时才填。
- 不因为对象本身默认 IDC 或 MAN。

例子：

- `查询公安局过去三个月流量`
  - 本端客户：公安局
  - 本端业务类型：空

## 12. 流向规则

### 12.1 显式流向优先

如果用户说：

- `流向=流入`
- `流向是流出`

则按用户显式声明。

### 12.2 方向句式默认按链路源端

`A流入到B`、`A流入至B` 描述的是链路 A -> B。

初始端点以 A 为本端时：

- 初始流向：流出

权限归一后，如果本端换成 B：

- 流向变成：流入

### 12.3 双向流量

以下表达返回双向：

- `流入流出`
- `流出流入`
- `双向`
- `交互`
- `上下行`
- `PCDN`
- `结算`

结果：

```json
"流向": ["流入", "流出"]
```

### 12.4 默认流向

如果没有任何流向信息，默认 `流出`。

例外：

- 路由端口查询无流向时可以保持空。
- 单端查询可不强行补流向。

## 13. 数据类型和单位

### 13.1 数据类型

优先级：

1. `95峰值`、`95峰`、`95th`、`95%` -> `95峰值`
2. `峰值`、非 95 的 `峰` -> `峰值`
3. 默认 -> `均值流速`

### 13.2 月均/日均不是指标定义

`月均`、`日均`、`小时均`表达时间粒度，不改变指标定义。

例子：

- `月均流量`
  - 时间粒度：月
  - 指标定义：均值流速

### 13.3 流速单位

只提取明确写出的单位：

- `Gbps`
- `Mbps`
- `Kbps`
- `bps`

组合/细分场景的最终问题里，指标定义不附带单位，避免下游识别失败。

## 14. 剔除条件规则

### 14.1 支持关键词

- `剔除`
- `排除`
- `过滤`
- `去掉`
- `不要`
- `不含`
- `除了`

### 14.2 否定剔除不作为剔除条件

以下表达表示不要剔除，不应误写成剔除：

- `不剔除天翼云`
- `无需剔除天翼云`
- `不用过滤天翼云`
- `不排除天翼云`

### 14.3 常见对象归一

- 包含 `天翼云` 和 `CDN` -> `天翼云CDN`
- 包含 `天翼云` -> `天翼云`
- 包含 `天翼看家` -> `天翼看家`

### 14.4 最终问题展开

如果剔除条件没有指定本端/对端，最终问题会展开为：

```text
本端剔除天翼云；对端剔除天翼云
```

如果原文已经指定：

```text
本端剔除天翼云；对端不剔除天翼云
```

则按原文保留。

## 15. 流量组合/细分规则

### 15.1 触发条件

以下词可能触发组合抽取：

- `分别`
- `细分`
- `细化`
- `区分`
- `对比`

或者同一句里出现多个：

- `省外流出`
- `省内流出`
- `省外流入`
- `省内流入`

### 15.2 大模型组合抽取规则

组合抽取使用最终查询视角：

- 本端：被查询主体、公共端、权限侧。
- 对端：另一侧。
- 流向：从本端视角定义。
- `A、B、C分别流入D`：
  - D 是本端
  - A/B/C 是对端
  - 流向是流入
- `D分别流出到A、B、C`：
  - D 是本端
  - A/B/C 是对端
  - 流向是流出

业务类型规则：

- `外省IDC+MAN` -> 对端=省外，对端业务类型=IDC+MAN
- `江苏IDC` -> 本端=江苏，本端业务类型=IDC
- `城域网` -> MAN
- 保留完整范围，不把 `江苏各个地市` 缩成 `江苏`

### 15.3 组合结构

组合项字段：

```json
{
  "本端": "江苏",
  "本端业务类型": "IDC",
  "对端": "省外",
  "对端业务类型": "MAN",
  "流向": "流出"
}
```

### 15.4 典型例子

例子 1：

```text
近一年，按月统计江苏各个地市流出外省均值流速情况，细分江苏IDC流出外省IDC、江苏IDC流出外省MAN
```

组合：

```json
[
  {
    "本端": "江苏各个地市",
    "本端业务类型": "IDC",
    "对端": "省外",
    "对端业务类型": "IDC",
    "流向": "流出"
  },
  {
    "本端": "江苏各个地市",
    "本端业务类型": "IDC",
    "对端": "省外",
    "对端业务类型": "MAN",
    "流向": "流出"
  }
]
```

最终问题走细分自然语言模板：

```text
查询近一年，按月统计江苏各个地市流出外省的均值流速，细分江苏IDC流出外省IDC、江苏IDC流出外省MAN。
```

例子 2：

```text
分别统计2026.1.5到5.17外省IDC+MAN、省内MAN、省内IDC分别流入江苏IDC均值流速情况
```

组合含义：

- 江苏 IDC 是本端。
- 外省 IDC+MAN、省内 MAN、省内 IDC 是对端组合。
- 流向是流入。

最终问题应贴近原意：

```text
查询2026.1.5到5.17，统计江苏的均值流速，细分外省IDC+MAN流入江苏IDC、省内MAN流入江苏IDC、省内IDC流入江苏IDC。
```

### 15.5 不是所有组合都走自然语言模板

只有每项组合都明确包含：

- 本端业务类型
- 对端
- 对端业务类型
- 流向

才走业务类型细分自然语言模板。

否则走通用 DSL 模板，输出 `流量组合：分别统计...`。

## 16. 结算类型规则

结算类型是独立属性，只看问题中是否明确规定了结算类型，不看本端/对端、省内/省外流向范围。

### 16.1 省间结算

问题明确提到以下短语时，结算类型为 `省间结算`：

- `省间结算`
- `省际结算`
- `跨省结算`
- `省外结算`
- `外省结算`

例子：

- `查询2026年省间结算详情数据`
  - 结算类型：省间结算

- `查询跨省结算详情`
  - 结算类型：省间结算

### 16.2 省内结算

问题明确提到以下短语时，结算类型为 `省内结算`：

- `省内结算`
- `本省结算`

例子：

- `查询2026年省内结算详情数据`
  - 结算类型：省内结算

### 16.3 两个都提到

如果省间类和省内类都明确提到：

```text
省间结算、省内结算
```

例子：

- `查询省间结算和省内结算详情数据`
  - 结算类型：省间结算、省内结算

### 16.4 都没提

只要是结算问题，但没有明确说省间结算或省内结算，默认两个都有：

```text
省间结算、省内结算
```

例子：

- `查询2026.1.1到2026.5.29剔除天翼云后省内各地市结算详情数据`
  - `省内各地市` 是地域范围，不是结算类型。
  - 结算类型：省间结算、省内结算

- `查询外省IDC流入江苏IDC结算详情数据`
  - `外省IDC流入江苏IDC` 是流量/端点范围，不是 `外省结算` 短语。
  - 结算类型：省间结算、省内结算

## 17. 权限规则

### 17.1 权限校验

如果权限是全量：

```json
{"province": "ALL", "city": "ALL"}
```

则放行。

如果权限是具体省/市：

- 本端和对端都完整时才校验。
- 两端至少一端要属于权限范围。
- 客户、账号、IP、网段等非地域对象默认视为权限内对象，具体归属交给 SQL 侧筛选。
- `省外/外省/省际/跨省` 是泛化外部范围，不能单独证明命中权限。

例子：

- 江苏权限，查询 `浙江到安徽`
  - 两端都不在江苏
  - 返回 403

- 江苏权限，查询 `北京流入至南京`
  - 南京在江苏
  - 放行

### 17.2 本端/对端视角归一

权限归一的目标：

- 最终本端尽量是用户权限侧。
- 流向从最终本端视角表达。
- 业务类型跟随端点交换。

规则：

1. 如果没有具体权限，不归一。
2. 如果本端或对端为空，不归一。
3. 如果命中跳过规则，不归一。
4. 如果对端命中权限、本端不命中权限：
   - 交换本端和对端
   - 交换本端业务类型和对端业务类型
   - 若原问题有方向句式且没有显式声明 `流向=...`，流向改为 `流入`
5. 如果本端命中权限、对端不命中权限：
   - 不交换端点
   - 若原问题有方向句式且没有显式声明，流向保持/归为 `流出`
6. 如果两端都命中权限：
   - 不强行按权限交换
   - 如果有流向且未显式声明，倾向语义源端作为本端，流向为 `流出`

例子：

- 江苏权限，`北京流入至南京的IDC流量`
  - 抽取阶段：本端北京、对端南京、本端业务类型IDC、流向流出
  - 权限归一：本端南京、对端北京、对端业务类型IDC、流向流入

### 17.3 跳过权限视角归一的情况

以下情况不做本端/对端交换：

- `PCDN`
- `ip+username`
- `拉流`
- `被拉流`
- `对端限制`
- `分别`
- `端口详情`
- `路由器`
- `所属地市`
- `所属IDC客户`
- `所属客户`
- 流向同时包含流入和流出

原因：

- 这些场景端点语义特殊，机械交换容易破坏下游识别。

## 18. 分组规则

分组分两步：

1. 规则生成候选维度。
2. 大模型从候选中选择需要分组的维度。

### 18.1 候选维度生成

端点标签会根据对象类型生成：

- `本端地市`
- `对端省份`
- `本端IP`
- `对端客户`
- `本端账号`
- `对端网段`
- `本端路由`

如果本端/对端是多值或集合，则生成候选：

- `江苏各地市` -> `本端地市`
- `多个IP` -> `本端IP`
- `客户A、客户B` -> `本端客户`

### 18.2 省内/省外不是分组

以下只作为范围过滤，不自动作为分组：

- `省外`
- `外省`
- `省内`
- `本省`
- `省际`
- `跨省`

例子：

- `江苏MAN最近一年省外流出，省内流出，省外流入，省内流入`
  - 用户是要四个范围桶，不是要按对端省份分组。
  - 不应输出：`分组方式：按对端省份分组`

### 18.3 流向不作为分组

流向永远只作为过滤条件，不作为分组维度。

原因：

- 底层表已经有流入均值流速、流出均值流速等指标列。

例子：

- `省外流入、省外流出`
  - 不输出 `按流向分组`

### 18.4 时间粒度不作为业务分组

`月均/日均/小时均` 输出为 `时间粒度`，不输出到 `分组方式`。

例子：

- `按月统计南京到北京流量`
  - 时间粒度：月
  - 分组方式：不因为按月自动写 `按月分组`

### 18.5 组合分组

流量组合里如果有多个本端业务类型：

- 候选 `本端业务类型`

如果同一个对端下存在多个对端业务类型：

- 候选 `对端业务类型`

如果多个不同对端不是纯省内/省外范围桶：

- 候选对端维度，如 `对端地市`、`对端省份`、`对端对象`

### 18.6 强制分组

即使大模型没选，以下也会作为强制维度加入：

- 多本端对象
- 多对端对象，且不是纯省内/省外范围桶
- 组合推导出的必要业务类型维度

但如果用户明确说：

- `整体汇总`
- `汇总值`
- `合计`
- `总计`
- `不分组`
- `不拆分`

则不强制端点分组。

## 19. 最终问题生成规则

最终输出分三类模板：

1. 结算专用模板
2. 业务类型细分自然语言模板
3. 通用 DSL 模板

### 19.1 结算专用模板

触发：

- `返回字段` 包含结算
- 或 `结算类型` 非空

模板：

```text
查询{时间}{剔除条件后}{本端或对端范围}结算详情数据，结算类型：{结算类型}
```

例子：

```text
查询2026.1.1到2026.5.29剔除天翼云后省内各地市结算详情数据，结算类型：省间结算、省内结算
```

### 19.2 业务类型细分自然语言模板

触发：

- 流量组合不少于 2 项
- 每项都有本端业务类型、对端、对端业务类型、流向

模板倾向贴近原问题，而不是通用 DSL。

例子：

```text
查询近一年，按月统计江苏各个地市流出外省的均值流速，细分江苏IDC流出外省IDC、江苏IDC流出外省MAN、江苏MAN流出外省IDC。
```

### 19.3 通用 DSL 模板

字段顺序：

1. 统计周期
2. 时间粒度
3. 分组方式
4. 本端对象
5. 对端对象
6. 本端业务类型
7. 对端业务类型
8. 流量组合
9. 指标定义
10. 返回字段
11. 排序方式
12. 返回数量
13. 过滤条件

例子：

```text
统计周期：昨天；本端地市：南京；对端省份：北京；对端业务类型：IDC；指标定义：均值流速；过滤条件：流向=流入
```

### 19.4 端点字段命名

最终问题不用笼统写 `本端` / `对端`，会按对象类型命名：

- 南京 -> `本端地市`
- 江苏 -> `本端省份`
- 172.1.1.1 -> `本端IP`
- 公安局 -> `本端客户`
- 账号 -> `本端账号`
- 网段 -> `本端网段`

对端同理。

### 19.5 过滤条件

过滤条件包含：

- 流向
- 跨省过滤
- 剔除条件
- 模糊匹配
- 路由端口条件

跨省过滤：

- 如果对端是 `省外/外省/省际/跨省`
- 或组合里的对端全部是这些
- 自动加：`仅保留跨省流量`

### 19.6 指标定义

通用规则：

- 指标定义默认 `均值流速`
- 有单位时普通场景输出 `均值流速（Gbps）`
- 组合场景不带单位
- 排名场景可能输出：`TOPIP及其均值流速`
- 路由端口场景可能输出：`路由器IP、路由器端口、均值流速`

## 20. 203 后修改规则

203 返回后，用户可能：

1. 确认：
   - 返回原问题，不修改。

2. 修改字段：
   - `本端错了，应该是南京`
   - `对端改成省外`
   - `本端业务类型是IDC`
   - `时间改成过去两个月`
   - 处理：进入 204，修改对应属性，再重新生成 203。

3. 说不清：
   - 系统会提示：请确认当前属性和最终问题是否正确；如需修改，请说明具体字段和正确值。

4. 直接问下一题：
   - 判为新任务，清空旧属性。

## 21. 典型 Case 对照

### 21.1 北京流入南京 IDC

原问题：

```text
直询昨天北京流入至南京的IDC流量
```

抽取和归一：

```json
{
  "本端": "南京",
  "对端": "北京",
  "本端业务类型": "",
  "对端业务类型": "IDC",
  "时间": "昨天",
  "流向": "流入"
}
```

理由：

- `北京流入至南京` 的语义源端是北京。
- `的IDC流量` 按已有规则归源端北京。
- 江苏权限下南京是本端，北京变对端，所以 IDC 最终是对端业务类型。

### 21.2 省内各地市结算详情

原问题：

```text
查询2026.1.1到2026.5.29剔除天翼云后省内各地市结算详情数据
```

属性：

```json
{
  "本端": "省内各地市",
  "对端": "",
  "时间": "2026.1.1到2026.5.29",
  "剔除条件": "剔除天翼云",
  "返回字段": "结算详情",
  "结算类型": "省间结算、省内结算"
}
```

理由：

- `省内各地市` 是地域范围。
- 问题没有明确说 `省内结算`。
- 未明确结算类型，所以默认省间结算、省内结算。

### 21.3 外省 MAN 流入江苏各地市 IDC

原问题：

```text
查询过去两个月，外省城域网流入到江苏各地市IDC且剔除天翼云的月均流量
```

属性：

```json
{
  "本端": "江苏各地市",
  "对端": "省外",
  "本端业务类型": "IDC",
  "对端业务类型": "MAN",
  "时间": "过去两个月",
  "时间粒度": "月",
  "数据类型": "均值流速",
  "流向": "流入",
  "剔除条件": "剔除天翼云"
}
```

分组：

- 本端是 `江苏各地市`，需要按本端地市分组。
- `省外` 是范围过滤，不应机械按对端省份分组，除非用户明确要按外省省份拆。

### 21.4 省外/省内四桶

原问题：

```text
江苏MAN最近一年省外流出，省内流出，省外流入，省内流入
```

属性重点：

```json
{
  "本端": "江苏",
  "本端业务类型": "MAN",
  "对端": "省外、省内",
  "流向": ["流入", "流出"],
  "流量组合": [
    {"对端": "省外", "本端业务类型": "MAN", "流向": "流出"},
    {"对端": "省内", "本端业务类型": "MAN", "流向": "流出"},
    {"对端": "省外", "本端业务类型": "MAN", "流向": "流入"},
    {"对端": "省内", "本端业务类型": "MAN", "流向": "流入"}
  ]
}
```

分组：

- 不按流向分组。
- 不因为 `省外、省内` 自动按对端省份分组。

## 22. 排查建议

当一个 case 出错，按这个顺序查：

1. 状态码是否正确：
   - 是新任务还是续接？
   - 203 后是否误判成修改或新任务？

2. 一级/二级/三级场景是否正确：
   - 是否因为关键词优先级进入了错误场景？
   - 三级场景是否被 205 补问？

3. 属性抽取是否正确：
   - 本端/对端是否保留完整范围？
   - 时间是否原文保留？
   - 业务类型是否绑定到正确端点？
   - 流量组合是否结构化正确？

4. 权限归一是否正确：
   - 是否发生了本端/对端交换？
   - 业务类型是否跟着交换？
   - 流向是否从最终本端视角表达？

5. 分组是否合理：
   - 是否把流向误当分组？
   - 是否把省内/省外范围误当对端省份分组？
   - 是否漏了各地市/多 IP 等必要分组？

6. 最终问题模板是否合适：
   - 结算是否走结算模板？
   - 业务类型细分是否走自然语言模板？
   - 普通场景是否走 DSL 模板？

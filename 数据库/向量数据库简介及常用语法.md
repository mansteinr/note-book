## 一、向量数据库概述

### 1.1 什么是向量数据库

向量数据库（Vector Database）是专门用于存储、管理和查询高维向量数据的数据库系统。它将非结构化数据（如文本、图像、音频等）通过嵌入模型转换为高维向量，并提供高效的相似性搜索能力。

### 1.2 核心概念

- **向量（Vector）**：由嵌入模型生成的高维浮点数数组，表示数据的语义特征
- **嵌入（Embedding）**：将非结构化数据转换为向量的过程
- **相似性搜索（Similarity Search）**：基于距离度量（如余弦相似度、欧氏距离）查找最相似的向量
- **索引（Index）**：加速向量搜索的数据结构，如 HNSW、IVF 等

### 1.3 常见应用场景

| 应用场景 | 说明 |
|---------|------|
| RAG（检索增强生成） | 结合大语言模型，提供外部知识检索 |
| 语义搜索 | 基于语义相似度而非关键词匹配进行搜索 |
| 推荐系统 | 基于用户/物品向量相似度进行推荐 |
| 图像检索 | 以图搜图、相似图片查找 |
| 去重检测 | 文本/图像/音频的相似性检测与去重 |
| 异常检测 | 识别与正常模式偏离的异常数据 |

## 二、Milvus 向量数据库

### 2.1 简介

**Milvus** 是一款开源的、专为海量特征向量设计的高性能向量数据库，由 Zilliz 公司开发并捐赠给 Linux AI 基金会（LF AI & Data）。

**核心特点：**
- 开源免费，社区活跃
- 支持多种向量索引类型（HNSW、IVF、DiskANN 等）
- 支持分布式部署，水平扩展能力强
- 提供丰富的 SDK（Python、Java、Go、Node.js 等）
- 支持混合查询（向量搜索 + 标量过滤）
- 支持多租户和权限管理

**架构组件：**
- **Access Layer**：对外提供 RESTful API 和 SDK 接口
- **Coordinator Service**：集群管理、元数据管理、任务调度
- **Worker Nodes**：执行具体的计算任务（数据节点、查询节点、索引节点）
- **Storage**：底层存储（支持 MinIO、S3、HDFS 等）

### 2.4 Milvus 支持的索引类型

| 索引类型 | 适用场景 | 特点 |
|---------|---------|------|
| **HNSW** | 中小规模数据，高召回率要求 | 基于图的索引，查询速度快，召回率高，内存占用大 |
| **IVF_FLAT** | 大规模数据，内存受限 | 倒排索引 + 暴力搜索，内存占用较小 |
| **IVF_PQ** | 超大规模数据，内存受限 | 倒排索引 + 乘积量化，压缩向量，内存占用小 |
| **DiskANN** | 超大规模数据，磁盘存储 | 基于磁盘的图索引，内存占用极小 |
| **FLAT** | 小规模数据，100% 召回率 | 暴力搜索，精确但速度慢 |

### 2.5 距离度量方式

| 度量方式 | 说明 | 适用场景 |
|---------|------|---------|
| **COSINE** | 余弦相似度 | 文本语义相似度，归一化向量 |
| **L2** | 欧氏距离 | 图像特征相似度 |
| **IP** | 内积 | 已归一化的向量，等价于余弦相似度 |

#### 2.6.2 多模态检索系统

**场景描述：** 构建以图搜图、以文搜图的多模态检索系统，使用 CLIP 模型统一图像和文本的向量空间。

```python
import clip
import torch
from PIL import Image

# 加载 CLIP 模型
model, preprocess = clip.load("ViT-B/32")

def get_image_embedding(image_path):
    """获取图像向量"""
    image = preprocess(Image.open(image_path)).unsqueeze(0)
    with torch.no_grad():
        return model.encode_image(image).numpy().flatten()

def get_text_embedding(text):
    """获取文本向量"""
    tokens = clip.tokenize([text])
    with torch.no_grad():
        return model.encode_text(tokens).numpy().flatten()

# 以文搜图：用户输入 "一只橘猫在沙发上睡觉"
text_emb = get_text_embedding("一只橘猫在沙发上睡觉")
results = image_collection.search(
    data=[text_emb],
    anns_field="image_embedding",
    param=search_params,
    limit=10,
    output_fields=["image_path", "tags"]
)
```

#### 2.6.3 实时推荐系统

**场景描述：** 基于用户实时行为（浏览、点击、购买）动态更新用户向量，实现毫秒级实时推荐。

```python
import numpy as np

def update_user_vector(user_id, new_behavior_embedding):
    """根据用户新行为更新用户向量"""
    # 获取当前用户向量
    results = collection.query(
        expr=f"user_id == {user_id}",
        output_fields=["user_embedding", "behavior_count"]
    )
    if results:
        current_emb = np.array(results[0]["user_embedding"])
        count = results[0]["behavior_count"]
        # 加权平均更新
        updated_emb = (current_emb * count + new_behavior_embedding) / (count + 1)
        # 删除旧向量，插入新向量
        collection.delete(expr=f"user_id == {user_id}")
        collection.insert([[user_id], [updated_emb.tolist()], [count + 1]])
```

#### 2.6.4 知识库问答系统（RAG）

**场景描述：** 企业级知识库问答，将文档分块后存入 Milvus，结合 LLM 实现精准问答。

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

def build_knowledge_base(documents):
    """构建知识库"""
    splitter = RecursiveCharacterTextSplitter(chunk_size=500, chunk_overlap=50)

    for doc in documents:
        chunks = splitter.split_text(doc["content"])
        embeddings = [get_embedding(chunk) for chunk in chunks]  # 调用 Embedding API

        data = [
            chunks,                                    # chunk_text
            embeddings,                                # chunk_embedding
            [doc["source"]] * len(chunks),             # source
            list(range(len(chunks)))                   # chunk_index
        ]
        collection.insert(data)

def retrieve_context(question, top_k=5):
    """检索相关上下文"""
    q_emb = get_embedding(question)
    results = collection.search(
        data=[q_emb],
        anns_field="chunk_embedding",
        param={"metric_type": "COSINE", "params": {"ef": 128}},
        limit=top_k,
        output_fields=["chunk_text", "source"]
    )
    return [hit.entity.get("chunk_text") for hit in results[0]]
```

## 三、Pinecone 向量数据库

**Pinecone** 是一款全托管的云原生向量数据库，无需管理基础设施，开箱即用。

**核心特点：**

### 3.6 Pinecone 使用场景

#### 3.6.1 快速构建 RAG 原型

**场景描述：** 创业团队需要快速验证 LLM 应用想法，不想投入精力维护向量数据库基础设施。

```python
from pinecone import Pinecone, ServerlessSpec
from openai import OpenAI

pc = Pinecone(api_key="your-api-key")
openai_client = OpenAI(api_key="your-openai-key")

# 创建索引（30秒内可用）
pc.create_index(
    name="rag-quickstart",
    dimension=1536,
    metric="cosine",
    spec=ServerlessSpec(cloud="aws", region="us-east-1")
)
index = pc.Index("rag-quickstart")

def embed_and_store(documents):
    """批量存储文档向量"""
    embeddings = [
        openai_client.embeddings.create(
            input=doc["content"],
            model="text-embedding-3-small"
        ).data[0]["embedding"]
        for doc in documents
    ]

    vectors = [
        {
            "id": f"doc_{i}",
            "values": emb,
            "metadata": {"text": doc["content"], "source": doc["source"]}
        }
        for i, (doc, emb) in enumerate(zip(documents, embeddings))
    ]
    index.upsert(vectors=vectors, batch_size=100)

def rag_query(question):
    """RAG 问答"""
    # 1. 生成问题向量
    q_emb = openai_client.embeddings.create(
        input=question, model="text-embedding-3-small"
    ).data[0]["embedding"]

    # 2. 检索相关文档
    results = index.query(vector=q_emb, top_k=5, include_metadata=True)
    context = "\n".join([m.metadata["text"] for m in results.matches])

    # 3. 调用 LLM 生成回答
    response = openai_client.chat.completions.create(
        model="gpt-4",
        messages=[
            {"role": "system", "content": f"基于以下上下文回答问题：\n{context}"},
            {"role": "user", "content": question}
        ]
    )
    return response.choices[0].message.content
```

#### 3.6.2 多租户 SaaS 应用

**场景描述：** SaaS 平台需要为每个客户隔离数据，Pinecone 的 Namespace 机制天然支持多租户。

```python
class TenantVectorStore:
    """多租户向量存储服务"""

    def __init__(self, index):
        self.index = index

    def add_documents(self, tenant_id, documents):
        """为特定租户添加文档"""
        vectors = [
            {
                "id": f"{tenant_id}_doc_{i}",
                "values": doc["embedding"],
                "metadata": {
                    "text": doc["text"],
                    "tenant_id": tenant_id,
                    "created_at": doc.get("created_at", "")
                }
            }
            for i, doc in enumerate(documents)
        ]
        # 使用 namespace 隔离租户数据
        self.index.upsert(vectors=vectors, namespace=tenant_id)

    def search(self, tenant_id, query_embedding, top_k=10):
        """在租户命名空间内搜索"""
        return self.index.query(
            vector=query_embedding,
            top_k=top_k,
            include_metadata=True,
            namespace=tenant_id  # 数据隔离
        )

    def delete_tenant_data(self, tenant_id):
        """删除租户所有数据"""
        self.index.delete(delete_all=True, namespace=tenant_id)
```

#### 3.6.4 实时内容推荐

**场景描述：** 新闻/内容平台基于用户阅读行为实时推荐相似内容。

```python
def recommend_similar_articles(article_id, article_embedding):
    """推荐相似文章"""
    # 先存储当前文章
    index.upsert(vectors=[{
        "id": article_id,
        "values": article_embedding,
        "metadata": {"status": "published"}
    }])

    # 搜索相似文章
    results = index.query(
        vector=article_embedding,
        top_k=10,
        filter={
            "id": {"$ne": article_id},  # 排除自身
            "status": {"$eq": "published"}
        },
        include_metadata=True
    )
    return [{"id": m.id, "score": m.score} for m in results.matches]

def update_user_preferences(user_id, read_article_ids):
    """更新用户偏好向量"""
    # 获取用户已读文章向量
    fetched = index.fetch(ids=read_article_ids)
    if fetched["vectors"]:
        import numpy as np
        vectors = [v["values"] for v in fetched["vectors"].values()]
        user_pref = np.mean(vectors, axis=0).tolist()

        # 更新用户偏好向量
        index.upsert(vectors=[{
            "id": f"user_{user_id}",
            "values": user_pref,
            "metadata": {"type": "user_preference"}
        }])
```

## 四、ChromaDB 向量数据库

### 4.1 简介

**ChromaDB** 是一款开源的、轻量级的嵌入式向量数据库，专为 AI 应用开发设计。它是 LangChain 和 LlamaIndex 等主流 AI 框架的默认向量存储，以"开发者体验优先"为核心理念。

**核心特点：**
- 开源免费（Apache 2.0 协议）
- 嵌入式部署，零配置启动（`pip install` 即可使用）
- 内置 Embedding 函数，自动调用 Embedding 模型
- 原生支持 Python 和 JavaScript SDK
- 支持持久化存储（基于 SQLite + 向量索引）
- 与 LangChain、LlamaIndex 等框架深度集成
- 支持元数据过滤和文档存储

**架构设计：**

```
┌─────────────────────────────────────────┐
│            ChromaDB 架构                 │
├─────────────────────────────────────────┤
│  Client API (Python / JavaScript)       │
├─────────────────────────────────────────┤
│  Collection Manager (集合管理)           │
├─────────────────────────────────────────┤
│  Embedding Function (内置 Embedding)     │
├─────────────────────────────────────────┤
│  Vector Index (HNSW 索引)               │
├─────────────────────────────────────────┤
│  Storage Layer (SQLite + 文件存储)       │
└─────────────────────────────────────────┘
```

**运行模式：**

| 模式 | 说明 | 适用场景 |
|-----|------|---------|
| **In-Process（嵌入式）** | 在应用进程内运行，数据持久化到本地文件 | 开发调试、单机应用、原型开发 |
| **Client/Server** | 独立部署服务，通过 HTTP API 访问 | 多应用共享、团队协作、生产环境 |

**优势：**
- 极简 API，5 行代码即可开始使用
- 内置 Embedding，无需额外调用外部 API
- 与 AI 生态集成度最高（LangChain 默认存储）
- 支持直接存储文档（Document），自动处理 Embedding
- 轻量级，资源占用少

**局限性：**
- 不支持分布式部署，不适合超大规模数据（百万级以下最佳）
- 索引类型仅支持 HNSW，不可配置
- 缺乏企业级功能（权限管理、审计日志等）
- 性能在大数据量下不如 Milvus
- 不支持 GPU 加速索引

### 4.3 常用语法（Python SDK）

#### 4.3.1 集合管理

```python
import chromadb

client = chromadb.PersistentClient(path="./chroma_db")

# 创建集合（指定距离度量）
collection = client.create_collection(
    name="my_documents",
    metadata={"hnsw:space": "cosine"}  # 支持 cosine、l2、ip
)

# 获取已有集合
collection = client.get_collection(name="my_documents")

# 获取或创建集合
collection = client.get_or_create_collection(
    name="my_documents",
    metadata={"hnsw:space": "cosine"}
)

# 列出所有集合
all_collections = client.list_collections()
print(f"共有 {len(all_collections)} 个集合")

# 删除集合
client.delete_collection(name="my_documents")

# 查看集合信息
print(f"集合名称: {collection.name}")
print(f"文档数量: {collection.count()}")
```

#### 4.3.2 数据插入

```python
# 方式一：直接插入文本（ChromaDB 自动调用 Embedding）
collection.add(
    documents=["这是第一条文本", "这是第二条文本", "这是第三条文本"],
    metadatas=[
        {"source": "doc1", "page": 1},
        {"source": "doc2", "page": 2},
        {"source": "doc3", "page": 3}
    ],
    ids=["id1", "id2", "id3"]
)

# 方式二：插入预计算的向量
collection.add(
    ids=["id4", "id5"],
    embeddings=[[0.1, 0.2, ...], [0.3, 0.4, ...]],  # 预计算向量
    documents=["预计算向量文本1", "预计算向量文本2"],
    metadatas=[{"source": "doc4"}, {"source": "doc5"}]
)

# 方式三：使用 Document 对象
from chromadb import Documents

collection.add(
    documents=Documents(
        ids=["id6"],
        documents=["Document 对象文本"],
        metadatas=[{"source": "doc6"}]
    )
)
```

#### 4.3.3 向量查询

```python
# 基于文本查询（自动 Embedding）
results = collection.query(
    query_texts=["搜索关键词或问题"],
    n_results=5,                    # 返回 Top-K
    where={"source": "doc1"},       # 元数据过滤
    where_document={"$contains": "关键词"}  # 文档内容过滤
)

# 查看结果
for i, (doc, distance, metadata) in enumerate(
    zip(results["documents"][0], results["distances"][0], results["metadatas"][0])
):
    print(f"#{i+1} 距离: {distance:.4f} | 来源: {metadata['source']}")
    print(f"   内容: {doc[:100]}...")

# 基于预计算向量查询
results = collection.query(
    query_embeddings=[[0.1, 0.2, ...]],
    n_results=10
)

# 多查询同时搜索
results = collection.query(
    query_texts=["问题1", "问题2"],
    n_results=3
)
# results["documents"] 是二维列表：[查询1的结果, 查询2的结果]
```

#### 4.4.2 本地知识库问答

**场景描述：** 个人或小团队构建本地知识库，无需部署远程服务。

```python
import chromadb
from pathlib import Path

def build_local_knowledge_base(docs_dir: str):
    """从本地文件构建知识库"""
    client = chromadb.PersistentClient(path="./local_kb")
    collection = client.get_or_create_collection("local_docs")

    for file_path in Path(docs_dir).glob("*.txt"):
        content = file_path.read_text(encoding="utf-8")
        # 简单分块
        chunks = [content[i:i+500] for i in range(0, len(content), 450)]

        collection.add(
            documents=chunks,
            metadatas=[{"source": file_path.name, "chunk_idx": i} for i in range(len(chunks))],
            ids=[f"{file_path.stem}_chunk_{i}" for i in range(len(chunks))]
        )

    print(f"已索引 {collection.count()} 个文档块")
    return collection

def ask_question(collection, question: str):
    """本地知识库问答"""
    results = collection.query(query_texts=[question], n_results=3)
    context = "\n".join(results["documents"][0])
    return f"基于以下信息回答问题：\n{context}\n\n问题：{question}"
```

#### 4.4.4 对话历史记忆

**场景描述：** 为 AI 聊天机器人添加长期记忆，基于语义相似度检索历史对话。

```python
import chromadb
from datetime import datetime

class ChatMemory:
    """对话记忆管理"""

    def __init__(self, user_id: str):
        self.client = chromadb.PersistentClient(path="./chat_memory")
        self.collection = self.client.get_or_create_collection(
            f"memory_{user_id}"
        )

    def add_message(self, role: str, content: str):
        """保存对话消息"""
        msg_id = f"{datetime.now().timestamp()}_{role}"
        self.collection.add(
            documents=[content],
            metadatas=[{
                "role": role,
                "timestamp": datetime.now().isoformat()
            }],
            ids=[msg_id]
        )

    def recall(self, query: str, n_results: int = 5) -> list:
        """根据当前话题回忆相关历史"""
        results = self.collection.query(
            query_texts=[query],
            n_results=n_results
        )
        return [
            {"content": doc, "metadata": meta}
            for doc, meta in zip(results["documents"][0], results["metadatas"][0])
        ]

# 使用示例
memory = ChatMemory(user_id="user_123")
memory.add_message("user", "我喜欢 Python 编程")
memory.add_message("assistant", "Python 是一门很好的编程语言")
memory.add_message("user", "今天天气不错")

# 回忆与编程相关的历史
relevant = memory.recall("编程相关的话题")
```

### 4.5 ChromaDB 常见面试题

**Q1：ChromaDB 的架构是怎样的？它是如何存储向量的？**

**答：**
ChromaDB 采用轻量级嵌入式架构：
- **存储层**：使用 SQLite 存储元数据和文档内容，使用 HNSW 索引文件存储向量
- **索引层**：默认使用 HNSW（Hierarchical Navigable Small World）算法
- **API 层**：提供 Python 和 JavaScript SDK，支持嵌入式和 Client/Server 两种模式
- **Embedding 层**：内置 Embedding 函数，可自动调用各种 Embedding 模型

数据持久化时，向量索引和元数据分别存储在不同文件中，通过 ID 关联。

**Q2：ChromaDB 与 Milvus 的主要区别是什么？**

**答：**

| 对比维度 | ChromaDB | Milvus |
|---------|----------|--------|
| 定位 | 轻量级嵌入式向量数据库 | 企业级分布式向量数据库 |
| 部署方式 | `pip install` 即可使用 | 需要 Docker 部署 |
| 数据规模 | 适合百万级以下 | 支持十亿级以上 |
| 索引类型 | 仅 HNSW | HNSW、IVF、DiskANN 等 |
| 分布式 | 不支持 | 原生支持 |
| 内置 Embedding | 支持 | 不支持（需外部计算） |
| 生态集成 | LangChain 默认存储 | 独立生态 |
| 适用场景 | 原型开发、本地应用 | 大规模生产环境 |

**Q3：ChromaDB 支持哪些距离度量方式？如何选择？**

**答：**
ChromaDB 支持三种距离度量：
- **cosine**（余弦距离）：默认值，适合文本语义相似度
- **l2**（欧氏距离）：适合图像特征等绝对距离场景
- **ip**（内积）：适合已归一化的向量

创建集合时通过 metadata 指定：
```python
collection = client.create_collection(
    name="my_collection",
    metadata={"hnsw:space": "cosine"}  # 或 "l2"、"ip"
)
```

**Q4：ChromaDB 的元数据过滤支持哪些操作符？**

**答：**
ChromaDB 支持丰富的元数据过滤操作符：

| 操作符 | 说明 | 示例 |
|-------|------|------|
| `$eq` | 等于 | `{"source": {"$eq": "doc1"}}` |
| `$ne` | 不等于 | `{"status": {"$ne": "deleted"}}` |
| `$gt` | 大于 | `{"score": {"$gt": 0.8}}` |
| `$gte` | 大于等于 | `{"count": {"$gte": 10}}` |
| `$lt` | 小于 | `{"price": {"$lt": 100}}` |
| `$lte` | 小于等于 | `{"age": {"$lte": 30}}` |
| `$in` | 在列表中 | `{"tag": {"$in": ["a", "b"]}}` |
| `$nin` | 不在列表中 | `{"type": {"$nin": ["spam"]}}` |
| `$and` | 逻辑与 | `{"$and": [{"a": 1}, {"b": 2}]}` |
| `$or` | 逻辑或 | `{"$or": [{"a": 1}, {"b": 2}]}` |

还支持文档内容过滤：
```python
where_document={"$contains": "关键词"}
where_document={"$not_contains": "排除词"}
```

**Q5：ChromaDB 如何处理 Embedding？内置了哪些 Embedding 模型？**

**答：**
ChromaDB 内置了 `onnxruntime` 作为默认 Embedding 引擎，使用 `all-MiniLM-L6-v2` 模型（384 维）。

同时支持多种 Embedding 集成：
- **OpenAI**：`text-embedding-3-small`、`text-embedding-3-large`
- **Sentence Transformers**：本地模型，如 `all-mpnet-base-v2`
- **HuggingFace**：通过 API 调用
- **Google PaLM**：`models/embedding-gecko-001`
- **Cohere**：`embed-english-v3.0`
- **自定义**：实现 `__call__` 方法即可

```python
from chromadb.utils import embedding_functions

# 使用 Sentence Transformers（推荐，本地运行）
ef = embedding_functions.SentenceTransformerEmbeddingFunction(
    model_name="all-MiniLM-L6-v2"
)
```

**Q6：ChromaDB 适合什么样的应用场景？不适合什么场景？**

**答：**

**适合：**
- 快速原型开发和 MVP 验证
- 本地知识库和文档搜索
- 与 LangChain/LlamaIndex 集成的 RAG 应用
- 对话机器人的长期记忆
- 中小规模（百万级以下）的向量搜索

**不适合：**
- 十亿级超大规模向量数据
- 需要分布式部署的高可用场景
- 需要复杂索引类型（IVF、DiskANN）的场景
- 需要企业级权限管理和审计的场景
- 对查询延迟要求极高的实时系统

**Q7：ChromaDB 如何实现持久化？数据存储在哪些文件中？**

**答：**
ChromaDB 使用 `PersistentClient` 实现持久化：

```python
client = chromadb.PersistentClient(path="./chroma_data")
```

数据存储在指定目录下，包含：
- **SQLite 数据库**：存储集合元数据、文档内容、元数据
- **HNSW 索引文件**：存储向量索引（每个集合一个目录）
- **WAL 日志**：保证数据一致性

重启应用后，数据自动恢复：
```python
# 重启后重新连接，数据自动加载
client = chromadb.PersistentClient(path="./chroma_data")
collection = client.get_collection("my_collection")
print(collection.count())  # 数据仍在
```

**Q8：ChromaDB 的性能如何？如何优化？**

**答：**
ChromaDB 在百万级数据量下表现良好，查询延迟通常在 10-100ms。

**优化建议：**
1. **批量操作**：使用 `add()` 批量插入，避免逐条插入
2. **合理分块**：文档分块大小影响检索质量（建议 300-800 字符）
3. **元数据过滤**：利用 `where` 条件减少候选集
4. **选择合适的 Embedding**：维度越低，存储和查询越快
5. **限制返回数量**：`n_results` 不要设置过大

**性能参考：**
- 10 万条数据：查询延迟 ~10ms
- 100 万条数据：查询延迟 ~50ms
- 超过 500 万条：建议迁移到 Milvus

**Q9：ChromaDB 如何与 LangChain 集成？**

**答：**
ChromaDB 是 LangChain 的默认向量存储，集成非常简单：

```python
from langchain_community.vectorstores import Chroma
from langchain_openai import OpenAIEmbeddings

# 从文档创建
vectorstore = Chroma.from_documents(
    documents=docs,
    embedding=OpenAIEmbeddings(),
    persist_directory="./chroma_db"
)

# 作为 Retriever 用于 RAG
retriever = vectorstore.as_retriever(search_kwargs={"k": 5})
```

优势：
- 自动处理文档分块和 Embedding
- 支持持久化
- 与 LangChain 的 QA Chain 无缝集成

**Q11：ChromaDB 如何处理并发访问？**

**答：**
- **嵌入式模式**：单进程内线程安全，但不支持多进程并发写入
- **Client/Server 模式**：支持多客户端并发访问，服务端处理并发请求

**建议：**
- 开发阶段使用嵌入式模式
- 生产环境使用 Client/Server 模式
- 高并发场景考虑使用 Milvus 或 Pinecone

**Q12：ChromaDB 的数据模型是怎样的？**

**答：**
ChromaDB 的数据模型由三层组成：

```
Client
  └── Collection（集合）
        └── Document（文档）
              ├── id: 唯一标识符
              ├── document: 文本内容（可选）
              ├── embedding: 向量（可选，自动生成）
              └── metadata: 元数据字典（可选）
```

**特点：**
- 每个 Document 必须有一个唯一 ID
- `document` 和 `embedding` 至少提供一个
- 如果只提供 `document`，ChromaDB 自动生成 `embedding`
- `metadata` 支持嵌套字典，可用于过滤查询

**Q13：ChromaDB 如何迁移到生产环境？**

**答：**
ChromaDB 适合原型开发，迁移到生产环境的方案：

1. **升级到 Client/Server 模式**
   - 部署独立的 ChromaDB 服务
   - 使用 `HttpClient` 连接

2. **迁移到 Milvus**
   - 导出 ChromaDB 数据
   - 使用 Milvus SDK 重新导入

```python
# 从 ChromaDB 导出数据
all_data = collection.get(include=["embeddings", "documents", "metadatas"])

# 导入到 Milvus
milvus_collection.insert([
    all_data["documents"],
    all_data["embeddings"],
    all_data["metadatas"]
])
```

3. **迁移到 Pinecone**
   - 使用 Pinecone SDK 批量导入

## 六、向量数据库与传统数据库对比

### 6.1 三类数据库概述

| 数据库类型 | 代表产品 | 核心定位 |
|-----------|---------|---------|
| **关系型数据库（RDBMS）** | MySQL、PostgreSQL、Oracle | 存储结构化数据，保证事务一致性（ACID） |
| **非关系型数据库（NoSQL）** | MongoDB、Cassandra、Redis | 灵活数据模型，高扩展性，适合非结构化/半结构化数据 |
| **向量数据库（Vector DB）** | Milvus、Pinecone、ChromaDB | 存储高维向量，提供高效相似性搜索 |

### 6.2 数据模型对比

| 对比维度 | MySQL（关系型） | MongoDB（文档型） | 向量数据库 |
|---------|----------------|------------------|-----------|
| **数据模型** | 表（Table）+ 行（Row）+ 列（Column） | 集合（Collection）+ 文档（Document） | 集合（Collection）+ 向量（Vector） |
| **数据结构** | 严格的二维表结构，预定义 Schema | 灵活的 BSON/JSON 文档，动态 Schema | 向量 + 元数据 + 文档 |
| **数据类型** | INT、VARCHAR、DATE、DECIMAL 等 | String、Int、Bool、Array、Object、Date | FLOAT_VECTOR（768/1536维）、VARCHAR、JSON |
| **关系表达** | 外键（Foreign Key）+ JOIN | `$lookup`（聚合管道） | 无原生关系支持，通过 ID 关联 |
| **Schema 约束** | 强 Schema，建表时定义列类型 | 弱 Schema，同一集合可存不同结构文档 | 中等 Schema，需定义向量维度和字段类型 |

**示例对比 — 存储一篇博客文章：**

```sql
-- MySQL：严格表结构
CREATE TABLE blog_posts (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(200) NOT NULL,
    content TEXT,
    author_id BIGINT,
    category VARCHAR(50),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (author_id) REFERENCES users(id)
);
```

```javascript
// MongoDB：灵活文档结构
db.blog_posts.insertOne({
    title: "向量数据库入门",
    content: "向量数据库是AI时代的关键基础设施...",
    author: { name: "张三", email: "zhangsan@example.com" },  // 嵌套文档
    tags: ["AI", "数据库", "向量搜索"],                         // 数组
    created_at: new Date()
});
```

```python
# 向量数据库（Milvus）：向量 + 元数据
fields = [
    FieldSchema(name="id", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="title", dtype=DataType.VARCHAR, max_length=200),
    FieldSchema(name="category", dtype=DataType.VARCHAR, max_length=50),
    FieldSchema(name="embedding", dtype=DataType.FLOAT_VECTOR, dim=768)  # 核心：向量字段
]
```

### 6.3 存储结构对比

| 对比维度 | MySQL | MongoDB | 向量数据库 |
|---------|-------|---------|-----------|
| **存储引擎** | InnoDB（默认） | WiredTiger | 自定义引擎（基于 HNSW/IVF） |
| **索引结构** | B+ 树 | B+ 树 + 多键索引 | HNSW、IVF、PQ、DiskANN |
| **数据组织** | 按行存储在页（Page）中 | BSON 文档存储在数据块中 | 向量分段存储在索引图中 |
| **索引文件** | `.ibd` 文件 | `.wt` 文件 | HNSW 图文件 / IVF 倒排文件 |
| **压缩方式** | 页级压缩 | Snappy / Zstd | 向量量化（PQ/SQ） |
| **内存管理** | Buffer Pool 缓存数据页 | WiredTiger 缓存 | 全量/部分索引加载到内存 |

**索引结构差异示意：**

```text
MySQL B+ 树索引：
         [50]
        /    \
    [20,35]   [65,80]
    / | \      / | \
  10 25 40  55 70  90    → 精确查找 O(log N)

向量数据库 HNSW 索引：
  Layer 2:    A -------- D
              |           |
  Layer 1:    A --- C --- D --- F
              |  /  |  /  |  /
  Layer 0:    A-B-C-D-E-F-G-H   → 近似查找 O(log N)
```

### 6.4 查询方式对比

| 对比维度 | MySQL | MongoDB | 向量数据库 |
|---------|-------|---------|-----------|
| **查询语言** | SQL（结构化查询语言） | MQL（MongoDB Query Language） | SDK API（Python/Java/Go） |
| **核心查询** | `SELECT ... WHERE col = value` | `db.collection.find({field: value})` | `collection.search(data=[vector], limit=10)` |
| **查询类型** | 精确匹配、范围查询、聚合 | 精确匹配、范围查询、聚合管道 | 相似性搜索（ANN）、范围搜索 |
| **模糊查询** | `LIKE '%keyword%'`（全表扫描） | 正则表达式 / 全文索引 | 语义相似度搜索（核心能力） |
| **关联查询** | `JOIN`（支持多表关联） | `$lookup`（仅左连接） | 不支持原生关联 |
| **事务支持** | 完整 ACID 事务 | 多文档事务（4.0+） | 单条原子操作，无复杂事务 |

**查询示例对比 — 搜索"AI 相关的文章"：**

```sql
FROM blog_posts
WHERE category = 'AI'
  AND content LIKE '%向量数据库%'   -- 只能匹配关键词，无法理解语义

LIMIT 10;
```

```javascript

    $text: { $search: "向量数据库" },  // 全文搜索
    category: "AI"

```

```python

results = collection.search(
    data=[get_embedding("什么是向量数据库")],  # 语义理解
    anns_field="embedding",
    param={"metric_type": "COSINE", "params": {"ef": 128}},
    limit=10,
    expr="category == 'AI'",  # 可选：标量过滤

```

### 6.9 选型决策指南

**选择 MySQL 当：**
- 数据具有严格的结构和关系
- 需要事务支持（如金融交易、订单处理）

**选择 MongoDB 当：**
- 数据结构灵活，Schema 经常变化
- 需要存储嵌套/文档型数据
- 读写量大，需要水平扩展
- 数据以文档/JSON 形式存在

**选择向量数据库当：**
- 需要语义搜索能力
- 处理非结构化数据（文本、图像、音频）
- 构建 RAG、推荐、以图搜图等 AI 应用
- 需要基于相似度的检索

**混合使用建议：**
- 现代 AI 应用通常需要多种数据库配合使用
- 向量数据库负责语义检索 → 传统数据库负责业务逻辑
- MySQL 存储核心业务数据 + 向量数据库存储语义向量 + MongoDB 存储非结构化内容

## 七、常见面试题

### 7.1 基础概念题

**Q1：什么是向量数据库？与传统数据库有什么区别？**

**答：**
向量数据库是专门用于存储和查询高维向量的数据库，核心能力是高效的相似性搜索。

| 对比维度 | 传统数据库 | 向量数据库 |
|---------|-----------|-----------|
| 数据类型 | 结构化数据（行、列） | 高维向量 + 元数据 |
| 查询方式 | 精确匹配（WHERE） | 相似性搜索（最近邻） |
| 索引结构 | B+树、Hash | HNSW、IVF、PQ 等 |
| 典型场景 | 业务数据 CRUD | 语义搜索、推荐、RAG |

**Q2：什么是 Embedding？如何选择合适的 Embedding 模型？**

**答：**
Embedding 是将非结构化数据（文本、图像等）转换为固定维度向量的过程。

选择 Embedding 模型时考虑：
- **任务类型**：文本用 BERT/GTE，图像用 CLIP/ResNet
- **向量维度**：维度越高表达能力越强，但存储和计算成本增加
- **语言支持**：中文场景选择中文优化模型（如 bge-large-zh）
- **性能基准**：参考 MTEB 等榜单的排名

**Q3：常见的向量距离度量方式有哪些？分别适用于什么场景？**

**答：**

| 度量方式 | 公式 | 适用场景 |
|---------|------|---------|
| 余弦相似度 | cos(θ) = A·B / (||A|| × ||B||) | 文本语义相似度，方向敏感 |
| 欧氏距离 | √Σ(Ai - Bi)² | 图像特征，绝对距离敏感 |
| 内积 | A·B = ΣAi × Bi | 已归一化向量，等价余弦 |

### 4.2 索引与性能题

**Q4：HNSW 索引的原理是什么？有什么优缺点？**

**答：**
HNSW（Hierarchical Navigable Small World）是基于图的分层索引结构。

**原理：**
- 构建多层导航图，上层稀疏用于快速定位，下层稠密保证召回率
- 搜索时从顶层开始，逐层向下导航，最终在底层找到最近邻

**优点：**
- 查询速度极快（O(log N)）
- 召回率高（可达 99%+）
- 支持增量更新

**缺点：**
- 内存占用大（需存储图结构）
- 构建索引时间长
- 不适合超大规模数据（需配合分布式）

**Q5：如何优化向量数据库的查询性能？**

**答：**

1. **索引优化**
   - 选择合适的索引类型（HNSW 适合中小规模，IVF 适合大规模）
   - 调整索引参数（HNSW 的 M 和 efConstruction）

2. **查询优化**
   - 调整搜索参数（HNSW 的 ef，IVF 的 nprobe）
   - 使用标量过滤减少候选集
   - 批量查询代替单条查询

3. **架构优化**
   - 水平扩展查询节点
   - 使用 SSD 存储索引
   - 预热热点数据到内存

4. **向量优化**
   - 降维（PCA、AutoEncoder）
   - 向量量化（PQ、SQ）
   - 归一化预处理

**Q6：向量数据库如何保证高可用性？**

**答：**

- **副本机制**：数据多副本存储，节点故障自动切换
- **分片策略**：数据分片分布到多个节点，避免单点故障
- **Raft 协议**：元数据节点使用 Raft 保证一致性
- **健康检查**：定期检测节点状态，自动剔除故障节点
- **灰度发布**：滚动升级，避免全集群不可用

### 4.3 应用场景题

**Q7：RAG 系统中向量数据库的作用是什么？**

**答：**

在 RAG（Retrieval-Augmented Generation）中，向量数据库负责：

1. **知识存储**：将外部知识文档转换为向量并存储
2. **语义检索**：根据用户问题检索最相关的知识片段
3. **上下文构建**：将检索结果作为上下文提供给 LLM

**流程：**
```
用户问题 → Embedding → 向量检索 → Top-K 文档 → 构建 Prompt → LLM 生成回答
```

**优化点：**
- 文档分块策略（按段落、固定长度、语义分块）
- 混合检索（向量检索 + 关键词检索）
- 重排序（Reranker 对检索结果二次排序）

**Q8：向量数据库在推荐系统中的应用？**

**答：**

1. **用户/物品向量化**：将用户行为和物品特征转换为向量
2. **相似性召回**：基于向量相似度快速召回候选物品
3. **实时推荐**：用户行为更新后实时调整推荐结果

**优势：**
- 支持海量候选集的高效召回
- 捕捉深层语义相似性
- 支持多模态推荐（文本 + 图像 + 视频）

**Q9：如何处理向量数据库的更新操作？**

**答：**

向量数据库的更新策略：

| 策略 | 说明 | 适用场景 |
|-----|------|---------|
| 删除 + 插入 | 先删除旧向量，再插入新向量 | 更新频率低的场景 |
| Upsert | 如果 ID 存在则更新，否则插入 | 需要原子更新的场景 |
| 版本管理 | 保留历史版本，查询时指定版本 | 需要追溯历史的场景 |

**注意事项：**
- 频繁更新会影响索引性能
- 批量更新优于单条更新
- 更新后需重新计算向量（如果原始数据变化）

### 4.4 对比与选型题

**Q10：Milvus 和 Pinecone 如何选择？**

**答：**

| 对比维度 | Milvus | Pinecone |
|---------|--------|----------|
| 部署方式 | 自建/云托管 | 全托管 SaaS |
| 开源性 | 开源 | 闭源 |
| 成本 | 自建成本低，云版本较高 | 按使用量付费 |
| 运维复杂度 | 需自行运维（自建） | 零运维 |
| 定制性 | 高度可定制 | 有限定制 |
| 数据主权 | 数据在自己手中 | 数据在第三方 |
| 适用场景 | 大规模、高定制需求 | 快速开发、中小规模 |

**选择建议：**
- 选择 Milvus：数据敏感、需要私有化部署、有运维能力、大规模数据
- 选择 Pinecone：快速验证、不想运维、中小规模、预算充足

**Q11：向量数据库与传统数据库的 ANN 搜索有什么区别？**

**答：**

| 对比维度 | 向量数据库 | 传统数据库 ANN |
|---------|-----------|---------------|
| 索引结构 | 专用向量索引（HNSW、IVF） | 通用索引（B+树） |
| 查询性能 | 毫秒级（百万级数据） | 秒级（需全表扫描或近似） |
| 扩展性 | 水平扩展，支持十亿级向量 | 垂直扩展，扩展性有限 |
| 功能完整性 | 支持混合查询、元数据过滤 | 需额外开发 |

**Q12：向量数据库的局限性有哪些？**

**答：**

1. **语义鸿沟**：Embedding 模型无法完全捕捉所有语义信息
2. **更新成本**：向量更新需重新计算，成本较高
3. **可解释性差**：向量相似度难以解释业务含义
4. **存储成本**：高维向量占用大量存储空间
5. **冷启动问题**：新数据缺乏历史行为，Embedding 质量低

**解决方案：**
- 混合检索（向量 + 关键词）弥补语义鸿沟
- 增量索引减少更新成本
- 结合业务规则提升可解释性
- 向量压缩技术降低存储成本

## 五、总结

向量数据库是 AI 时代的关键基础设施，Milvus 和 Pinecone 分别代表了开源和云托管两种典型方案。选择合适的向量数据库需要综合考虑数据规模、运维能力、成本预算和数据主权等因素。

**核心要点：**
1. 理解向量数据库的核心价值：高效的相似性搜索
2. 掌握索引原理：HNSW、IVF 等索引的适用场景
3. 熟悉 RAG 应用：向量数据库在 LLM 应用中的关键作用
4. 关注性能优化：索引参数、查询策略、架构设计
5. 合理选型：根据业务需求选择开源或云托管方案

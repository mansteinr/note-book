查询mysql日志步骤

1、先通过下面的表格快速了解，不同目的该看哪种日志，以及用什么命令：

错误日志是排查问题时的第一站。你可以先用下面的命令在 MySQL 内部确认它的准确路径，再用 tail 命令查看。

```
-- 
1. 登录MySQL后，查询错误日志路径
SHOW VARIABLES LIKE 'log_error';

# 2. 实时查看最新错误信息（替换为你的实际路径）
sudo tail -f /var/log/mysqld.log
```


查看慢查询日志（性能优化重点）

如果数据库响应慢，就需要分析慢查询日志。关键在于先确认它已开启并设置好阈值。

```
-- 1. 检查慢查询日志是否开启，以及文件位置
SHOW VARIABLES LIKE 'slow_query_log%';
-- 2. 查看当前慢查询阈值（默认10秒）
SHOW VARIABLES LIKE 'long_query_time';
-- 3. 如果未开启，可临时开启（重启失效）
SET GLOBAL slow_query_log = 'ON';
-- 4. 设置一个更敏感的阈值，如2秒
SET GLOBAL long_query_time = 2;
```


实时监控 + 关键词过滤
```
# 实时监控错误日志，只显示包含 "ERROR" 的行
sudo tail -f /var/log/mysqld.log | grep "ERROR"

# 实时监控慢查询日志，只显示查询时间超过2秒的（假设日志格式包含 "Query_time: 2."）
sudo tail -f /var/log/mysql/slow.log | grep "Query_time: [2-9]"

# 实时监控，同时过滤多个关键词（使用 -E 正则）
sudo tail -f /var/log/mysqld.log | grep -E "ERROR|Fatal|CRITICAL"
```


| 日志类型 | 主要作用 | 常见文件路径 | 核心查看命令 |
|---------|---------|-------------|-------------|
| 错误日志 (Error Log) | 排查 MySQL 启动失败、运行崩溃、连接错误等问题，最常用。 | `/var/log/mysqld.log` 或 `/var/log/mysql/error.log` | `sudo tail -f /var/log/mysqld.log` |

## 一、数据库简介

### 1.1 核心概念

**数据库（Database）** 是按照数据结构来组织、存储和管理数据的仓库。数据库管理系统（DBMS）是用于管理数据库的软件系统，提供数据的定义、创建、查询、更新和管理等功能。

### 1.2 发展历程

| 阶段 | 时间 | 模型 | 代表 |
|-----|------|------|------|
| 第一代 | 1960s | 层次/网状模型 | IMS、CODASYL |
| 第二代 | 1970s-1980s | 关系模型 | Oracle、DB2、MySQL |
| 第三代 | 1990s-2000s | 对象关系模型 | PostgreSQL |
| 第四代 | 2010s-至今 | NoSQL / NewSQL | MongoDB、Redis、TiDB |

### 1.3 数据库主要类型

| 类型 | 特点 | 代表产品 |
|-----|------|---------|
| **关系型数据库（RDBMS）** | 表结构、SQL、ACID事务 | MySQL、PostgreSQL、Oracle、SQL Server |
| **键值数据库** | 高性能、简单结构 | Redis、Memcached |
| **文档数据库** | 灵活Schema、JSON存储 | MongoDB、CouchDB |
| **列族数据库** | 大规模分布式写入 | HBase、Cassandra |
| **图数据库** | 图结构、关系遍历 | Neo4j、JanusGraph |
| **搜索引擎** | 全文检索、倒排索引 | Elasticsearch、Solr |
| **时序数据库** | 时间序列数据优化 | InfluxDB、TimescaleDB |
| **向量数据库** | 高维向量相似性搜索 | Milvus、Pinecone、ChromaDB |

### 1.4 面试题

**Q1：什么是数据库？请简述数据库管理系统（DBMS）的主要功能。**

**答：**
数据库是按照数据结构来组织、存储和管理数据的仓库。DBMS 的主要功能包括：
- **数据定义**：提供 DDL 定义数据库结构（表、索引、视图等）
- **数据操作**：提供 DML 进行增删改查操作
- **数据控制**：提供 DCL 进行权限管理和安全控制
- **事务管理**：保证事务的 ACID 特性
- **数据完整性**：维护数据的正确性和一致性
- **并发控制**：管理多用户同时访问的数据一致性
- **故障恢复**：提供备份和恢复机制
- **数据存储管理**：优化数据的物理存储和访问效率

---

**Q2：关系型数据库与非关系型数据库有什么区别？各自适用于什么场景？**

**答：**

| 对比维度 | 关系型数据库 | 非关系型数据库 |
|---------|------------|--------------|
| 数据模型 | 二维表（行和列） | 键值、文档、列族、图等 |
| Schema | 严格预定义 | 灵活/动态 |
| 查询语言 | SQL（标准化） | 各有专用查询方式 |
| 事务支持 | 完整 ACID | 通常最终一致性（BASE） |
| 扩展方式 | 垂直扩展为主 | 水平扩展为主 |
| 关联查询 | 支持 JOIN | 通常不支持 |
| 适用场景 | 复杂查询、事务处理 | 高并发、海量数据、灵活Schema |

**关系型适用场景：** 金融交易、订单管理、ERP 系统等需要强一致性和复杂查询的场景。
**非关系型适用场景：** 缓存加速、日志分析、社交网络、物联网等需要高扩展性和高并发的场景。

---

**Q3：请解释 ACID 特性。**

**答：**
ACID 是关系型数据库事务的四个基本特性：

- **Atomicity（原子性）**：事务是一个不可分割的最小工作单元，事务中的操作要么全部成功，要么全部失败回滚。通过 undo log 实现。
- **Consistency（一致性）**：事务执行前后，数据库从一个一致性状态转换到另一个一致性状态，数据的完整性约束不会被破坏。由其他三个特性共同保证。
- **Isolation（隔离性）**：并发执行的事务之间互不干扰，通过锁机制和 MVCC 实现。
- **Durability（持久性）**：事务一旦提交，对数据的改变就是永久的，即使系统故障也不会丢失。通过 redo log 实现。

---

**Q4：什么是数据库的三大范式？**

**答：**

- **第一范式（1NF）**：数据库表的每一列都是不可分割的基本数据项（原子性），不能有重复的列。
- **第二范式（2NF）**：在 1NF 基础上，非主键列必须完全依赖于主键，不能只依赖主键的一部分（消除部分依赖）。适用于有复合主键的场景。
- **第三范式（3NF）**：在 2NF 基础上，非主键列不能依赖于其他非主键列（消除传递依赖）。

**反范式化**：在实际生产中，为了查询性能，有时会故意违反范式，引入冗余数据（如反范式化设计），减少 JOIN 操作。

---

**Q5：什么是反范式化？为什么要反范式化？**

**答：**
反范式化是指为了查询性能，有意在数据库中引入冗余数据，违反规范化原则的设计策略。

**常见反范式化手段：**
- **冗余字段**：在订单表中冗余用户名字段，避免 JOIN 用户表
- **汇总表**：预先计算并存储统计结果
- **拆分表改为合并表**：减少 JOIN 次数

**优点：** 减少 JOIN 操作，提升查询性能，降低复杂度
**缺点：** 增加存储空间，数据更新时需要维护一致性，可能导致数据异常

---

**Q6：数据库的 CAP 定理是什么？**

**答：**
CAP 定理（Brewer 定理）指出，一个分布式系统不可能同时满足以下三个特性：

- **C（Consistency，一致性）**：所有节点在同一时间看到相同的数据
- **A（Availability，可用性）**：每个请求都能得到非错误的响应
- **P（Partition tolerance，分区容错性）**：系统在网络分区的情况下仍能继续运行

由于网络分区在分布式系统中不可避免，实际上只能在 C 和 A 之间选择：
- **CP 系统**：保证一致性和分区容错，如 ZooKeeper、HBase
- **AP 系统**：保证可用性和分区容错，如 Cassandra、DynamoDB

---

**Q7：什么是数据库的索引？索引的优缺点是什么？**

**答：**
索引是数据库中用于加速数据检索的数据结构，类似于书籍的目录。

**优点：**
- 大幅加快查询速度
- 加速排序和分组操作
- 保证数据唯一性（唯一索引）

**缺点：**
- 占用额外存储空间
- 降低写入性能（INSERT/UPDATE/DELETE 需维护索引）
- 需要定期维护和优化

**常见索引类型：** B+树索引、Hash索引、全文索引、空间索引、位图索引等。

---

**Q8：请简述数据库的发展经历了哪几个阶段？**

**答：**

1. **人工管理阶段（1950s前）**：数据不保存，无专门软件管理数据
2. **文件系统阶段（1950s-1960s）**：数据以文件形式存储，有数据冗余和不一致性
3. **数据库系统阶段（1960s-至今）**：
   - 层次/网状数据库（1960s-1970s）
   - 关系数据库（1970s-至今）
   - NoSQL/NewSQL（2000s-至今）
   - 云原生数据库（2010s-至今）

## 二、常用语法

### 2.1 DDL（数据定义语言）

```sql
-- 创建数据库
CREATE DATABASE IF NOT EXISTS mydb
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_unicode_ci;

-- 创建表
CREATE TABLE users (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY COMMENT '用户ID',
    username VARCHAR(50) NOT NULL UNIQUE COMMENT '用户名',
    email VARCHAR(100) NOT NULL COMMENT '邮箱',
    password_hash VARCHAR(255) NOT NULL COMMENT '密码哈希',
    age TINYINT UNSIGNED COMMENT '年龄',
    status ENUM('active', 'inactive', 'banned') DEFAULT 'active' COMMENT '状态',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    INDEX idx_username (username),
    INDEX idx_email (email),
    INDEX idx_created_at (created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='用户表';

-- 修改表结构
ALTER TABLE users ADD COLUMN phone VARCHAR(20) COMMENT '手机号' AFTER email;
ALTER TABLE users MODIFY COLUMN age SMALLINT UNSIGNED COMMENT '年龄';
ALTER TABLE users DROP COLUMN phone;
ALTER TABLE users RENAME COLUMN username TO user_name;

-- 创建索引
CREATE INDEX idx_status ON users(status);
CREATE UNIQUE INDEX uk_email ON users(email);

-- 创建视图
CREATE VIEW active_users AS
SELECT id, username, email, created_at
FROM users
WHERE status = 'active';

-- 删除操作
DROP INDEX idx_status ON users;
DROP VIEW active_users;
DROP TABLE IF EXISTS users;
DROP DATABASE IF EXISTS mydb;
```

### 2.3 DQL（数据查询语言）

```sql
-- 基础查询
SELECT id, username, email FROM users WHERE age > 25 ORDER BY created_at DESC LIMIT 10;

-- 条件查询
SELECT * FROM users
WHERE status = 'active'
  AND age BETWEEN 20 AND 35
  AND username LIKE 'zhang%'
  AND email IN ('zhangsan@example.com', 'lisi@example.com');

-- 聚合查询
SELECT status, COUNT(*) AS cnt, AVG(age) AS avg_age
FROM users
GROUP BY status
HAVING cnt > 5
ORDER BY cnt DESC;

-- JOIN 查询
SELECT u.id, u.username, o.order_no, o.total_amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE o.created_at >= '2024-01-01'
ORDER BY o.created_at DESC;

-- 子查询
SELECT username, email
FROM users
WHERE id IN (
    SELECT user_id FROM orders
    WHERE total_amount > (SELECT AVG(total_amount) FROM orders)
);

-- 窗口函数
SELECT username, total_amount,
    ROW_NUMBER() OVER (PARTITION BY status ORDER BY total_amount DESC) AS rn,
    RANK() OVER (ORDER BY total_amount DESC) AS ranking,
    SUM(total_amount) OVER (PARTITION BY status) AS dept_total,
    LAG(total_amount, 1) OVER (ORDER BY created_at) AS prev_amount
FROM users u
JOIN orders o ON u.id = o.user_id;

-- EXISTS 查询
SELECT u.username
FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.total_amount > 1000
);

-- UNION 查询
SELECT username AS name, 'user' AS type FROM users
UNION ALL
SELECT product_name, 'product' FROM products;

-- CASE 表达式
SELECT username,
    CASE
        WHEN age < 18 THEN '未成年'
        WHEN age BETWEEN 18 AND 30 THEN '青年'
        WHEN age BETWEEN 31 AND 50 THEN '中年'
        ELSE '老年'
    END AS age_group
FROM users;
```

### 2.5 高级查询技巧

```sql
-- 分页查询（深分页优化）
-- 不推荐（深分页性能差）
SELECT * FROM users ORDER BY id LIMIT 1000000, 10;

-- 推荐（延迟关联）
SELECT u.* FROM users u
INNER JOIN (SELECT id FROM users ORDER BY id LIMIT 1000000, 10) AS tmp
ON u.id = tmp.id;

-- 推荐（游标分页）
SELECT * FROM users WHERE id > 1000000 ORDER BY id LIMIT 10;

-- 递归查询（CTE）
WITH RECURSIVE category_tree AS (
    SELECT id, name, parent_id, 1 AS level
    FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.name, c.parent_id, ct.level + 1
    FROM categories c
    JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT * FROM category_tree ORDER BY level;

-- 透视表（行转列）
SELECT user_id,
    SUM(CASE WHEN month = 'Jan' THEN amount ELSE 0 END) AS jan_amount,
    SUM(CASE WHEN month = 'Feb' THEN amount ELSE 0 END) AS feb_amount,
    SUM(CASE WHEN month = 'Mar' THEN amount ELSE 0 END) AS mar_amount
FROM monthly_sales
GROUP BY user_id;
```

### 2.6 面试题

**Q1：`DELETE`、`TRUNCATE` 和 `DROP` 有什么区别？**

**答：**

| 对比维度 | DELETE | TRUNCATE | DROP |
|---------|--------|----------|------|
| 类型 | DML | DDL | DDL |
| 作用 | 删除行数据 | 清空表数据 | 删除整个表 |
| 可回滚 | 可以（事务内） | 不可以 | 不可以 |
| 触发器 | 触发 | 不触发 | 不触发 |
| 自增ID | 不重置 | 重置 | 随表删除 |
| 速度 | 慢（逐行删除） | 快（释放数据页） | 最快 |
| WHERE条件 | 支持 | 不支持 | 不支持 |

---

**Q2：`WHERE` 和 `HAVING` 的区别是什么？**

**答：**
- **WHERE**：在分组前过滤行，不能使用聚合函数，作用于单行数据
- **HAVING**：在分组后过滤组，可以使用聚合函数，作用于聚合后的结果

**执行顺序：** FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

---

**Q3：请解释 SQL 中各种 JOIN 的区别。**

**答：**

| JOIN 类型 | 说明 |
|----------|------|
| `INNER JOIN` | 只返回两个表中匹配的行 |
| `LEFT JOIN` | 返回左表所有行，右表不匹配则填 NULL |
| `RIGHT JOIN` | 返回右表所有行，左表不匹配则填 NULL |
| `FULL OUTER JOIN` | 返回两个表的所有行，不匹配则填 NULL |
| `CROSS JOIN` | 笛卡尔积，返回所有组合 |
| `SELF JOIN` | 表与自身连接（用于层级关系等） |

---

**Q4：什么是子查询？相关子查询和普通子查询有什么区别？**

**答：**
- **普通子查询**：独立执行，不依赖外部查询，只执行一次
- **相关子查询**：依赖外部查询的值，对外部查询的每一行都执行一次

```sql
-- 普通子查询（先执行内部）
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders);

-- 相关子查询（每行都执行内部）
SELECT u.username,
    (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u;
```

**优化建议：** 尽量用 JOIN 替代子查询，相关子查询在大数据量下性能较差。

---

**Q5：什么是窗口函数？与 GROUP BY 有什么区别？**

**答：**
窗口函数（Window Function）在不改变行数的情况下，对一组相关行进行计算。

**与 GROUP BY 的区别：**
- GROUP BY 会合并行，每个分组只返回一行
- 窗口函数保留每一行，同时添加聚合计算结果

```sql
-- 窗口函数：保留每行，同时显示部门总薪资
SELECT name, department, salary,
    SUM(salary) OVER (PARTITION BY department) AS dept_total,
    RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dept_rank
FROM employees;
```

**常用窗口函数：** `ROW_NUMBER()`、`RANK()`、`DENSE_RANK()`、`LAG()`、`LEAD()`、`SUM() OVER()`、`AVG() OVER()`

**Q6：如何优化深分页查询？**

**答：**

```sql
-- 问题：深分页性能差
SELECT * FROM users ORDER BY id LIMIT 1000000, 10;
-- MySQL 需要扫描 1000010 行，丢弃前 1000000 行

-- 方案一：延迟关联
SELECT u.* FROM users u
INNER JOIN (SELECT id FROM users ORDER BY id LIMIT 1000000, 10) tmp
ON u.id = tmp.id;

-- 方案二：游标分页（推荐）
SELECT * FROM users WHERE id > 1000000 ORDER BY id LIMIT 10;

-- 方案三：记录上次最后一条的位置
SELECT * FROM users WHERE id > #{lastMaxId} ORDER BY id LIMIT 10;
```

---

**Q7：`UNION` 和 `UNION ALL` 的区别是什么？**

**答：**
- **UNION**：合并结果集并去重，会进行排序操作，性能较低
- **UNION ALL**：合并结果集不去重，不进行排序，性能较高

**建议：** 如果确定没有重复数据或不需要去重，优先使用 `UNION ALL`。

**Q8：请写出 SQL 语句的执行顺序。**

**答：**

```
FROM → JOIN → ON → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

理解执行顺序有助于优化 SQL 查询，例如：
- WHERE 在 GROUP BY 之前执行，所以 WHERE 不能用聚合函数
- HAVING 在 GROUP BY 之后执行，可以使用聚合函数
- SELECT 在 ORDER BY 之前执行，ORDER BY 可以使用 SELECT 中的别名

## 四、性能优化

### 4.1 索引优化

#### 索引设计原则

1. **选择性高的列建索引**：区分度越高，索引效果越好
2. **频繁查询的列建索引**：WHERE、JOIN、ORDER BY、GROUP BY 中的列
3. **避免过多索引**：每个索引增加写入开销
4. **使用联合索引**：遵循最左前缀原则
5. **覆盖索引**：查询列都在索引中，避免回表

#### 索引失效场景

```sql
-- 1. 对索引列使用函数或运算
WHERE YEAR(created_at) = 2024          -- 索引失效
WHERE created_at >= '2024-01-01'       -- 索引有效

-- 2. 隐式类型转换
WHERE phone = 13800138000              -- phone是VARCHAR，传入数字，索引失效
WHERE phone = '13800138000'            -- 索引有效

-- 3. LIKE 以通配符开头
WHERE name LIKE '%张'                  -- 索引失效
WHERE name LIKE '张%'                  -- 索引有效

-- 4. OR 条件中有非索引列
WHERE indexed_col = 1 OR non_indexed_col = 2  -- 索引失效

-- 5. 联合索引不满足最左前缀
-- 索引 (a, b, c)
WHERE a = 1 AND c = 3                  -- 只用到 a 的索引
WHERE b = 2 AND c = 3                  -- 索引失效
WHERE a = 1 AND b = 2 AND c = 3       -- 完全使用索引
```

### 4.2 查询优化

```sql
-- 1. 避免 SELECT *
SELECT id, username, email FROM users;  -- 推荐
SELECT * FROM users;                     -- 不推荐

-- 2. 使用 EXISTS 替代 IN（子查询结果集大时）
-- 推荐
SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
-- 不推荐
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders);

-- 3. 合理使用 LIMIT
SELECT * FROM users WHERE status = 'active' LIMIT 100;

-- 4. 避免在 WHERE 中对索引列运算
WHERE created_at >= '2024-01-01' AND created_at < '2024-02-01'  -- 推荐
WHERE DATE(created_at) = '2024-01-15'                            -- 不推荐

-- 5. 使用批量操作代替循环
-- 推荐
INSERT INTO users (name) VALUES ('a'), ('b'), ('c');
-- 不推荐
INSERT INTO users (name) VALUES ('a');
INSERT INTO users (name) VALUES ('b');
INSERT INTO users (name) VALUES ('c');
```

### 4.3 存储优化

| 优化手段 | 说明 |
|---------|------|
| **选择合适的数据类型** | INT 优于 VARCHAR 存储数字，TINYINT 存储小范围值 |
| **使用 NOT NULL** | NULL 值影响索引和比较，尽量设置默认值 |
| **适当拆分大表** | 将不常访问的大字段拆分到扩展表 |
| **分区表** | 按时间或范围分区，减少扫描范围 |
| **压缩存储** | 使用 InnoDB 页压缩或行压缩 |

### 4.4 面试题

**Q1：什么是覆盖索引？有什么好处？**

**答：**
覆盖索引（Covering Index）是指查询的所有列都包含在索引中，不需要回表查询数据行。

```sql
-- 联合索引 (username, email, status)
-- 以下查询为覆盖索引查询：
SELECT username, email, status FROM users WHERE username = 'zhangsan';
-- 因为 SELECT 的列都在索引中，无需回表
```

**好处：**
- 避免回表操作，减少随机 I/O
- 查询速度显著提升
- 减少数据页的访问

**Q2：什么是索引下推（ICP）？**

**答：**
索引下推（Index Condition Pushdown，ICP）是 MySQL 5.6 引入的优化技术。

**原理：** 在索引遍历过程中，先对索引中包含的字段进行过滤，减少回表次数。

```sql
-- 联合索引 (name, age)
SELECT * FROM users WHERE name LIKE '张%' AND age > 25;

-- 无ICP：先通过 name 找到所有姓张的记录，回表后再过滤 age
-- 有ICP：在索引层面就过滤掉 age <= 25 的记录，减少回表次数
```

**Q5：什么是 MVCC？它是如何实现的？**

**答：**
MVCC（Multi-Version Concurrency Control，多版本并发控制）是 InnoDB 实现高并发读写的核心机制。

**核心思想：** 通过保存数据的历史版本，让读操作不阻塞写操作，写操作不阻塞读操作。

**实现原理：**
1. **隐藏列**：每行数据包含 `DB_TRX_ID`（最近修改的事务ID）和 `DB_ROLL_PTR`（回滚指针）
2. **Undo Log**：记录数据的历史版本，形成版本链
3. **Read View**：事务执行快照读时生成的读视图，包含：
   - `m_ids`：生成 Read View 时活跃的事务ID列表
   - `min_trx_id`：活跃事务中最小的ID
   - `max_trx_id`：下一个将分配的事务ID
   - `creator_trx_id`：创建该 Read View 的事务ID

**可见性判断规则：**
- 版本链中 `DB_TRX_ID < min_trx_id` → 可见
- 版本链中 `DB_TRX_ID >= max_trx_id` → 不可见
- `min_trx_id <= DB_TRX_ID < max_trx_id` → 如果在 `m_ids` 中则不可见，否则可见

**Q7：什么是数据库连接池？为什么要使用连接池？**

## 五、事务与并发控制

### 5.1 面试题

**Q1：事务的隔离级别有哪些？各自解决什么问题？**

**答：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 实现方式 |
|---------|------|-----------|------|---------|
| READ UNCOMMITTED | 可能 | 可能 | 可能 | 无 |
| READ COMMITTED | 不会 | 可能 | 可能 | 快照读每次生成新ReadView |
| REPEATABLE READ（默认） | 不会 | 不会 | 可能（InnoDB通过Gap Lock解决） | 快照读只生成一次ReadView |
| SERIALIZABLE | 不会 | 不会 | 不会 | 串行执行 / 加锁 |

**并发问题：**
- **脏读**：读到其他事务未提交的数据
- **不可重复读**：同一事务中两次读取同一行数据不同
- **幻读**：同一事务中两次查询，行数不同（新增/删除）

---

**Q2：什么是死锁？如何避免和解决？**

**答：**
死锁是两个或多个事务互相持有对方需要的锁，导致都无法继续执行。

**产生条件：**
1. 互斥条件
2. 持有并等待
3. 不可抢占
4. 循环等待

**避免策略：**
- 按固定顺序访问资源
- 缩短事务持续时间
- 使用较低的隔离级别
- 合理使用索引，减少锁范围

**解决方式：**
- **超时检测**：设置锁等待超时时间
- **死锁检测**：InnoDB 自动检测并回滚代价小的事务
- **等待图**：构建事务等待关系图，检测环路

```sql
-- 查看死锁信息
SHOW ENGINE INNODB STATUS;
-- 设置锁等待超时
SET innodb_lock_wait_timeout = 10;
-- 开启死锁检测
SET innodb_deadlock_detect = ON;
```

---

**Q3：InnoDB 的行锁有哪些类型？**

**答：**

| 锁类型 | 说明 |
|-------|------|
| **Record Lock（记录锁）** | 锁定单行记录 |
| **Gap Lock（间隙锁）** | 锁定索引之间的间隙，防止幻读 |
| **Next-Key Lock** | Record Lock + Gap Lock，锁定记录及其前面的间隙 |
| **Insert Intention Lock** | 插入意向锁，特殊的间隙锁 |
| **Shared Lock（S锁）** | 共享锁，读锁 |
| **Exclusive Lock（X锁）** | 排他锁，写锁 |
| **Intention Lock** | 意向锁，表级锁，辅助判断 |

**注意：** InnoDB 的行锁是基于索引实现的，如果查询没有使用索引，会退化为表锁。

---

**Q4：什么是悲观锁和乐观锁？如何实现？**

**答：**

**悲观锁：** 假设冲突一定会发生，先加锁再操作。
```sql
-- 使用 SELECT ... FOR UPDATE
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- 执行业务逻辑
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;
```

**乐观锁：** 假设冲突不会发生，不加锁，提交时检查是否被修改。
```sql
-- 使用版本号
UPDATE accounts SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = #{old_version};
-- 如果影响行数为0，说明被其他事务修改，需要重试
```

| 对比维度 | 悲观锁 | 乐观锁 |
|---------|-------|-------|
| 加锁时机 | 读取数据时 | 提交时检查 |
| 冲突处理 | 阻塞等待 | 重试或报错 |
| 适用场景 | 写多读少、冲突频繁 | 读多写少、冲突较少 |
| 性能 | 较低（锁开销） | 较高（无锁开销） |

## 六、NoSQL 数据库

### 6.1 Redis 面试题

**Q1：Redis 为什么这么快？**

**答：**
1. **纯内存操作**：所有数据在内存中，避免磁盘 I/O
2. **单线程模型**：避免上下文切换和锁竞争（6.0 引入多线程处理网络 I/O）
3. **高效数据结构**：SDS、跳表、压缩列表等优化结构
4. **I/O 多路复用**：使用 epoll/kqueue 处理大量连接
5. **RESP 协议**：简单的文本协议，解析开销小

---

**Q2：Redis 的持久化方式有哪些？**

**答：**

| 方式 | 原理 | 优点 | 缺点 |
|-----|------|------|------|
| **RDB** | 定时生成数据快照（fork子进程） | 文件紧凑，恢复快 | 可能丢失最后一次快照后的数据 |
| **AOF** | 记录每条写命令 | 数据安全性高 | 文件大，恢复慢 |
| **混合持久化** | AOF重写时前半段为RDB，后半段为增量AOF | 兼顾安全和恢复速度 | Redis 4.0+ |

---

**Q3：Redis 的内存淘汰策略有哪些？**

**答：**

| 策略 | 说明 |
|-----|------|
| `noeviction` | 不淘汰，内存满时拒绝写入（默认） |
| `allkeys-lru` | 所有键中淘汰最近最少使用的 |
| `allkeys-lfu` | 所有键中淘汰最不经常使用的（Redis 4.0+） |
| `volatile-lru` | 设置了过期时间的键中淘汰 LRU |
| `volatile-lfu` | 设置了过期时间的键中淘汰 LFU |
| `allkeys-random` | 随机淘汰 |
| `volatile-random` | 在设置了过期时间的键中随机淘汰 |
| `volatile-ttl` | 淘汰剩余存活时间最短的键 |

---

**Q4：Redis 的缓存穿透、缓存击穿、缓存雪崩是什么？如何解决？**

**答：**

| 问题 | 描述 | 解决方案 |
|-----|------|---------|
| **缓存穿透** | 查询不存在的数据，请求直达数据库 | 布隆过滤器、缓存空值 |
| **缓存击穿** | 热点Key过期，大量请求同时到达数据库 | 互斥锁（SETNX）、逻辑过期 |
| **缓存雪崩** | 大量Key同时过期，请求全部到达数据库 | 过期时间加随机值、多级缓存、限流降级 |

---

**Q5：Redis 集群方案有哪些？**

**答：**

| 方案 | 原理 | 特点 |
|-----|------|------|
| **主从复制** | 主节点写，从节点读 | 读写分离，无自动故障转移 |
| **哨兵模式** | 监控主从，自动故障转移 | 自动切换，但写入能力有限 |
| **Cluster集群** | 16384个哈希槽分片 | 自动分片，水平扩展 |

---

### 6.2 MongoDB 面试题

**Q6：MongoDB 的文档模型有什么优势？**

**答：**
- **灵活Schema**：同一集合可以存储不同结构的文档
- **嵌套结构**：支持嵌入文档和数组，减少 JOIN
- **动态查询**：支持丰富的查询操作符
- **水平扩展**：天然支持分片

**Q7：MongoDB 的索引类型有哪些？**

**答：**
- **单字段索引**：对单个字段建索引
- **复合索引**：对多个字段建索引
- **多键索引**：对数组字段建索引
- **文本索引**：全文搜索
- **2dsphere**：地理空间查询
- **TTL索引**：自动过期删除
- **Hashed索引**：用于分片

## 七、分布式数据库

### 7.1 面试题

**Q1：什么是分布式数据库？与传统数据库有什么区别？**

**答：**
分布式数据库是将数据分散存储在多个物理节点上，通过网络协作提供统一数据库服务的系统。

| 对比维度 | 传统单机数据库 | 分布式数据库 |
|---------|-------------|------------|
| 扩展方式 | 垂直扩展（升级硬件） | 水平扩展（增加节点） |
| 数据规模 | 受限于单机容量 | 理论上无限扩展 |
| 可用性 | 单点故障 | 多副本高可用 |
| 事务 | 单机事务简单 | 分布式事务复杂 |
| 运维 | 简单 | 复杂 |

---

**Q2：什么是分布式事务？有哪些解决方案？**

**答：**
分布式事务是指跨多个数据库或服务的事务操作，需要保证 ACID 特性。

| 方案 | 原理 | 优点 | 缺点 |
|-----|------|------|------|
| **2PC（两阶段提交）** | 协调者发起准备和提交两个阶段 | 强一致性 | 同步阻塞、单点故障 |
| **3PC（三阶段提交）** | 增加CanCommit阶段，引入超时 | 减少阻塞 | 仍有单点问题 |
| **TCC** | Try-Confirm-Cancel 三阶段 | 性能好 | 业务侵入大 |
| **Saga** | 长事务拆分为多个本地事务+补偿 | 无全局锁 | 隔离性差 |
| **本地消息表** | 消息队列+本地事务 | 最终一致性 | 需要额外表 |
| **消息队列** | 异步消息保证最终一致性 | 解耦、高性能 | 只保证最终一致性 |

---

**Q3：什么是数据分片？分片策略有哪些？**

**答：**
数据分片（Sharding）是将数据水平拆分到多个数据库实例的过程。

| 策略 | 原理 | 优点 | 缺点 |
|-----|------|------|------|
| **Hash分片** | `shard = hash(key) % N` | 数据均匀 | 扩缩容困难 |
| **范围分片** | 按ID或时间范围分片 | 便于扩展 | 数据可能不均匀 |
| **一致性Hash** | 虚拟节点环 | 扩缩容友好 | 实现复杂 |
| **地理分片** | 按地理位置分片 | 就近访问 | 跨区查询困难 |

---

**Q4：什么是 NewSQL？它解决了什么问题？**

**答：**
NewSQL 是一类新兴的分布式关系数据库，旨在结合 NoSQL 的扩展性和 SQL 的 ACID 特性。

**代表产品：** TiDB、CockroachDB、OceanBase、YugabyteDB

**解决的问题：**
- 传统关系数据库扩展性差
- NoSQL 缺乏事务支持和 SQL 接口
- 云原生环境下的弹性需求

**核心特性：**
- 水平扩展能力
- SQL 支持
- ACID 事务
- 云原生架构
- 分布式一致性

## 八、综合实战题

**Q1：设计一个电商系统的数据库，需要考虑哪些方面？**

**答：**

**核心表设计：**
```sql
-- 用户表
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) NOT NULL UNIQUE,
    email VARCHAR(100) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    phone VARCHAR(20),
    status TINYINT DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_username (username),
    INDEX idx_phone (phone)
) ENGINE=InnoDB;

-- 商品表
CREATE TABLE products (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(200) NOT NULL,
    price DECIMAL(10,2) NOT NULL,
    stock INT NOT NULL DEFAULT 0,
    category_id BIGINT,
    description TEXT,
    status TINYINT DEFAULT 1,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_category (category_id),
    INDEX idx_price (price)
) ENGINE=InnoDB;

-- 订单表
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    order_no VARCHAR(32) NOT NULL UNIQUE,
    total_amount DECIMAL(10,2) NOT NULL,
    status TINYINT DEFAULT 0 COMMENT '0待支付 1已支付 2已发货 3已完成 4已取消',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_user (user_id),
    INDEX idx_order_no (order_no),
    INDEX idx_status (status)
) ENGINE=InnoDB;
```

**需要考虑的方面：**
1. **索引设计**：高频查询字段建索引，联合索引遵循最左前缀
2. **分库分表**：订单表按用户ID分片，商品表按类目分片
3. **缓存策略**：热点商品用 Redis 缓存，库存预扣减
4. **读写分离**：商品查询走从库，下单走主库
5. **数据一致性**：下单使用分布式事务或最终一致性
6. **安全**：密码哈希存储，敏感数据加密

**Q2：如何设计一个高并发的秒杀系统？**

**答：**

```text
用户请求 → CDN静态化 → Nginx限流 → 应用层限流
    → Redis预扣库存 → 消息队列异步下单 → MySQL落库
```

**关键设计：**
1. **库存预热**：活动开始前将库存加载到 Redis
2. **Redis 预扣减**：`DECR` 原子操作扣减库存
3. **异步下单**：扣减成功后发送 MQ 消息，异步创建订单
4. **限流降级**：令牌桶限流，服务降级保护
5. **防超卖**：Redis Lua 脚本保证原子性
6. **防刷单**：用户限购、IP限流、验证码

```lua
-- Redis Lua 脚本：原子扣减库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock > 0 then
    redis.call('DECR', KEYS[1])
    return 1
end
return 0
```

**Q3：数据库迁移的方案有哪些？如何保证数据一致性？**

**答：**

**迁移方案：**
1. **停机迁移**：停止服务，导出数据，导入新库（简单但影响业务）
2. **双写迁移**：同时写入新旧库，逐步切读（平滑但复杂）
3. **增量同步**：全量同步 + 增量同步（如 Canal 监听 binlog）

**双写迁移流程：**
1. 新库搭建完成
2. 全量数据同步到新库
3. 开启双写（先写旧库，异步写新库）
4. 增量数据同步（binlog 监听）
5. 数据校验
6. 逐步切读（灰度切到新库）
7. 全量切到新库
8. 停止双写，下线旧库

**Q4：如何设计一个慢查询监控系统？**

**答：**

**核心功能：**
1. **慢查询采集**：开启 MySQL 慢查询日志
2. **日志解析**：使用 pt-query-digest 或 mysqldumpslow 分析
3. **告警通知**：超过阈值发送告警（邮件/钉钉/企业微信）
4. **可视化**：Grafana + Prometheus 展示趋势
5. **自动优化建议**：基于 EXPLAIN 结果给出索引建议

**实现方案：**
```text
MySQL慢查询日志 → Filebeat采集 → Kafka → 分析服务
    → Elasticsearch存储 → Kibana展示
    → 告警规则 → 通知服务
```

**Q5：请描述你对数据库未来发展趋势的看法。**

**答：**

1. **云原生数据库**：Serverless、弹性扩缩容、按使用量付费（如 Aurora Serverless）
2. **HTAP 融合**：同时支持 OLTP 和 OLAP（如 TiDB、OceanBase）
3. **AI + 数据库**：向量数据库兴起，AI 驱动的自动调优
4. **多模数据库**：同时支持关系、文档、图、时序等多种数据模型
5. **边缘数据库**：数据在边缘节点处理，减少延迟
6. **数据库自治**：自动索引、自动扩缩容、自动故障修复

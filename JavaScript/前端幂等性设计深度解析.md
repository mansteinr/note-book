# 一、幂等性概述

## 1.1 什么是幂等性

**幂等性（Idempotency）** 源自数学概念，指一个操作执行一次和执行多次，对系统状态产生的影响完全相同。在 Web 开发语境下，即：**用户发起同一请求，无论因为何种原因（网络重试、用户连点、系统故障恢复）被执行多少次，结果都应与执行一次一致。**

```
幂等的本质：
  f(f(x)) = f(x)

  请求执行 1 次  →  结果 A
  请求执行 3 次  →  结果 A（不是 3A）
  请求执行 100 次 →  结果 A（不是 100A）
```

| 维度 | 说明 |
|------|------|
| **结果一致性** | 多次调用返回相同结果（或语义等价的结果） |
| **副作用控制** | 多次调用不会产生重复的副作用（不重复扣款、不重复下单） |
| **安全保证** | 即使网络抖动、用户误操作，系统状态依然正确 |

## 1.2 前端幂等 vs 后端幂等

前端幂等和后端幂等不是"二选一"的关系，而是**分层防御**的关系：

```
用户操作
  │
  ▼
┌─────────────────────────────────────────┐
│  前端幂等（第一道防线）                    │
│  - 按钮防抖/禁用                          │
│  - 请求去重拦截器                         │
│  - Token 获取与携带                       │
│  - 唯一请求 ID 注入                       │
│  - 超时重试控制                           │
└──────────────────┬──────────────────────┘
                   │  HTTP 请求
                   ▼
┌─────────────────────────────────────────┐
│  后端幂等（第二道防线，最终保障）            │
│  - Token 校验                            │
│  - 唯一键约束（DB 唯一索引）               │
│  - 状态机校验                            │
│  - Redis 分布式锁                       │
│  - 乐观锁版本号                          │
└─────────────────────────────────────────┘
```

| 对比项 | 前端幂等 | 后端幂等 |
|--------|----------|----------|
| **定位** | 第一道防线，减少重复请求到达后端 | 最终保障，确保数据一致性 |
| **手段** | 按钮禁用、请求拦截、Token 携带 | 唯一索引、分布式锁、状态机 |
| **可靠性** | 中等（可被绕过：Fiddler、Postman 直接调接口） | 高（数据库约束兜底） |
| **用户体验** | 直接影响（按钮灰、loading 提示） | 间接影响（返回友好错误提示） |
| **能否单独使用** | 不能（不安全，可绕过） | 能（但用户体验差，重复请求会到达后端） |
| **最佳实践** | 前后端配合，分层防御 | 前后端配合，分层防御 |

> **核心原则**：前端幂等是"锦上添花"——减少重复请求到达后端的概率、提升用户体验；后端幂等是"雪中送炭"——确保无论前端如何发请求，数据都不会错乱。两者缺一不可，但后端幂等是底线。

## 1.3 为什么前端需要幂等

前端面临重复请求的场景远比想象的多：

| 场景 | 触发原因 | 后果 |
|------|----------|------|
| **用户快速连点提交按钮** | 手抖、不确定是否点到了、 impatient | 重复下单/重复发消息 |
| **网络超时后自动重试** | Axios retry 拦截器、fetch 重试封装 | 同一请求发 N 次 |
| **页面刷新/后退后重复提交** | 浏览器重新触发已缓存请求 | 重复操作 |
| **多标签页同时操作** | 用户开了多个标签页 | 并发重复请求 |
| **双击/三击穿透** | 移动端 touch 事件穿透 | 快速多次触发 |
| **弱网下用户反复点击** | "怎么没反应，再点一下" | 多次提交 |
| **CDN/PWA 离线重放** | Service Worker 缓存请求后批量重放 | 延迟重复请求 |

## 1.4 非幂等的真实危害

```
真实案例链：
  用户下单 → 网络慢 → 用户以为没成功 → 又点了一次
    → 后端收到 2 个请求 → 创建了 2 个订单 → 用户被扣 2 次款

  更严重的：
  支付接口非幂等 → 重试 3 次 → 扣 3 次款 → 用户投诉 → 赔付

  统计：
  - 电商系统：非幂等下单导致的重复订单率约 0.1%~0.5%
  - 支付系统：非幂等导致的重复扣款是 P0 级事故
  - 消息系统：非幂等导致的消息重复发送影响用户体验
```

# 二、幂等性核心概念

## 2.1 数学定义

```
幂等（Idempotent）：
  函数 f 满足  f(f(x)) = f(x)  对所有 x 成立

  直观理解：对结果再做一次同样操作，结果不变

非幂等（Non-idempotent）：
  f(f(x)) ≠ f(x)

  示例：f(x) = x + 1
    f(1) = 2
    f(f(1)) = f(2) = 3  ← 每次执行结果不同
```

## 2.2 HTTP 语义与幂等

HTTP 协议本身对方法的幂等性有明确约定：

| HTTP 方法 | 幂等 | 安全 | 说明 |
|-----------|------|------|------|
| **GET** | ✅ 是 | ✅ 是 | 只读，不应有副作用 |
| **HEAD** | ✅ 是 | ✅ 是 | 同 GET，但不返回 body |
| **OPTIONS** | ✅ 是 | ✅ 是 | 探测服务器支持的方法 |
| **PUT** | ✅ 是 | ❌ 否 | 完整替换资源，多次执行结果一致 |
| **DELETE** | ✅ 是 | ❌ 否 | 删除资源，删第一次和第十次结果一致（已删除） |
| **POST** | ❌ 否 | ❌ 否 | 创建资源，每次执行可能创建新资源 |
| **PATCH** | ❌ 否 | ❌ 否 | 部分更新，取决于实现 |

```
关键区分：
  PUT /users/1  → { name: "张三" }
    执行 3 次：用户 1 的名字始终是 "张三"  ← 幂等

  POST /users  → { name: "张三" }
    执行 3 次：创建了 3 个名为"张三"的用户  ← 非幂等

  实际工程中：
  - 前端幂等设计主要针对 POST 请求（创建类操作）
  - DELETE 天然幂等，但前端仍应防重复（减少无效请求）
  - PUT 天然幂等，但有些 PUT 实际是 POST 伪装的（如 PUT /orders 的自增 ID）
```

## 2.3 幂等性边界：强幂等 vs 最终幂等

| 类型 | 定义 | 典型场景 | 实现难度 |
|------|------|----------|----------|
| **强幂等** | 任意时刻多次调用，结果完全一致 | 账户扣款、库存扣减 | 高（需分布式锁 + 事务） |
| **最终幂等** | 短时间窗口内多次调用结果一致，但允许有短暂的中间不一致 | 消息发送、通知推送 | 中（Token + TTL） |
| **弱幂等** | 只保证不产生重复的副作用，但返回值可能不同（如第二次返回"已处理"） | 订单查询、状态变更 | 低（唯一索引兜底） |

```
示例对比：
  强幂等：扣款 100 元
    第 1 次调用：余额 1000 → 900
    第 2 次调用：余额 900 → 900（不重复扣）
    第 3 次调用：余额 900 → 900

  弱幂等：查询订单状态
    第 1 次调用：返回 { status: "PENDING", code: 200 }
    第 2 次调用：返回 { status: "PAID", code: 200 }  ← 状态可能变了，但不会有副作用
```

## 2.4 幂等性的时间窗口

```
幂等不是永久的，需要定义"时间窗口"：

  短期幂等（秒级 / 分钟级）
  ┌──────────────────────────────────┐
  │ 请求 A（带 token-001）            │
  │   ├ 3 秒内重试 → 幂等返回        │
  │   └ 5 分钟后重试 → Token 失效    │
  └──────────────────────────────────┘
    适用：表单提交、支付、消息发送

  长期幂等（小时 / 天级）
  ┌──────────────────────────────────┐
  │ 请求 A（带业务唯一键 orderId）     │
  │   ├ 1 小时后重试 → 幂等返回       │
  │   └ 7 天后重试 → 数据库唯一键兜底 │
  └──────────────────────────────────┘
    适用：订单创建、批量导入
```

# 三、前端幂等场景分析

## 3.1 表单提交场景

```
用户填写表单 → 点击"提交" → 网络慢 → 用户再点 → 重复提交

  典型表单：注册、信息修改、审批提交

  风险：重复创建记录 / 重复审批
```

**前端策略**：
1. 提交按钮立即禁用 + loading
2. 请求去重拦截器（相同 URL + 参数指纹）
3. Token 机制（后端校验）

## 3.2 支付场景

```
用户确认支付 → 调用支付接口 → 银行处理慢 → 超时重试 → 重复扣款

  这是最高危场景，P0 级事故

  风险：重复扣款、重复入账
```

**前端策略**：
1. 支付按钮防抖 + 倒计时禁用（3 秒内不可再次点击）
2. 每次支付携带唯一 paymentId
3. 请求超时后不自动重试，而是引导用户查结果

## 3.3 订单创建场景

```
用户选好商品 → 点击"下单" → 网络超时 → 用户刷新 → 重新提交 → 重复下单

  风险：重复创建订单、重复锁定库存
```

**前端策略**：
1. 下单按钮防抖
2. 前端生成唯一 orderId（UUID），随请求携带
3. 后端 DB 唯一索引兜底

## 3.4 文件上传场景

```
用户上传大文件 → 上传到 80% 断网 → 自动断点续传 → 服务端可能收到重复的分片

  风险：文件损坏、存储浪费
```

**前端策略**：
1. 文件内容 Hash（MD5/SHA-256）作为唯一标识
2. 分片上传携带分片序号
3. 秒传判断（Hash 已存在则跳过）

## 3.5 消息发送场景

```
用户在聊天框输入消息 → 回车发送 → 网络抖动 → 自动重试 → 消息重复发送

  风险：用户体验差、消息混乱
```

**前端策略**：
1. 前端生成 messageId（UUID）
2. 发送时携带 messageId
3. 后端去重（Redis SETNX）

## 3.6 场景-策略对照表

| 场景 | 危害等级 | 推荐策略组合 | 时间窗口 |
|------|----------|-------------|----------|
| 支付扣款 | P0 | 按钮防抖 + 唯一ID + 后端分布式锁 | 长期 |
| 订单创建 | P1 | 按钮防抖 + 前端唯一ID + DB唯一索引 | 长期 |
| 表单提交 | P2 | 按钮防抖 + Token + 请求去重 | 中期 |
| 消息发送 | P2 | 唯一messageId + 后端去重 | 短期 |
| 文件上传 | P1 | 内容Hash + 分片序号 | 长期 |
| 数据查询 | P3 | 请求去重（缓存） | 短期 |
| 状态更新 | P1 | 乐观锁版本号 + 状态机 | 长期 |

# 四、前端幂等设计策略总览

## 4.1 六大策略矩阵

```
┌─────────────────────────────────────────────────────────────────────┐
│                    前端幂等六大策略                                   │
├──────────┬──────────────────────────────────────────────────────────┤
│ 策略一    │ 按钮防抖与禁用                                           │
│          │ → 最简单，用户体验层                                      │
├──────────┼──────────────────────────────────────────────────────────┤
│ 策略二    │ Token 机制                                               │
│          │ → 最经典，前后端配合                                      │
├──────────┼──────────────────────────────────────────────────────────┤
│ 策略三    │ 唯一请求 ID（Client Request ID）                         │
│          │ → 最通用，全链路追踪                                      │
├──────────┼──────────────────────────────────────────────────────────┤
│ 策略四    │ 请求去重拦截器（Axios/Fetch 封装）                       │
│          │ → 最透明，对业务零侵入                                    │
├──────────┼──────────────────────────────────────────────────────────┤
│ 策略五    │ 乐观锁与版本号                                           │
│          │ → 最精准，状态更新场景                                    │
├──────────┼──────────────────────────────────────────────────────────┤
│ 策略六    │ 组合防重复提交方案                                       │
│          │ → 最完整，生产级方案                                      │
└──────────┴──────────────────────────────────────────────────────────┘
```

## 4.2 各策略对比

| 策略 | 实现层 | 侵入性 | 可靠性 | 适用场景 | 是否需后端配合 |
|------|--------|--------|--------|----------|---------------|
| 按钮防抖 | UI 组件 | 低 | 低 | 所有提交按钮 | 否 |
| Token 机制 | 请求层 | 中 | 高 | 表单提交、关键操作 | 是 |
| 唯一请求 ID | 请求层 | 低 | 高 | 所有写操作 | 是 |
| 请求去重拦截器 | HTTP 层 | 极低 | 中 | 防止相同请求并发 | 否 |
| 乐观锁版本号 | 数据层 | 中 | 高 | 状态更新、并发编辑 | 是 |
| 组合方案 | 全栈 | 高 | 极高 | 生产级关键业务 | 是 |

# 五、策略一：按钮防抖与禁用（最基础）

## 5.1 原理

```
用户点击提交按钮
    │
    ├─ 第一次点击：触发请求 + 立即禁用按钮
    │
    ├─ 后续点击：按钮已禁用，不触发请求
    │
    └─ 请求完成（成功/失败）：恢复按钮
```

这是最简单也最常用的手段，但只能防止"同一页面同一会话"内的重复点击，无法防止网络重试、多标签页、直接调接口等场景。

## 5.2 Vue3 实现：自定义指令 v-debounce

```typescript
// src/directives/debounce.ts
import type { Directive, DirectiveBinding } from 'vue'

interface DebounceOptions {
  handler: (...args: any[]) => void
  delay?: number        // 防抖延迟（毫秒）
  immediate?: boolean   // 是否立即执行第一次
  lockDuringRequest?: boolean // 请求期间锁定
}

/**
 * v-debounce 指令
 * 用法：<el-button v-debounce="{ handler: submit, delay: 500 }">提交</el-button>
 */
const debounceDirective: Directive<HTMLElement, DebounceOptions> = {
  mounted(el: HTMLElement, binding: DirectiveBinding<DebounceOptions>) {
    const { handler, delay = 500, immediate = true, lockDuringRequest = true } = binding.value || {}

    let timer: ReturnType<typeof setTimeout> | null = null
    let isLocked = false

    el.addEventListener('click', (event: Event) => {
      event.stopPropagation()

      // 如果锁定中，直接拦截
      if (isLocked) {
        event.preventDefault()
        return
      }

      // 立即执行模式：第一次点击直接触发
      if (immediate && !timer) {
        isLocked = lockDuringRequest
        handler()
      }

      // 清除之前的定时器（防抖核心）
      if (timer) clearTimeout(timer)

      // 设置新的定时器
      timer = setTimeout(() => {
        isLocked = false
        timer = null
      }, delay)
    })
  },
  unmounted(el: HTMLElement) {
    // 清理工作由事件监听器自动完成
  },
}

export default debounceDirective
```

## 5.3 Vue3 实现：Composable useDebounce

```typescript
// src/composables/useDebounce.ts
import { ref, type Ref } from 'vue'

interface UseDebounceOptions {
  delay?: number
  leading?: boolean   // 是否在延迟开始时调用
  trailing?: boolean  // 是否在延迟结束时调用
}

/**
 * 防抖 Composable
 * 用法：
 *   const { run, cancel, pending } = useDebounce(submitForm, { delay: 1000 })
 *   run(formData)
 */
export function useDebounce<T extends (...args: any[]) => any>(
  fn: T,
  options: UseDebounceOptions = {}
) {
  const { delay = 500, leading = true, trailing = false } = options

  const pending = ref(false)
  let timer: ReturnType<typeof setTimeout> | null = null

  const run = (...args: Parameters<T>) => {
    if (pending.value) {
      // 已有请求进行中，拦截
      return
    }

    if (leading && !timer) {
      pending.value = true
      Promise.resolve(fn(...args))
        .finally(() => {
          pending.value = false
        })
    }

    if (timer) clearTimeout(timer)

    if (trailing || !leading) {
      timer = setTimeout(() => {
        if (trailing && !leading) {
          pending.value = true
          Promise.resolve(fn(...args))
            .finally(() => {
              pending.value = false
            })
        }
        timer = null
      }, delay)
    }
  }

  const cancel = () => {
    if (timer) {
      clearTimeout(timer)
      timer = null
    }
    pending.value = false
  }

  return {
    run,
    cancel,
    pending,
  } as {
    run: (...args: Parameters<T>) => void
    cancel: () => void
    pending: Ref<boolean>
  }
}
```

```typescript
// src/hooks/useDebounce.ts
import { useRef, useState, useCallback } from 'react'

interface UseDebounceOptions {
  delay?: number
  leading?: boolean
}

export function useDebounce<T extends (...args: any[]) => any>(
  fn: T,
  options: UseDebounceOptions = {}
) {
  const { delay = 500, leading = true } = options
  const [pending, setPending] = useState(false)
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null)
  const isLockedRef = useRef(false)
  const fnRef = useRef(fn)
  fnRef.current = fn

  const run = useCallback(
    (...args: Parameters<T>) => {
      if (isLockedRef.current) return

      if (leading && !timerRef.current) {
        isLockedRef.current = true
        setPending(true)
        Promise.resolve(fnRef.current(...args)).finally(() => {
          isLockedRef.current = false
          setPending(false)
        })
      }

      if (timerRef.current) clearTimeout(timerRef.current)

      timerRef.current = setTimeout(() => {
        timerRef.current = null
      }, delay)
    },
    [delay, leading]
  )

  const cancel = useCallback(() => {
    if (timerRef.current) {
      clearTimeout(timerRef.current)
      timerRef.current = null
    }
    isLockedRef.current = false
    setPending(false)
  }, [])

  return { run, cancel, pending }
}
```

## 5.5 局限性与适用边界

| 局限 | 说明 | 补充策略 |
|------|------|----------|
| 无法防止网络重试 | Axios retry 拦截器发的请求不受按钮控制 | 搭配请求去重拦截器 |
| 无法防止多标签页 | 每个标签页有独立的按钮状态 | 搭配唯一 ID / Token |
| 无法防止直接调接口 | 用户用 Postman 直接发请求 | 后端幂等兜底 |
| 无法防止浏览器后退重放 | 后退触发缓存的表单提交 | 搭配 Token + 禁用缓存 |

> **结论**：按钮防抖是**必要但不充分**的手段，必须搭配其他策略使用。

# 六、策略二：Token 机制（最经典）

## 6.1 原理与完整流程

```
Token 幂等机制核心思想：
  1. 前端在展示表单/操作页时，先向后端请求一个一次性 Token
  2. 提交请求时携带该 Token
  3. 后端校验 Token：
     - Token 有效且未被使用 → 执行业务 + 标记 Token 已用
     - Token 无效或已使用 → 返回"请勿重复提交"
  4. Token 使用后即失效（一次性）
```

## 6.2 流程图解

```
┌────────────┐                    ┌────────────┐                 ┌──────────┐
│   前端      │                    │   后端 API  │                 │  Redis   │

      │                                 │                             │
      │  ① GET /api/token               │                             │
      ├────────────────────────────────>│                             │
      │                                 │  ② SET token:abc123 EX 600  │
      │                                 ├────────────────────────────>│

      │                                 │                             │
```

## 6.3 前端 Vue3 完整实现

```typescript
// src/api/idempotent.ts
import axios, { type AxiosInstance, type AxiosRequestConfig } from 'axios'

const http: AxiosInstance = axios.create({
  baseURL: '/api',
  timeout: 10000,
})

// ==================== Token 管理 ====================

class IdempotencyTokenManager {
  private tokenKey = 'idempotency_token'
  private storage: Storage

  constructor(storage: Storage = sessionStorage) {
    this.storage = storage
  }

  /**
   * 从后端获取幂等 Token
   */
  async fetchToken(): Promise<string> {
    const res = await http.get('/token/generate')
    const token = res.data.data.token
    this.setToken(token)
    return token
  }

  /**
   * 获取当前 Token（如果没有则自动获取）
   */
  async ensureToken(): Promise<string> {
    const existing = this.getToken()
    if (existing) return existing
    return this.fetchToken()
  }

  getToken(): string | null {
    return this.storage.getItem(this.tokenKey)
  }

  setToken(token: string) {
    this.storage.setItem(this.tokenKey, token)
  }

  /**
   * 消费后清除 Token（提交成功/失败后清除，下次需重新获取）
   */
  clearToken() {
    this.storage.removeItem(this.tokenKey)
  }
}

export const tokenManager = new IdempotencyTokenManager()
```

```typescript
// src/api/http.ts —— Axios 拦截器自动注入 Token
import axios from 'axios'
import { tokenManager } from './idempotent'

const http = axios.create({ baseURL: '/api', timeout: 10000 })

// 需要幂等的接口路径白名单
const IDEMPOTENT_PATHS = ['/order/create', '/payment/pay', '/form/submit']

function isIdempotentRequired(url: string): boolean {
  return IDEMPOTENT_PATHS.some((path) => url.includes(path))
}

// 请求拦截器：自动注入 Token
http.interceptors.request.use(
  async (config) => {
    if (config.method === 'post' && isIdempotentRequired(config.url || '')) {
      try {
        const token = await tokenManager.ensureToken()
        config.headers['X-Idempotency-Token'] = token
      } catch (err) {
        console.error('[Idempotency] 获取 Token 失败', err)
      }
    }
    return config
  },
  (error) => Promise.reject(error)
)

// 响应拦截器：Token 被消费后清除
http.interceptors.response.use(
  (response) => {
    // 请求成功后清除 Token
    if (isIdempotentRequired(response.config.url || '')) {
      tokenManager.clearToken()
    }
    return response
  },
  (error) => {
    // Token 重复使用错误（409），不清除（说明已被消费）
    if (error.response?.status === 409) {
      tokenManager.clearToken()
      ElMessage.warning('请勿重复提交，请刷新页面后重试')
    }
    // 其他错误也清除 Token（让下次重新获取）
    if (error.config && isIdempotentRequired(error.config.url || '')) {
      tokenManager.clearToken()
    }
    return Promise.reject(error)
  }
)

export default http
```

## 6.4 后端 Spring Boot 配合方案

```java
// ==================== Token 生成接口 ====================
@RestController
@RequestMapping("/api/token")
public class TokenController {

    @Autowired
    private StringRedisTemplate redisTemplate;

    /**
     * 生成幂等 Token
     * 存入 Redis，TTL 10 分钟
     */
    @GetMapping("/generate")
    public Result<String> generateToken() {
        String token = UUID.randomUUID().toString().replace("-", "");
        String key = "idempotent:token:" + token;
        // SET NX + EX，保证原子性
        redisTemplate.opsForValue().set(key, "1", 10, TimeUnit.MINUTES);
        return Result.success(token);
    }
}

// ==================== 自定义注解 ====================
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface IdempotentToken {
    /** Token 请求头名称 */
    String headerName() default "X-Idempotency-Token";
    /** 错误提示消息 */
    String message() default "请勿重复提交";
}

// ==================== AOP 拦截器 ====================
@Aspect
@Component
public class IdempotentTokenAspect {

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Around("@annotation(idempotentToken)")
    public Object around(ProceedingJoinPoint joinPoint, IdempotentToken idempotentToken) throws Throwable {
        HttpServletRequest request = ((ServletRequestAttributes)
            RequestContextHolder.currentRequestAttributes()).getRequest();

        String token = request.getHeader(idempotentToken.headerName());
        if (StrUtil.isBlank(token)) {
            throw new BusinessException(400, "缺少幂等 Token");
        }

        String key = "idempotent:token:" + token;

        // ⭐ 核心操作：DEL 返回 1 说明存在（删除成功），返回 0 说明不存在
        // 用 Lua 脚本保证原子性：GET + DEL 一次完成
        String luaScript =
            "if redis.call('get', KEYS[1]) then " +
            "  redis.call('del', KEYS[1]) " +
            "  return 1 " +
            "else " +
            "  return 0 " +
            "end";

        DefaultRedisScript<Long> script = new DefaultRedisScript<>(luaScript, Long.class);
        Long result = redisTemplate.execute(script, Collections.singletonList(key));

        if (result == null || result == 0) {
            // Token 不存在 → 已被消费过 → 拒绝
            throw new BusinessException(409, idempotentToken.message());
        }

        // Token 校验通过，执行业务
        return joinPoint.proceed();
    }
}

// ==================== 业务接口使用 ====================
@RestController
@RequestMapping("/api/order")
public class OrderController {

    @Autowired
    private OrderService orderService;

    @PostMapping("/create")
    @IdempotentToken  // ← 一行注解搞定幂等校验
    public Result<Order> createOrder(@RequestBody OrderDTO dto) {
        Order order = orderService.createOrder(dto);
        return Result.success(order);
    }
}
```

## 6.5 Token 存储与失效策略

| 存储方式 | 优点 | 缺点 | 推荐场景 |
|----------|------|------|----------|
| **sessionStorage** | 标签页隔离，关闭即清除 | 不跨标签页 | 表单提交 |
| **localStorage** | 跨标签页共享 | 需手动清理 | 跨页面操作 |
| **内存（Map/变量）** | 最快，无序列化 | 刷新丢失 | SPA 单页操作 |
| **Cookie** | 自动携带 | 大小受限、跨域问题 | 不推荐 |

```typescript
// 智能存储策略：优先内存，降级 sessionStorage
class SmartTokenStorage {
  private memoryToken: string | null = null
  private fallback: Storage

  constructor() {
    this.fallback = typeof sessionStorage !== 'undefined' ? sessionStorage : {
      getItem: () => null,
      setItem: () => {},
      removeItem: () => {},
    } as Storage
  }

  getToken(): string | null {
    return this.memoryToken || this.fallback.getItem('idempotency_token')
  }

  setToken(token: string) {
    this.memoryToken = token
    this.fallback.setItem('idempotency_token', token)
  }

  clearToken() {
    this.memoryToken = null
    this.fallback.removeItem('idempotency_token')
  }
}
```

## 6.6 Token 机制的异常处理

```
异常场景与处理策略：

  ① Token 获取失败
     → 前端：提示"系统繁忙"，禁止提交
     → 后端：无 Token 的请求直接拒绝

  ② Token 过期（TTL 到了）
     → 前端：提交前检查 Token 是否还在，不在则重新获取
     → 实现：提交前 await ensureToken()

  ③ Token 被使用但请求失败了
     → 问题：Token 已被后端消费（DEL 了），但业务执行失败了
     → 处理：让用户重新提交（会获取新 Token）
     → 优化：后端在 Token DEL 之后执行业务，如果业务失败可以回滚 Token
     → 更优：后端用 Lua 脚本，Token DEL 和业务在同一事务中

  ④ 网络超时，不确定请求是否到达后端
     → 前端：不自动重试（Token 已发，重试会被拒）
     → 引导用户查询结果，确认后再决定是否重新提交
```

```java
// 后端优化：Token 校验 + 业务执行 + 失败回滚
@Around("@annotation(idempotentToken)")
public Object around(ProceedingJoinPoint joinPoint, IdempotentToken idempotentToken) throws Throwable {
    // ... Token 校验同上 ...

    String key = "idempotent:token:" + token;

    try {
        // 执行业务
        Object result = joinPoint.proceed();
        return result;
    } catch (Throwable e) {
        // 业务执行失败，恢复 Token（让用户可以重试）
        redisTemplate.opsForValue().set(key, "1", 10, TimeUnit.MINUTES);
        throw e;
    }
}
```

# 七、策略三：唯一请求 ID 机制

## 7.1 原理

```
唯一请求 ID（Client Request ID / Trace ID）机制：
  1. 前端在发起请求前生成一个全局唯一 ID（UUID / 雪花 ID）
  2. 将 ID 放入请求头 X-Request-Id
  3. 后端收到请求后用 Redis SETNX 判断是否处理过
     - SETNX 成功 → 第一次请求 → 正常处理
     - SETNX 失败 → 重复请求 → 返回已有结果或拒绝
  4. 同一 RequestId 的请求只会被处理一次
```

```
与 Token 机制的区别：
  Token：    后端生成 Token → 前端携带 → 后端校验（需要额外一次获取 Token 的请求）
  RequestId：前端生成 ID   → 直接携带 → 后端校验（无额外请求，更轻量）

  Token 更安全（后端控制 Token 的发放和有效性）
  RequestId 更轻量（无额外请求，适合全量接口覆盖）
```

## 7.2 ID 生成策略

```typescript
// src/utils/requestId.ts

/**
 * 方案 1：UUID v4（最通用）
 */
function uuidv4(): string {
  // 优先使用原生 crypto.randomUUID（浏览器支持）
  if (typeof crypto !== 'undefined' && crypto.randomUUID) {
    return crypto.randomUUID()
  }
  // 降级：手动生成
  return 'xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx'.replace(/[xy]/g, (c) => {
    const r = (Math.random() * 16) | 0
    const v = c === 'x' ? r : (r & 0x3) | 0x8
    return v.toString(16)
  })
}

/**
 * 方案 2：时间戳 + 随机数（可排序，适合日志排查）
 * 格式：YYYYMMDDHHmmssSSS-random6
 */
function timestampId(): string {
  const now = new Date()
  const ts = [
    now.getFullYear(),
    String(now.getMonth() + 1).padStart(2, '0'),
    String(now.getDate()).padStart(2, '0'),
    String(now.getHours()).padStart(2, '0'),
    String(now.getMinutes()).padStart(2, '0'),
    String(now.getSeconds()).padStart(2, '0'),
    String(now.getMilliseconds()).padStart(3, '0'),
  ].join('')
  const random = Math.random().toString(36).substring(2, 8)
  return `${ts}-${random}`
}

/**
 * 方案 3：业务唯一键（最推荐，与业务关联）
 * 示例：order-create-{userId}-{timestamp}-{random}
 */
function businessRequestId(prefix: string, userId: string | number): string {
  const ts = Date.now()
  const random = Math.random().toString(36).substring(2, 8)
  return `${prefix}-${userId}-${ts}-${random}`
}

/**
 * 统一出口
 */
export function generateRequestId(prefix?: string, userId?: string | number): string {
  if (prefix && userId !== undefined) {
    return businessRequestId(prefix, userId)
  }
  return uuidv4()
}
```

## 7.4 后端去重实现（Redis + Spring Boot）

```java
// ==================== 自定义注解 ====================
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    /** Request ID 请求头名 */
    String headerName() default "X-Request-Id";
    /** 幂等 key 前缀 */
    String prefix() default "idempotent:req:";
    /** 过期时间（秒），默认 24 小时 */
    int expireSeconds() default 86400;
    /** 重复请求时的消息 */
    String message() default "请勿重复提交";
}

// ==================== AOP 实现 ====================
@Aspect
@Component
@Slf4j
public class IdempotentAspect {

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Around("@annotation(idempotent)")
    public Object around(ProceedingJoinPoint joinPoint, Idempotent idempotent) throws Throwable {
        HttpServletRequest request = ((ServletRequestAttributes)
            RequestContextHolder.currentRequestAttributes()).getRequest();

        String requestId = request.getHeader(idempotent.headerName());
        if (StrUtil.isBlank(requestId)) {
            // 没有携带 Request-Id，放行（兼容旧客户端）
            log.warn("[Idempotent] 缺少 Request-Id，放行: {}", request.getRequestURI());
            return joinPoint.proceed();
        }

        String key = idempotent.prefix() + requestId;

        // ⭐ 原子操作：SETNX + EX（不存在则设置，并设置过期时间）
        String luaScript =
            "if redis.call('setnx', KEYS[1], ARGV[1]) == 1 then " +
            "  redis.call('expire', KEYS[1], ARGV[2]) " +
            "  return 1 " +
            "else " +
            "  return 0 " +
            "end";

        DefaultRedisScript<Long> script = new DefaultRedisScript<>(luaScript, Long.class);
        Long result = redisTemplate.execute(
            script,
            Collections.singletonList(key),
            "1",
            String.valueOf(idempotent.expireSeconds())
        );

        if (result == null || result == 0) {
            // SETNX 失败 → 已存在 → 重复请求
            log.warn("[Idempotent] 重复请求被拦截, Request-Id: {}", requestId);
            throw new BusinessException(409, idempotent.message());
        }

        try {
            // 首次请求，正常执行业务
            Object resultObj = joinPoint.proceed();
            return resultObj;
        } catch (Throwable e) {
            // 业务执行失败，删除 key 允许重试
            redisTemplate.delete(key);
            log.info("[Idempotent] 业务失败，已清除幂等标记, Request-Id: {}", requestId);
            throw e;
        }
    }
}

// ==================== 业务使用 ====================
@RestController
@RequestMapping("/api/payment")
public class PaymentController {

    @PostMapping("/pay")
    @Idempotent(expireSeconds = 3600, message = "请勿重复支付")  // ← 1 小时内幂等
    public Result<PaymentResult> pay(@RequestBody PaymentDTO dto) {
        return Result.success(paymentService.pay(dto));
    }
}
```

# 八、策略四：请求去重拦截器

## 8.1 原理

```
请求去重拦截器核心思想：
  在 HTTP 客户端层面，对"相同请求"进行去重。
  相同请求 = 相同 URL + 相同 Method + 相同参数

  如果有相同请求正在进行中 → 不发新请求，复用已有的 Promise
  如果有相同请求已完成（缓存窗口内）→ 直接返回缓存结果
```

```
场景：
  用户快速连点"查询" → 3 个相同请求同时发出
  去重后：只发 1 个请求，3 个调用者共享同一个 Promise

  用户在 500ms 内点了 5 次"提交" →
  去重后：只发 1 次，其余 4 次被拦截
```

## 8.2 请求指纹生成

```typescript
// src/utils/requestFingerprint.ts

/**
 * 生成请求指纹（用于判断请求是否相同）
 * 策略：method + url + 序列化参数
 */
export function getRequestFingerprint(
  method: string,
  url: string,
  data?: any,
  params?: any
): string {
  // 序列化规则：
  // 1. 排序 key（保证 { a: 1, b: 2 } 和 { b: 2, a: 1 } 指纹一致）
  // 2. 忽略函数、Symbol、undefined
  // 3. 忽略时间戳字段（如 _t）避免每次都不同

  const serialize = (obj: any): string => {
    if (obj === null || obj === undefined) return ''
    if (typeof obj !== 'object') return String(obj)

    const sortedKeys = Object.keys(obj)
      .filter((k) => !['_t', '_timestamp', 'nonce'].includes(k)) // 忽略随机字段
      .sort()

    return sortedKeys
      .map((k) => {
        const val = obj[k]
        if (typeof val === 'object') return `${k}:${serialize(val)}`
        return `${k}:${val}`
      })
      .join('|')
  }

  const parts = [
    method.toUpperCase(),
    url,
    serialize(data),
    serialize(params),
  ].filter(Boolean)

  return parts.join('::')
}
```

## 8.3 Axios 拦截器完整实现

```typescript
// src/api/requestDedup.ts
import axios, {
  type AxiosInstance,
  type AxiosRequestConfig,
  type AxiosResponse,
  type InternalAxiosRequestConfig,
} from 'axios'
import { getRequestFingerprint } from '@/utils/requestFingerprint'

// 进行中的请求 Map（指纹 → Promise）
const pendingRequests = new Map<string, AbortController>()

// 已完成的请求缓存（指纹 → { data, timestamp }）
const responseCache = new Map<string, { data: any; timestamp: number; ttl: number }>()

interface DedupOptions {
  /** 是否启用去重 */
  enableDedup?: boolean
  /** 缓存 TTL（毫秒），0 表示不缓存只去重进行中请求 */
  cacheTTL?: number
}

// 扩展 AxiosRequestConfig 支持 dedup 配置
declare module 'axios' {
  interface AxiosRequestConfig {
    dedup?: DedupOptions
  }
}

const http: AxiosInstance = axios.create({
  baseURL: '/api',
  timeout: 10000,
})

// ==================== 请求拦截器 ====================
http.interceptors.request.use(
  (config: InternalAxiosRequestConfig) => {
    const dedupConfig = config.dedup ?? { enableDedup: false }

    if (!dedupConfig.enableDedup) return config

    const fingerprint = getRequestFingerprint(
      config.method || 'get',
      config.url || '',
      config.data,
      config.params
    )

    // ① 检查是否有相同请求正在进行
    const existing = pendingRequests.get(fingerprint)
    if (existing) {
      // 已有相同请求 → 返回一个永远 pending 的 Promise（被 abort）
      // 实际上 Axios 会用 AbortController 取消
      console.log(`[Dedup] 拦截重复请求: ${config.url}`)
      return Promise.reject(new axios.Cancel('请求去重：已有相同请求进行中'))
    }

    // ② 检查缓存
    if (dedupConfig.cacheTTL && dedupConfig.cacheTTL > 0) {
      const cached = responseCache.get(fingerprint)
      if (cached && Date.now() - cached.timestamp < cached.ttl) {
        console.log(`[Dedup] 命中缓存: ${config.url}`)
        // 返回缓存数据（构造一个假响应）
        return Promise.reject({
          __cached: true,
          data: cached.data,
        })
      }
    }

    // ③ 注册新请求
    const controller = new AbortController()
    config.signal = controller.signal
    pendingRequests.set(fingerprint, controller)

    // 把指纹存到 config 上，响应拦截器要用
    ;(config as any).__fingerprint = fingerprint
    ;(config as any).__dedupConfig = dedupConfig

    return config
  },
  (error) => Promise.reject(error)
)

// ==================== 响应拦截器 ====================
http.interceptors.response.use(
  (response: AxiosResponse) => {
    const fingerprint = (response.config as any).__fingerprint
    const dedupConfig = (response.config as any).__dedupConfig

    if (fingerprint) {
      // 请求完成，从 pending 中移除
      pendingRequests.delete(fingerprint)

      // 如果配置了缓存，存入缓存
      if (dedupConfig?.cacheTTL && dedupConfig.cacheTTL > 0) {
        responseCache.set(fingerprint, {
          data: response.data,
          timestamp: Date.now(),
          ttl: dedupConfig.cacheTTL,
        })
      }
    }

    return response
  },
  (error) => {
    // 缓存命中时返回缓存数据
    if (error?.__cached) {
      return Promise.resolve({ data: error.data, status: 200, __fromCache: true })
    }

    // 取消的请求不处理
    if (axios.isCancel(error)) {
      return Promise.reject(error)
    }

    // 从 pending 中移除失败的请求
    const fingerprint = (error.config as any)?.__fingerprint
    if (fingerprint) {
      pendingRequests.delete(fingerprint)
    }

    return Promise.reject(error)
  }
)

// ==================== 清除缓存 ====================
export function clearDedupCache() {
  responseCache.clear()
  pendingRequests.forEach((controller) => controller.abort())
  pendingRequests.clear()
}

export default http
```

## 8.4 Fetch 封装实现

```typescript
// src/api/fetchDedup.ts

const pendingFetch = new Map<string, Promise<Response>>()

interface DedupFetchOptions extends RequestInit {
  dedup?: boolean
  dedupTTL?: number
}

const responseCacheFetch = new Map<string, { response: Response; timestamp: number; ttl: number }>()

/**
 * 带去重的 Fetch 封装
 */
export async function dedupFetch(
  input: string,
  options: DedupFetchOptions = {}
): Promise<Response> {
  const { dedup = false, dedupTTL = 0, ...fetchOptions } = options

  if (!dedup) {
    return fetch(input, fetchOptions)
  }

  const method = (fetchOptions.method || 'GET').toUpperCase()
  const fingerprint = `${method}::${input}::${JSON.stringify(fetchOptions.body || '')}`

  // 检查缓存
  if (dedupTTL > 0) {
    const cached = responseCacheFetch.get(fingerprint)
    if (cached && Date.now() - cached.timestamp < cached.ttl) {
      return cached.response.clone()
    }
  }

  // 检查是否有进行中的相同请求
  const existing = pendingFetch.get(fingerprint)
  if (existing) {
    // 等待已有的请求完成
    return existing.then((res) => res.clone())
  }

  // 发起新请求
  const promise = fetch(input, fetchOptions)
  pendingFetch.set(fingerprint, promise)

  try {
    const response = await promise

    // 存入缓存
    if (dedupTTL > 0) {
      responseCacheFetch.set(fingerprint, {
        response: response.clone(),
        timestamp: Date.now(),
        ttl: dedupTTL,
      })
    }

    return response
  } finally {
    pendingFetch.delete(fingerprint)
  }
}
```

## 8.5 拦截器去重的局限

| 局限 | 说明 | 解决方案 |
|------|------|----------|
| 无法跨页面/标签 | 每个页面有自己的内存 Map | 搭配 BroadcastChannel 或后端去重 |
| 刷新页面失效 | 内存中的 Map 清空 | 搭配 Token / 唯一 ID |
| 无法防止有意的重复 | 用户修改参数绕过去重 | 后端幂等兜底 |
| GET 去重可能返回旧数据 | 缓存的响应可能不是最新 | GET 去重 TTL 设短（1~5 秒） |

# 九、策略五：乐观锁与版本号机制

## 9.1 原理

```
乐观锁核心思想：
  给数据加版本号（version），每次更新时校验版本号是否变化。
  如果版本号不匹配 → 说明数据已被其他人修改 → 拒绝本次更新。

  适用于：状态更新、并发编辑、防止覆盖
```

```
流程：
  ① 前端加载数据时获取当前 version：GET /api/order/123 → { id: 123, status: "PENDING", version: 3 }
  ② 用户修改后提交：PUT /api/order/123 → { status: "PAID", version: 3 }
  ③ 后端校验：
     - 数据库当前 version = 3 → 匹配 → 更新成功，version → 4
     - 数据库当前 version = 4 → 不匹配 → 返回 409 "数据已被修改，请刷新后重试"
  ④ 如果其他人已经更新过（version=4），当前提交会被拒绝
```

## 10.1 组合策略设计

```typescript
 *
 * 用法：
 * <el-button v-submit-lock="{ handler: submit, lockTime: 1000 }">提交</el-button>
 */
export const submitLockDirective: Directive<HTMLElement, SubmitLockOptions> = {
  mounted(el: HTMLElement, binding: DirectiveBinding<SubmitLockOptions>) {
    const {
      handler,
      lockTime = 1000,
      autoUnlock = true,
      loadingText = '提交中...',
    } = binding.value || {}

    let isLocked = false
    let lockTimer: ReturnType<typeof setTimeout> | null = null
    const originalText = el.textContent || ''

    const setLocked = (locked: boolean) => {
      isLocked = locked
      if (locked) {
        el.setAttribute('disabled', 'true')
        el.classList.add('is-loading')
        el.textContent = loadingText
      } else {
        el.removeAttribute('disabled')
        el.classList.remove('is-loading')
        el.textContent = originalText
      }
    }

    el.addEventListener('click', async (event: Event) => {
      if (isLocked) {
        event.preventDefault()
        event.stopPropagation()
        return
      }

      setLocked(true)

      // 最小锁定时间（即使请求很快返回，也至少锁定 lockTime 毫秒）
      if (lockTimer) clearTimeout(lockTimer)
      lockTimer = setTimeout(() => {
        if (autoUnlock && !isLocked) return
      }, lockTime)

      try {
        await handler()
        if (autoUnlock) {
          // 确保至少锁定 lockTime 毫秒
          setTimeout(() => setLocked(false), Math.max(0, lockTime))
        }
      } catch (error) {
        // 出错后解锁，让用户可以重试
        setTimeout(() => setLocked(false), Math.max(0, lockTime))
        console.error('[SubmitLock] 请求失败', error)
      }
    })
  },
}
```

```typescript
  lockTime?: number
  loadingText?: string
}

export function useSubmitLock<T extends (...args: any[]) => Promise<any>>(
  handler: T,
  options: UseSubmitLockOptions = {}
) {
  const { lockTime = 1000 } = options
  const [isLocked, setIsLocked] = useState(false)
  const [loading, setLoading] = useState(false)
  const lockRef = useRef(false)
  const minLockTimer = useRef<ReturnType<typeof setTimeout> | null>(null)
  const handlerRef = useRef(handler)
  handlerRef.current = handler

  const run = useCallback(
    async (...args: Parameters<T>) => {
      if (lockRef.current) return

      lockRef.current = true
      setIsLocked(true)
      setLoading(true)

      // 最小锁定时间
      if (minLockTimer.current) clearTimeout(minLockTimer.current)
      minLockTimer.current = setTimeout(() => {
        // 最小锁定时间到了，但还需要等请求完成
      }, lockTime)

      try {
        await handlerRef.current(...args)
      } catch (error) {
        console.error('[SubmitLock] 请求失败', error)
      } finally {
        // 确保至少锁定 lockTime 毫秒
        const elapsed = Date.now()
        const minEnd = Date.now() + lockTime
        const delay = Math.max(0, minEnd - elapsed)

        setTimeout(() => {
          lockRef.current = false
          setIsLocked(false)
          setLoading(false)
        }, delay)
      }
    },
    [lockTime]
  )

  return { run, isLocked, loading }
}
```

```typescript
import http from '@/api/http'
import { generateRequestId } from '@/utils/requestId'
import { tokenManager } from '@/api/idempotent'

interface SafeRequestOptions {
  /** 是否需要 Token 幂等 */
  withToken?: boolean
  /** 是否需要唯一 Request-Id */
  withRequestId?: boolean
  /** 是否去重（拦截并发相同请求） */
  dedup?: boolean
}

/**
 * 安全请求封装（组合多种幂等策略）
 */
export async function safePost<T = any>(
  url: string,
  data?: any,
  options: SafeRequestOptions = {}
): Promise<T> {
  const { withToken = false, withRequestId = true, dedup = true } = options

  const headers: Record<string, string> = {}

  // 注入唯一 Request-Id
  if (withRequestId) {
    headers['X-Request-Id'] = generateRequestId()
  }

  // 注入 Token
  if (withToken) {
    const token = await tokenManager.ensureToken()
    headers['X-Idempotency-Token'] = token
  }

  const res = await http.post(url, data, {
    headers,
    dedup: dedup ? { enableDedup: true } : undefined,
  })

  // 消费 Token
  if (withToken) {
    tokenManager.clearToken()
  }

  return res.data
}
```

```typescript
// src/composables/useIdempotent.ts —— 统一幂等提交 Composable
import { ref } from 'vue'
import { generateRequestId } from '@/utils/requestId'
import { tokenManager } from '@/api/idempotent'
import http from '@/api/http'

interface UseIdempotentOptions {
  /** 幂等策略 */
  strategy: 'token' | 'requestId' | 'both'
  /** Token 获取方式：manual = 手动获取, auto = 自动获取 */
  tokenMode?: 'manual' | 'auto'
  /** 去重 */
  dedup?: boolean
  /** 最小锁定时间（毫秒） */
  lockTime?: number
}

/**
 * 统一幂等提交 Composable
 *
 * 用法：
 * const { submit, loading, error } = useIdempotent({
 *   strategy: 'both',
 *   dedup: true,
 *   lockTime: 1500,
 * })
 *
 * submit('/api/order/create', formData)
 */
export function useIdempotent(options: UseIdempotentOptions) {
  const { strategy, tokenMode = 'auto', dedup = true, lockTime = 1000 } = options

  const loading = ref(false)
  const error = ref<Error | null>(null)
  const data = ref<any>(null)

  let isLocked = false

  const submit = async (url: string, payload?: any) => {
    if (isLocked || loading.value) {
      console.warn('[Idempotent] 请求被锁定拦截')
      return null
    }

    isLocked = true
    loading.value = true
    error.value = null

    const headers: Record<string, string> = {}

    try {
      // 注入 Token
      if (strategy === 'token' || strategy === 'both') {
        if (tokenMode === 'auto') {
          await tokenManager.fetchToken()
        }
        const token = tokenManager.getToken()
        if (token) headers['X-Idempotency-Token'] = token
      }

      // 注入 Request-Id
      if (strategy === 'requestId' || strategy === 'both') {
        headers['X-Request-Id'] = generateRequestId()
      }

      const res = await http.post(url, payload, {
        headers,
        dedup: dedup ? { enableDedup: true } : undefined,
      })

      data.value = res.data

      // 消费 Token
      if (strategy === 'token' || strategy === 'both') {
        tokenManager.clearToken()
      }

      return res.data
    } catch (err: any) {
      error.value = err

      if (err.response?.status === 409) {
        // 幂等冲突
        console.warn('[Idempotent] 重复请求被后端拒绝')
      }

      throw err
    } finally {
      // 最小锁定时间
      setTimeout(() => {
        isLocked = false
        loading.value = false
      }, lockTime)
    }
  }

  return { submit, loading, error, data }
}
```

```java
// ==================== 1. 统一注解 ====================
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Idempotent {
    /** 幂等策略 */
    IdempotentStrategy strategy() default IdempotentStrategy.REQUEST_ID;

    /** Request-Id 或 Token 的请求头名 */
    String headerName() default "X-Request-Id";

    /** Redis key 前缀 */
    String prefix() default "idempotent:";

    /** 过期时间（秒） */
    int expireSeconds() default 86400;

    /** 重复请求提示消息 */
    String message() default "请勿重复提交";
}

public enum IdempotentStrategy {
    REQUEST_ID,  // 唯一请求 ID
    TOKEN,       // Token 机制
    BOTH         // 两者都校验
}

// ==================== 2. AOP 切面 ====================
@Aspect
@Component
@Slf4j
public class IdempotentAspect {

    @Autowired
    private StringRedisTemplate redisTemplate;

    @Autowired
    private IdempotentKeyGenerator keyGenerator;

    @Around("@annotation(idempotent)")
    public Object around(ProceedingJoinPoint joinPoint, Idempotent idempotent) throws Throwable {
        HttpServletRequest request = getRequest();

        // 生成幂等 key
        String key = keyGenerator.generate(request, idempotent);

        if (StrUtil.isBlank(key)) {
            // 无法生成 key（缺少请求头），放行或拒绝
            log.warn("[Idempotent] 无法生成幂等 key，放行: {}", request.getRequestURI());
            return joinPoint.proceed();
        }

        // 原子操作：SETNX + EX
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(key, "1", idempotent.expireSeconds(), TimeUnit.SECONDS);

        if (Boolean.FALSE.equals(acquired)) {
            // key 已存在 → 重复请求
            log.warn("[Idempotent] 重复请求拦截: key={}", key);
            throw new BusinessException(409, idempotent.message());
        }

        try {
            // 执行业务
            return joinPoint.proceed();
        } catch (Throwable e) {
            // 业务失败，清除 key 允许重试
            redisTemplate.delete(key);
            log.info("[Idempotent] 业务失败，清除幂等标记: key={}", key);
            throw e;
        }
    }

    private HttpServletRequest getRequest() {
        return ((ServletRequestAttributes) RequestContextHolder.currentRequestAttributes()).getRequest();
    }
}

// ==================== 3. Key 生成器 ====================
@Component
public class IdempotentKeyGenerator {

    public String generate(HttpServletRequest request, Idempotent idempotent) {
        IdempotentStrategy strategy = idempotent.strategy();

        if (strategy == IdempotentStrategy.REQUEST_ID || strategy == IdempotentStrategy.BOTH) {
            String requestId = request.getHeader("X-Request-Id");
            if (StrUtil.isNotBlank(requestId)) {
                return idempotent.prefix() + "req:" + requestId;
            }
        }

        if (strategy == IdempotentStrategy.TOKEN || strategy == IdempotentStrategy.BOTH) {
            String token = request.getHeader("X-Idempotency-Token");
            if (StrUtil.isNotBlank(token)) {
                return idempotent.prefix() + "token:" + token;
            }
        }

        return null;
    }
}
```

## 12.1 文件上传幂等

```typescript
// src/utils/fileHash.ts —— 文件内容 Hash 实现秒传 + 断点续传
import SparkMD5 from 'spark-md5'

/**
 * 计算文件 MD5 Hash（用于秒传判断）
 */
export async function calculateFileHash(file: File, onProgress?: (percent: number) => void): Promise<string> {
  return new Promise((resolve, reject) => {
    const chunkSize = 2 * 1024 * 1024 // 2MB 分片读取
    const chunks = Math.ceil(file.size / chunkSize)
    const spark = new SparkMD5.ArrayBuffer()
    const reader = new FileReader()

    let currentChunk = 0

    reader.onload = (e) => {
      spark.append(e.target!.result as ArrayBuffer)
      currentChunk++
      onProgress?.(Math.round((currentChunk / chunks) * 100))

      if (currentChunk < chunks) {
        loadNext()
      } else {
        resolve(spark.end())
      }
    }

    reader.onerror = (e) => reject(e)

    const loadNext = () => {
      const start = currentChunk * chunkSize
      const end = Math.min(start + chunkSize, file.size)
      reader.readAsArrayBuffer(file.slice(start, end))
    }

    loadNext()
  })
}

/**
 * 分片上传（每个分片携带序号 + 文件 Hash）
 */
export async function uploadFileChunked(
  file: File,
  uploadUrl: string,
  onProgress?: (percent: number) => void
) {
  // 1. 计算文件 Hash
  const fileHash = await calculateFileHash(file, onProgress)

  // 2. 检查是否已上传（秒传）
  const checkRes = await fetch(`${uploadUrl}/check?hash=${fileHash}`)
  const { exists, url } = await checkRes.json()
  if (exists) {
    return { fileHash, url, skip: true }  // 秒传成功
  }

  // 3. 分片上传
  const chunkSize = 5 * 1024 * 1024 // 5MB
  const chunks = Math.ceil(file.size / chunkSize)

  for (let i = 0; i < chunks; i++) {
    const start = i * chunkSize
    const end = Math.min(start + chunkSize, file.size)
    const blob = file.slice(start, end)

    // 每个分片携带文件 Hash + 分片序号（幂等：重复上传同一分片不会出错）
    const formData = new FormData()
    formData.append('file', blob)
    formData.append('hash', fileHash)
    formData.append('chunkIndex', String(i))
    formData.append('totalChunks', String(chunks))
    formData.append('fileName', file.name)

    await fetch(uploadUrl, {
      method: 'POST',
      body: formData,
      headers: { 'X-Request-Id': `${fileHash}-${i}` }, // 每分片唯一 ID
    })

    onProgress?.(Math.round(((i + 1) / chunks) * 100))
  }

  // 4. 通知后端合并分片
  await fetch(`${uploadUrl}/merge`, {
    method: 'POST',

  })

  return { fileHash, url: `${uploadUrl}/${fileHash}`, skip: false }
```

## 12.2 弱网/超时重试幂等

```typescript
// src/api/safeRetry.ts —— 安全的重试封装（重试时保持幂等）
import http from '@/api/http'
import { generateRequestId } from '@/utils/requestId'

interface SafeRetryOptions {
  maxRetries?: number
  retryDelay?: number
  timeout?: number
}

/**
 * 安全重试：重试时使用相同的 Request-Id（保证幂等）
 *
 * 关键点：
 * 1. 同一个请求的重试使用相同的 Request-Id
 * 2. 后端通过 Request-Id 去重，重试不会产生副作用
 * 3. 只有 5xx / 超时才重试，4xx 不重试（业务错误）
 */
export async function safeRetryRequest(
  url: string,
  data?: any,
  options: SafeRetryOptions = {}
): Promise<any> {
  const { maxRetries = 3, retryDelay = 1000, timeout = 10000 } = options

  // 生成唯一 Request-Id，所有重试复用
  const requestId = generateRequestId()

  let lastError: Error | null = null

  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const res = await http.post(url, data, {
        timeout,
        headers: { 'X-Request-Id': requestId }, // ⭐ 重试复用同一 ID
      })
      return res.data
    } catch (err: any) {
      lastError = err

      // 409 = 幂等冲突（请求已处理过）→ 不重试，直接返回
      if (err.response?.status === 409) {
        console.log('[SafeRetry] 请求已处理，无需重试')
        return err.response.data
      }

      // 4xx 业务错误 → 不重试
      if (err.response?.status >= 400 && err.response?.status < 500) {
        throw err
      }

      // 最后一次重试也失败了
      if (attempt === maxRetries) {
        console.error(`[SafeRetry] 重试 ${maxRetries} 次后仍失败: ${url}`)
        throw err
      }

      // 等待后重试（指数退避）
      const delay = retryDelay * Math.pow(2, attempt)
      console.warn(`[SafeRetry] 第 ${attempt + 1} 次重试，等待 ${delay}ms`)
      await new Promise((resolve) => setTimeout(resolve, delay))
    }
  }

  throw lastError!
}
```

```typescript
// src/utils/offlineQueue.ts —— 离线请求队列（断网后排队，恢复后提交）
import { generateRequestId } from '@/utils/requestId'

const DB_NAME = 'offline_queue'
const STORE_NAME = 'pending_requests'

// 打开 IndexedDB
function openDB(): Promise<IDBDatabase> {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open(DB_NAME, 1)
    request.onerror = () => reject(request.error)
    request.onsuccess = () => resolve(request.result)
    request.onupgradeneeded = (event) => {
      const db = (event.target as IDBOpenDBRequest).result
      if (!db.objectStoreNames.contains(STORE_NAME)) {
        db.createObjectStore(STORE_NAME, { keyPath: 'requestId' })
      }
    }
  })
}

interface QueuedRequest {
  requestId: string
  url: string
  method: string
  body: any
  headers: Record<string, string>
  timestamp: number
}

// 入队（离线时调用）
export async function enqueueRequest(req: Omit<QueuedRequest, 'requestId' | 'timestamp'>) {
  const db = await openDB()
  const tx = db.transaction(STORE_NAME, 'readwrite')
  const item: QueuedRequest = {
    ...req,
    requestId: generateRequestId(),  // ⭐ 生成唯一 ID
    timestamp: Date.now(),
  }
  tx.objectStore(STORE_NAME).add(item)
  return item
}

// 出队并提交（网络恢复后调用）
export async function flushQueue() {
  const db = await openDB()
  const tx = db.transaction(STORE_NAME, 'readonly')
  const all: QueuedRequest[] = await new Promise((resolve) => {
    const req = tx.objectStore(STORE_NAME).getAll()
    req.onsuccess = () => resolve(req.result)
  })

  for (const item of all) {
    try {
      await fetch(item.url, {
        method: item.method,
        body: JSON.stringify(item.body),
        headers: {
          'Content-Type': 'application/json',
          'X-Request-Id': item.requestId,  // ⭐ 携带唯一 ID 保证幂等
          ...item.headers,
        },
      })
      // 成功后从队列删除
      const delTx = db.transaction(STORE_NAME, 'readwrite')
      delTx.objectStore(STORE_NAME).delete(item.requestId)
    } catch (err) {
      console.error(`[OfflineQueue] 提交失败: ${item.requestId}`, err)
      // 失败的留在队列里，下次重试
    }
  }
}

// 监听网络恢复
window.addEventListener('online', () => {
  console.log('[OfflineQueue] 网络恢复，开始提交队列')
  flushQueue()
})
```

```typescript
const CHANNEL_NAME = 'submit_lock'

class CrossTabSubmitLock {
  private channel: BroadcastChannel
  private lockedKeys = new Set<string>()

  constructor() {
    if (typeof BroadcastChannel !== 'undefined') {
      this.channel = new BroadcastChannel(CHANNEL_NAME)
      this.channel.onmessage = (event) => {
        const { type, key } = event.data
        if (type === 'lock') {
          this.lockedKeys.add(key)
        } else if (type === 'unlock') {
          this.lockedKeys.delete(key)
        }
      }
    } else {
      // 降级：使用 localStorage + storage 事件
      this.channel = {
        postMessage: (data: any) => {
          localStorage.setItem(CHANNEL_NAME, JSON.stringify({ ...data, _ts: Date.now() }))
        },
        onmessage: null,
        close: () => {},
      } as any

      window.addEventListener('storage', (e) => {
        if (e.key === CHANNEL_NAME && e.newValue) {
          const data = JSON.parse(e.newValue)
          if (data.type === 'lock') this.lockedKeys.add(data.key)
          else if (data.type === 'unlock') this.lockedKeys.delete(data.key)
        }
      })
    }
  }

  /**
   * 尝试获取锁
   */
  tryLock(key: string): boolean {
    if (this.lockedKeys.has(key)) return false
    this.lockedKeys.add(key)
    this.channel.postMessage({ type: 'lock', key })
    return true
  }

  /**
   * 释放锁
   */
  unlock(key: string) {
    this.lockedKeys.delete(key)
    this.channel.postMessage({ type: 'unlock', key })
  }
}
```

# 十四、面试高频题

## 14.1 基础概念篇

**Q1：什么是幂等性？前端幂等和后端幂等有什么区别？**

> 幂等性指一个操作执行一次和多次的结果完全一致。前端幂等是第一道防线，通过按钮防抖、请求去重、Token 携带等手段减少重复请求到达后端；后端幂等是最终保障，通过唯一索引、分布式锁、状态机等确保数据一致性。前端幂等可被绕过（直接调接口），后端幂等不可省略。最佳实践是前后端配合分层防御。

**Q2：HTTP 哪些方法是幂等的？POST 不幂等怎么处理？**

> GET、HEAD、OPTIONS、PUT、DELETE 是幂等的。POST 天然不幂等（每次可能创建新资源），处理方式有两种：1）前端生成唯一业务 ID 随 POST 携带，后端用唯一索引兜底；2）前端先获取 Token，提交时携带 Token，后端校验 Token 一次性消费。工程实践中 PUT/DELETE 虽然语义幂等，前端仍应防重复以减少无效请求。

**Q3：Token 机制和唯一 Request-Id 机制有什么区别？各自适用什么场景？**

> Token 由后端生成发放，安全性更高，适合 P0 级操作（支付、关键下单），但需要额外的获取 Token 请求。Request-Id 由前端生成，无额外请求，更轻量，适合全量接口覆盖，但安全性稍低（前端可伪造）。实际项目中关键操作用 Token + Request-Id 双重保障，普通操作用 Request-Id 即可。

## 14.2 设计实战篇

**Q4：设计一个支付页面的前端幂等方案。**

> 分层设计：
> 1. UI 层：支付按钮防抖 + 点击后 3 秒倒计时禁用 + loading 状态
> 2. 请求层：Axios 拦截器注入唯一 Request-Id + 请求去重（相同请求进行中拦截）
> 3. Token 层：页面加载时获取支付 Token，提交时携带，后端校验一次性消费
> 4. 重试层：网络超时不自动重试，引导用户查询支付结果（避免 Token 已消费导致重试失败）
> 5. 后端层：Redis SETNX 去重 + DB 唯一索引兜底 + 状态机校验（只有 PENDING 状态才能支付）

**Q5：用户连点了 5 次提交按钮，你的方案能拦截几次？分别在什么层拦截？**

> 5 次都能拦截：第 1 次正常触发；第 2~5 次在按钮防抖层被拦截（按钮已禁用/loading）。如果按钮防抖被绕过（如禁用 JS），请求去重拦截器会拦截第 2~5 次（相同请求进行中）。如果前端拦截全部失效，后端通过 Token/Request-Id 去重拦截第 2~5 次。最终 DB 唯一索引兜底，即使后端去重失效也不会创建重复数据。

**Q6：弱网环境下请求超时了，前端应该自动重试吗？如何保证重试的幂等？**

> 不应盲目自动重试。正确做法：
> 1. 超时后先不重试，提示用户"网络超时，是否查询操作结果"
> 2. 如果用户确认要重试，重试时复用相同的 Request-Id（不是生成新的）
> 3. 后端收到相同 Request-Id 的请求会去重：如果第一次已成功，返回已有结果；如果第一次未到达，正常处理
> 4. 重试限制 3 次，指数退避（1s → 2s → 4s），只对 5xx/超时重试，4xx 不重试

## 14.3 进阶场景篇

**Q7：多标签页同时操作怎么防重复提交？**

> 三层方案：
> 1. BroadcastChannel 跨标签页通信：一个标签页提交时通知其他标签页锁定
> 2. 后端基于用户 ID + 操作类型的分布式锁（Redis），同一用户同一操作 5 秒内只能提交一次
> 3. DB 唯一索引兜底：如订单表 order_no 唯一，即使前两层失效也不会创建重复数据

**Q8：文件上传如何实现幂等？**

> 基于文件内容 Hash：
> 1. 前端计算文件 MD5/SHA-256 Hash（分片读取，避免大文件内存溢出）
> 2. 上传前先查询 Hash 是否已存在（秒传判断）
> 3. 分片上传时每个分片携带文件 Hash + 分片序号，后端通过序号去重（重复上传同一分片不会出错）
> 4. 每个分片的请求携带唯一 Request-Id（格式：fileHash-chunkIndex），后端 SETNX 去重
> 5. 合并分片时也携带唯一 Request-Id（格式：fileHash-merge）

**Q9：离线场景（PWA）如何保证提交幂等？**

> 使用 IndexedDB 队列 + 唯一 Request-Id：
> 1. 离线时将请求存入 IndexedDB 队列，每条请求携带唯一 Request-Id
> 2. 监听 online 事件，网络恢复后从队列中按序提交
> 3. 每条请求携带原始的 Request-Id，后端通过 Request-Id 去重
> 4. 即使网络恢复后同一请求被提交了多次（断断续续恢复），后端也只会处理一次
> 5. 提交成功后从队列删除，失败的留在队列下次重试

**Q10：前端 Token 机制中，如果 Token 已被后端消费但业务执行失败了，用户怎么办？**

> 这是一个 Token 机制的痛点。标准处理流程：
> 1. 后端在 Token 校验通过后执行业务，如果业务失败，恢复 Token（重新 SET 回 Redis）
> 2. 前端收到 5xx 错误后不清除本地 Token，让用户可以重试
> 3. 用户重试时携带原 Token，后端校验 Token 仍然有效，正常处理
> 4. 如果 Token 恢复失败（极端情况），前端提示用户刷新页面获取新 Token
> 5. 最优解：后端用 Lua 脚本将 Token DEL 和业务执行放在同一事务中，业务失败自动回滚 Token

# 十五、最佳实践与 Checklist

## 15.1 前端幂等设计原则

```
六大设计原则：

  1. 分层防御
     → UI 层防抖 + 请求层去重 + 后端幂等 + DB 唯一索引
     → 每一层都能独立兜底

  2. 后端兜底
     → 前端幂等可被绕过，后端幂等是最终保障
     → 前端做的所有工作只是"减少无效请求"和"提升体验"

  3. 按场景选策略
     → 支付：Token + Request-Id + 分布式锁 + DB 唯一索引
     → 表单：Request-Id + 按钮防抖
     → 查询：请求去重（缓存）
     → 状态更新：乐观锁版本号

  4. 不盲目重试
     → 网络超时不要立即重试，先引导用户查结果
     → 重试时复用原 Request-Id，不是生成新的
     → 只重试 5xx/超时，不重试 4xx

  5. 用户体验优先
     → 按钮禁用 + loading 提示
     → 重复提交给出友好提示（"请勿重复提交"）
     → 版本冲突引导用户刷新

  6. 全链路可追踪
     → 每个请求携带唯一 Request-Id
     → 前端日志、后端日志、DB 记录都可关联
     → 出问题时可快速定位是哪一次请求
```

```
  □ 重试是否只对 5xx/超时触发，4xx 不重试？
  □ 是否处理了 409 幂等冲突响应？
  □ Token 获取失败是否有降级处理？
  □ 多标签页是否考虑了跨页面同步？
  □ 离线场景是否使用了 IndexedDB 队列？

后端 Checklist：

  □ 关键接口是否标注了 @Idempotent 注解？
  □ Redis SETNX 是否使用了 Lua 脚本保证原子性？
  □ 业务失败时是否清除了 Redis 幂等标记（允许重试）？
  □ DB 是否有唯一索引兜底？
  □ 唯一索引冲突时是否返回已有结果（而不是报错）？
  □ 状态更新是否使用了乐观锁版本号？
  □ Token 的 TTL 是否合理（不能太短导致正常提交失败，不能太长导致长期可重用）？
  □ 是否记录了幂等拦截日志（方便排查）？
```

## 15.3 架构层面 Checklist

```
架构 Checklist：

  □ 前后端是否约定了统一的幂等请求头（X-Request-Id / X-Idempotency-Token）？
  □ 是否有统一的错误码规范（409 = 幂等冲突）？
  □ 前端 HTTP 封装是否统一注入了幂等头？
  □ 后端是否有统一的 AOP 注解处理幂等？
  □ Redis 是否做了高可用（幂等依赖 Redis，Redis 挂了怎么办）？
  □ 是否有降级策略（Redis 不可用时降级为 DB 唯一索引兜底）？
  □ 是否有监控告警（幂等拦截率、重试率、Token 失败率）？
  □ 是否有压测验证（并发 N 次提交是否只创建 1 条数据）？
  □ 是否有 E2E 测试覆盖关键场景？
  □ 团队是否对幂等设计有统一规范文档？
```

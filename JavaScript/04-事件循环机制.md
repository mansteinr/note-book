## 一、核心概念解析

### 1.1 JavaScript 单线程模型

JavaScript 从设计之初就采用**单线程模型**，这一选择源于其最初的定位——浏览器端的脚本语言，主要职责是操作 DOM 和处理用户交互。

**单线程设计的原因：**

1. **DOM 操作安全**：若多线程同时操作 DOM（如一个线程添加节点、另一个线程删除同一节点），将产生竞态条件，浏览器无法决定以哪个操作为准。
2. **简化编程模型**：单线程避免了锁、死锁等并发问题，降低了开发门槛。
3. **历史成本**：在 1995 年 Netscape 时代，多线程编程对浏览器实现而言成本过高。

**单线程的挑战与解决：**

单线程意味着所有任务必须排队执行。若某个任务耗时很长（如网络请求、文件读取），后续任务将被阻塞。为此，JavaScript 引入了**事件循环机制**，将耗时任务委托给宿主环境（浏览器/Node.js）的 Web APIs 或 C++ API 处理，待任务完成后通过回调通知主线程，从而实现**异步非阻塞**。

```javascript
// 同步阻塞示例：以下代码会冻结页面 3 秒
console.log('开始');
const start = Date.now();
while (Date.now() - start < 3000) { /* 死循环阻塞 */ }
console.log('结束'); // 3 秒后才输出

// 异步非阻塞示例：通过事件循环避免阻塞
console.log('开始');
setTimeout(() => console.log('3 秒后执行'), 3000);
console.log('结束'); // 立即输出，不等待 setTimeout
```

> **注意**：JavaScript 的"单线程"指的是**主线程（Main Thread）**。实际上，宿主环境（浏览器/Node.js）内部存在多个线程负责处理定时器、网络请求、文件 I/O 等，但这些线程对 JavaScript 开发者不可见，回调最终回到主线程执行。

### 1.2 事件循环机制概述

**事件循环（Event Loop）** 是 JavaScript 运行时的核心调度机制，负责协调**调用栈**、**任务队列**和**宿主环境 API** 之间的协作，使单线程能够处理异步操作。

事件循环的核心思想可以用一句话概括：

> **主线程不断从任务队列中取出任务，放入调用栈执行，执行完毕后取下一个，循环往复。**

```
┌─────────────────────────────────────────────────────────┐
│                    JavaScript 运行时                      │
│                                                         │
│  ┌──────────────┐         ┌──────────────────────────┐  │
│  │              │  取出任务  │     任务队列 (Queues)     │  │
│  │   调用栈     │ ◄──────── │                          │  │
│  │ (Call Stack) │           │  ┌────────────────────┐  │  │
│  │              │           │  │   微任务队列        │  │  │
│  │  LIFO 后进   │           │  │  (Microtask Queue)  │  │  │
│  │  先出结构    │           │  └────────────────────┘  │  │
│  │              │           │  ┌────────────────────┐  │  │
│  │              │           │  │   宏任务队列        │  │  │
│  │              │           │  │  (Macrotask Queue)  │  │  │
│  └──────┬───────┘           │  └────────────────────┘  │  │
│         │                   └──────────────────────────┘  │
│         │ 回调完成                        ▲               │
│         ▼                                │ 注册回调       │
│  ┌──────────────┐                        │               │
│  │  宿主环境     │────────────────────────┘               │
│  │  Web APIs    │                                        │
│  │ (浏览器/Node) │                                        │
│  │              │                                        │
│  │ · setTimeout │                                        │
│  │ · DOM Events │                                        │
│  │ · fetch/AJAX │                                        │
│  │ · fs.readFile│                                        │
│  └──────────────┘                                        │
└─────────────────────────────────────────────────────────┘
```

### 1.3 调用栈与执行上下文

**调用栈（Call Stack）** 是 JavaScript 引擎用来管理**执行上下文**的数据结构，遵循 **LIFO（Last In, First Out，后进先出）** 原则。

```javascript
function multiply(a, b) {
  return a * b;
}

function square(n) {
  return multiply(n, n);
}

function printSquare(n) {
  const squared = square(n);
  console.log(squared);
}

printSquare(4);
```

调用栈变化过程：

```
步骤 1: 压入 printSquare(4)
┌─────────────────────┐
│ printSquare(4)      │ ← 栈顶
└─────────────────────┘

步骤 2: printSquare 内部调用 square(4)，压入 square(4)
┌─────────────────────┐
│ square(4)           │ ← 栈顶
│ printSquare(4)      │
└─────────────────────┘

步骤 3: square 内部调用 multiply(4, 4)，压入 multiply(4, 4)
┌─────────────────────┐
│ multiply(4, 4)      │ ← 栈顶
│ square(4)           │
│ printSquare(4)      │
└─────────────────────┘

步骤 4: multiply 返回 16，弹出 multiply(4, 4)
┌─────────────────────┐
│ square(4)           │ ← 栈顶
│ printSquare(4)      │
└─────────────────────┘

步骤 5: square 返回 16，弹出 square(4)
┌─────────────────────┐
│ printSquare(4)      │ ← 栈顶
└─────────────────────┘

步骤 6: console.log(16) 执行后，弹出 printSquare(4)
┌─────────────────────┐
│       (空栈)         │
└─────────────────────┘
```

> **关键点**：调用栈为空时，事件循环才会从任务队列中取出下一个任务执行。**调用栈非空时，事件循环处于阻塞状态**，不会处理任何任务队列中的回调。

### 1.4 任务队列：宏任务与微任务

JavaScript 中存在两类任务队列，它们的执行优先级不同：

| 对比维度 | 宏任务（Macrotask） | 微任务（Microtask） |
|---------|--------------------|--------------------|
| **规范来源** | HTML 规范（浏览器）/ libuv（Node.js） | ECMAScript 规范 |
| **执行优先级** | 低（每次 Tick 取 1 个） | 高（清空整个队列后才执行宏任务） |
| **队列数量** | 可能有多个（按任务类型） | 只有 1 个 |
| **常见 API** | `setTimeout`、`setInterval`、`setImmediate`(Node)、I/O、UI 事件、`MessageChannel` | `Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`process.nextTick`(Node) |
| **注册方式** | 宿主环境 API 将回调推入宏任务队列 | JS 引擎将回调推入微任务队列 |

**微任务的执行时机：**

```
┌─────────────────────────────────────────────────┐
│                  一次事件循环 (Tick)              │
│                                                 │
│  1. 从宏任务队列取出 1 个任务执行                  │
│     ↓                                           │
│  2. 执行过程中可能产生新的微任务和宏任务            │
│     ↓                                           │
│  3. 宏任务执行完毕，调用栈清空                     │
│     ↓                                           │
│  4. ★ 清空所有微任务队列（含执行中新增的微任务）    │
│     ↓                                           │
│  5. 执行 UI 渲染（浏览器，如果需要）               │
│     ↓                                           │
│  6. 回到步骤 1，进入下一个 Tick                   │
└─────────────────────────────────────────────────┘
```

> **重要**：微任务队列的清空是**递归的**——在清空过程中新产生的微任务也会在当前 Tick 内执行，直到微任务队列完全为空。这意味着微任务可以无限"插队"，导致宏任务被无限推迟（即"宏任务饿死"）。

### 1.5 事件循环执行流程

以下是事件循环的**通用执行流程**（适用于浏览器和 Node.js 的抽象模型）：

```javascript
// 伪代码：事件循环核心逻辑
while (true) {
  // 1. 检查调用栈是否为空
  if (callStack.isEmpty()) {

    // 2. 清空微任务队列（递归执行，直到为空）
    while (!microtaskQueue.isEmpty()) {
      const microtask = microtaskQueue.dequeue();
      callStack.push(microtask);
      callStack.execute();
    }

    // 3. 执行渲染（仅浏览器，每帧约 16.67ms @ 60Hz）
    if (isBrowser && needsRendering()) {
      runRequestAnimationFrameCallbacks();
      render(); // Layout → Paint → Composite
    }

    // 4. 从宏任务队列取出 1 个任务执行
    if (!macrotaskQueue.isEmpty()) {
      const macrotask = macrotaskQueue.dequeue();
      callStack.push(macrotask);
      callStack.execute();
    }
  }
}
```

## 二、浏览器事件循环

### 2.1 浏览器事件循环模型

根据 **HTML Living Standard** 规范，浏览器的事件循环由以下核心组件构成：

```
┌────────────────────────────────────────────────────────────────┐
│                    浏览器事件循环架构                             │
│                                                                │
│  ┌─────────────┐     ┌─────────────────┐    ┌───────────────┐  │
│  │  调用栈      │     │  Web APIs       │    │  任务队列      │  │
│  │ (Call Stack) │     │  (浏览器 API)    │    │  (Task Queues)│  │
│  │              │     │                 │    │               │  │
│  │  · 同步代码   │     │  · DOM API     │    │ ┌───────────┐ │  │
│  │  · 函数调用   │     │  · Timer API   │    │ │微任务队列  │ │  │
│  │  · 回调执行   │     │  · Network API │    │ │(1个)      │ │  │
│  │              │     │  · Storage API  │    │ └───────────┘ │  │
│  └──────┬───────┘     │  · CSS API     │    │ ┌───────────┐ │  │
│         │             │                 │    │ │宏任务队列  │ │  │
│         │ 回调完成     │  将回调推入     │    │ │(≥1个)     │ │  │
│         ▼             │  对应队列       │    │ └───────────┘ │  │
│  ┌─────────────┐     │                 │    │               │  │
│  │  微任务清空  │◄────┤  · setTimeout   │───►│  微任务:      │  │
│  │ (每次宏任务  │     │    → 宏任务     │    │  Promise.then│  │
│  │  之后)       │     │  · Promise     │    │  queueMicro  │  │
│  └─────────────┘     │    → 微任务     │    │  task        │  │
│                      │  · MutationObs  │    │  MutationObs │  │
│  ┌─────────────┐     │    → 微任务     │    │               │  │
│  │  渲染管线    │     │                 │    │  宏任务:      │  │
│  │ (Render)    │     │                 │    │  setTimeout  │  │
│  │  · rAF 回调  │     │                 │    │  setInterval │  │
│  │  · Layout   │     │                 │    │  I/O         │  │
│  │  · Paint    │     │                 │    │  UI 事件     │  │
│  └─────────────┘     │                 │    │  MessageChan │  │
│                      └─────────────────┘    └───────────────┘  │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 渲染时机与 requestAnimationFrame

浏览器事件循环的独特之处在于包含**渲染阶段**。渲染并非每个 Tick 都发生，而是受显示器刷新率（通常 60Hz，即约每 16.67ms 一次）和页面状态共同决定。

**`requestAnimationFrame`（rAF）** 的回调在**渲染前**执行，适合用于动画：

```
一帧（约 16.67ms @ 60Hz）的执行顺序：

┌──────────────────────────────────────────────┐
│  1. 执行一个宏任务                             │
│  2. 清空所有微任务                             │
│  3. 执行 requestAnimationFrame 回调  ★        │
│  4. 浏览器渲染（Layout → Paint → Composite）  │
│  5. 进入下一帧                                 │
└──────────────────────────────────────────────┘
```

```javascript
// rAF 在渲染前执行，保证动画流畅
function animate(timestamp) {
  element.style.transform = `translateX(${timestamp / 10}px)`;
  requestAnimationFrame(animate); // 递归调用，每帧执行
}
requestAnimationFrame(animate);
```

> **注意**：rAF 回调不在宏任务队列中，也不在微任务队列中，它有独立的回调队列。当浏览器决定渲染时，会在微任务清空后、渲染前执行所有 rAF 回调。

### 2.3 浏览器事件循环完整流程

根据 HTML 规范，浏览器事件循环的完整步骤如下：

```
┌─────────────────────────────────────────────────────────────────┐
│                  浏览器事件循环 (HTML Standard)                   │
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  Step 1: 选择一个任务源（task source）                     │    │
│  │          从对应的宏任务队列中取出最老的任务                  │    │
│  │          如果队列为空，跳到 Step 4（微任务）                │    │
│  └───────────────────────┬─────────────────────────────────┘    │
│                          ▼                                      │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  Step 2: 将任务推入调用栈执行                              │    │
│  │          执行过程中可能产生新的微任务和宏任务                │    │
│  └───────────────────────┬─────────────────────────────────┘    │
│                          ▼                                      │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  Step 3: 清空微任务队列（Perform a microtask checkpoint） │    │
│  │          循环执行直到微任务队列为空                         │    │
│  │          ★ 执行过程中新产生的微任务也会被立即执行           │    │
│  └───────────────────────┬─────────────────────────────────┘    │
│                          ▼                                      │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  Step 4: 更新渲染（Update the rendering）                 │    │
│  │          ① 执行 requestAnimationFrame 回调               │    │
│  │          ② 计算样式（Recalc Style）                       │    │
│  │          ③ 布局（Layout / Reflow）                        │    │
│  │          ④ 绘制（Paint）                                   │    │
│  │          ⑤ 合成（Composite）                               │    │
│  │          ※ 仅在需要渲染时执行（性能优化）                  │    │
│  └───────────────────────┬─────────────────────────────────┘    │
│                          ▼                                      │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  Step 5: 回到 Step 1，进入下一次循环                      │    │
│  └─────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
```

## 三、Node.js 事件循环

### 3.1 Node.js 事件循环阶段

Node.js 的事件循环由 **libuv** 库实现，与浏览器事件循环有显著差异。它采用**多阶段（Phase）**模型，每个阶段维护一个先进先出（FIFO）的回调队列。

```
   ┌───────────────────────────────────────────────┐
   │              Node.js 事件循环阶段               │
   │                                               │
   │  ┌─────────────────────────────────────┐      │
   │  │  1. timers 阶段                     │      │
   │  │     执行 setTimeout / setInterval   │      │
   │  │     到期的回调                      │      │
   │  └──────────────┬──────────────────────┘      │
   │                 ▼                              │
   │  ┌─────────────────────────────────────┐      │
   │  │  2. pending callbacks 阶段           │      │
   │  │     执行上一轮延迟的 I/O 回调        │      │
   │  │     （如 TCP errno、DNS 错误等）     │      │
   │  └──────────────┬──────────────────────┘      │
   │                 ▼                              │
   │  ┌─────────────────────────────────────┐      │
   │  │  3. idle, prepare 阶段              │      │
   │  │     内部使用（开发者通常不接触）     │      │
   │  └──────────────┬──────────────────────┘      │
   │                 ▼                              │
   │  ┌─────────────────────────────────────┐      │
   │  │  4. poll 阶段  ★ 核心阶段           │      │
   │  │     · 获取新的 I/O 事件             │      │
   │  │     · 执行 I/O 相关回调             │      │
   │  │     · 若无定时器到期，将在此阻塞    │      │
   │  │       等待新事件                    │      │
   │  └──────────────┬──────────────────────┘      │
   │                 ▼                              │
   │  ┌─────────────────────────────────────┐      │
   │  │  5. check 阶段                      │      │
   │  │     执行 setImmediate 回调          │      │
   │  └──────────────┬──────────────────────┘      │
   │                 ▼                              │
   │  ┌─────────────────────────────────────┐      │
   │  │  6. close callbacks 阶段            │      │
   │  │     执行 close 事件回调             │      │
   │  │     如 socket.on('close', ...)      │      │
   │  └──────────────┬──────────────────────┘      │
   │                 │                              │
   │                 ▼                              │
   │         回到 timers 阶段                       │
   │         （下一轮循环）                         │
   └───────────────────────────────────────────────┘

   ★ 每个阶段切换之间，都会清空：
     1. process.nextTick 队列（优先级最高）
     2. 微任务队列（Promise.then 等）
```

**各阶段详解：**

| 阶段 | 说明 | 常见 API |
|------|------|----------|
| **timers** | 检查是否有到期的定时器，执行其回调 | `setTimeout`、`setInterval` |
| **pending callbacks** | 执行上一轮循环中延迟到本轮的 I/O 回调 | 系统级错误回调（如 `ECONNREFUSED`） |
| **idle, prepare** | libuv 内部使用，开发者通常不需要关注 | — |
| **poll** | 最重要的阶段：获取新的 I/O 事件，执行 I/O 回调。若无定时器到期且 poll 队列为空，则会阻塞等待新事件（除非有 setImmediate） | `fs.readFile`、`net.createServer` 的连接回调 |
| **check** | 执行 `setImmediate` 注册的回调 | `setImmediate` |
| **close callbacks** | 执行关闭事件的回调 | `socket.on('close', ...)` |

> **注意**：Node.js 11 之前，微任务在每个**阶段**结束后才清空；Node.js 11+ 已与浏览器对齐，改为每个**宏任务**执行完毕后立即清空微任务。

### 3.2 process.nextTick 与微任务

`process.nextTick` 是 Node.js 独有的 API，其优先级**高于** Promise 微任务：

```javascript
Promise.resolve().then(() => console.log('Promise'));
process.nextTick(() => console.log('nextTick'));

// 输出：
// nextTick    ← 优先级更高，先执行
// Promise
```

**`process.nextTick` 的特点：**

1. **优先级最高**：在每个阶段切换之间、所有微任务之前执行
2. **递归陷阱**：若在 `nextTick` 回调中再次调用 `nextTick`，会导致事件循环无法进入下一个阶段（"饿死"）

```javascript
// ❌ 危险：nextTick 递归会阻塞事件循环
function recursiveNextTick() {
  process.nextTick(recursiveNextTick);
}
recursiveNextTick();
// 事件循环永远无法进入下一个阶段，I/O 回调无法执行
```

**`process.nextTick` vs `setImmediate`：**

```javascript
// process.nextTick：在当前阶段结束时执行（阶段切换前）
// setImmediate：在 check 阶段执行（下一个事件循环）
process.nextTick(() => console.log('nextTick'));
setImmediate(() => console.log('immediate'));

// 输出：
// nextTick     ← 当前阶段结束后立即执行
// immediate    ← 下一轮 check 阶段执行
```

### 3.3 Node.js 事件循环流程

```
┌─────────────────────────────────────────────────────────────┐
│                   Node.js 事件循环执行流程                     │
│                                                             │
│  ┌───────────────────────────────────────────────────┐      │
│  │  进入阶段 N（如 timers）                            │      │
│  └──────────────────────┬────────────────────────────┘      │
│                         ▼                                   │
│  ┌───────────────────────────────────────────────────┐      │
│  │  执行该阶段的回调队列（FIFO，可执行多个）            │      │
│  │  每个回调执行完毕后：                               │      │
│  └──────────────────────┬────────────────────────────┘      │
│                         ▼                                   │
│  ┌───────────────────────────────────────────────────┐      │
│  │  ★ 清空 process.nextTick 队列（优先级最高）         │      │
│  └──────────────────────┬────────────────────────────┘      │
│                         ▼                                   │
│  ┌───────────────────────────────────────────────────┐      │
│  │  ★ 清空微任务队列（Promise.then 等）                │      │
│  └──────────────────────┬────────────────────────────┘      │
│                         ▼                                   │
│  ┌───────────────────────────────────────────────────┐      │
│  │  检查是否有 process.nextTick / 微任务（可能新增）   │      │
│  │  有则回到上面两步继续清空                            │      │
│  └──────────────────────┬────────────────────────────┘      │
│                         ▼                                   │
│  ┌───────────────────────────────────────────────────┐      │
│  │  阶段 N 结束，进入下一个阶段 N+1                    │      │
│  └───────────────────────────────────────────────────┘      │
│                                                             │
│  ※ Node.js 11+ 在每个宏任务回调执行后立即清空微任务，         │
│     与浏览器行为一致（而非等到整个阶段结束）                  │
└─────────────────────────────────────────────────────────────┘
```

## 四、浏览器与 Node.js 事件循环差异对比

### 4.1 架构差异

| 对比维度 | 浏览器 | Node.js |
|---------|-------|---------|
| **实现规范** | HTML Living Standard | libuv |
| **任务队列结构** | 宏任务队列 + 微任务队列（2 类） | 6 个阶段队列 + 微任务队列 + nextTick 队列 |
| **渲染阶段** | ✅ 有（rAF → Layout → Paint） | ❌ 无（Node.js 不负责 UI 渲染） |
| **process.nextTick** | ❌ 不支持 | ✅ 支持（优先级高于微任务） |
| **setImmediate** | ❌ 不支持（已废弃） | ✅ 支持（check 阶段执行） |
| **微任务清空时机** | 每个宏任务执行后 | Node 11+ 同浏览器；Node 10 及之前为每个阶段结束后 |
| **宏任务执行粒度** | 每次 Tick 取 1 个宏任务 | 每个阶段可执行多个回调（FIFO） |

### 4.2 微任务处理差异

```
浏览器（所有版本）和 Node.js 11+ 的微任务处理：

  宏任务 A ──→ 清空微任务 ──→ 宏任务 B ──→ 清空微任务 ──→ ...
                 ↑ 每个宏任务后立即清空

Node.js 10 及之前的微任务处理：

  阶段N所有宏任务 ──→ 清空微任务 ──→ 阶段N+1所有宏任务 ──→ 清空微任务
                     ↑ 整个阶段结束后才清空
```

```javascript
// 以下代码在 Node.js 10 和 Node.js 11+ 中输出顺序不同
setTimeout(() => {
  console.log('timer1');
  Promise.resolve().then(() => console.log('promise1'));
}, 0);

setTimeout(() => {
  console.log('timer2');
  Promise.resolve().then(() => console.log('promise2'));
}, 0);

// Node.js 10 输出：timer1, timer2, promise1, promise2
// Node.js 11+ 输出：timer1, promise1, timer2, promise2  ← 与浏览器一致
```

### 4.3 API 差异对照表

| 功能 | 浏览器 | Node.js | 说明 |
|------|-------|---------|------|
| 延迟执行 | `setTimeout` | `setTimeout` | 两者均支持 |
| 周期执行 | `setInterval` | `setInterval` | 两者均支持 |
| 高优先级回调 | `queueMicrotask` | `process.nextTick` | nextTick 优先级高于微任务 |
| 微任务 | `queueMicrotask` | `queueMicrotask` | Node 11+ 支持 |
| 下一轮事件循环 | `MessageChannel` / `postMessage` | `setImmediate` | 浏览器 setImmediate 已废弃 |
| 动画帧回调 | `requestAnimationFrame` | ❌ | 仅浏览器有渲染阶段 |
| 空闲回调 | `requestIdleCallback` | ❌ | 仅浏览器有渲染空闲 |

## 五、面试题实战

### 5.1 基础执行顺序（基础）

#### 题干

```javascript
console.log('1');

setTimeout(function () {
  console.log('2');
  Promise.resolve().then(() => console.log('3'));
}, 0);

Promise.resolve().then(() => console.log('4'));

console.log('5');
```

#### 解题思路

1. **同步代码**：`console.log('1')` → 输出 `1`，`console.log('5')` → 输出 `5`
2. **宏任务注册**：`setTimeout` 回调进入宏任务队列
3. **微任务注册**：`Promise.resolve().then(4)` 进入微任务队列
4. 同步代码执行完毕，调用栈清空
5. **清空微任务**：执行 `console.log('4')` → 输出 `4`
6. **执行宏任务**：`setTimeout` 回调执行，输出 `2`，内部注册微任务 `3`
7. **清空微任务**：执行 `console.log('3')` → 输出 `3`

#### 正确输出

```
1
5
4
2
3
```

#### 知识点拓展

- 宏任务内部的微任务会在该宏任务执行完毕后**立即执行**，而不是等到下一个 Tick
- 微任务可以源源不断地产生新微任务，可能导致宏任务"饿死"

### 5.2 async/await 执行顺序（进阶）

#### 题干

```javascript
async function async1() {
  console.log('A');
  await async2();
  console.log('B');
}

async function async2() {
  console.log('C');
}

console.log('D');
setTimeout(() => console.log('E'), 0);
async1();
new Promise(resolve => {
  console.log('F');
  resolve();
}).then(() => console.log('G'));
console.log('H');
```

#### 解题思路

`async/await` 是 Promise 的语法糖：
- `async` 函数内的同步代码**立即执行**
- `await` 之后的代码等价于 `.then` 回调，被放入**微任务队列**

逐步分析：

```
1. 同步：console.log('D')           → 输出 D
2. 同步：setTimeout(E)              → 宏任务队列: [E]
3. 同步：调用 async1()
   ├── 同步：console.log('A')       → 输出 A
   ├── 同步：调用 async2()
   │   └── 同步：console.log('C')   → 输出 C
   └── await 之后：console.log('B') → 微任务队列: [B]
4. 同步：new Promise(executor)
   ├── 同步：console.log('F')       → 输出 F
   ├── 同步：resolve()
   └── .then(G)                     → 微任务队列: [B, G]
5. 同步：console.log('H')           → 输出 H
6. 清空微任务：B → G                → 输出 B, G
7. 执行宏任务：E                    → 输出 E
```

#### 正确输出

```
D
A
C
F
H
B
G
E
```

#### 知识点拓展

- `await` 后面的代码等价于 `.then` 回调，作为微任务执行
- `async` 函数返回一个 Promise，`await` 会暂停执行直到 Promise 决议
- `await` 后面如果是普通值，会被 `Promise.resolve()` 包装

### 5.3 Promise 链式调用与微任务延迟（进阶）

#### 题干

```javascript
setTimeout(() => console.log('A'), 0);

Promise.resolve()
  .then(() => {
    console.log('B');
    return Promise.resolve().then(() => {
      console.log('C');
      return Promise.resolve().then(() => {
        console.log('D');
      });
    });
  })
  .then(() => console.log('E'));

console.log('F');
```

#### 解题思路

本题的核心难点在于理解：**当 `.then` 的回调返回一个 Promise 时，后续的 `.then` 必须等待该 Promise 完全 resolve 后才会执行**。

逐步分析：

```
1. 同步：console.log('F')                        → 输出 F
2. 同步：setTimeout(A)                           → 宏任务队列: [A]
3. 同步：Promise.resolve().then(回调B)            → 微任务队列: [B]
4. 同步代码结束，清空微任务队列

── 微任务第 1 轮 ──
5. 执行回调 B：console.log('B')                   → 输出 B
   内部执行 return Promise.resolve().then(回调C)
   · Promise.resolve() 已 settled → 回调 C 入微任务队列
   · 回调 B 返回一个 Promise（内层 .then 的结果）
   · ★ 外层 .then(E) 等待此 Promise resolve，暂不入队
   微任务队列: [C]

── 微任务第 2 轮 ──
6. 执行回调 C：console.log('C')                   → 输出 C
   内部执行 return Promise.resolve().then(回调D)
   · 回调 D 入微任务队列
   · 回调 C 返回一个 Promise
   微任务队列: [D]

── 微任务第 3 轮 ──
7. 执行回调 D：console.log('D')                   → 输出 D
   · 回调 D 返回 undefined
   · 内层 Promise resolve → 触发回调 C 的 Promise resolve
   → 触发回调 B 的 Promise resolve → 外层 .then(E) 入队
   微任务队列: [E]

── 微任务第 4 轮 ──
8. 执行回调 E：console.log('E')                   → 输出 E
   微任务队列: []（空）

── 微任务清空完毕，执行宏任务 ──
9. 执行 setTimeout 回调：console.log('A')         → 输出 A
```

#### 正确输出

```
F
B
C
D
E
A
```

> **关键纠错**：容易误认为 `E` 会在 `C` 之后、`D` 之前执行（基于"外部 `.then` 在回调 B 执行后立即注册"的错误推理）。实际上，当回调 B 返回的是一个 Promise 时，外层 `.then(E)` 必须等待该 Promise 链**完全 resolve** 后才会执行。因此 `D` 一定在 `E` 之前。

#### 知识点拓展

- 当 `.then` 回调返回一个 Promise 时，后续 `.then` 会被推迟到该 Promise resolve 后执行
- 这是 ECMA 规范中 **PromiseResolveThenableJob** 的行为：返回 thenable 会引入额外的微任务调度
- 微任务队列在清空过程中，新加入的微任务会在**当前 Tick 内**继续执行
- 递归微任务可能导致宏任务被无限推迟（"饿死"）

### 5.4 requestAnimationFrame 执行时机（进阶）

#### 题干

```javascript
console.log('1');

setTimeout(() => console.log('2'), 0);

requestAnimationFrame(() => console.log('3'));

Promise.resolve().then(() => console.log('4'));

console.log('5');
```

#### 解题思路

`requestAnimationFrame`（rAF）的回调不在宏任务队列中，而是在**渲染前**执行。执行顺序为：同步代码 → 微任务 → rAF → 渲染 → 宏任务。

```
1. 同步：console.log('1')                         → 输出 1
2. 同步：setTimeout(2)                            → 宏任务队列: [2]
3. 同步：requestAnimationFrame(3)                 → rAF 回调队列: [3]
4. 同步：Promise.resolve().then(4)                → 微任务队列: [4]
5. 同步：console.log('5')                         → 输出 5

6. 清空微任务：console.log('4')                   → 输出 4
7. 执行 rAF 回调：console.log('3')                → 输出 3
8. 渲染（如果有变化）
9. 执行宏任务：console.log('2')                   → 输出 2
```

#### 正确输出

```
1
5
4
3
2
```

> **注意**：rAF 的执行时机依赖于浏览器是否在当前 Tick 进行渲染。上述结果在大多数情况下成立，但如果代码执行时不在浏览器的渲染窗口内（如标签页不可见），rAF 回调可能会被延迟到下一次渲染前执行，可能导致 `2`（setTimeout）先于 `3`（rAF）输出。

#### 知识点拓展

- `requestAnimationFrame` 的回调在**每一帧渲染之前**执行
- 执行顺序：`微任务 → rAF → 渲染 → 宏任务`
- rAF 适合做动画，因为它与显示器刷新率同步（通常 60Hz），保证动画流畅
- 当标签页不可见时，rAF 回调会被暂停以节省性能

### 5.5 Node.js 事件循环阶段（进阶）

#### 题干

```javascript
// Node.js 环境
const fs = require('fs');

setTimeout(() => console.log('A'), 0);
setImmediate(() => console.log('B'));

fs.readFile(__filename, () => {
  setTimeout(() => console.log('C'), 0);
  setImmediate(() => console.log('D'));
  process.nextTick(() => console.log('E'));
});
```

#### 解题思路

**主模块中的 `setTimeout` vs `setImmediate`：**

`setTimeout(fn, 0)` 在 **timers 阶段**执行，`setImmediate` 在 **check 阶段**执行。在主模块中，两者的执行顺序取决于事件循环进入 timers 阶段时，1ms 的阈值是否已过，因此**顺序不确定**。

**I/O 回调中的 `setTimeout` vs `setImmediate`：**

在 `fs.readFile` 的回调中（poll 阶段），`setImmediate` 会在当前事件循环的 **check 阶段**执行，而 `setTimeout` 会在**下一轮事件循环**的 timers 阶段执行。因此 `setImmediate`（D）一定先于 `setTimeout`（C）。

**`process.nextTick`：**

在 I/O 回调执行完毕后、阶段切换之前，`process.nextTick`（E）优先于所有微任务和下一个阶段的回调执行。

```
第 1 轮事件循环：
  timers 阶段：A（可能执行，取决于 1ms 阈值）
  poll 阶段：fs.readFile 回调执行
    · 注册 setTimeout(C) → 下一轮 timers
    · 注册 setImmediate(D) → 当前轮 check 阶段
    · 注册 nextTick(E) → 阶段切换前执行
  ★ nextTick：E
  check 阶段：D

第 2 轮事件循环：
  timers 阶段：C
```

#### 正确输出

```
// A 和 B 顺序不确定（主模块中）
A 或 B
B 或 A
// I/O 回调中顺序确定：
E
D
C
```

#### 知识点拓展

- `process.nextTick` 并非标准微任务，它在每个阶段切换之间执行，优先级高于 Promise 微任务
- Node.js 中 `setTimeout(fn, 0)` 实际上会被强制设置为至少 1ms 延迟
- 在 I/O 回调中，`setImmediate` 总是先于 `setTimeout` 执行（因为 check 阶段在 timers 阶段之前结束）

### 5.6 综合执行顺序（高阶）

#### 题干

```javascript
async function async1() {
  console.log('async1 start');
  await async2();
  console.log('async1 end');
}

async function async2() {
  console.log('async2');
}

console.log('script start');

setTimeout(function () {
  console.log('setTimeout');
}, 0);

async1();

new Promise(function (resolve) {
  console.log('promise1');
  resolve();
}).then(function () {
  console.log('promise2');
});

process.nextTick(() => console.log('nextTick'));

console.log('script end');
```

（假设为 Node.js 环境）

#### 解题思路

本题综合考察同步代码、`async/await`、`Promise`、`setTimeout`、`process.nextTick` 的执行顺序。

```
1. 同步：console.log('script start')              → 输出 script start
2. 同步：setTimeout(setTimeout)                   → 宏任务队列: [setTimeout]
3. 同步：调用 async1()
   ├── 同步：console.log('async1 start')          → 输出 async1 start
   ├── 同步：调用 async2()
   │   └── 同步：console.log('async2')            → 输出 async2
   └── await 之后：console.log('async1 end')      → 微任务队列: [async1 end]
4. 同步：new Promise(executor)
   ├── 同步：console.log('promise1')              → 输出 promise1
   ├── 同步：resolve()
   └── .then(promise2)                            → 微任务队列: [async1 end, promise2]
5. 同步：process.nextTick(nextTick)               → nextTick 队列: [nextTick]
6. 同步：console.log('script end')                → 输出 script end

7. ★ 清空 nextTick 队列：console.log('nextTick')  → 输出 nextTick
8. 清空微任务队列：
   · console.log('async1 end')                    → 输出 async1 end
   · console.log('promise2')                      → 输出 promise2
9. 执行宏任务：console.log('setTimeout')           → 输出 setTimeout
```

#### 正确输出

```
script start
async1 start
async2
promise1
script end
nextTick
async1 end
promise2
setTimeout
```

#### 知识点拓展

- Node.js 中 `process.nextTick` 优先级高于 Promise 微任务
- 浏览器中无 `process.nextTick`，对应场景可用 `queueMicrotask`
- 本题是面试高频题，综合考察了所有核心概念

### 5.7 渲染阻塞与事件循环（高阶）

#### 题干

```javascript
document.body.innerHTML = 'Start';

setTimeout(() => {
  document.body.innerHTML = 'After Timeout';
}, 0);

Promise.resolve().then(() => {
  document.body.innerHTML = 'After Microtask';
});

requestAnimationFrame(() => {
  document.body.innerHTML = 'After RAF';
});

document.body.innerHTML = 'End';
```

#### 解题思路

浏览器渲染发生在**微任务清空 + rAF 回调执行完毕之后**。在渲染之前对 DOM 的多次修改，只有最后一次会反映在屏幕上。

```
1. 同步：document.body.innerHTML = 'Start'
   · DOM 修改，但不立即渲染
2. 同步：setTimeout 注册宏任务
3. 同步：Promise.resolve().then 注册微任务
4. 同步：requestAnimationFrame 注册 rAF 回调
5. 同步：document.body.innerHTML = 'End'
   · DOM 最终值为 'End'，同步代码覆盖了 'Start'

6. 清空微任务：innerHTML = 'After Microtask'
   · DOM 值变为 'After Microtask'，仍未渲染
7. 执行 rAF 回调：innerHTML = 'After RAF'
   · DOM 值变为 'After RAF'
8. ★ 渲染：屏幕显示 'After RAF'
9. 执行宏任务：innerHTML = 'After Timeout'
   · DOM 值变为 'After Timeout'
10. ★ 下一次渲染：屏幕显示 'After Timeout'
```

#### 正确输出

```
用户实际看到的内容：
初始渲染: End          ← 同步代码执行完毕后的状态（Start 被 End 覆盖）
第一帧渲染: After RAF   ← 微任务 + rAF 执行后的状态
第二帧渲染: After Timeout ← 宏任务执行后的状态

注意：用户不会看到 'Start' 和 'After Microtask'
```

#### 知识点拓展

- 浏览器渲染时机：**微任务清空 + rAF 执行完毕后才渲染**
- 多次 DOM 修改会被合并，只触发一次渲染
- `document.body.innerHTML = 'Start'` 被后续同步代码覆盖，不会触发渲染
- 理解渲染时机对性能优化至关重要

## 六、易错点与最佳实践

### 6.1 常见易错点

| 易错点 | 错误理解 | 正确理解 |
|--------|---------|---------|
| `setTimeout(fn, 0)` 立即执行 | 0 延迟等于立即执行 | 即使 0 延迟，也进入宏任务队列，在同步代码和微任务之后执行（浏览器中最小延迟约 4ms） |
| `async/await` 是同步的 | `await` 后的代码和同步代码一样 | `await` 后的代码是微任务，在当前同步代码执行完毕后执行 |
| 宏任务优先级高于微任务 | 宏任务先执行 | 微任务优先级高于宏任务，每次宏任务执行后都清空微任务队列 |
| `requestAnimationFrame` 是宏任务 | rAF 在宏任务队列中 | rAF 在微任务之后、渲染之前执行，不在宏任务队列中 |
| 浏览器和 Node.js 事件循环相同 | 两者完全一样 | 浏览器有渲染阶段，Node.js 有 6 个阶段和 `process.nextTick` |
| `.then` 回调返回 Promise 后续立即执行 | 外层 `.then` 在回调返回后立即注册 | 必须等返回的 Promise 完全 resolve 后，外层 `.then` 才执行 |
| `process.nextTick` 是微任务 | 与 `Promise.then` 同级 | `process.nextTick` 优先级高于微任务，在阶段切换时执行 |

### 6.2 最佳实践

```javascript
// 1. 使用 queueMicrotask 替代 Promise.resolve().then()（语义更清晰）
queueMicrotask(() => {
  // 微任务逻辑
});

// 2. 避免长时间阻塞微任务队列
// ❌ 微任务递归可能导致宏任务饿死
function badMicrotask() {
  queueMicrotask(badMicrotask);
}

// 3. 使用 requestAnimationFrame 做动画（与渲染同步）
function animate() {
  element.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(animate);
}

// 4. 使用 requestIdleCallback 处理低优先级任务（仅浏览器）
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0) {
    doLowPriorityWork();
  }
});

// 5. 避免在微任务中执行耗时操作（会阻塞渲染）
// ❌ 微任务中执行耗时操作会延迟渲染
Promise.resolve().then(() => {
  heavyComputation(); // 阻塞渲染
});

// 6. 批量 DOM 操作，减少重排重绘
// ❌ 逐条修改样式，触发多次重排
for (let i = 0; i < 100; i++) {
  element.style.left = i + 'px';
}

// ✅ 使用 DocumentFragment 或 requestAnimationFrame 批量处理
requestAnimationFrame(() => {
  for (let i = 0; i < 100; i++) {
    element.style.left = i + 'px';
  }
});

// 7. Node.js 中避免 process.nextTick 递归
// ❌ 会阻塞事件循环
function badNextTick() {
  process.nextTick(badNextTick);
}

// ✅ 使用 setImmediate 让事件循环继续
function goodImmediate() {
  setImmediate(goodImmediate);
}
```

## 七、执行顺序速查表

```
优先级从高到低（完整版）：

┌─────────────────────────────────────────────────────────┐
│  1. 同步代码（调用栈中的代码）                             │
│     · console.log                                        │
│     · 函数调用                                           │
│     · async 函数内 await 之前的代码                       │
│                                                         │
│  2. process.nextTick（仅 Node.js）                       │
│     · 优先级高于所有微任务                                │
│     · 在每个阶段切换之间执行                              │
│                                                         │
│  3. 微任务（Microtask）                                   │
│     · Promise.then / catch / finally                    │
│     · queueMicrotask                                    │
│     · MutationObserver（浏览器）                          │
│     · async 函数内 await 之后的代码                       │
│                                                         │
│  4. requestAnimationFrame（仅浏览器）                     │
│     · 在渲染前执行                                       │
│     · 每帧执行一次（约 16.67ms @ 60Hz）                   │
│                                                         │
│  5. 浏览器渲染（仅浏览器）                                │
│     · 计算样式 → 布局 → 绘制 → 合成                      │
│                                                         │
│  6. 宏任务（Macrotask）                                   │
│     · setTimeout / setInterval                          │
│     · setImmediate（Node.js）                            │
│     · I/O 回调                                           │
│     · UI 事件                                            │
│     · MessageChannel / postMessage                      │
└─────────────────────────────────────────────────────────┘

执行规则：
  · 每次取出 1 个宏任务执行
  · 宏任务执行完毕后，清空所有微任务（含执行中新产生的）
  · 微任务清空后，执行渲染（浏览器，如果需要）
  · 进入下一个 Tick，取下一个宏任务
```

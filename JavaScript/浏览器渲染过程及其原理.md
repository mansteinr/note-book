# 浏览器渲染过程及其原理

## 一、渲染基本流程

浏览器渲染是将 HTML、CSS、JavaScript 转换为屏幕上像素的完整过程。整个过程涉及多个阶段，形成一条严密的流水线。

### 1.1 渲染流水线总览

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          渲染主线程                                      │
│                                                                         │
│  HTML ──→ 解析HTML ──→ DOM 树 ──┐                                       │
│                                  ├──→ 样式计算 ──→ 布局树 ──→ 分层 ──→ 绘制指令
│  CSS  ──→ 解析CSS ──→ CSSOM树 ──┘                                      │
│                                                                         │
└──────────────────────────────────┬──────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                          合成线程                                       │
│                                                                         │
│  绘制指令 ──→ 分块 ──→ 光栅化 ──→ 合成 ──→ 提交给 GPU 进程               │
│                                                                         │
└──────────────────────────────────┬──────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────────┐
│                          GPU 进程                                       │
│                                                                         │
│  接收合成结果 ──→ 系统调用 ──→ GPU 硬件 ──→ 屏幕显示                    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.2 构建 DOM 树

**DOM（Document Object Model）** 是 HTML 文档的对象化表示，以树形结构描述节点间的层次关系。

#### 解析过程

```
HTML 字符串
    │
    ▼
┌─────────────┐
│  字节流解码   │  将字节流按指定编码（如 UTF-8）解码为字符
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   词法分析   │  将字符流转换为一个个 Token（标签、属性、文本）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   语法分析   │  根据 Token 构建 DOM 节点，形成树形结构
└──────┬──────┘
       │
       ▼
   DOM 树
```

#### 示例

```html
<!DOCTYPE html>
<html>
  <head>
    <title>示例</title>
    <link rel="stylesheet" href="style.css" />
  </head>
  <body>
    <div class="container">
      <h1>标题</h1>
      <p>段落内容</p>
    </div>
    <script src="app.js"></script>
  </body>
</html>
```

对应的 DOM 树结构：

```
Document
└── html
    ├── head
    │   ├── title: "示例"
    │   └── link (rel="stylesheet")
    └── body
        ├── div.container
        │   ├── h1: "标题"
        │   └── p: "段落内容"
        └── script (src="app.js")
```

#### 解析过程中的阻塞行为

| 资源类型 | 是否阻塞 HTML 解析 | 说明 |
|---------|-------------------|------|
| 外部 CSS（`<link>`） | **不阻塞** | 预解析线程负责下载和解析 CSS |
| 内联 CSS（`<style>`） | 阻塞 | 在主线程中直接解析 |
| 外部 JS（`<script>`） | **阻塞** | 等待下载和执行完成 |
| `async` JS | **不阻塞** | 下载不阻塞，下载完立即执行 |
| `defer` JS | **不阻塞** | 下载不阻塞，DOM 解析完成后按序执行 |
| `<img>` | 不阻塞 | 异步加载，不影响 DOM 解析 |

```html
<!-- 阻塞解析：等待下载和执行 -->
<script src="blocking.js"></script>

<!-- 不阻塞解析：下载与解析并行，下载完立即执行（可能打断 DOM 构建） -->
<script src="non-blocking.js" async></script>

<!-- 不阻塞解析：下载与解析并行，DOM 解析完成后才执行 -->
<script src="deferred.js" defer></script>
```

> **为什么 JS 会阻塞 HTML 解析？**
> 因为 JS 可能会修改 DOM 结构（如 `document.write`、`appendChild`），浏览器必须暂停解析，等待 JS 执行完毕后再继续，以避免解析结果与 JS 修改产生冲突。

### 1.3 构建 CSSOM 树

**CSSOM（CSS Object Model）** 是 CSS 样式表的对象化表示，同样以树形结构存储样式规则。

#### 解析过程

```
CSS 文本（外部/内联/浏览器默认）
    │
    ▼
┌─────────────┐
│   词法分析   │  将 CSS 文本转换为 Token（选择器、属性、值）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│   语法分析   │  根据 CSS 语法规则构建节点
└──────┬──────┘
       │
       ▼
   CSSOM 树
```

#### CSSOM 树结构

```
StyleSheetList (document.styleSheets)
├── 默认样式表（User Agent Stylesheet）
├── 外部样式表（<link>）
│   └── body { font-size: 16px; }
│       div.container { width: 100%; }
│       h1 { color: #333; }
└── 内联样式表（<style>）
    └── p { line-height: 1.6; }
```

#### CSS 解析的特点

1. **CSS 解析与 HTML 解析并行**：预解析线程负责下载和解析外部 CSS，不阻塞主线程的 HTML 解析
2. **CSS 不阻塞 DOM 构建**：但会阻塞后续的渲染（样式计算需要 CSSOM）
3. **CSS 阻塞 JS 执行**：如果 JS 在 CSS 之前，JS 执行可能会被阻塞（因为 JS 可能读取样式信息）

```javascript
// 这段 JS 会等待 CSS 加载完成后再执行
// 因为它可能依赖样式信息
const color = getComputedStyle(document.body).color;
```

### 1.4 样式计算

样式计算阶段会为 DOM 树中的每个节点计算最终的样式属性（Computed Style）。

#### 计算流程

```
DOM 树 + CSSOM 树
        │
        ▼
┌──────────────────────────────────────────────┐
│              样式计算四步骤                    │
│                                              │
│  1. 确定声明值                                │
│     │                                        │
│     ▼                                        │
│  2. 层叠冲突                                  │
│     ├── 比较源的重要性                        │
│     ├── 比较优先级（specificity）              │
│     └── 比较次序                              │
│     │                                        │
│     ▼                                        │
│  3. 使用继承                                  │
│     │                                        │
│     ▼                                        │
│  4. 使用默认值                                │
└──────────────────┬───────────────────────────┘
                   │
                   ▼
          带有 Computed Style 的 DOM 树
```

#### 步骤 1：确定声明值

将作者样式表（开发者编写的 CSS）和用户代理样式表（浏览器默认样式）的声明值合并，并将部分值进行标准化转换。

```css
/* 原始声明 */
color: red;             /* → color: rgb(255, 0, 0) */
font-size: 2em;         /* → font-size: 32px (假设父级 font-size: 16px) */
font-weight: bold;      /* → font-weight: 700 */
```

#### 步骤 2：层叠冲突

当多条样式规则作用于同一节点时，按以下优先级解决冲突：

**2.1 比较源的重要性**（从高到低）

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | `!important` 作者样式 | 开发者用 `!important` 标记的样式 |
| 2 | `!important` 用户样式 | 用户自定义的 `!important` 样式 |
| 3 | `!important` 用户代理样式 | 浏览器默认的 `!important` 样式 |
| 4 | 作者样式 | 开发者编写的普通样式 |
| 5 | 用户样式 | 用户自定义的普通样式 |
| 6 | 用户代理样式 | 浏览器默认样式 |

**2.2 比较优先级（Specificity）**

当源相同时，比较选择器的优先级：

```
内联样式 (style="...")     → (1, 0, 0, 0)
ID 选择器 (#id)            → (0, 1, 0, 0)
类/属性/伪类 (.class)      → (0, 0, 1, 0)
元素/伪元素 (div)          → (0, 0, 0, 1)
通配符/继承 (*)            → (0, 0, 0, 0)
```

```css
/* 优先级比较示例 */
#header .title { color: red; }    /* (0,1,1,0) — 生效 */
.header .title  { color: blue; }  /* (0,0,2,0) */
.title          { color: green; } /* (0,0,1,0) */
```

**2.3 比较次序**

当源和优先级都相同时，后声明的规则覆盖先声明的规则。

```css
p { color: red; }   /* 先声明 — 被覆盖 */
p { color: green; } /* 后声明 — 生效 */
```

#### 步骤 3：使用继承

对于未显式声明的可继承属性，从父节点继承值。

```css
div { color: red; }
/* <p> 位于 div 内部，会继承 color: red */
```

**可继承属性**（常见）：
- 字体相关：`font-family`、`font-size`、`font-weight`
- 文本相关：`color`、`text-align`、`line-height`、`letter-spacing`
- 列表相关：`list-style`、`list-style-type`
- 可见性：`visibility`、`cursor`

**不可继承属性**（常见）：
- 盒模型：`width`、`height`、`margin`、`padding`、`border`
- 定位：`position`、`top`、`left`、`z-index`
- 背景：`background`、`background-color`
- 布局：`display`、`flex`、`grid`

#### 步骤 4：使用默认值

经过上述步骤仍无法确定的属性，使用 CSS 规范定义的默认值。

### 1.5 布局（Layout）

布局阶段根据 Computed Style 计算每个节点的**几何信息**（尺寸和位置），生成布局树（Layout Tree）。

#### 布局树与 DOM 树的关系

布局树与 DOM 树**不一定一一对应**：

```
DOM 树                              布局树
├── div (display: none)             ├── div.container
│   └── p                            │   ├── h1 (匿名行盒包裹文本)
└── div.container                    │   └── p
    ├── h1: "标题"                   └── ::before (伪元素)
    ├── p: "段落"                       
    └── ::before (伪元素)
```

**不对应的原因**：

| 情况 | DOM 树 | 布局树 |
|------|--------|--------|
| `display: none` 的元素 | 存在 | **不存在**（无几何信息） |
| 伪元素（`::before`、`::after`） | **不存在** | 存在（有几何信息） |
| 匿名行盒/块盒 | 不存在 | 存在（W3C 规范要求） |
| `head`、`title` 等不可见元素 | 存在 | 不存在 |

#### 包含块（Containing Block）

元素的位置和尺寸通常相对于其**包含块**计算：

| `position` 值 | 包含块 |
|---------------|--------|
| `static`、`relative` | 最近的祖先块元素的内容区 |
| `absolute` | 最近的 `position` 非 `static` 的祖先元素的**内边距区** |
| `fixed` | 视口（viewport） |
| `absolute`/`fixed`（特殊） | 满足以下条件的最近祖先的**内边距区**：`transform`/`perspective` 非 `none`，或 `will-change: transform`，或 `filter` 非 `none` |

### 1.6 分层（Layer）

浏览器将布局树分成多个**图层**，以便局部更新时只重绘对应图层。

#### 分层策略

以下情况会创建独立图层：

| 属性/元素 | 说明 |
|-----------|------|
| `position: fixed` | 固定定位元素 |
| `transform` 非 `none` | 3D 变换触发独立层 |
| `opacity` < 1 | 透明度小于 1 |
| `will-change` | 显式告知浏览器该属性将变化 |
| `<video>`、`<canvas>` | 媒体元素 |
| `filter` 非 `none` | 滤镜效果 |
| 堆叠上下文 | `z-index` 非 `auto` 的定位元素 |

```css
/* 主动提升为独立图层（用于动画优化） */
.animated-element {
  will-change: transform;
  transform: translateZ(0); /* hack 方式触发独立层 */
}
```

> **注意**：图层过多会消耗大量内存，需谨慎使用。

### 1.7 绘制（Paint）

为每个图层生成**绘制指令集**，类似于 Canvas 的绘图命令序列。

```
绘制指令示例：
1. drawRect(0, 0, 100, 50, color: #fff)
2. drawText("Hello", x: 10, y: 30, font: 16px)
3. drawBorder(0, 0, 100, 50, width: 1px, color: #ccc)
```

### 1.8 分块（Tiling）

合成线程将每个图层划分为多个小**块（Tile）**，优先处理视口附近的块。

```
┌──────────────────────────────────────┐
│                  图层                  │
│  ┌────┬────┬────┬────┬────┬────┐    │
│  │ T1 │ T2 │ T3 │ T4 │ T5 │ T6 │    │
│  ├────┼────┼────┼────┼────┼────┤    │
│  │ T7 │ T8 │ T9 │T10 │T11 │T12 │    │
│  └────┴────┴────┴────┴────┴────┘    │
│                  ▲                    │
│                  │ 视口               │
│         优先光栅化 T7-T10              │
└──────────────────────────────────────┘
```

### 1.9 光栅化（Raster）

GPU 进程将每个块转换为**位图**（Bitmap），即像素信息。

```
块（矢量信息） ──→ GPU 光栅化 ──→ 位图（像素信息）

位图 = [[R,G,B,A], [R,G,B,A], ...]  二维数组
```

- 光栅化由 GPU 进程的多线程并行完成
- 优先处理靠近视口的块（更底层的"懒加载"）

### 1.10 合成与显示（Draw）

合成线程生成**指引信息（quad）**，标明每个位图在屏幕上的位置，提交给 GPU 硬件完成最终显示。

```
位图 + 位置信息（quad）
        │
        ▼
   GPU 进程（系统调用）
        │
        ▼
    GPU 硬件
        │
        ▼
    屏幕显示
```

> **为什么合成线程不直接与 GPU 硬件通信？**
> 渲染进程运行在**沙盒（Sandbox）**中，出于安全考虑无法直接访问硬件。必须通过 GPU 进程作为中介。

## 二、关键渲染路径及优化策略

### 2.1 关键渲染路径定义

**关键渲染路径（Critical Rendering Path, CRP）** 是指浏览器初次渲染页面必须经历的最短路径。优化关键渲染路径可以加快**首屏渲染速度**。

### 2.2 关键资源识别

| 资源类型 | 是否关键 | 说明 |
|---------|---------|------|
| HTML | **是** | 必须解析才能构建 DOM |
| CSS（`<link>` 在 `<head>`） | **是** | 阻塞渲染，必须下载并解析 |
| JS（`<script>`） | **是** | 阻塞 DOM 解析 |
| JS（`async`） | 否 | 不阻塞，下载完立即执行 |
| JS（`defer`） | 否 | 不阻塞，DOM 解析后执行 |
| 图片 | 否 | 不阻塞渲染（但影响布局） |
| 字体 | 否 | 不阻塞渲染（但影响文字显示） |

### 2.3 优化策略

#### 策略 1：缩短关键路径长度

```html
<!-- ❌ 阻塞渲染：CSS 在 head 中，JS 在 body 末尾仍可能阻塞 -->
<head>
  <link rel="stylesheet" href="style.css">  <!-- 关键资源 -->
</head>
<body>
  <script src="app.js"></script>  <!-- 阻塞 DOM 解析 -->
</body>

<!-- ✅ 优化：非关键 JS 使用 async/defer -->
<head>
  <link rel="stylesheet" href="critical.css">  <!-- 内联关键 CSS 更佳 -->
</head>
<body>
  <script src="app.js" defer></script>  <!-- 不阻塞解析 -->
  <script src="analytics.js" async></script>  <!-- 完全异步 -->
</body>
```

#### 策略 2：内联关键 CSS

```html
<head>
  <!-- 内联首屏关键 CSS -->
  <style>
    body { margin: 0; font-family: sans-serif; }
    .header { height: 60px; background: #fff; }
    .hero { min-height: 400px; }
  </style>
  
  <!-- 异步加载非关键 CSS -->
  <link rel="preload" href="full.css" as="style" onload="this.rel='stylesheet'">
</head>
```

#### 策略 3：预加载关键资源

```html
<!-- 预加载字体 -->
<link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin>

<!-- 预加载关键 JS -->
<link rel="preload" href="/js/critical.js" as="script">

<!-- DNS 预解析 -->
<link rel="dns-prefetch" href="//cdn.example.com">

<!-- 预连接 -->
<link rel="preconnect" href="//cdn.example.com">
```

#### 策略 4：资源压缩与合并

```javascript
// webpack.config.js
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendors',
          chunks: 'all'
        }
      }
    }
  }
};
```

#### 策略 5：代码分割与懒加载

```javascript
// 路由级懒加载（React）
const Home = React.lazy(() => import('./pages/Home'));
const About = React.lazy(() => import('./pages/About'));

// 组件级懒加载
const HeavyChart = React.lazy(() => import('./components/HeavyChart'));

// 使用 Suspense 包裹
<Suspense fallback={<div>Loading...</div>}>
  <Home />
</Suspense>
```

```javascript
// 图片懒加载
const observer = new IntersectionObserver((entries) => {
  entries.forEach(entry => {
    if (entry.isIntersecting) {
      const img = entry.target;
      img.src = img.dataset.src;
      observer.unobserve(img);
    }
  });
});

document.querySelectorAll('img[data-src]').forEach(img => observer.observe(img));
```

### 2.4 性能指标

| 指标 | 全称 | 含义 | 目标值 |
|------|------|------|--------|
| **FP** | First Paint | 首次绘制 | < 1s |
| **FCP** | First Contentful Paint | 首次内容绘制 | < 1.8s |
| **LCP** | Largest Contentful Paint | 最大内容绘制 | < 2.5s |
| **TTI** | Time to Interactive | 可交互时间 | < 3.8s |
| **CLS** | Cumulative Layout Shift | 累积布局偏移 | < 0.1 |
| **FID** | First Input Delay | 首次输入延迟 | < 100ms |

## 三、回流与重绘

### 3.1 回流（Reflow / Layout）

**回流**是指重新计算布局树（Layout Tree）的过程。当 DOM 结构或几何属性变化时触发。

#### 触发回流的操作

```javascript
// 1. 修改 DOM 结构
element.appendChild(newNode);
element.removeChild(childNode);

// 2. 修改尺寸/位置属性
element.style.width = '200px';
element.style.height = '100px';
element.style.margin = '10px';
element.style.padding = '5px';
element.style.left = '50px';
element.style.top = '100px';

// 3. 修改影响布局的 CSS 属性
element.style.display = 'none';
element.style.position = 'absolute';
element.style.float = 'left';

// 4. 修改文字大小
element.style.fontSize = '20px';
element.style.lineHeight = '1.5';

// 5. 修改窗口大小
window.resizeTo(800, 600);

// 6. 读取布局信息（强制同步布局）
element.offsetWidth;
element.offsetHeight;
element.clientWidth;
element.clientHeight;
element.scrollTop;
element.scrollLeft;
element.getBoundingClientRect();
window.getComputedStyle(element);
```

> **强制同步布局（Layout Thrashing）**：读取布局属性会强制浏览器立即执行回流以返回最新值。

#### 回流的影响范围

回流不仅影响当前元素，还可能影响**父元素、子元素、兄弟元素**甚至整个页面。

```
修改 element.width
        │
        ├──→ 子元素位置可能变化
        ├──→ 兄弟元素位置可能变化
        ├──→ 父元素尺寸可能变化
        └──→ 整个页面布局可能重排
```

### 3.2 重绘（Repaint）

**重绘**是指重新生成绘制指令的过程。当元素外观变化但布局不变时触发。

#### 触发重绘的操作

```javascript
// 修改视觉样式但不影响布局
element.style.color = 'red';
element.style.backgroundColor = '#fff';
element.style.visibility = 'hidden';  // 注意：display:none 会触发回流
element.style.borderStyle = 'dashed';
element.style.boxShadow = '0 0 10px #000';
element.style.textDecoration = 'underline';
```

#### 回流与重绘的关系

```
回流 ──→ 必然触发重绘
重绘 ──→ 不一定触发回流
```

| 操作 | 回流 | 重绘 |
|------|------|------|
| 修改 `width`、`height` | ✅ | ✅ |
| 修改 `color`、`background` | ❌ | ✅ |
| 修改 `transform` | ❌ | ❌ |
| 修改 `opacity` | ❌ | ❌ |
| `display: none` | ✅ | ✅ |
| `visibility: hidden` | ❌ | ✅ |

### 3.3 性能优化策略

#### 优化 1：批量修改 DOM

```javascript
// ❌ 每次修改都触发回流
element.style.width = '100px';
element.style.height = '200px';
element.style.margin = '10px';
// 触发 3 次回流

// ✅ 使用 cssText 批量修改
element.style.cssText = 'width: 100px; height: 200px; margin: 10px;';
// 触发 1 次回流

// ✅ 切换 class
element.className = 'new-style';
// 触发 1 次回流

// ✅ 使用 DocumentFragment 批量插入
const fragment = document.createDocumentFragment();
for (let i = 0; i < 100; i++) {
  const li = document.createElement('li');
  li.textContent = `Item ${i}`;
  fragment.appendChild(li);
}
ul.appendChild(fragment);  // 只触发 1 次回流
```

#### 优化 2：避免强制同步布局

```javascript
// ❌ 读写交替导致强制同步布局（Layout Thrashing）
elements.forEach(el => {
  const width = el.offsetWidth;  // 读（触发回流）
  el.style.width = width + 10 + 'px';  // 写
  // 下一次循环的读操作会立即触发回流
});

// ✅ 先读后写，避免交替
const widths = elements.map(el => el.offsetWidth);  // 批量读
elements.forEach((el, i) => {
  el.style.width = widths[i] + 10 + 'px';  // 批量写
});
```

#### 优化 3：使用 `transform` 代替位置属性

```css
/* ❌ 触发回流 */
.moving-element {
  transition: left 0.3s, top 0.3s;
  left: 100px;
  top: 100px;
}

/* ✅ 只触发合成，不回流不重绘 */
.moving-element {
  transition: transform 0.3s;
  transform: translate(100px, 100px);
}
```

#### 优化 4：使用 `will-change` 提示浏览器

```css
/* 告知浏览器该元素将变化，浏览器会提前优化 */
.animated {
  will-change: transform, opacity;
}

/* 动画结束后移除，避免内存浪费 */
.animated.done {
  will-change: auto;
}
```

#### 优化 5：离线 DOM 修改

```javascript
// 方法 1：隐藏 → 修改 → 显示
element.style.display = 'none';
// 批量修改...
element.style.display = 'block';

// 方法 2：使用 DocumentFragment
const fragment = document.createDocumentFragment();
// 在 fragment 上修改...
document.body.appendChild(fragment);

// 方法 3：克隆节点修改后替换
const clone = element.cloneNode(true);
// 在 clone 上修改...
element.parentNode.replaceChild(clone, element);
```

#### 优化 6：使用 `requestAnimationFrame`

```javascript
// 将布局操作放到下一帧执行
function updateLayout() {
  // 读取布局信息
  const width = element.offsetWidth;
  
  requestAnimationFrame(() => {
    // 在下一帧写入
    element.style.width = width + 10 + 'px';
  });
}
```

### 3.4 各属性对渲染阶段的影响

| CSS 属性 | 回流 | 重绘 | 合成 | 说明 |
|---------|------|------|------|------|
| `width`、`height` | ✅ | ✅ | ❌ | 影响布局 |
| `margin`、`padding` | ✅ | ✅ | ❌ | 影响布局 |
| `color`、`background` | ❌ | ✅ | ❌ | 只影响外观 |
| `visibility` | ❌ | ✅ | ❌ | 占位但不显示 |
| `display` | ✅ | ✅ | ❌ | 改变布局结构 |
| `transform` | ❌ | ❌ | ✅ | 只影响合成阶段 |
| `opacity` | ❌ | ❌ | ✅ | 只影响合成阶段 |
| `position` | ✅ | ✅ | ❌ | 改变定位方式 |

> **核心结论**：优先使用只触发合成的属性（`transform`、`opacity`），避免触发回流和重绘。

## 四、面试题及深度解析

### 题目 1：浏览器渲染页面的完整流程

#### 题干

请详细描述浏览器从接收 HTML 到最终显示页面的完整过程。

#### 参考答案

1. **解析 HTML 构建 DOM 树**：渲染主线程将 HTML 字符串解析为 DOM 树。期间遇到 CSS 由预解析线程并行下载解析，遇到 JS 则暂停解析等待执行。

2. **解析 CSS 构建 CSSOM 树**：CSS 被解析为 CSSOM 树，包含浏览器默认样式、外部样式、内联样式等。

3. **样式计算**：遍历 DOM 树，为每个节点计算最终样式（Computed Style），经过确定声明值、层叠冲突、继承、默认值四个步骤。

4. **布局**：根据 Computed Style 计算每个节点的几何信息（尺寸、位置），生成布局树。布局树与 DOM 树不一定一一对应（如 `display:none` 的元素不在布局树中，伪元素在布局树中但不在 DOM 树中）。

5. **分层**：将布局树分成多个图层，便于局部更新。`transform`、`opacity`、`will-change` 等属性会触发独立图层。

6. **绘制**：为每个图层生成绘制指令集。

7. **分块**：合成线程将图层划分为多个小块，优先处理视口附近的块。

8. **光栅化**：GPU 进程将块转换为位图（像素信息）。

9. **合成与显示**：合成线程生成指引信息（quad），提交给 GPU 进程，最终由 GPU 硬件完成屏幕显示。

#### 深度解析

- **CSS 不阻塞 DOM 解析**：因为预解析线程负责 CSS 下载和解析
- **JS 阻塞 DOM 解析**：因为 JS 可能修改 DOM
- **CSS 阻塞渲染**：样式计算需要 CSSOM，CSS 未就绪不会渲染
- **`transform` 效率高**：只影响最后的合成阶段，不经过渲染主线程

### 题目 2：回流与重绘的区别

#### 题干

请解释回流（Reflow）和重绘（Repaint）的区别，如何避免？

#### 参考答案

| 对比项 | 回流（Reflow） | 重绘（Repaint） |
|--------|---------------|----------------|
| 定义 | 重新计算布局树 | 重新生成绘制指令 |
| 触发条件 | DOM 结构或几何属性变化 | 外观属性变化（颜色、背景等） |
| 性能开销 | 大 | 小 |
| 关系 | 回流必然引起重绘 | 重绘不一定引起回流 |

**避免策略**：

1. 使用 `transform` 代替 `top/left` 做动画
2. 使用 `visibility: hidden` 代替 `display: none`
3. 批量修改 DOM（`cssText`、`className`、`DocumentFragment`）
4. 避免强制同步布局（先读后写，不要读写交替）
5. 对复杂动画使用绝对定位脱离文档流
6. 使用 `will-change` 提示浏览器优化

### 题目 3：`async` 与 `defer` 的区别

#### 题干

```html
<script src="a.js"></script>
<script src="b.js" async></script>
<script src="c.js" defer></script>
```

请分析三种 script 加载方式的区别。

#### 参考答案

| 属性 | 下载 | 执行时机 | 执行顺序 | 阻塞 HTML 解析 |
|------|------|---------|---------|---------------|
| 无（默认） | 阻塞 | 下载完立即执行 | 按顺序 | 是 |
| `async` | 不阻塞 | 下载完立即执行 | **不保证顺序** | 否（执行时阻塞） |
| `defer` | 不阻塞 | DOM 解析完成后、`DOMContentLoaded` 之前 | **按顺序** | 否 |

```
HTML 解析:  ████████████████████████████████→
                │              │           │
默认 script:    │下载+执行██████│           │
                ▼ 阻塞         ▼           ▼
HTML 解析:  ████░░░░░░░░░░██████████████████→

async:      ████████████████████████████████→
                │ 下载(并行)    │ 执行(短阻塞)
                ▼              ▼
                ████           ██

defer:      ████████████████████████████████→ DOMContentLoaded
                │ 下载(并行)              │ 执行(按顺序)
                ▼                        ▼
                ████                      ████
```

**使用场景**：
- `async`：独立脚本（如统计、广告），不依赖 DOM 和其他脚本
- `defer`：需要按顺序执行且依赖 DOM 的脚本

### 题目 4：为什么 `transform` 的效率高？

#### 题干

为什么使用 `transform` 做动画比使用 `top/left` 效率高？

#### 参考答案

```
使用 top/left 做动画：
  修改 top/left
      │
      ▼
  回流（重新计算布局树）── 渲染主线程
      │
      ▼
  重绘（重新生成绘制指令）── 渲染主线程
      │
      ▼
  分块 → 光栅化 → 合成

使用 transform 做动画：
  修改 transform
      │
      ▼
  直接进入合成阶段 ── 合成线程（不经过渲染主线程）
      │
      ▼
  GPU 矩阵变换 → 屏幕更新
```

**核心原因**：
1. `transform` 不影响布局，不触发回流
2. `transform` 不影响绘制指令，不触发重绘
3. `transform` 只影响最后的合成阶段，在**合成线程**中完成
4. 合成线程与渲染主线程独立，即使主线程被 JS 阻塞，`transform` 动画仍然流畅

### 题目 6：强制同步布局（Layout Thrashing）

#### 题干

```javascript
function resizeAll(elements) {
  for (let i = 0; i < elements.length; i++) {
    elements[i].style.width = elements[i].offsetWidth + 10 + 'px';
  }
}
```

以上代码有什么性能问题？如何优化？

#### 参考答案

**问题分析**：

每次循环中先读取 `offsetWidth`（触发回流），再写入 `style.width`（使布局失效）。下一次循环读取 `offsetWidth` 时，浏览器被迫立即执行回流以返回最新值。这种"读写交替"的模式称为**强制同步布局（Layout Thrashing）**，性能极差。

```
循环 1: 读(回流) → 写(标记失效)
循环 2: 读(强制回流!) → 写(标记失效)
循环 3: 读(强制回流!) → 写(标记失效)
...
```

**优化方案**：

```javascript
// 方案 1：先读后写（批量操作）
function resizeAll(elements) {
  const widths = elements.map(el => el.offsetWidth);  // 批量读
  elements.forEach((el, i) => {
    el.style.width = widths[i] + 10 + 'px';  // 批量写
  });
}

// 方案 2：使用 requestAnimationFrame
function resizeAll(elements) {
  const widths = elements.map(el => el.offsetWidth);
  requestAnimationFrame(() => {
    elements.forEach((el, i) => {
      el.style.width = widths[i] + 10 + 'px';
    });
  });
}
```

### 题目 7：CSS 选择器对渲染性能的影响

#### 题干

CSS 选择器的匹配顺序是从左到右还是从右到左？为什么？如何优化？

#### 参考答案

**匹配顺序：从右到左**

```
选择器: div.container > ul li.item

匹配过程（从右到左）：
1. 先找到所有 .item 元素
2. 向上查找，过滤出祖先为 li 的
3. 继续向上，过滤出祖先为 ul 的
4. 继续向上，过滤出父级为 div.container 的
```

**为什么从右到左？**

从左到右需要先找到所有 `div.container`，再向下遍历到 `li.item`，匹配过程中可能大量无效遍历。从右到左先缩小范围（最具体的选择器），再向上验证，效率更高。

**优化建议**：

```css
/* ❌ 不推荐：选择器层级过深 */
.container .content .list .item .link { color: red; }

/* ❌ 不推荐：通配符开销大 */
* { box-sizing: border-box; }
.container * { color: red; }

/* ✅ 推荐：使用单一 class */
.link { color: red; }

/* ✅ 推荐：BEM 命名 */
.list__item__link { color: red; }
```

### 题目 8：GPU 加速与硬件加速

#### 题干

什么是 GPU 加速？哪些 CSS 属性会触发 GPU 加速？

#### 参考答案

**GPU 加速**是指将渲染任务从 CPU 转移到 GPU 执行，利用 GPU 的并行计算能力加速渲染。

**触发 GPU 加速的 CSS 属性**：

```css
.element {
  /* 3D 变换 — 触发 GPU 加速 */
  transform: translate3d(0, 0, 0);
  transform: translateZ(0);

  /* will-change — 显式提示 */
  will-change: transform;

  /* opacity — 触发独立图层 */
  opacity: 0.99;

  /* filter — 触发独立图层 */
  filter: blur(0);

  /* position: fixed — 触发独立图层 */
  position: fixed;
}
```

**GPU 加速的原理**：

```
CPU 渲染路径（传统）:
  布局 → 绘制 → 分块 → 光栅化 → 合成
  └──────── 全部在 CPU ────────┘

GPU 加速路径:
  布局 → 绘制 → 分块 → GPU 光栅化 → GPU 合成
  └── CPU ──┘         └──── GPU ────┘
```

**注意事项**：

```css
/* ❌ 过度使用 GPU 加速会导致内存问题 */
* {
  transform: translateZ(0);  /* 每个元素都创建图层，内存爆炸 */
}

/* ✅ 只对需要动画的元素使用 */
.animated-card {
  will-change: transform;
}

/* ✅ 动画结束后移除 */
.animated-card.animation-end {
  will-change: auto;
}
```

| 优点 | 缺点 |
|------|------|
| 动画流畅（60fps） | 占用 GPU 内存 |
| 不阻塞主线程 | 图层过多导致性能下降 |
| 适合复杂动画 | 部分老设备不支持 |

## 五、总结

### 渲染流程速查表

```
HTML ──→ DOM 树 ──┐
                   ├──→ 样式计算 ──→ 布局 ──→ 分层 ──→ 绘制 ──→ 分块 ──→ 光栅化 ──→ 合成 ──→ 显示
CSS  ──→ CSSOM ──┘         │         │        │         │         │          │
                      回流(Reflow)   │      重绘(Repaint)│      合成(Composite)
                      (渲染主线程)    │      (渲染主线程) │      (合成线程/GPU)
```

### 性能优化核心原则

1. **减少关键资源数量**：内联关键 CSS，异步加载非关键资源
2. **减少回流重绘**：使用 `transform`/`opacity` 做动画，批量修改 DOM
3. **避免强制同步布局**：先读后写，不要读写交替
4. **合理使用 GPU 加速**：`will-change`、`transform: translateZ(0)`
5. **代码分割与懒加载**：按路由/组件分割，图片懒加载
6. **预加载关键资源**：`preload`、`preconnect`、`dns-prefetch`

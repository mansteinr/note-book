## 一、浏览器架构概述

### 1.1 多进程架构演进

浏览器的架构从早期的单进程模型，逐步演进为现代的多进程、多线程架构，核心驱动力是**稳定性、安全性、性能**三大诉求。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     浏览器架构演进历程                                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  阶段 1: 单进程架构（2008 年以前）                                      │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  所有功能（页面渲染、网络、插件、UI）运行在同一进程中              │   │
│  │  问题：                                                         │   │
│  │  - 一个页面崩溃导致整个浏览器退出                                 │   │
│  │  - 插件漏洞可直接获取系统权限                                     │   │
│  │  - 多核 CPU 利用率低                                             │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  阶段 2: 多进程架构（Chrome 2008 首创）                                 │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  每个标签页独立进程 + 浏览器主进程 + 插件进程                    │   │
│  │  优势：                                                         │   │
│  │  - 标签页崩溃不影响整体                                           │   │
│  │  - 沙箱隔离提升安全性                                             │   │
│  │  - 多核并行处理能力提升                                           │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  阶段 3: 面向服务架构（SOA，Chrome 60+）                                │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  将功能拆分为独立服务：网络、GPU、Storage、Audio、Video 等       │   │
│  │  支持按需启动、资源复用，进一步降低内存开销                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.2 浏览器核心进程划分

现代 Chrome 浏览器包含以下核心进程，每个进程职责明确，通过 IPC（进程间通信）协作：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                   Chrome 核心进程与职责划分                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ① Browser Process（浏览器主进程）                                │   │
│  │  ────────────────────────────────────────────────────────────   │   │
│  │  • 控制 Chrome 应用的整体生命周期                                │   │
│  │  • 管理窗口（创建/销毁）、地址栏、书签、前进后退按钮              │   │
│  │  • 处理文件访问（下载、文件系统 API）                              │   │
│  │  • 协调其他进程的创建与销毁                                       │   │
│  │  • 系统级 UI 绘制（标题栏、工具栏）                               │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ② Renderer Process（渲染进程）【每个标签页独立一个】              │   │
│  │  ────────────────────────────────────────────────────────────   │   │
│  │  • 页面内容渲染（HTML/CSS/JS 解析与执行）                        │   │

│  │  • Blink 渲染引擎 + V8 JavaScript 引擎运行                       │   │
│  │  • 运行在沙箱环境中，无直接文件/系统访问权                        │   │
│  │  • 默认内存限制：512MB~1.5GB（因平台而异）                       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ③ GPU Process（GPU 进程）                                       │   │
│  │  ────────────────────────────────────────────────────────────   │   │
│  │  • 处理所有 GPU 相关请求（光栅化、合成、纹理上传）                │   │
│  │  • 统一管理 GPU 资源（显存、上下文）                             │   │
│  │  • 驱动显卡硬件：OpenGL / Metal / Direct3D / Vulkan              │   │
│  │  • 为所有渲染进程提供共享 GPU 服务                                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ④ Network Service（网络进程）                                    │   │
│  │  ────────────────────────────────────────────────────────────   │   │
│  │  • 处理所有网络请求（HTTP/HTTPS/WebSocket/FTP）                 │   │
│  │  • 缓存管理（HTTP Cache、Service Worker Cache）                 │   │
│  │  • Cookie 管理、CORS 检查、证书验证                              │   │
│  │  • 网络栈：TCP/IP、QUIC 协议实现                                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ⑤ Storage Service（存储进程）                                    │   │

│                                                                         │

### 1.3 渲染进程内部线程模型

每个渲染进程内部是一个复杂的多线程系统，核心线程划分如下：

| 线程名称 | 核心职责 | 关键说明 |
|---------|---------|---------|
| **Main Thread（主线程）** | HTML/CSS 解析、样式计算、布局、绘制、JS 执行 | 渲染核心，约 80% 的工作在此完成；任何阻塞 >50ms 即为 Long Task |
| **Compositor Thread（合成线程）** | 分块调度、光栅化调度、合成帧生成 | 不占用主线程，是 GPU 加速的关键 |
| **Raster Thread（光栅化线程）** | 执行具体的 Tile 光栅化任务 | 通常是线程池，数量 = CPU 核心数 |
| **Worker Threads（Worker 线程）** | Web Worker / Service Worker / Worklet | 独立 JS 上下文，不阻塞主线程 |
| **IO Thread（IO 线程）** | 与其他进程的 IPC 通信、网络数据接收 | 负责和浏览器进程/网络进程通信 |
| **Compositor Tile Worker** | 执行 GPU 光栅化的具体任务 | 由合成线程调度，运行在 GPU 进程侧 |

```
┌─────────────────────────────────────────────────────────────────────────┐
│                渲染进程线程协作示意图（简化）                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                        Main Thread                              │   │
│  │  HTML解析 → DOM → 样式计算 → 布局 → 分层 → 绘制指令(DisplayList) │   │
│  │  JS执行(V8) ←────────────────────────────────────────────────  │   │
│  └────────────────────────────────────┬────────────────────────────┘   │
│                                       │ Commit(提交)                    │
│                                       ▼                                 │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │                      Compositor Thread                          │   │
│  │  接收DisplayList → 分块(Tiling) → 调度光栅化 → 合成图层 → Draw  │   │
│  └──────────────────────┬──────────────────────┬────────────────────┘   │
│                         │                      │                        │
│                         ▼                      ▼                        │
│  ┌────────────────────────────┐    ┌────────────────────────────┐     │
│  │    Raster Thread Pool      │    │     GPU Process            │     │
│  │  (Raster Worker × N)      │    │  GPU光栅化 → 帧缓冲 → 屏幕  │     │
│  └────────────────────────────┘    └────────────────────────────┘     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 1.4 进程间通信（IPC）机制

Chrome 采用命名管道（Named Pipe）和共享内存（Shared Memory）实现高效 IPC：
- **小数据**：通过 Mojo IPC 消息传递（序列化后通过管道）
- **大数据（如图层位图）**：通过共享内存区域，避免数据拷贝
- **同步调用**：仅在必要时使用，通常是异步消息 + Callback

### 1.5 多浏览器架构差异对比

| 维度 | Chrome (Blink) | Firefox (Gecko) | Safari (WebKit) |
|------|----------------|-----------------|-----------------|
| **进程模型** | 每站点实例（Site Isolation）跨域 iframe 独立进程 | 多进程（Electrolysis），默认 4~8 个内容进程 | 每标签页独立进程，XPC 跨进程通信 |
| **沙箱强度** | 最强（Seccomp-BPF + 进程隔离 + Site Isolation） | 中等（进程沙箱 + 权限分离） | 强（macOS/iOS 系统沙箱 + 进程隔离） |
| **渲染引擎** | Blink（WebKit 分支，2013 年 fork） | Gecko（自研，Quantum 项目重构） | WebKit（开源，Apple 主导） |
| **合成架构** | 独立合成线程 + Skia GPU | 独立合成线程 + WebRender（Rust 重写） | 独立合成线程 + Core Animation |
| **JS 引擎** | V8（Google 自研，JIT：TurboFan） | SpiderMonkey（Mozilla 自研，JIT：IonMonkey） | JavaScriptCore（Apple 自研，JIT：LLInt→Baseline→DFG→FTL） |
| **GPU 光栅化** | 默认开启（Chrome 80+） | WebRender 默认开启（Firefox 93+） | 部分开启（取决于设备） |
| **内存占用** | 较高（进程多、隔离严格） | 中等（进程数可配置） | 较低（进程复用优化） |

### 2.1 核心渲染阶段全景

浏览器渲染是将 HTML/CSS/JS 资源转换为屏幕像素的一条严密流水线，每个阶段的输出是下一个阶段的输入。

│  ────────────          ───────────────────────         ─────────────    │

│  └────────┘   └───────────────┬──────────────────────┘             │    │
│       │                       │                                    │    │
│       ▼                       ▼                                    │    │
│  ┌────────┐   ┌──────────────────────────────────────┐             │    │
│  │ CSS    │──▶│ ② CSS解析 ──▶ Style Rules(CSSOM)     │             │    │
│  └────────┘   └───────────────┬──────────────────────┘             │    │
│                               ▼                                    │    │
│                    ┌──────────────────────────────┐                 │    │
│                    │ ③ 样式计算 ComputedStyle     │                 │    │
│                    └───────────────┬──────────────┘                 │    │
│                                    ▼                                  │    │

### 2.3 核心概念速查表

| 阶段 | 核心产物 | 执行位置 | 性能敏感度 | 关键优化点 |
|------|---------|---------|-----------|-----------|
| HTML 解析 | DOM Tree | 渲染主线程 | ⭐⭐⭐ | 减少标签嵌套、defer/async |
| CSS 解析 | Style Rules | 渲染主线程 | ⭐⭐ | 压缩CSS、按需加载(media) |
| 样式计算 | ComputedStyle | 渲染主线程 | ⭐⭐⭐ | 降低选择器复杂度、减少嵌套 |
| 布局 | Render Tree + 几何信息 | 渲染主线程 | ⭐⭐⭐⭐⭐ | 避免触发回流、批量读写DOM |
| 分层 | Layer Tree | 渲染主线程 | ⭐⭐ | 合理分层、避免图层爆炸 |
| 绘制 | Display List | 渲染主线程 | ⭐⭐⭐ | 减少重绘区域、简化绘制指令 |
| 分块 | Tile列表 | 合成线程 | ⭐ | 视口优先策略(浏览器自动) |
| 光栅化 | GPU 位图 | GPU 进程 | ⭐⭐⭐ | 减少图层数量和尺寸、简化绘制 |
| 合成 | 合成帧 | 合成线程+GPU | ⭐⭐⭐⭐ | 优先使用transform/opacity |
| 显示 | 屏幕像素 | GPU + 显示器 | ⭐⭐ | 对齐VSync、避免丢帧 |

## 三、HTML 解析过程

### 3.1 HTML 解析器工作机制

HTML 解析由 **Blink 引擎**（Chrome/Edge/Opera）或 **WebKit**（Safari）中的 HTMLParser 完成，是一个**增量、容错、可中断**的过程。

#### 解析四步骤详解

```
┌─────────────────────────────────────────────────────────────────────────┐
│                     HTML 解析四步骤（含技术细节）                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Step 1: 字节流解码（Byte Stream Decoding）                              │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  输入：TCP 接收的原始字节流（可能分 chunk 到达）                   │   │
│  │  处理流程：                                                       │   │
│  │    1. 检测 BOM（Byte Order Mark）→ 推断编码                       │   │
│  │    2. 读取 <meta charset="UTF-8"> → 确定编码                      │   │
│  │    3. 若无 charset 声明 → 使用 HTTP Content-Type 头               │   │
│  │    4. 仍无法确定 → 统计字节分布推测编码（中文通常误判为 GBK）       │   │
│  │    5. 通过编码表（ICU 库）转换为 Unicode 字符流                    │   │
│  │                                                                 │   │
│  │  示例：                                                           │   │
│  │  字节流(hex): 3C 68 74 6D 6C 3E E4 B8 AD E6 96 87               │   │
│  │       │                                                           │   │
│  │       ▼ (UTF-8 解码)                                              │   │
│  │  字符流: <html>中文                                                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 2: 词法分析（Tokenization）                                       │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  实现：基于状态机的逐字符扫描（HTML5 规范定义了 80+ 种状态）       │   │
│  │  核心状态：Data → TagOpen → TagName → BeforeAttrName → ...      │   │
│  │                                                                 │   │
│  │  Token 类型及示例：                                               │   │
│  │  ┌──────────────┬────────────────────────────────────────────┐ │   │
│  │  │ DOCTYPE      │ <!DOCTYPE html>                             │ │   │
│  │  │ StartTag     │ <div class="a" id="b"> → attrs=[[class,a], │ │   │
│  │  │              │                  [id,b], [self-closing,false]]│ │   │
│  │  │ EndTag       │ </div>                                       │ │   │
│  │  │ Comment      │ <!-- comment -->                             │ │   │
│  │  │ Character    │ 普通文本（逐字符累加，直到遇到 < ）             │ │   │
│  │  │ EOF          │ 文档结束标记                                  │ │   │
│  │  └──────────────┴────────────────────────────────────────────┘ │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 3: 语法分析（Tree Construction）                                  │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  数据结构：Open Element Stack（开放元素栈）                        │   │
│  │  算法：HTML5 规范中定义的"树构建调度算法"                          │   │
│  │                                                                 │   │
│  │  栈操作规则：                                                     │   │
│  │  • StartTag → 创建 Element 节点→ 压栈 → 设置 attrs              │   │
│  │  • EndTag   → 弹栈直到匹配的 StartTag → 建立父子关系            │   │
│  │  • Character→ 创建 Text 节点 → 追加为当前栈顶的子节点           │   │
│  │  • 容错处理：遇到不匹配的标签时自动补全/闭合                      │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 4: DOM 树组装                                                     │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  最终产物：以 Document 为根的连通有向无环图（实际上是树）          │   │
│  │  同时生成：                                                       │   │
│  │   • Flat Tree（分布树，用于 Shadow DOM 扁平化遍历）               │   │
│  │   • NodeLists（live collection，如 document.forms）              │   │
│  │   • Accessibility Tree（无障碍树）                               │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 完整解析示例

```html
<!-- 原始 HTML（含省略标签的容错场景） -->
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <title>HTML 解析示例
</head>
<body>
  <p>第一段<p>第二段  <!-- 注意：<p> 未闭合，浏览器自动补全 -->
  <ul><li>Item 1<li>Item 2</ul>  <!-- 省略 </li> -->
  <img src="logo.png" alt="Logo">  <!-- 自闭合标签 -->

```

```

├── DocumentType: html
└── html (lang="zh-CN")
    ├── head

    │   └── title: "HTML 解析示例"
    └── body

        ├── p: "第二段"          ← 第二个 <p> 触发前一个闭合
        ├── ul

        │   └── li: "Item 2"

```

### 3.2 预解析器（Preload Scanner）

当 HTML 解析器遇到 `<script>` 标签而暂停主线程解析时，**预解析器（Preload Scanner / Speculative Parser）** 会**先行扫描**后续的 HTML 内容，查找可以提前下载的资源。这是现代浏览器最重要的性能优化之一。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    预解析器工作机制与时间线                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  时间轴 ─────────────────────────────────────────────────────────────▶  │
│                                                                         │
│  主线程HTML解析:                                                        │
│  ████████░░░░░░░░░░░░░░█████████████████████████████████████            │
│     ↑           ↑              ↑                                        │
│  遇到<script>  暂停解析    JS执行完，恢复解析                             │
│     │           │              │                                        │
│     ▼           ▼              ▼                                        │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  暂停期间：预解析器启动！（独立轻量扫描器，不构建DOM）              │   │
│  │  ─────────────────────────────────────────────────────────────   │   │
│  │  扫描内容：                                                       │   │
│  │  • <img src="...">  → 提前发起图片下载                           │   │
│  │  • <link rel="stylesheet" href="..."> → 提前下载CSS              │   │
│  │  • <script src="..."> → 提前下载JS（主线程到这里时直接执行）       │   │
│  │  • <video poster src="..."> → 提前下载封面图                      │   │
│  │  • @import url(...) in <style> → 额外扫描inline CSS              │   │
│  │                                                                 │   │
│  │  ⚠️ 重要限制：预解析器不执行任何JS，不处理 document.write          │   │
│  │     因此如果 document.write 写入了资源标签，这些标签无法被预扫描   │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  性能收益：                                                             │
│  • 典型场景下，首屏加载时间可缩短 15%~40%                              │
│  • 避免「主线程等JS下载 → JS执行完才发现有CSS → 又等CSS下载」的串行浪费 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

**代码示例：document.write 破坏预解析**
```html
<!-- ❌ 反模式：document.write 写入的 <script> 无法被预解析 -->
<script>
  // 主线程执行到这里，预解析器无法预知下面会写入什么
  document.write('<script src="heavy.js"><\/script>');
  // heavy.js 只能从这一刻才开始下载，严重延迟首屏
</script>

<!-- ✅ 推荐：直接写静态标签，预解析器可提前发现 -->
<script src="heavy.js" defer></script>
```

### 3.3 增量解析与容错机制

HTML 解析器的设计哲学是「**永远不要让用户看到错误页面**」，因此具备极强的容错能力：

| 容错场景 | 浏览器处理方式 | 示例 |
|---------|--------------|------|
| **未闭合标签** | 自动补全闭合 | `<p>text<p>text2` → 两个独立 `<p>` |
| **非法嵌套** | 提前闭合父元素 | `<p>text<div>child</div></p>` → `<p>` 在 `<div>` 前自动闭合 |
| **未知标签** | 创建为 HTMLUnknownElement | `<custom>` → HTMLElement 子类，不影响其他解析 |
| **位置错误标签** | 自动调整到合法位置 | `<body>` 内的 `<link>` 仍生效；`<head>` 外的 `<meta>` 移动到 head |
| **字符编码中途声明** | 重新解析已收到的字节流 | `<meta charset="UTF-8">` 在第 1024 字节后才出现时触发重解析 |
| **document.write 插入脚本** | 同步执行并继续解析后续内容 | 但**注意**：异步脚本中调用 document.write 会导致 `document.open()` 并清空当前文档 |

### 3.4 DOM 树构建

#### DOM 节点类型

| 节点类型 (nodeType) | 常量值 | 说明 | 示例 |
|--------------------|--------|------|------|
| `ELEMENT_NODE` | 1 | 元素节点（HTML标签） | `<div>`, `<p>`, `<img>` |
| `TEXT_NODE` | 3 | 文本节点 | `"Hello World"` |
| `PROCESSING_INSTRUCTION_NODE` | 7 | 处理指令 | `<?xml-stylesheet?>` |
| `COMMENT_NODE` | 8 | 注释节点 | `<!-- comment -->` |
| `DOCUMENT_NODE` | 9 | 文档根节点 | `document` |
| `DOCUMENT_TYPE_NODE` | 10 | DOCTYPE 声明 | `<!DOCTYPE html>` |
| `DOCUMENT_FRAGMENT_NODE` | 11 | 文档片段（轻量容器） | `document.createDocumentFragment()` |

> **注意**：`ATTRIBUTE_NODE`（2）在 DOM Level 4 中已废弃，属性现在作为 NamedNodeMap 存储在 Element 上，不再是独立节点。

                        ════════════════════════════════▶  ████

**CSS 间接阻塞 JS 执行的陷阱：**
```html
<head>
  <!-- 先加载 CSS（可能很慢） -->
  <link rel="stylesheet" href="slow.css"><!-- 假设下载需要5秒 -->

  <!-- 后加载的 JS：即使 JS 下载只要 50ms -->
  <script src="fast.js"></script>
  <!-- ❌ 仍需要等 5 秒 slow.css！
       因为浏览器无法预知 fast.js 中是否会读取依赖样式的 API，
       如 getComputedStyle()、offsetWidth、clientWidth 等。
       为了保证返回一致的结果，JS 执行被 CSS 间接阻塞。 -->
</head>
```

## 四、CSS 解析过程

### 4.1 CSS 解析器与规则处理

CSS 解析由 Blink/WebKit 中的 CSSParser（基于 Bison/Flex 生成的 LALR 解析器，或现代手写递归下降解析器）完成。

```

### 4.2 CSSOM 的真实结构（修正）

> **重要修正**：很多资料将 CSSOM 描述为「与 DOM 树对应的并行树结构」，这在技术上不准确。**实际上 CSSOM 是一组按源顺序排列的 StyleSheet 规则集合，通过选择器索引与 DOM 节点关联**，而不是「每个 DOM 节点对应一个 CSSOM 节点」。样式计算阶段才真正完成 DOM 节点与 CSS 规则的匹配。

```
┌─────────────────────────────────────────────────────────────────────────┐
│          CSSOM 的真实结构 vs 常见误解对比（重要概念修正）                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ❌ 常见误解（CSSOM 是与 DOM 一一对应的树）：                           │
│  DOM:  html → body → div.container → p → span                         │
│  CSSOM: html → body → div.container → p → span  ❌ 错误               │
│                                                                         │
│  ✅ 真实结构（CSSOM = 规则集合 + 选择器索引 + 样式计算结果）：           │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  Style Rules 集合（按源顺序排列，可能来自多个 <link>/<style>）     │   │
│  │  ┌───────────────────────────────────────────────────────────┐ │   │
│  │  │ R1: * { box-sizing: border-box; }       [特异性 0,0,0,0]  │ │   │
│  │  │ R2: body { margin: 0; font: 16px sans; } [特异性 0,0,0,1]  │ │   │
│  │  │ R3: .container { max-width: 1200px; }     [特异性 0,0,1,0]  │ │   │
│  │  │ R4: p { line-height: 1.6; color: #333; }   [特异性 0,0,0,1]  │ │   │
│  │  │ R5: #header .nav a { ... }                 [特异性 0,1,1,1]  │ │   │
│  │  │ R6: @media (max-width:768px) { .container{padding:0 16px} } │ │   │
│  │  │ R7: div > p + p { margin-top: 1em; }       [特异性 0,0,1,2]  │ │   │
│  │  └───────────────────────────────────────────────────────────┘ │   │
│  │                                                                 │   │
│  │  辅助加速结构（浏览器内部实现，不在 W3C 规范中）：                 │   │
│  │  ┌───────────────────────────────────────────────────────────┐ │   │
│  │  │  • RuleHashes: 按选择器类型分组                              │ │   │
│  │  │    - ID规则表:   #header → [R5]                             │ │   │
│  │  │    - Class规则表: .container → [R3], .nav → [R5]            │ │   │
│  │  │    - Tag规则表:   body → [R2], p → [R4,R7]                  │ │   │
│  │  │    - Universal规则: * → [R1]                                │ │   │
│  │  │  • BloomFilter(布隆过滤器): 快速排除不匹配的规则               │ │   │
│  │  │    当遇到一个 p.container 节点时，先查布隆过滤器，             │ │   │
│  │  │    如果规则里既不含 p 也不含 .container，直接跳过该规则表     │ │   │
│  │  └───────────────────────────────────────────────────────────┘ │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  样式计算阶段（真正的 DOM ↔ CSS 关联）：                                  │
│  对每个 DOM 节点，从规则集合中匹配所有选择器，按优先级合并 → ComputedStyle │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.3 选择器匹配优化机制

现代浏览器对选择器匹配进行了大量优化，核心原则是**从右向左匹配（Right-to-Left Matching）**。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                  选择器从右向左匹配的原理与收益                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  选择器示例：.container ul li.active a span                              │
│                                                                         │
│  ❌ 从左向右匹配（低效）：                                               │
│  找到所有 .container → 遍历其子孙找 ul → 找 li → 过滤 .active → ...    │
│  问题：大部分 .container 的子孙都不满足完整路径，大量回溯                 │
│                                                                         │
│  ✅ 从右向左匹配（高效）：                                               │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  1. 最右关键字是 span → 先查 Tag 规则表，找到所有 <span> 节点     │   │
│  │  2. 检查它的直接父节点是否是 <a>                                │   │
│  │  3. 检查 <a> 的祖先链是否存在 li.active                          │   │
│  │  4. 检查 li.active 的祖先是否有 ul                               │   │
│  │  5. 检查 ul 的祖先是否有 .container                              │   │
│  │  6. 全部满足 → 匹配成功，否则立即失败（快速排除）                │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  为什么更快？                                                            │
│  • 起点从「数量很少的匹配结果」开始，而不是从「可能匹配的所有祖先」开始   │
│  • 中途不匹配可立即剪枝，避免深度回溯                                    │
│                                                                         │
│  开发者可做的优化：                                                      │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  ✅ 最右选择器尽量具体（高特异性、少节点匹配）                    │   │
│  │     .list-item .title  >  div a .title                         │   │
│  │  ❌ 避免过度嵌套的后代选择器                                      │   │
│  │     body div ul li a span （6 层，每层都要祖先链检查）            │   │
│  │  ✅ 优先使用 Class/ID 而非 Tag 作为最右选择器                     │   │
│  │     .btn-primary  >  button.btn-primary （前者先过滤 class）    │   │
│  │  ❌ 避免使用通配符 * 作为最右选择器                                │   │
│  │     .container * （匹配所有元素，然后逐一检查祖先链）             │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 五、样式计算（Style Computation）

### 5.1 样式计算四阶段流水线

样式计算的目标是为**每个 DOM 节点**生成一份完整的、无歧义的 `ComputedStyle`（所有 CSS 属性均有唯一值）。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                   样式计算四阶段完整流水线                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  输入: DOM 节点 + 所有匹配的 CSS 规则 + 浏览器 UA stylesheet            │
│  输出: ComputedStyle (Immutable, ~300 个 CSS 属性全部有值)               │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ Phase 1: 声明值收集（Cascading Value Collection）                 │   │
│  │ ─────────────────────────────────────────────────────────────   │   │
│  │  • 遍历 UA / User / Author 所有样式表                            │   │
│  │  • 对当前节点执行选择器匹配（从右向左 + 布隆过滤器加速）           │   │
│  │  • 收集所有匹配的声明，形成 per-property 候选列表                 │   │
│  │  • 同时收集 inline style（style="" 属性）                         │   │
│  │  • 输出: { color: [候选1,候选2,候选3], width: [...], ... }       │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                    │                                    │
│                                    ▼                                    │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ Phase 2: 层叠冲突解决（Cascade Resolution）                       │   │
│  │ ─────────────────────────────────────────────────────────────   │   │
│  │  对每个属性的候选列表，按三层优先级排序取最高者：                   │   │
│  │  1. Origin & Importance（按优先级从高到低）                       │   │
│  │     Author !important > User !important > UA !important >       │   │
│  │     Author 普通 > User 普通 > UA 普通                             │   │
│  │  2. Specificity（特异性: 行内,ID,类/属性/伪类,元素/伪元素）       │   │
│  │  3. Source Order（源顺序: 后加载优先）                            │   │
│  │  输出: { color: blue(胜出), width: 200px(胜出), ... }            │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                    │                                    │
│                                    ▼                                    │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ Phase 3: 继承值传播（Inheritance）                                 │   │
│  │ ─────────────────────────────────────────────────────────────   │   │
│  │  对 Phase 2 仍无值的属性：                                        │   │
│  │  • 标记为「可继承」的属性 → 从父节点的 ComputedStyle 拷贝         │   │
│  │  • 标记为「不可继承」的属性 → 跳过，留待 Phase 4 处理             │   │
│  │  支持的显式关键字：inherit / initial / unset / revert / revert-layer │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                    │                                    │
│                                    ▼                                    │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │ Phase 4: 默认值填充（Defaulting / Value Processing）             │   │
│  │ ─────────────────────────────────────────────────────────────   │   │
│  │  对剩余所有仍无值的属性：                                         │   │
│  │  • 不可继承属性 → 填 initial value（CSS 规范定义）                │   │
│  │  • 特殊关键字处理: unset(可继承→inherit, 不可继承→initial)       │   │
│  │  • 单位转换: em/rem/% → 计算为 px（生成 Used Value）             │   │
│  │  • 颜色解析: red/blue/#FF0000/rgba(255,0,0,1) → RGBA 四元组    │   │
│  │  • 枚举值归一化: flex-start / block / pointer-events 等         │   │
│  │  输出: 完整、无歧义的 ComputedStyle 对象                        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.2 层叠优先级算法详解

#### 三层优先级体系（CSS Cascade 规范）

```
┌─────────────────────────────────────────────────────────────────────────┐
│              CSS 层叠优先级完整规范（依据 W3C CSS Cascade 4）              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Level 1: Origin + Importance（从高到低，胜出者直接进入下一轮比较）      │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  0. <div style="color:red !important"> 行内!important         ‖  │   │
│  │  1. 作者样式表 .box { color:red !important }                  ‖  │   │
│  │  2. 用户样式表（浏览器自定义样式）!important                  ‖  │   │
│  │  3. User Agent 样式表（浏览器默认）!important                  ‖  │   │
│  │  4. @layer 声明的动画 @keyframes {...}                        ‖  │   │
│  │  5. 作者样式表 普通声明                                         ‖  │   │
│  │  6. 行内样式 style="color:red"（非!important）                 ‖  │   │
│  │  7. 用户样式表 普通声明                                         ‖  │   │
│  │  8. User Agent 样式表 普通声明（浏览器默认）                    ‖  │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Level 2: Specificity（仅 Level 1 打平时比较）                          │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  元组表示: (Inline, IDs, Classes/Attrs/Pseudo-classes, Elements/Pseudo-elements)│   │
│  │  比较规则: 从左到右逐位比较，高位胜出；高位相同再比低位             │   │
│  │                                                                 │   │
│  │  示例（选择器排序，特异性从高到低）：                              │   │
│  │  ┌───────────────────────────────────────────────────────────┐ │   │
│  │  │ style="color:red"            (1,0,0,0)  ← 行内样式        │ │   │
│  │  │ #app .nav li.active::before  (0,1,2,2)                    │ │   │
│  │  │ #header ul li                (0,1,0,2)                    │ │   │
│  │  │ .menu ul li a.current        (0,0,2,3)                    │ │   │
│  │  │ ul li.item span              (0,0,1,3)                    │ │   │
│  │  │ div p span::after            (0,0,0,3)                    │ │   │
│  │  │ *                            (0,0,0,0)  ← 通配符无特异性   │ │   │
│  │  └───────────────────────────────────────────────────────────┘ │   │
│  │                                                                 │   │
│  │  ⚠️ 关键认知: (0,1,0,0) > (0,0,999,999)                        │   │
│  │     1 个 ID 选择器 > 999 个 Class 选择器（不是十进制进位！）    │   │
│  │     这也是为什么业界通常建议少用 ID 选择器（特异性太高，难覆盖） │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Level 3: Source Order / Layer Order（前两级均打平时比较）              │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  1. 声明位于 @layer 中：按声明 layer 的出现顺序（先出现优先级低） │   │
│  │  2. 未在 @layer 中声明 > 任何 @layer 中声明                      │   │
│  │  3. 同层级/无 layer：按 CSS 源码出现顺序（后出现覆盖先出现）     │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.3 属性继承与默认值填充

| 继承分类 | 属性类别 | 示例属性 | 原理说明 |
|---------|---------|---------|---------|
| **可继承** | 字体相关 | `font-family`, `font-size`, `font-weight`, `line-height`, `letter-spacing` | 文本属性默认继承，保证段落文字风格统一 |
| **可继承** | 颜色/文本 | `color`, `text-align`, `text-indent`, `text-transform`, `direction` | 避免在每个 p/span 重复设置颜色 |
| **可继承** | 列表相关 | `list-style`, `list-style-type`, `list-style-position` | 列表项自动继承父容器的列表样式 |
| **可继承** | 其他 | `visibility`, `cursor`, `quotes`, `orphans`, `widows` | 视觉交互属性 |
| **不可继承** | 布局盒模型 | `display`, `width`, `height`, `margin`, `padding`, `border`, `box-sizing` | 每个盒子独立布局 |
| **不可继承** | 定位 | `position`, `top/right/bottom/left`, `float`, `z-index` | 独立定位上下文 |
| **不可继承** | 背景 | `background`, `background-color`, `background-image` | 背景独立（视觉上透明会透出父元素，这不是继承） |
| **不可继承** | 视觉效果 | `opacity`, `transform`, `filter`, `box-shadow`, `overflow`, `border-radius` | 独立渲染效果 |

**特殊关键字含义：**
```css
/* 继承：强制从父元素拷贝可继承/不可继承属性的值 */
.child { border: inherit; }  /* 继承父元素的 border（即使 border 不可继承） */

/* initial：重置为规范定义的初始值（不看父元素） */
.special { color: initial; }  /* color 的 initial 是 black（不是父元素的 color） */

/* unset：智能重置 - 可继承属性 → inherit；不可继承属性 → initial */
.reset { all: unset; }  /* 一把清除，非常适合组件隔离 */

/* revert：回退到「当前来源层」之上一层的值 */
.override { color: revert; }  /* Author 声明中使用 → 回到 UA 或 User 样式值 */
```

### 5.4 样式共享机制（Style Sharing）

为了避免对每个 DOM 节点重复计算相同的 ComputedStyle，现代浏览器实现了**样式共享缓存（Style Sharing Cache）**，这是一项非常重要的性能优化（在复杂页面上可节省 30%~60% 样式计算时间）。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                   样式共享缓存命中条件（WebKit/Blink）                    │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  两个 DOM 节点可共享 ComputedStyle 当且仅当：                            │
│  ✅ 标签名相同（tagName）                                                │
│  ✅ class 属性值完全相同（包括顺序和字符串表示）                           │
│  ✅ id 属性相同                                                          │
│  ✅ 相同的父节点（或父节点样式也可共享）                                  │
│  ✅ inline style 属性完全相同                                            │
|  ✅ 伪类状态相同（:hover/:focus/:active/:checked 等）                    │
│  ✅ 受相同的 @media 规则影响                                             │
|  ✅ 相同的属性覆盖（例如 CSS 变量声明）                                  │
│                                                                         │
│  实际效果：                                                             │
│  • 列表项（li）、表格行（tr）、卡片组件通常 90%+ 命中共享缓存            │
│  • 命中共享：O(1) 哈希查找，无需执行 4 阶段样式计算                       │
│  • 未命中：完整执行 4 阶段流水线，并写入缓存供后续节点复用               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 6.1 布局树（Render Tree）构建

布局树（Blink 中叫 `LayoutObject` 树，WebKit 中叫 `RenderObject` 树，Firefox 中叫 `Frame Tree`）从 DOM 树中筛选出**需要渲染的可见节点**。

│              DOM Tree vs Render Tree 对比（含伪元素与 display:none）     │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  DOM Tree（所有节点，不可见节点保留）:                                    │
│  html                                                                   │

│  │   ├── title (display:none)│ 不进入 Render Tree                      │

│  └── body                                                                │
│      ├── script ←─── display:none (HTML 隐式 UA 样式)，不渲染          │
│      ├── .header (position:relative) ← 进入                            │
│      │   └── ::before ← content 属性存在 → 生成独立 RenderObject       │
│      ├── main                                                           │
│      │   ├── p ← 进入                                                   │
│      │   ├── #hidden (display:none) ← 不进入（自身+子树都跳过）        │

### 6.3 包含块（Containing Block）确定规则

包含块是百分比计算的参考基准，其确定规则是 CSS 布局中最容易混淆的知识点之一。

| 元素定位模式 | 包含块（Containing Block）判定规则 |
|------------|---------------------------------|
| **static / relative**（常规流） | 最近的**块级祖先元素**（非 display:inline）的**内容区域（Content Box）** |
| **absolute** | 最近的**非 static 定位的祖先元素**的**内边距区域（Padding Box）**；如果找不到则为 Initial Containing Block（视口） |
| **fixed** | 通常为**视口（Viewport）**；但如果有祖先元素设置了 `transform`、`perspective`、`filter`（非 none）、`will-change:transform`、或 `contain:layout paint size`，则该祖先的 Padding Box 成为包含块 |
| **sticky** | 包含块同 relative；但偏移约束受最近的滚动容器和视口阈值限制 |
| **Initial Containing Block** | 根元素 html 的包含块，尺寸等于视口（连续媒体）或页面盒（分页媒体） |

**经典陷阱：`position:fixed` 被 transform「擒获」**
```html
<!-- ❌ fixed 定位被父元素 transform 限制在父容器内，而不是视口 -->
<div class="parent" style="transform: scale(1); width: 300px; height: 300px; overflow: hidden;">
  <div class="child" style="position: fixed; top: 0; right: 0;">
    我本想相对视口固定在右上角，但因为父元素有 transform，
    我被「困」在了 parent 的 300×300 区域内，且随 parent 滚动！
  </div>
</div>
```

### 6.4 增量布局与脏标记系统

现代浏览器不会在每次样式变化时重新计算整个页面的布局，而是采用**脏标记（Dirty Bit / Dirtify）** + **增量布局（Incremental Layout）** 系统，将重算范围限制到最小。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                  增量布局与脏标记系统工作流程                             │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. 触发：JS 修改了某元素的 width/position 等                            │
│     │                                                                   │
│     ▼                                                                   │
│  2. 标记该 RenderObject 为「NeedsLayout」（脏）                        │
│     • 同时向上标记所有祖先链为「需要子树布局（ChildNeedsLayout）」      │
│     • 向下标记后代为「可能受影响（可能不需要，实际检查时判断）」         │
│                                                                         │
│     脏标记扩散示意图：                                                   │
│     html (ChildNeedsLayout)                                             │
│       └── body (ChildNeedsLayout)                                       │
│             └── .container (ChildNeedsLayout)                           │
│                   └── .card (NeedsLayout) ← 实际被修改的节点           │
│                         ├── .title (可能影响，需测量)                   │
│                         └── .content (可能影响，需测量)                 │
│                                                                         │
│     │                                                                   │
│     ▼                                                                   │
│  3. 实际执行布局（在下次 VSync 到来或强制读取时触发）                   │
│     • 从根节点开始 DFS 遍历 Render Tree                                 │
│     • 只重算标记为脏的子树；干净子树直接复用上次的几何信息               │
│     • 重算时根据「约束从外到内、尺寸从内到外」的盒模型规则              │
│                                                                         │
│     布局遍历方向：                                                       │
│     ① Constraint Pass（从上到下）：父节点 → 向子节点传递可用空间约束   │
│     ② Measure Pass（从下到上）：叶子节点 → 计算自身尺寸 → 告知父节点   │
│     ③ Placement Pass（从上到下）：父节点 → 根据子节点尺寸决定位置      │
│                                                                         │
│     │                                                                   │
│     ▼                                                                   │
│  4. 所有脏标记清除，RenderObject 附带全新 geometry                      │
│                                                                         │
│  浏览器优化策略：                                                       │
│  ┌─────────────────────────────────────────────────────────────────┐   │
│  │  • 异步批量执行：避免每次 DOM 修改都立即布局                     │   │
│  │    （但读取 offsetWidth 等会强制同步布局，见 Layout Thrashing）  │   │
│  │  • 子树布局隔离：Flex/Grid 容器布局不影响兄弟节点                │   │
│  │  • 多线程优化：部分测量可在 Worker 进行（Chrome LayoutNG 项目） │   │
│  │  • 布局缓存：相同输入下复用上次结果（Layout Unit Tests）        │   │
│  └─────────────────────────────────────────────────────────────────┘   │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 6.5 BFC、IFC、FFC、GFC 格式化上下文

格式化上下文（Formatting Context）是 CSS 布局规则的作用域，决定盒子的排列方式和相互影响范围。

| 格式化上下文 | 全称 | 触发条件 | 布局规则 | 典型应用 |
|------------|------|---------|---------|---------|
| **BFC** | Block Formatting Context | `overflow: hidden/auto/scroll`; `float` ≠ none; `display: flow-root/inline-block/flex/grid/table-cell`; `position: absolute/fixed` | 块级盒子从上到下垂直排列；同 BFC 内相邻块级 margin 会折叠；BFC 不会与 float 元素重叠；BFC 是独立的容器，内部子元素不影响外部 | 清除浮动、防止 margin 折叠、自适应多栏布局 |
| **IFC** | Inline Formatting Context | 块级容器中仅含 inline 级盒子时生成 | 行内盒子从左到右水平排列；可跨行折行；行高（line-box）由最高盒子决定；`vertical-align` 控制盒子在行内的垂直对齐 | 文本排版、图片和文字混排 |
| **FFC** | Flex Formatting Context | `display: flex / inline-flex` | 主轴方向排列（row/column）；flex-grow/shrink/basis 控制分配；支持 wrap 换行；独立对齐模型（justify/align-content/items/self） | 一维弹性布局、导航栏、圣杯 |
| **GFC** | Grid Formatting Context | `display: grid / inline-grid` | 二维行列网格排布；`grid-template-rows/columns` 定义轨道；`grid-area/column/row` 放置子项；支持 `repeat()`/`auto-fill`/`minmax()` | 二维复杂布局、仪表盘、卡片流 |

## 十一、回流、重绘与合成对比

### 11.1 渲染更新流水线与属性影响

```
属性: width/height/padding/position/display/flex-direction 等【几何属性】
  → Style(可跳过否?否) → Layout【回流Reflow⭐⭐⭐⭐⭐】 → Paint【重绘】 → Composite【合成】 → Display
属性: color/background-color/border-color/text-shadow/box-shadow(无blur) 等【视觉属性】
  → Style → (跳过Layout✅) → Paint【重绘Repaint⭐⭐⭐】 → Composite → Display
属性: transform / opacity(✅独立合成层) / scroll(合成层) 等【仅合成属性】
  → Style → (跳过Layout✅) → (跳过Paint✅重绘) → Composite【仅合成⭐】 → Display
```

### 11.2 Reflow vs Repaint vs Composite 完整多维对比

| 维度 | 回流 Reflow | 重绘 Repaint | 仅合成 Composite |
|------|-----------|-------------|-----------------|
| **触发条件** | 修改元素几何属性或内容或窗口尺寸 | 修改视觉属性(颜色/阴影/文字外观)不改变几何 | 独立合成层上transform/opacity/滚动 |
| **执行阶段** | 布局Layout + 之后全部阶段 | 绘制Paint + 之后阶段 | 仅合成Composite + Display |
| **执行线程** | 渲染主线程 Main | 渲染主线程 Main (+ 光栅化 GPU) | 合成线程Compositor + GPU Process（几乎不阻塞主线程） |
| **性能成本** | ⭐⭐⭐⭐⭐ 最高（牵一发动全身，Dirty子树遍历+盒模型三Pass） | ⭐⭐⭐ 中等（Display List更新 + Tile重光栅化） | ⭐ 最低（仅GPU混合纹理+平移） |
| **相对耗时** | 100 （基准） | 10~30 | 0.1~1 |
| **影响范围** | 自身 + 所有后代 + 可能兄弟/父节点（增量布局尽力隔离） | 自身 + 同Paint Layer重叠区域Tile | 仅当前合成层 |
| **典型耗时** | 几十ms ~ 几百ms（大型布局） | 几ms ~ 几十ms | <1ms |
| **用户感知** | 严重卡顿、掉多帧 | 画面局部变化、滚动掉帧 | 几乎丝滑60fps+ |

**仅触发合成（跳过Layout+Paint，最推荐用于动画）**
```
transform: translate / translateX / translateY / translate3d / translateZ
          scale / scaleX/Y/Z / rotate / rotateX/Y/Z / rotate3d / skew / matrix / matrix3d
opacity (⚠️前提：元素为独立Graphics Layer合成层！若不是→触发重绘)
滚动(页面滚动、overflow:scroll容器滚动)
filter / backdrop-filter（⚠️仅元素有合成层时可用；否则触发重绘且昂贵）
```

### 11.4 强制同步布局 Layout Thrashing 💀

> 最容易被前端忽视的性能杀手！循环内 先读后写 → 浏览器被迫一次又一次立即执行完整布局（而不是异步批量合并）。

**问题代码（💀每元素触发一次完整布局）**
```js
const list = document.querySelectorAll('.item');
list.forEach(el => {
  const w = el.offsetWidth;         // ① 读：强制先执行所有挂起的样式+布局以得到最新值
  el.style.width = (w + 10) + 'px'; // ② 写：标记脏节点
});
// N个元素 → 触发N次完整布局！N=100 → 100ms+卡顿💀
```

**修复（✅先批量读后批量写，2次布局搞定）**
```js
const list = document.querySelectorAll('.item');
const widths = [...list].map(el => el.offsetWidth); // ① 批量一次性全部读完（布局1次）
list.forEach((el, i) => {
  el.style.width = (widths[i] + 10) + 'px'; // ② 批量写（布局合并1次）
});
// 仅2次布局✅
```

**触发强制同步布局的读取API清单：**
- 几何: `offsetWidth/Height/Left/Top`、`clientWidth/Height/Left/Top`、`scrollWidth/Height/Left/Top`、`getBoundingClientRect()`、`getClientRects()`
- 样式: `getComputedStyle()`、`elementFromPoint()/elementsFromPoint()`、`caretRangeFromPoint()`
- 其他: `innerText`（⚠️老IE遗留但现代浏览器仍可能）、`select()`（表单元素测量）

### 11.5 will-change 与 CSS Containment（主动优化API）

**will-change：告诉浏览器「这个属性马上要变，提前准备好」**
```css
/* 正确用法：动画前给目标元素临时加，动画结束移除 */
.smooth-slider.about-to-animate { will-change: transform, opacity; }

/* ❌ 错误用法：全局永久加（导致合成层常驻→显存爆炸） */
* { will-change: transform, opacity; } /* 💀禁止 */
.class-permanent { will-change: transform; } /* 静态元素也常驻合成层→浪费 */
```

**CSS Containment：严格隔离子树渲染影响范围**
```css
.card-item {
  contain: layout paint size style;
  /*
    layout: 内部布局不影响外部（独立BFC+不对外传）
    paint:  内部绘制不出边界+外部绘制不影响内部
    size:   尺寸不取决于内部内容（必须显式设置宽/高）
    style:  counter/quote等样式不与外部互相泄露
    简写: contain: strict → layout paint size;
          contain: content → layout paint style
  */
}
/* 适用场景：列表项、组件卡片区 — 回流/重绘时只重绘子树，性能提升30%+ */
```

## 十二、关键渲染路径 CRP 优化

### 12.1 CRP 定义与衡量指标

**定义**：浏览器从接收HTML到渲染出首屏可交互内容所需的完整路径。
`HTML下载→HTML解析→CSS下载→CSSOM构建→样式计算→布局→绘制→光栅化→合成→首屏显示`

**核心优化目标：**
1. 减少**关键资源数量**（CRP上必须等的资源数）
2. 减小**关键资源大小**（KB越少越快）
3. 优化**关键资源加载顺序**（关键越早越好；非关键越晚/异步越好）
4. 减少**RTT往返次数**（关键链路越短越好）

**Web Vitals核心性能指标（Google官方）**

| 指标 | 全称 | 优秀阈值 | 说明 |
|------|------|---------|------|
| **LCP** | Largest Contentful Paint | <2.5s | 首屏最大内容元素渲染完成时间（主衡量） |
| **FID** | First Input Delay | <100ms | 用户首次点击/触摸到浏览器开始响应的延迟（即将被INP替代） |
| **INP** | Interaction to Next Paint | <200ms | 综合所有交互事件：click/touch/keyboard→下帧显示的p95延迟（2024年3月替代FID） |
| **CLS** | Cumulative Layout Shift | <0.1 | 全生命周期累积布局偏移（视觉稳定度：图片未给尺寸/字体切换/动态插入导致位移） |
| **FCP** | First Contentful Paint | <1.8s | 首次显示任何DOM内容（文本/像素/图片） |
| **TTFB** | Time To First Byte | <800ms | 服务器首字节响应时间 |
| **TTI** | Time to Interactive | <3.8s | 主线程无Long Task+所有资源完成+可稳定响应 |

指标关系链：`TTFB → FCP → LCP → TTI；FID/INP(全程)；CLS(全程)`

### 12.2 HTML 优化

```html
<!-- 1 压缩+精简：移除不必要注释/空白/包装DIV；语义化减少嵌套；gzip/brotli服务端开启 -->
<!-- 2 资源提示放最前 -->
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width,initial-scale=1">
  <link rel="preconnect" href="https://api.example.com">
  <link rel="dns-prefetch" href="//cdn.example.com">
  <link rel="preload" href="/fonts/Inter-Bold.woff2" as="font" type="font/woff2" crossorigin>
  <!-- 3 Critical CSS 内联 -->
  <style>/* 首屏可见区域全部CSS，≤14KB最佳(1个TCP慢启动窗口) */
    body{margin:0;font:16px/1.6 Inter,sans-serif}
    .hero{min-height:100vh;display:grid;place-items:center;background:#0ea5e9;color:#fff}
    .nav{position:sticky;top:0;height:60px;background:rgba(255,255,255,.9);backdrop-filter:blur(10px)}
  </style>
  <!-- 4 非关键CSS 异步加载 -->
  <link rel="preload" href="/styles/non-critical.css" as="style">
  <link rel="stylesheet" href="/styles/non-critical.css" media="print" onload="this.media='all'">
</head>
<body>
  <!-- 5 首屏HTML结构在前；大数据渲染用骨架屏+懒渲染 -->
  <nav class="nav">...</nav>
  <section class="hero">首屏可见区域内容优先</section>
  <script type="module" src="/app.js"></script>
  <!-- 或者 defer: <script defer src="/app.js"></script> -->
  <!-- 第三方统计/广告 异步延迟 -->
  <script async src="https://www.googletagmanager.com/gtag/js?id=G-XXXX"></script>
</body>
```

### 12.3 CSS 优化

| 策略 | 说明 |
|------|------|
| **Critical CSS 内联** | 首屏≤14KB样式内联；剩下的异步加载。工具：critical、penthouse、Vite/Rollup插件 |
| **按需加载（media查询）** | `<link media="(max-width:768px)" href="m.css">` → 仅移动端视口阻塞首屏 |
| **禁止CSS中@import** | @import要等当前CSS下载完再解析→发现@import→再下一轮下载→增加1~2RTT；打包工具替换或直接多个link标签 |
| **压缩+去无用** | postcss cssnano/purgecss(移除未使用class,尤其是Tailwind项目) |
| **CSS 变量减少重复** | 全局`:root{--primary:#0ea5e9}`，比重复写颜色字符串体积小 |
| **字体优化** | `<link rel=preload as=font>` + `font-display:swap`（避免 FOIT 隐形文本）+ unicode-range子集化 |

### 12.4 JavaScript 优化

```html
<!-- 1 script放body尾部或defer/module -->
<script defer src="app.js"></script>          <!-- 支持老浏览器，DOM解析完按序执行 -->
<script type="module" src="app.js"></script>  <!-- 现代浏览器，支持ESM，默认defer语义 -->
<script async src="https://analytics.cdn/xxx.js"></script>  <!-- 第三方统计/广告/无依赖独立脚本 -->

<!-- 2 代码分割 Code Splitting 动态import -->
<!-- <button id="btn">打开报表</button>  JS侧: -->
<script>
btn.onclick = async () => {
  const { default: HeavyReportModal } = await import('./HeavyReport.js');
  // 打包工具会自动分割为独立chunk，点击时才下载200KB报表逻辑
  HeavyReportModal.show();
}
</script>

<!-- 3 减少主线程 Long Task >50ms -->
<!-- Web Worker 处理纯计算（图表大数据、加密、富文本Diff） -->
<script>
const worker = new Worker('./crypto-worker.js');
worker.postMessage({ blob: hugeFile });   // 主线程发送巨量数据
worker.onmessage = e => console.log('SHA256:', e.data); // 不阻塞UI
</script>

<!-- 4 动画用 requestAnimationFrame -->
<script>
// ✅ 对齐VSync，不丢帧
let p = 0;
function frame() {
  el.style.transform = `translateX(${p}px)`;
  p += 2;
  if (p < 400) requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
// ❌ setInterval(()=>{...}, 16) — 频率不稳，易与VSync错开丢帧
</script>
```

### 12.5 资源提示 Resource Hints 完整速查

| 标签 | 用途 | 时机 | 优先级 | 典型场景 |
|------|------|------|--------|---------|
| `<link rel="dns-prefetch" href="//a.com">` | 提前DNS解析域名→IP | 页面空闲时后台 | 低 | 第三方CDN域名；页面后续跳转可能用到 |
| `<link rel="preconnect" href="https://a.com">` | DNS+TCP+TLS握手全链路预热 | 尽早(head最前) | 中高 | API域名、字体CDN、图片CDN（首屏必须用到的） |
| `<link rel="preload" href="critical.js" as="script">` | 强制性提前下载指定资源，在head解析到就并行下 | 关键资源越前越好 | 高 | 首屏字体、首屏CSS、页面入口JS、首屏Hero背景图 |
| `<link rel="prefetch" href="/next-page.js">` | 空闲时提前下，**当前页用不到**给下一页 | body尾部或当前页关键加载完后 | 最低 | 用户下一步大概率去的：搜索结果详情页、商品详情下一页 |
| `<link rel="prerender" href="/next-page.html">` | 提前完整渲染下一页面（重量级） | 确定性极高用户下一步 | 最高但资源消耗巨大 | 搜索→详情页、结账第一步→第二步（90%用户会去的） |

## 十三、渲染性能分析实战 DevTools

### 13.1 Performance 面板使用流程

**标准步骤（建议Chrome 110+无痕模式分析，排除扩展干扰）：**
1. F12 → Performance 面板 → 勾选 Screenshots / Web Vitals / Memory
2. 点击圆形录制按钮「Record」 → 在页面上执行目标操作（加载/滚动/点按钮动画） → Stop
3. 顶部 **Overview 轨道**三根线（绿FPS/蓝CPU/紫NET）快速判断问题：
   - FPS <60 频繁出现红条 → 掉帧，往下找原因
   - CPU 持续满占用+橙色区块长时间 → 主线程压力
4. 放大 **Main 轨道**（点击Main左端 或 W/A/S/D缩放平移）分析：
   - 橙色：JS执行（Function Call→若单块>50ms=Long Task⚠️）
   - 紫色：样式计算 Recalculate Style
   - 绿色：布局 Layout（大块+顶部红色「Forced reflow」=强制同步布局💀）
   - 绿色(浅)：Paint Prep + Paint
   - 灰色小条：其他系统任务
5. **Compositor 轨道**：紫色条 → 合成线程Tile调度+光栅化任务数量
6. **Raster 轨道**：大量Worker长条 → 过度光栅化（图层过多或过大）
7. **Frames 轨道**：每帧虚线框 → 悬停看Frame时间 → 超过16.67ms标红=丢帧
8. **Interactions 轨道**（INP专项）：每个交互事件条 → 点击展开 Input Delay + Processing Duration + Presentation Delay → 定位长交互INP超标

**快速诊断清单：**
- ❗Main轨道有>50ms橙色条 → Long Task JS性能问题
- ❗Layout绿色顶部红色「Forced reflow is likely performance issue」 → 强制同步布局，展开栈定位读写循环
- ❗Recalculate Style紫色块宽+调用次数多 → 选择器复杂或批量DOM样式切换
- ❗Paint绘制频繁+面积大 → Rendering面板Paint flashing全屏绿闪
- ❗Frames轨道丢帧+Compositor占比高 → 合成层过多或GPU压力

### 13.2 Rendering 面板调试技巧

F12 → 顶部菜单⋮ → More tools → **Rendering** 面板勾选：

| 开关 | 效果 | 排查目标 |
|------|------|---------|
| ✅ Paint flashing | 每次repaint区域瞬间亮绿色闪 | 找出不必要的重绘（滚动时整张屏幕绿闪=有重绘优化空间） |
| ✅ Layout Shift Regions | CLS位移区域短暂亮蓝 | 排查CLS超标：图片无尺寸/动态插入/字体切换 |
| ✅ Layer borders | 合成层显示橙色边框+详情角标 | 一眼识别图层数量/尺寸；定位图层爆炸来源 |
| ✅ FPS meter | 左上角实时FPS/GPU/JS Heap小窗口 | 滚动/动画时实时FPS<45即有性能问题 |
| ✅ Scrolling performance issues | 滚动慢的区域高亮青蓝 | touch事件listener未passive: true导致阻塞滚动（高频问题） |
| ✅ Highlight ad frames | 广告iframe高亮红 | 排查第三方广告占用主线程 |

### 13.3 Layers 面板图层分析

F12 → 顶部⋮ → More tools → **Layers** 面板：
- 左下角图层树列表：查看全部Graphics Layer合成层数量、大小、内存估算
- 选中任一层 → 右边 Details 面板显示：**Memory Estimate（显存占用）、Paint count、Composited Reasons（为何晋升合成层！）**
  - 常见Composited Reasons：`IntersectionObserver`（3D变换）/ `SquashingDisallowed: hasTransformAncestor`（隐式合成层）/ `ScrollsOverflow` / `Will-change transform`
- 左上3D视图可拖拽旋转+缩放查看图层堆叠关系

### 13.4 性能瓶颈定位实战流程（SOP）

```
第1步 FPS粗查：Performance录制 → Overview FPS绿色曲线是否有明显低谷 ←60fps红线
  ↓
第2步 Frame逐帧定位：Frames轨道找到丢帧（红色/>16.67ms）→ 点击该帧
  ↓
第3步 逐层级分析该Frame内三大阶段耗时：
  ├─ Main > 8ms  → 主线程瓶颈
  │   ├─ 橙色JS条>5ms → 展开调用栈看Top函数
  │   ├─ 紫色Style>2ms → 调用栈看class切换/选择器匹配
  │   ├─ 绿色Layout>2ms → 检查顶部Forced reflow警告
  │   └─ 浅绿Paint>1ms → Rendering面板paint flashing找重绘区域
  │
  ├─ Compositor > 5ms → 合成阶段瓶颈
  │   ├─ Raster Worker多且长 → 图层过多过大或新Tile光栅化频繁
  │   └─ 合成Draw耗时 → Layers面板图层过多
  │
  └─ GPU > 5ms → GPU瓶颈（带宽/填充率不足，移动端低端GPU常见）
      → Layers面板全选图层，Memory汇总判断是否显存过大
  ↓
第4步 验证修复：改代码 → 重新录制 → 对比before/after截图/Web Vitals指标
  达标标准：LCP<2.5s / INP<200ms / CLS<0.1（Google Core Web Vitals三绿）

## 十四、项目级优化案例

### 14.1 案例背景：某 B2C 电商平台商品列表页性能优化

**项目背景**
> 公司主营跨境电商，商品列表页是流量最高的转化漏斗入口（UV占全站40%+）。2023 Q3 Core Web Vitals数据显示：移动端 LCP=4.8s（需<2.5s）、INP=340ms（需<200ms）、CLS=0.28（需<0.1），三项全红。Google搜索排名因CWV下滑被降权（SEO曝光-18%），列表页→详情页跳出率上升12%，GMV同比下降6.8%。业务部门提出要求：2个月内移动端 CWV 三项全绿，GMV回升至同比+5%以上。

**页面现状（问题基线）**
- 首屏结构：Header(60px) + 分类筛选Tab栏 + 搜索过滤侧边栏 + 瀑布流商品卡片(1列/2列响应式) + 底部分页
- 每页加载 60 个商品卡片，卡片含主图+角标标签+价格划线对比+销量徽章+购物车浮按钮
- 技术栈：Vue 3.2 + Vite 4 + Pinia + Axios + SCSS，SSR未启用(纯CSR SPA)
- 打包后首屏 vendor chunk: 380KB / page chunk: 240KB / CSS: 128KB（未gzip）
- Performance 录制发现：Main 轨道最长 Long Task = 480ms（商品列表渲染），CLS 集中在图片加载和 font 切换时

### 14.2 技术选型与方案论证

| 优化维度 | 候选方案 | 最终选择 | 选型理由 |
|---------|---------|---------|---------|
| **首屏渲染模式** | ① 纯CSR ② Nuxt SSR ③ 预渲染(Prerender.io) ④ 流式SSR | **④ 流式SSR (Nuxt 3 + Nitro)** | 纯CSR首屏空窗长；Nuxt SSR完整SSR首包大；流式SSR分块传输、先骨架后数据渐进渲染，LCP收益最大（预估-40%+），迁移成本可接受 |
| **列表渲染架构** | ① 传统v-for全量渲染 ② vue-virtual-scroller虚拟列表 ③ 自研IntersectionObserver懒渲染 | **② 虚拟列表(每页60→仅渲染10×缓冲5=15个真实DOM)** | 列表>600+商品搜索场景DOM数过万导致布局200ms+；虚拟列表固定视口内节点，滚动性能10×提升 |
| **首屏关键CSS** | ① 全量CSS打包<link> ② Critical内联+异步加载剩余 ③ 按组件拆分CSS懒加载 | **② Critical内联+purgecss去无用** | Tailwind/Custom CSS共128KB实际首屏仅需18KB；内联18KB直接消除CSS请求RTT |
| **图片方案** | ① 原img+手动width/height ② 响应式srcset+sizes+固定尺寸占位 ③ 渐进式JPEG ④ WebP/AVIF自动格式协商 | **②+④ 响应式+AVIF/WebP+尺寸占位** | CLS来源50%来自图片无尺寸+压缩格式体积过大；此组合CLS预计-80% LCP-25% |
| **字体方案** | ① 阻塞加载 ② font-display:swap ③ FOUT用系统字体临时 ④ 子集化+preload | **②+③+④ font-display:optional + unicode-range子集 + preload** | 字体450KB→子集化28KB+swap避免FOIT隐形+optional避免CLS字体跳行 |
| **Long Task消除** | ① requestIdleCallback 分片 ② Web Worker搬运计算 ③ 使用Suspense异步分块渲染 | **①+②+③ 分片+Worker+Suspense三级策略** | 480ms大任务(计算+渲染+序列化)拆成16段<30ms |

**整体架构图（优化后）：**
```
CDN (Brotli + HTTP/3 Push Critical Assets)
  ↓
Nginx边缘 图片格式协商 Accept → Nginx_image_filter 自动 WebP/AVIF
  ↓
Nuxt 3 Nitro 流式 SSR Server（K8s部署 香港+欧洲+美西POP点）
  ├─ 先传输 HTML head + Critical CSS内联 + 骨架屏HTML（<20ms）
  ├─ Suspense边界 resolve → 分块传输 分类筛选+过滤栏 HTML
  └─ Suspense边界 resolve → 商品卡片首屏10个 分块传输 HTML
  ↓
Client:
  首屏水合仅10个虚拟列表节点
  ↓滚动时 IntersectionObserver → 懒加载下一批15个
```

### 14.4 关键挑战与解决方案

**挑战 #1：虚拟列表 + 锚点导航/返回后记忆滚动位置失效**
- 问题：从详情页返回列表→虚拟列表仅渲染视口内元素，滚动位置快照对应节点不在DOM中→位置恢复失败，用户跳到顶部
- 解决：封装 useScrollRestoration composable，Pinia store 额外存每页滚动偏移值 key=pageId；`<keep-alive>` 激活时 nextTick 后精准调用 `window.scrollTo(0, savedY)`，并额外在 RecycleScroller 的 `update:startIndex` 回调中二次校准（双保险）。同时使用 `scrollRestoration = 'manual'` 关闭浏览器原生恢复（与虚拟列表冲突）。

**挑战 #2：字体 swap 模式 + 中文宽高差异导致 CLS 突增 0.15**
- 问题：首屏渲染用fallback系统字体(宽度大)→网络字体Noto Sans SC加载完→重新布局→行高变化大→整页文字位移→CLS=0.15
- 解决：
  1. 改用 `font-display: optional`（100ms内字体未就绪→整页周期内不再换字体，避免CLS）
  2. 字体 Metric 调整：`@font-face { size-adjust: 97%; ascent-override: 102%; descent-override: 34%; }` 使fallback字体和正式字体在同一font-size下宽度高度误差 <2%，即使后续交换CLS也<0.003
  3. preload Critical Font子集（head最前preconnect+preload）

**挑战 #3：SSR + 虚拟列表水合不匹配（Hydration Mismatch）**
- 问题：SSR流式输出首屏10个卡片HTML（服务端计算首屏可见卡片）→客户端RecycleScroller测量视口后实际渲染14个 → 水合节点树不一致报错「Hydration node mismatch」白屏
- 解决：Nuxt `<ClientOnly>` 包装 RecycleScroller，首屏SSR输出**静态的首屏10卡片HTML骨架**（与SSR发送完全一致）；水合后用 rAF 下一帧无缝切换到虚拟列表真实渲染。用户感知零差异，水合一致性校验通过。

**挑战 #4：`will-change`滥用导致低端安卓GPU崩溃（华为荣耀畅玩 4+%用户）**
- 问题：为每个卡片hover效果全局`.goods-card{will-change:transform}` → 低端机合成层157个 → 渲染进程GPU OOM被系统杀死→白屏退出
- 解决：
  1. 移除全局will-change，改为只在卡片开始hover瞬间加class `document.addEventListener('pointerover', e => el.classList.add('hover-promoted'), { once: true, passive: true }`，结束后再移除
  2. Layers面板验收：合成层数从157 → 稳态7~13个，仅hover时临时+1个
  3. 低端设备检测（`navigator.hardwareConcurrency <4 || deviceMemory <2`）→ 关闭backdrop-filter等视觉效果，渐进降级

### 15.1 渲染原理高频题

**Q1：请系统描述浏览器的完整渲染过程？**
```
答法框架（总分，7段法）：
总起：浏览器渲染由多进程+多线程协作完成，从网络字节到屏幕像素，主线程/合成线程/GPU进程三阶段配合。

① 网络→解析阶段
   Network线程下载HTML → 主线程HTMLParser(BOM+meta+ICU)解码→Tokenization→Tree Construction栈构建DOM Tree
   并行：预解析器(Preload Scanner)提前扫描后续资源(img/link/script src)避免串行下载
   CSS文件下载解析 → 生成StyleSheet集合（规则表+RuleHash+BloomFilter，注意CSSOM不是严格并行树，是规则集合概念修正）

② 样式计算阶段（主线程4步）
   Phase1声明值收集 UA/User/Author + inline + 选择器RL匹配+布隆过滤加速
   Phase2冲突解决 Cascade 三层优先级：Origin+Importance > Specificity(Inline-ID-Class-Tag元组，非十进制！) > Source+LayerOrder
   Phase3继承 可继承从父ComputedStyle拷贝(inherit/initial/unset/revert关键字)
   Phase4默认值填充 不可继承initial + em/%→Used Value px + 颜色归一化RGBA
   同 ComputedStyle共享缓存命中跳过（复杂页节省30~60%时间）

③ 布局阶段（Reflow，主线程）
   DOM树剔除display:none/head/script等→Render Tree (LayoutObject/RenderObject Tree)
   增量布局Dirty标记系统：修改元素→自身NeedsLayout + 祖先链ChildNeedsLayout
   三Pass：Constraint(上→下约束) → Measure(下→上尺寸上报) → Placement(上→下放位置)
   盒模型content-box/border-box；包含块判定（fixed被transform「擒获」常考点）；BFC/IFC/FFC/GFC格式化上下文

④ 分层阶段（主线程）
   先创建Paint Layer（每个Stacking Context）→ 按条件晋升Graphics Layer合成层
   晋升条件：3D变换 translateZ / video / WebGL canvas / 合成层后代 / overflow-scroll滚动 / backdrop-filter / transform动画 / will-change提示
   内存公式：w×h×4×DPR²，4K全屏31MB→10层=310MB，移动端目标<30层

⑤ 绘制阶段（主线程）→ 只生成Display List（SkPicture矢量指令），不着色
   绘制顺序：堆栈上下文内部(负z→块级→float→行内→z=0定位→正z)；指令成本：backdrop-filter>shadow>渐变>圆角裁剪>文本>图片>纯色填充

⑥ 分块+光栅化+合成（合成线程 + GPU进程，主线程不参与✅）
   Commit提交Display List → 合成线程Tiling分块(256/512) → 视口优先P0/P1/P2/P3队列调度光栅化
   Skia GPU管线：顶点→片元→输出合并→Tile纹理
   合成：Active/Pending Tree → Draw Quads组装(z+transform+opacity+clip) → 提交GPU进程
   独立于主线程：JS阻塞100ms时，仍可滚动/transform动画（此为GPU动画流畅核心原理）

⑦ 显示阶段（GPU + 显示器）
   三缓冲Front/Mid/Back → VSync VBlank → SwapBuffer Page Flip原子交换 → 显示控制器扫描Front到屏幕
   60Hz每帧16.67ms；错过VSync窗口=掉帧（Jank卡顿）

收尾：结合以上机制说明性能优化三大方向：减少回流→减少重绘→优先合成
```

**Q2：Reflow / Repaint / Composite 有什么区别？如何触发？性能对比？**

```
核心对比表+举例说明：
| 名称    | 中文   | 触发操作          | 涉及阶段                      | 成本    | 典型耗时例       |
|---------|--------|------------------|-------------------------------|---------|----------------|
| Reflow  | 回流   | width/top/display/font-size等几何变化 | Layout→Paint→Composite→Display | ⭐⭐⭐⭐⭐ 最高 | 大列表回流30-300ms |
| Repaint | 重绘   | color/background/box-shadow等视觉变化 | (Skip Layout)→Paint→Composite→Display | ⭐⭐⭐ 中 | 1-15ms |
| Composite | 合成 | transform/opacity(独立合成层)/滚动 | (Skip Layout+Paint)→Composite→Display | ⭐ 最低 | <0.5ms |

优化口诀：动画只用 transform+opacity；批量先读后写避免强制同步布局。
```

**Q3：CSS会阻塞DOM解析吗？JS会吗？为什么？**

```
✅ 正确答案（带精确边界）：
CSS (<link rel=stylesheet>)：❌ 不阻塞DOM解析（主线程可继续构建DOM节点）
                      ✅ 但阻塞首屏渲染（避免FOUC闪烁）
                      ⚠️ 间接阻塞：若<link后紧跟<script>，则script执行前必须等CSSOM就绪（因为JS可能读offsetWidth/getComputedStyle依赖样式）

普通<script src="x">：✅ 完全阻塞DOM解析（暂停）+ 阻塞渲染
           原因：规范规定JS可调用document.write动态写入标签，主线程必须等JS执行完才能安全继续后续DOM树构建，否则树结构冲突
async <script async src>：❌ 下载不阻塞（并行）/ ⚠️ 下载完立即打断主线程执行，执行顺序无保证
                         适用：独立第三方统计/广告，不依赖DOM也不被其他依赖
defer <script defer src>：❌ 完全不阻塞
                         时机：DOM解析完成后→defer脚本按标签出现顺序执行→之后触发DOMContentLoaded
                         适用：页面主逻辑（90%场景推荐优先使用defer或type=module）

预解析器机制弥补：即便主线程被普通script阻塞，Preload Scanner仍继续扫描后续字节→提前发起<img>/<link>/其他<script src>下载，典型首屏-15~40%加载时间。
```

**Q5：什么是强制同步布局（Layout Thrashing）？怎么修复？请写代码示例。**

```
定义：JavaScript在一帧内 先「读取」会触发回流的几何API (offsetWidth等) → 再「写入」样式 → 浏览器无法使用异步批量布局策略，被迫立即执行完整布局以获得准确测量值。循环N次→N次完整布局💀

触发强制同步布局API列表：
offset/Width/Height/Left/Top, client/Width/Height/Left/Top, scroll/Width/Height/Left/Top, getBoundingClientRect(), getClientRects(), getComputedStyle(), elementFromPoint(), caretRangeFromPoint(), innerText()

反模式代码💀：
const items = document.querySelectorAll('.grid-item');
items.forEach(el => {
  const w = el.offsetWidth;        // 读 → 浏览器先完成所有挂起布局算最新宽度
  el.style.width = (w * 1.2) + 'px'; // 写 → 标记Dirty；下一次循环读offsetWidth时 → 又要完整布局！
});
// N=100 → 100次布局 → 120ms卡顿

✅修复代码（先批量读后批量写，2次布局搞定）：
const widths = [...items].map(el => el.offsetWidth);  // 第1次布局→一次性拿到所有值
items.forEach((el, i) => {
  el.style.width = (widths[i] * 1.2) + 'px'; // 所有写操作→浏览器合并→第2次布局
});
```

## 十六、总结与快速参考

### 16.1 渲染流水线关键节点回顾

```
主线程流水线（Main Thread）：
  HTML字节流→解码→Tokenize→Tree Construction → DOM Tree
  CSS字节流→Tokenize→Style Rule构建         → Style Rules(含选择器索引+布隆过滤器)
  DOM + Style Rules → 样式计算4阶段Cascade → ComputedStyle(每节点全值)
  ComputedStyle → Render Tree构建(display:none剔除) → Dirty增量布局三Pass → Layout Tree+Geometry
  Layout Tree → Paint Layer树+Graphics Layer晋升 → Layer Tree
  Layer Tree → 按z顺序+堆栈上下文 生成Display List(SkPicture矢量)

Commit IPC / 共享内存 → 合成线程流水线

合成线程+GPU流水线（Compositor Thread + GPU Process）：
  Display List → Tiling 256/512 Tile切分 → 视口优先P0/P1/P2/P3优先级队列
  Raster Worker池调度 → Skia GPU Command Buffer → GPU纹理Tile位图
  Active/Pending Tree光栅化就绪 → 原子Activate切换
  层树遍历+z排序 → 组装Draw Quads(纹理+transform+opacity+clip+blend)
  → IPC提交GPU进程 → GPU Skia/ANGLE执行 → 结果写入Back Buffer
  → VSync到来SwapBuffer Front/Back → 显示控制器扫描屏幕→人眼看到✅

丢帧常见路径（按概率排序）：
  主线程Long Task>50ms → 错过Commit窗口 → 80%
  强制同步布局N次 → Layout持续高 → 5%
  大区域Paint + 阴影模糊重 → 10%
  合成层过多 → 光栅化/合成慢 → 3%
  GPU驱动/显存瓶颈 → 2%
```

### 16.2 性能优化核心原则

```
原则1 避免回流 > 减少重绘 > 优先合成
  ✔ transform / opacity 做动画 = 仅合成（成本≈1）
  ✔ color / background 变化 = 重绘（成本≈10）
  ✔ width / position 变化 = 回流（成本≈100）

原则2 先批量读后批量写 → 消除强制同步布局💀
  分离读写阶段：1st pass全读offsets → 2nd pass全写styles

原则3 CRP关键资源三减：减数量 → 减大小 → 减往返
  数量：媒体查询拆分CSS不匹配不阻；非关键JS defer/async；字体子集减少体积
  大小：brotli>gzip；PurgeCSS + Tree Shaking；图片AVIF 60%体积
  往返：preconnect/TCP+TLS预热；Critical内联消除CSS RTT；HTTP/3多路复用

原则4 合理分层不滥用：
  只给动画中元素 will-change / translateZ(0)；动画结束移除
  监控Layers面板 移动端<30层 / 桌面端<80层

原则5 测量优先不瞎优化：
  DevTools Performance录制+RUM真实数据；Web Vitals三绿为最终标准
  没有测量的优化是耍流氓；用Chrome DevTools性能分析SOP 13.4节执行

原则6 渐进降级可访问：
  低端机/HWConcurrency<4：关闭backdrop-filter/3D阴影/无限滚动；静态降级渲染
  无障碍模式：关闭prefers-reduced-motion用户的动画
```

- 目标：减关键资源数量 → 减关键资源大小 → 优化加载顺序 → 减少RTT往返
- Web Vitals三绿：LCP<2.5s / INP<200ms / CLS<0.1
- CSS阻塞渲染不阻塞解析；普通JS全阻塞；defer最安全；async第三方
- 资源提示优先级：preconnect(高，做链路预热) > preload(当前页关键) > dns-prefetch(轻) > prefetch(下一页空闲) > prerender(重)

## 第1章 概述

### 1.1 什么是浏览器渲染

**渲染（Render）** 是指浏览器将从服务器获取的 HTML、CSS、JavaScript 等资源，经过一系列处理后，最终转换为屏幕上可交互的像素图像的完整过程。

从数据形态的角度看，渲染本质上是一次 **"字符串 → 结构化对象 → 几何信息 → 位图 → 屏幕像素"** 的多级转换流水线：

```
HTML 字符串
    │
    ▼
HTML 解析
    │
    ▼
DOM Tree
    │
    │
    ├──────────────────┐
    │                  │
    ▼                  ▼
CSS 字符串          JavaScript
    │                  │
    ▼                  │
CSS 解析               │
    │                  │
    ▼                  │
CSSOM                  │
    │                  │
    └────────┬─────────┘
             ▼
       Style Calculation
          样式计算
             │
             ▼
           Layout
            布局
             │
             ▼
          Paint
           绘制
             │
             ▼
      Rasterization
         光栅化
             │
             ▼
          Compositing
            合成
             │
             ▼
            GPU
             │
             ▼
         屏幕像素
```

### 1.2 为什么需要理解渲染原理

掌握浏览器渲染原理具有重要的实际价值：

| 价值维度 | 说明 |
|---------|------|
| **性能优化** | 精准定位页面卡顿、首屏慢、动画掉帧等问题，采取针对性优化策略 |
| **排错能力** | 理解层叠上下文、包含块、BFC 等概念，快速解决样式异常 |
| **技术选型** | 在 CSS 动画与 JS 动画、不同布局方案间做出合理选择 |
| **面试必考** | 渲染流水线、Reflow/Repaint、CRP 是前端中高级岗位的高频考点 |

### 1.3 渲染流程总览

从用户输入 URL 到页面呈现，核心流程可以概括为两大阶段：

1. **网络阶段**：浏览器进程 → 网络进程 → 发起 HTTP/HTTPS 请求 → 获取 HTML 文档
2. **渲染阶段**：网络线程将 HTML 转交给渲染主线程 → 经过完整的 8 步渲染流水线

渲染流水线的 8 个核心阶段：

| 阶段 | 英文术语 | 执行线程 | 核心产出 |
|-----|---------|---------|---------|
| 解析 HTML | Parse HTML | 渲染主线程 | DOM 树 + CSSOM 树 |
| 样式计算 | Recalculate Style | 渲染主线程 | 带 Computed Style 的 DOM 树 |
| 布局 | Layout | 渲染主线程 | Layout Tree（尺寸+位置） |
| 分层 | Layer | 渲染主线程 | Layer Tree（图层树） |
| 绘制 | Paint | 渲染主线程 | 每个图层的绘制指令集 |
| 分块 | Tiling | 合成线程 + 线程池 | 图层切分为多个 Tile |
| 光栅化 | Rasterize | GPU 进程 + GPU 硬件 | 每个 Tile 对应的位图 |
| 合成显示 | Composite & Display | 合成线程 → GPU 进程 → 硬件 | 屏幕最终像素 |

> **关键区分**：前 5 步（解析 → 绘制）运行在 **渲染主线程**，后 3 步（分块 → 光栅化 → 合成）运行在 **合成线程 / GPU 进程**。这一划分直接决定了哪些 CSS 属性高效、哪些会阻塞主线程。

## 第2章 浏览器进程与线程模型

### 2.1 多进程架构（以 Chrome 为例）

现代浏览器采用 **多进程架构**（而非单进程），核心原因是：**稳定性（沙盒隔离）+ 安全性 + 利用多核 CPU**。

Chrome 浏览器主要包含以下进程：

```
┌─────────────────────────────────────────────────────────┐
│  Chrome 多进程架构                                         │
├─────────────────────────────────────────────────────────┤
│  ① 浏览器进程（Browser Process）── 主控进程，1个              │
│     ├── 地址栏、书签、前进后退按钮                             │
│     ├── 文件读写 / 网络请求权限管理                           │
│     └── 负责其他进程的创建与销毁                              │
│                                                           │
│  ② 渲染进程（Renderer Process）── 每个标签页 1个，沙盒隔离       │
│     └── 运行 HTML / CSS / JS，核心是 Blink 渲染引擎 + V8     │
│                                                           │
│  ③ GPU 进程（GPU Process）── 1个                              │
│     └── 接收合成线程指令，驱动 GPU 硬件完成光栅化与最终成像       │
│                                                           │
│  ④ 网络进程（Network Process）── 1个                          │
│     └── 负责所有 HTTP/HTTPS/WebSocket 请求的发起与接收         │
│                                                           │
│  ⑤ 插件进程（Plugin Process）── 每个插件 1个                   │
│     └── 运行 Flash、PDF 等插件（现代浏览器已逐步淘汰）           │
└─────────────────────────────────────────────────────────┘
```

> **安全设计**：渲染进程运行在 **沙盒（Sandbox）** 中，无法直接访问操作系统 API、磁盘文件或硬件。因此渲染进程需要将结果通过 IPC（进程间通信）交给 GPU 进程，再由 GPU 进程与硬件交互。

### 2.2 渲染进程内部线程构成

每个渲染进程内部是 **多线程模型**：

| 线程名称 | 核心职责 |
|---------|---------|
| **渲染主线程（Main Thread）** | 最核心的线程：执行 JS、解析 HTML/CSS、样式计算、布局、分层、生成绘制指令。同时负责事件循环与 DOM 操作 |
| **合成线程（Compositor Thread）** | 接收主线程提交的 Layer Tree + Paint Records，执行分块（Tiling），调度光栅化，生成 Quad 合成信息 |
| **光栅化线程池（Raster Thread Pool）** | 配合 GPU 进程，并行完成多个 Tile 的光栅化工作 |
| **预解析线程（Preload Scanner / Preparser）** | 在主线程解析 HTML 时，提前扫描 `<link>`、`<script>`、`<img>` 等标签，预下载外部资源 |
| **Worker 线程** | 执行 Web Worker / Service Worker 代码（不持有 DOM，与主线程通过 postMessage 通信） |
| **定时器 / 事件触发线程** | 管理 setTimeout、setInterval、IO 事件回调，到时后将任务推入消息队列 |

### 2.3 线程间协作机制

线程间通过 **消息队列 + 事件循环（Event Loop）** 进行协作：

```
网络进程获取 HTML
      │
      ▼
包装为 Task ──▶  渲染主线程消息队列
                        │
                        ▼
                  事件循环机制
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
      执行宏任务（解析HTML）    执行微任务（Promise.then）
            │
            ├─▶ 预解析线程并行下载 CSS/JS
            │
            ▼
      样式计算 → 布局 → 分层 → 绘制
            │
            ▼
      提交给合成线程 ──▶ 分块 ──▶ 光栅化 ──▶ 合成显示
```

## 第3章 关键渲染路径 CRP

### 3.1 CRP 的定义与阶段划分

**关键渲染路径（Critical Rendering Path, CRP）** 是指浏览器从收到 HTML、CSS、JS 资源开始，到完成首次像素绘制（First Paint）所需经过的最短关键路径。

CRP 的 6 个标准步骤：

```
① 开始解析 HTML
      │
      ▼
② 构建 DOM 树  ←─────────────┐
      │                       │ 阻塞
      ▼                       │
③ 遇到 <link> / <style>  ────▶ ④ 构建 CSSOM 树
      │
      ▼
⑤ 样式计算 + 布局（需 DOM + CSSOM 都就绪）
      │
      ▼
⑥ 绘制 + 合成 → 屏幕出现首屏像素（First Paint）
```

衡量 CRP 性能的核心指标：

- **FP（First Paint）**：首次绘制，浏览器第一次向屏幕输出像素
- **FCP（First Contentful Paint）**：首次内容绘制，屏幕第一次出现文字/图片等内容
- **LCP（Largest Contentful Paint）**：最大内容绘制，视口内最大元素渲染完成

### 3.2 阻塞资源深度分析

#### 3.2.1 CSS 的阻塞特性

**CSS 不会阻塞 HTML 的解析，但会阻塞页面的渲染。**

| 行为 | 是否阻塞 | 原因分析 |
|-----|---------|---------|
| HTML 解析 | ❌ 不阻塞 | 预解析线程会提前下载 CSS，主线程继续解析 HTML，无需等待 CSS 返回 |
| 页面渲染（Render） | ✅ 阻塞 | 渲染必须等 CSSOM 构建完成才能进行样式计算，否则无法确定元素样式 |
| JavaScript 执行 | ✅ 间接阻塞 | JS 执行时若访问 `getComputedStyle()` 或操作样式，浏览器会等待 CSSOM 就绪 |

```html
<!-- 优化前：CSS 阻塞首屏渲染 -->
<link rel="stylesheet" href="critical.css">      <!-- 首屏关键样式 -->
<link rel="stylesheet" href="non-critical.css">  <!-- 非首屏样式也会阻塞首屏 -->

<!-- 优化后：非关键 CSS 异步加载 -->
<link rel="stylesheet" href="critical.css">
<link rel="stylesheet" href="non-critical.css" media="print" onload="this.media='all'">
```

#### 3.2.2 JavaScript 的阻塞特性

**默认情况下，`<script>` 会同时阻塞 HTML 的解析和页面的渲染。**

原因：JS 执行期间可能执行 `document.write()`、修改 DOM 结构、读取/修改元素样式等操作，如果 JS 执行时 HTML 继续解析，会出现 DOM/CSS 状态不一致的竞态问题。

三种 `<script>` 加载模式对比：

| 属性 | HTML 解析阻塞 | 执行时机 | 多个脚本执行顺序 | 适用场景 |
|-----|-------------|---------|----------------|---------|
| `<script src="a.js">`（默认） | ✅ 阻塞 | 下载完成立即执行 | 按出现顺序 | 有相互依赖关系的核心脚本 |
| `<script async src="a.js">` | ❌ 不阻塞 | 下载完成立即执行（并行下载） | **不保证顺序**（谁先下载完谁先执行） | 无依赖的独立脚本（如埋点统计） |
| `<script defer src="a.js">` | ❌ 不阻塞 | HTML 解析完成后、`DOMContentLoaded` 前执行 | **按出现顺序**（推荐） | 依赖 DOM 且有顺序要求的脚本 |

```html
<!-- 推荐：defer 用于业务逻辑脚本，async 用于无依赖第三方脚本 -->
<script defer src="app.js"></script>
<script async src="analytics.js"></script>
```

### 3.3 预解析器与资源预加载

浏览器在主线程正式解析 HTML 之前，会启动一个 **预解析线程（Preload Scanner）**，它的工作范围非常专一：

- 扫描标签：`<link>`、`<script>`、`<img>`、`<video>`、`@import` 等
- 提前发起外部资源的 HTTP 请求，不等主线程解析到对应行才开始下载
- **不会**执行 JS，**不会**构建 DOM，**不会**处理内联脚本中的动态资源

开发者可以通过资源提示（Resource Hints）进一步加速：

```html
<!-- 预加载关键资源（优先级最高，在当前页面必须用到） -->
<link rel="preload" href="/fonts/my-font.woff2" as="font" crossorigin>
<link rel="preload" href="/critical.css" as="style">

<!-- 预连接（提前完成 DNS + TCP + TLS 握手） -->
<link rel="preconnect" href="https://cdn.example.com">

<!-- 预解析 DNS -->
<link rel="dns-prefetch" href="https://third-party.com">

<!-- 预渲染下一页面（仅在高确定性跳转时使用，消耗资源） -->
<link rel="prerender" href="/next-page.html">
```

### 3.4 CRP 优化核心原则

1. **减少关键资源数量**：内联首屏 CSS、异步加载非关键 JS、延迟加载非首屏图片
2. **减小关键资源体积**：压缩 HTML/CSS/JS、Tree-Shaking、移除未使用 CSS
3. **优化资源加载顺序**：关键资源放到 `<head>`，非关键资源放到 `</body>` 前或使用 defer/async
4. **减少 CRP 往返次数**：合理使用 CDN、HTTP/2 多路复用、启用 Gzip/Brotli 压缩

## 第4章 渲染流水线详解

### 4.1 HTML 解析（Parse HTML）→ DOM 树

HTML 解析的核心产物是 **DOM（Document Object Model）树**，它以树形结构完整描述了页面的语义层级与节点关系。

解析过程分为两个子阶段：

#### 4.1.1 Tokenization（分词阶段）

分词器将 HTML 字符串逐个字符扫描，识别出语法标记（Token）：

```
输入字符串：<div class="title">Hello</div>

分词结果（Token 流）：
  ┌─ StartTag:  tagName="div", attributes=[{name:"class", value:"title"}]
  ├─ Character: "Hello"
  └─ EndTag:    tagName="div"
```

分词器采用 **状态机** 机制工作，遇到 `<` 进入标签开始状态，遇到 `>` 回到数据状态，以此类推。

#### 4.1.2 Tree Construction（树构建阶段）

树构建器消费 Token 流，按照 HTML 规范维护一个 **开放元素栈**，逐步构建出 DOM 树：

```
Token: StartTag <html>   →  入栈，创建 <html> 节点
Token: StartTag <body>   →  入栈，创建 <body> 节点，挂到 <html> 下
Token: StartTag <div>    →  入栈，创建 <div> 节点，挂到 <body> 下
Token: Character "Hello" →  创建文本节点，挂到 <div> 下
Token: EndTag </div>     →  出栈
Token: EndTag </body>    →  出栈
Token: EndTag </html>    →  出栈，解析完成
```

> **容错机制**：浏览器内置了强大的 HTML 容错解析器，例如遇到 `<p><div></p>` 这种嵌套错误，会自动关闭 `<p>` 再打开 `<div>`，而不会抛出解析异常。

#### 4.1.3 CSS 解析 → CSSOM 树

与 DOM 树并行，CSS 会被解析为 **CSSOM（CSS Object Model）树**：

```
StyleSheetList（根节点）
  ├── User Agent Stylesheet（浏览器默认样式表，无法通过 JS 访问）
  │     └── html, body, div, p, a ... 等元素的默认样式
  ├── User Stylesheet（用户自定义样式表，可选）
  ├── Author Stylesheet（页面作者样式表）
  │     ├── 外部样式表（<link href="a.css">）
  │     ├── 内部样式表（<style> ... </style>）
  │     └── 内联样式（style="color: red" 属性）
```

开发者可以通过以下 API 访问样式：

```javascript
// 访问作者样式表列表（不含 UA 默认样式）
document.styleSheets  // StyleSheetList，元素为 CSSStyleSheet

// 动态添加样式规则
const styleSheet = document.styleSheets[0];
styleSheet.addRule(".card", "box-shadow: 0 2px 8px rgba(0,0,0,.1)");

// 访问内联样式
const div = document.querySelector("div");
div.style.color = "#15a7a7";

// 读取最终计算样式（只读）
const computed = getComputedStyle(div);
console.log(computed.color);  // "rgb(21, 167, 167)"
```

> **参考资源**：Chrome 的 User Agent 样式表源码可在 [chromium/html.css](https://github.com/chromium/chromium/blob/main/third_party/blink/renderer/core/html/resources/html.css) 查看。

### 4.2 样式计算（Recalculate Style）

样式计算阶段遍历 DOM 树的每个节点，计算出该节点的 **Computed Style**（所有 CSS 属性的最终值）。

值的确定遵循严格的四步流程：

```
确定声明值  →  层叠冲突  →  使用继承  →  使用默认值
   (Step1)     (Step2)     (Step3)      (Step4)
```

#### 4.2.1 第一步：确定声明值

收集 **所有来源** 的样式声明，并将相对/语义值标准化为绝对值：

| 输入值 | 标准化后 |
|-------|---------|
| `color: red` | `color: rgb(255, 0, 0)` |
| `font-size: 2em` | `font-size: 32px`（假设父级 16px） |
| `width: 50%` | 保留 `50%`（百分比在布局阶段解析为绝对值） |
| `line-height: 1.5` | 保留比值（布局阶段结合 font-size 计算） |

#### 4.2.2 第二步：层叠冲突（Cascade）

同一属性被多个来源声明时，通过 **三重比较规则** 确定生效值：

```
比较源的重要性  →  比较优先级  →  比较次序
     (1)              (2)          (3)
```

> **注意**：`!important` 声明会 **反转源的重要性顺序**，优先级从高到低为：
> 1. 作者样式 `!important`
> 2. 用户样式 `!important`
> 3. 用户代理样式 `!important`
> 4. 作者样式（普通）
> 5. 用户样式（普通）
> 6. 用户代理样式（普通）

##### 比较源的重要性

三种来源（不含 `!important` 时）重要性排序：

| 优先级 | 来源 | 说明 |
|-------|-----|------|
| 1（高） | 页面作者样式（Author） | 开发者编写的 CSS，含外部、内部、内联 |
| 2 | 用户样式（User） | 用户通过浏览器扩展/配置注入的自定义样式 |
| 3（低） | 用户代理样式（User Agent） | 浏览器内置默认样式（如 `<a>` 默认蓝色下划线） |

##### 比较优先级（Specificity）

同源冲突时，按 **选择器特异性** 比较。特异性用四元组 `(a, b, c, d)` 表示，从左向右依次比较：

| 组成部分 | 说明 | 贡献 |
|---------|------|------|
| `a` | 内联样式（`style="..."`） | 1 0 0 0 |
| `b` | ID 选择器（`#id`） | 0 1 0 0 |
| `c` | 类、伪类、属性选择器（`.cls`、`:hover`、`[attr]`） | 0 0 1 0 |
| `d` | 标签、伪元素选择器（`div`、`::before`） | 0 0 0 1 |
| — | 通配符 `*`、子连接符 `>`、兄弟连接符 `+` | 不贡献 |

**示例计算**：

```css
/* 特异性：(0, 1, 1, 1) */
#header .nav-item.active > a { }
/*  拆解：#header=1个ID → b=1
           .nav-item=1个类 → c=1
           .active=1个类 → c=2（合计c=2? 重新计算）
      更正：#header(1) + .nav-item(1) + .active(1) + a(1)
           = (0, 1, 2, 1) */

/* 特异性：(0, 0, 2, 1) */
div.card.rounded { }
/*  拆解：div(1) + .card(1) + .rounded(1) = (0, 0, 2, 1) */
```

##### 比较次序（Order）

若前两项完全相同，则 **后声明的覆盖先声明的**：

```css
p { color: red;    }  /* 先声明，被覆盖 */
p { color: green;  }  /* 后声明，生效 */
```

#### 4.2.3 第三步：使用继承（Inherit）

经过层叠仍未赋值的属性，如果该属性支持继承，则使用 **最近祖先元素的 Computed Value**。

```html
<div style="color: red; font-size: 16px;">
  <p>Hello</p>  <!-- p 未声明 color，继承 div 的 rgb(255,0,0) -->
</div>
```

**继承规则**：

- **就近原则**：使用最近一级有声明的祖先，与权重无关
- **可继承属性**：大多数字体/文本相关属性（`color`、`font-*`、`line-height`、`text-*`、`letter-spacing`、`list-style`、`visibility` 等）
- **不可继承属性**：盒模型属性（`width`、`height`、`margin`、`padding`、`border`）、定位属性（`position`、`top/left`）、`background`、`display`、`overflow` 等
- **强制继承**：显式声明 `width: inherit` 可让不可继承属性强制继承父值

#### 4.2.4 第四步：使用默认值（Initial）

经过前三步仍未确定值的属性，使用 CSS 规范定义的 **初始值（Initial Value）**：

```
color 初始值：CanvasText（通常是黑色）
width 初始值：auto
height 初始值：auto
margin 初始值：0
display 初始值：inline
```

> **小技巧**：在 Chrome DevTools 中查看元素 → Computed 面板，可以看到所有属性经过四步计算后的最终值，非常便于调试。

### 4.3 布局（Layout）

布局阶段（也称为 **Reflow**）遍历 DOM 节点，计算每个节点在视口内的 **精确几何信息**：

- 元素盒子的 **宽度 / 高度**（`width`、`height` 百分比、`auto` 等在这一步被解析为绝对值）
- 元素相对于 **包含块** 的 **位置**（`x`、`y` 坐标）

#### 4.3.1 布局树与 DOM 树的关系

布局阶段产出的是 **Layout Tree（布局树）**，它与 DOM 树 **并非一一对应**：

```
DOM 树                       Layout 树
├── <html>                   ├── <html> 盒子
│   ├── <head>  (display:none 的 head 节点)  ←── 被排除（无几何信息）
│   └── <body>               └── <body> 盒子
│       ├── <div style="display:none">    ←── 被排除（display:none）
│       ├── <div class="card">            ├── .card 盒子
│       │   └── ::before (伪元素)          │   ├── ::before 匿名盒
│       │   └── "some text"  (裸文本)      │   ├── 匿名行盒（包裹 "some text"）
│       │   └── <span>Text</span>          │   └── <span> 盒子
│       └── <div>                          └── <div> 盒子
```

**布局树不包含以下节点**：

1. **`display: none` 的节点**：不占据空间，无几何信息
2. **`<head>`、`<script>`、`<meta>`** 等不渲染的标签
3. **内容为空的行盒**（无文本、无子元素、无内边距边框）

**布局树比 DOM 树多出以下节点**：

1. **伪元素节点**（`::before`、`::after`）：在 DOM 中不存在，但有几何信息
2. **匿名盒（Anonymous Box）**：为满足 W3C 规范的盒子嵌套规则而生成

> **注意区别**：`visibility: hidden` 的元素 **会** 出现在布局树中（它仍占据空间），只是绘制阶段不渲染颜色。

#### 4.3.2 包含块（Containing Block）

元素的宽高百分比、`margin`、`padding`、绝对/固定定位的偏移量等都是以 **包含块** 的数值为基准计算的，而非简单的父元素。

**包含块的确定规则（基于 `position` 属性）**：

| `position` 值 | 包含块来源 | 基准区域 |
|--------------|-----------|---------|
| `static` / `relative` / `sticky` | 最近的祖先 **块级元素**（`display: block/list-item/inline-block/flex/grid`） | **内容区（Content Box）** |
| `absolute` | 最近的 `position` **非 `static`** 的祖先元素 | **内边距区（Padding Box）** |
| `fixed` | 初始包含块（通常是 **视口 viewport**） | 视口尺寸 |
| 特殊情况 | 祖先具有 `transform / perspective / filter: none` / `will-change: transform` / `contain: paint` | 该祖先的 **内边距区**（即使 `position: fixed` 也会被"捕获"） |

**典型场景**：

```css
/* 场景1：父元素 padding: 20px，子元素 width: 50% */
.parent { width: 400px; padding: 20px; }
.child  { position: relative; width: 50%; }
/* child width = parent content-box 宽度 × 50% = (400 - 20×2) × 50% = 180px */

/* 场景2：fixed 元素被 transform 祖先"捕获"（常见坑） */
.wrapper  { transform: translateX(0); }  /* 有 transform 值非 none */
.modal    { position: fixed; top: 10px; left: 10px; }
/* 此时 .modal 的包含块是 .wrapper，而非视口！fixed 退化为 absolute 效果 */
```

#### 4.3.3 匿名盒（Anonymous Box）

为了满足 W3C 规范的两条核心规则，浏览器会自动生成 **匿名盒**：

> **规则一**：所有文本内容必须位于行盒（Inline Box）中。
> **规则二**：行盒与块盒（Block Box）不能直接相邻。

**示例 1：匿名行盒（Anonymous Inline Box）**

```html
<section>
  some text           <!-- 直接写在块级元素中的裸文本 -->
  <p>More text</p>
</section>
```

生成的盒子结构：

```
<section> 块盒
  ├── 匿名行盒  ────  包裹 "some text"（规则一生成）
  └── <p> 块盒
        └── 匿名行盒  ────  包裹 "More text"
```

**示例 2：匿名块盒（Anonymous Block Box）**

```html
<div>
  <span>Inline 1</span>   <!-- 行盒 -->
  <p>Block child</p>      <!-- 块盒  ← 与行盒相邻违反规则二 -->
  <span>Inline 2</span>   <!-- 行盒 -->
</div>
```

生成的盒子结构：

```
<div> 块盒
  ├── 匿名块盒（规则二生成）
  │     └── <span>Inline 1</span> 行盒
  ├── <p> 块盒
  │     └── 匿名行盒包裹 "Block child"
  └── 匿名块盒（规则二生成）
        └── <span>Inline 2</span> 行盒
```

### 4.4 分层（Layer）

#### 4.4.1 分层的动机与意义

现代页面具有复杂的滚动、堆叠、动画效果。如果所有元素都绘制在 **同一张画布** 上，任何局部变更都会触发整张画布的重新绘制，性能极差。

浏览器因此引入 **图层（Layer）** 机制：将布局树按规则拆分为多个独立图层，每个图层可以 **独立绘制、独立光栅化、独立合成**。当某个图层变化时，只需重新处理该图层即可，其他图层不受影响。

> **分层是性能与内存的权衡**：图层越多 → 局部更新越快，但内存占用越高（每个图层都需要存储位图）。浏览器有复杂的启发式策略，不会无脑分层。

#### 4.4.2 影响分层决策的 CSS 属性

分层决策与 **堆叠上下文（Stacking Context）** 高度相关。以下属性会触发浏览器将元素提升为独立图层（不同浏览器策略略有差异）：

| 分类 | 常见触发属性 / 元素 |
|-----|-------------------|
| **3D 变换** | `transform: translate3d()`、`transform: rotate3d()`、`perspective: ...` |
| **视频 / 画布** | `<video>` 元素、`<canvas>` 元素（2D/WebGL） |
| **合成属性** | `opacity < 1`、`filter: ...`（需要单独处理 Alpha 混合） |
| **will-change** | `will-change: transform / opacity / top / ...`（开发者显式提示） |
| **滚动内容** | 拥有独立滚动条的元素（`overflow: scroll/auto` 且实际溢出） |
| **层叠提升** | 被其他合成层覆盖，需要提升到独立层以保证正确堆叠顺序 |

### 4.5 绘制（Paint）

绘制阶段（Paint）不直接输出像素，而是为 **每个图层** 生成一份 **绘制指令集（Paint Records / Display List）**：

```
图层 "Layer-0 (.header)" 的绘制指令：
  [1] FILL_RECT   color=#ffffff, x=0, y=0, w=1920, h=60          ← 背景色
  [2] DRAW_TEXT   text="Logo", font="20px sans-serif", x=24, y=38
  [3] DRAW_RECT   border=1px solid #e5e5e5, x=0, y=59, w=1920, h=1  ← 底部分割线

图层 "Layer-1 (.card)" 的绘制指令：
  [1] SAVE_STATE
  [2] SET_CLIP    rounded_rect x=0,y=0,w=300,h=200,r=8
  [3] FILL_RECT   color=linear-gradient(...), x=0,y=0,w=300,h=200
  [4] DRAW_IMAGE  src="cover.jpg", x=0,y=0,w=300,h=120
  [5] DRAW_TEXT   text="标题", x=16,y=148
  [6] RESTORE_STATE
```

绘制完成后，渲染主线程将 **图层树 + 每个图层的绘制指令集** 通过 IPC 提交给 **合成线程**，主线程的任务到此为止。

### 4.6 分块（Tiling）

合成线程收到图层数据后，不会一次性处理整个图层，而是将每个图层 **切分为多个矩形瓦片（Tile）**：

```
图层 2000 × 4000px（典型长页面）
  ┌──────┬──────┬──────┬──────┐
  │Tile00│Tile10│Tile20│Tile30│  ← 视口附近的高优先级 Tile
  ├──────┼──────┼──────┼──────┤
  │Tile01│Tile11│Tile21│Tile31│     优先光栅化、优先显示
  ├──────┼──────┼──────┼──────┤
  │Tile02│Tile12│Tile22│Tile32│  ← 中优先级
  ├──────┼──────┼──────┼──────┤
  │Tile03│Tile13│Tile23│Tile33│  ← 低优先级（远离视口）
  └──────┴──────┴──────┴──────┘
```

**分块的设计目的**：

1. **优先显示视口内容**：用户打开长页面时，先看到首屏内容，避免等待整个页面光栅化
2. **内存友好**：只需保留视口附近 + 预加载区域的位图，远离视口的 Tile 可以丢弃
3. **并行加速**：分块工作由合成线程从线程池调度多个工作线程并行完成

分块完成后，合成线程将每个 Tile 的信息提交给 GPU 进程进行光栅化。

### 4.7 光栅化（Rasterize）

光栅化（Rasterization）将每个 Tile 的 **绘制指令集** 转换为 **位图（Bitmap）**，即一张用二维数组存储的 RGBA 像素矩阵：

```
绘制指令集 ──(光栅化)──▶ 位图 (Bitmap)
                          ┌──────────────────────────┐
                          │ (0,0) RGBA(255,255,255,1)│
                          │ (0,1) RGBA(21,167,167,1) │  ← 每个像素 4 字节
                          │ ......                  │
                          └──────────────────────────┘
                                256 × 256 px 的 Tile = 256 KB
```

光栅化通常在 **GPU 进程** 中使用 **GPU 硬件并行加速** 完成（也支持 CPU 回退）。
GPU 进程内部会开启多个光栅化线程，按 **视口优先** 的顺序完成 Tile 光栅化：靠近视口的 Tile 先完成，远离视口的后完成，完全不可见的暂时跳过。

### 4.8 合成显示（Composite & Display）

合成阶段是渲染流水线的最后一步：

1. **合成线程** 收集每个 Tile 的位图，结合其位置、旋转、缩放、透明度等信息，生成 **Quad（四边形指引信息）**。每个 Quad 记录一个位图对应屏幕上的哪个矩形区域、应用何种变换矩阵。
2. 合成线程将所有 Quad 通过 IPC 提交给 **GPU 进程**。
3. GPU 进程调用系统图形 API（DirectX / OpenGL / Metal），将 Quad 交给 GPU 硬件进行最终合成，并调用显卡驱动输出到显示器的 **帧缓冲区（Framebuffer）**。
4. 显示器按固定刷新率（通常 60Hz / 120Hz / 144Hz）从帧缓冲区读取数据并显示到屏幕。

> **关键洞察**：`transform`（位移、旋转、缩放、倾斜）和 `opacity` 属性的应用发生在 **合成阶段**，由合成线程和 GPU 完成，**完全不经过渲染主线程**。这正是它们效率极高的根本原因。
>
> **关于沙盒**：渲染进程（包括主线程和合成线程）运行在沙盒中，没有直接访问 GPU 硬件的权限，必须通过 GPU 进程中转才能和显卡驱动交互。这是浏览器安全架构的重要一环。

## 第5章 重排 Reflow 与重绘 Repaint

### 5.1 重排（Reflow / Layout）

**重排**（也叫 **回流**，英文 Reflow / Layout）：当 DOM 的几何信息（尺寸、位置、结构）发生变化时，浏览器重新执行 **布局阶段**，即重新计算 Layout Tree。

#### 5.1.1 触发条件

任何会改变元素 **几何信息** 的操作都会触发重排：

| 类别 | 具体操作 / 属性 |
|-----|----------------|
| **DOM 结构变化** | 添加 / 删除 / 替换 DOM 节点、移动节点位置 |
| **盒模型属性** | 修改 `width`、`height`、`padding`、`border`、`margin` |
| **布局属性** | 修改 `top` / `right` / `bottom` / `left`（非 static 定位时） |
| **文本内容** | 输入框输入文字、修改文本内容（`textContent`）导致尺寸变化 |
| **定位与浮动** | 修改 `position`（`relative/absolute/fixed`）、`float` |
| **内容变化** | 图片加载完成（尺寸从 0 变为实际大小）、字体加载完成（字体替换导致行高变化） |
| **窗口变化** | `resize` 事件（视口变化导致所有百分比重新计算） |
| **盒类型变化** | 修改 `display`（如 `inline` → `block`，盒模型从行盒变为块盒） |

#### 5.1.2 重排的影响范围

浏览器基于 **渲染树的增量更新** 策略优化重排范围：

- **局部重排（Incremental Layout）**：只重新计算受影响的子树。例如修改某个普通 `div` 的宽度，只重排该 `div` 及其子节点 + 后续可能受挤压的兄弟节点。
- **全局重排（Global Layout）**：重新计算整棵布局树。例如修改 `<html>` 根节点的 `font-size`（em/rem 连锁变化）、触发 `window.resize`（视口变化）。

### 5.2 重绘（Repaint）

**重绘**（英文 Repaint / Paint）：当元素的 **可见样式** 发生变化，但 **不影响几何信息** 时，浏览器重新执行 **绘制阶段**，重新生成该图层的绘制指令集。

#### 5.2.1 触发条件

仅改变视觉外观、不改变尺寸/位置/结构的操作：

| 属性 / 操作 | 说明 |
|-----------|------|
| `color`、`background-color`、`border-color`、`outline-color` | 颜色类属性 |
| `box-shadow`、`text-shadow` | 阴影类属性 |
| `visibility`、`outline-style`、`background-image`（不改变尺寸） | 可见外观类 |
| 修改渐变、图案填充等 | 背景装饰类 |

> **核心关系**：**Reflow 一定会引起 Repaint**（布局变化后，绘制信息也必须重新生成）；但 **Repaint 不一定伴随 Reflow**（单纯颜色修改不需要重新布局）。

### 5.3 浏览器的异步合并机制

如果 JS 中每次修改样式都立即执行一次重排/重绘，连续 100 次修改就会触发 100 次流水线，性能极差。

为此浏览器采用 **批量异步更新** 策略：

```
JS 执行期间（事件循环的一个 Task 内）：
  style.width = "100px";   ┐
  style.height = "50px";   │ 不会立即重排，写入"渲染队列"
  style.margin = "8px";    │
  ...                      ┘

JS 执行完成（当前 Task 结束）：
  → 渲染主线程从渲染队列中取出所有样式变更
  → 一次性合并，只做 1 次 Layout + 1 次 Paint
```

这一机制极大降低了重排频率。

### 5.4 强制同步布局（Forced Synchronous Layout）

**强制同步布局**（简称 FSL）是指 JS 在同一个任务中，**先修改样式 → 然后立即读取布局属性**，迫使浏览器不得不中断异步合并、立即执行重排以返回最新值。

```javascript
// ❌ 反例：连续 100 次强制同步布局，性能灾难
for (let i = 0; i < 100; i++) {
  const div = divs[i];
  div.style.width = (i + 1) + "px";       // 写操作 → 进入渲染队列
  const h = div.offsetHeight;             // 读操作 → 浏览器被迫立即重排！
  // 每次循环都触发 1 次 Layout，100 次 = 100 次重排
}

// ✅ 正例：先批量写，再批量读
// 阶段一：全部写
for (let i = 0; i < 100; i++) {
  divs[i].style.width = (i + 1) + "px";
}
// 阶段二：全部读（只触发 1 次 Layout）
for (let i = 0; i < 100; i++) {
  const h = divs[i].offsetHeight;
}
```

常见会 **触发强制同步布局** 的读取属性 / 方法：

```
offsetWidth / offsetHeight / offsetLeft / offsetTop
clientWidth / clientHeight / clientLeft / clientTop
scrollWidth / scrollHeight / scrollLeft / scrollTop
getComputedStyle()
getBoundingClientRect()
scrollTo() / scrollIntoView()
```

### 5.5 Reflow / Repaint 优化策略

| 优先级 | 策略 | 说明 |
|-------|------|------|
| 🔴 P0 | **优先使用合成属性（transform / opacity）** | 只触发最后一步合成，不经过主线程 Layout + Paint |
| 🔴 P0 | **读写分离，批量操作** | 先写完所有样式，再统一读取布局属性，避免 FSL |
| 🟠 P1 | **使用 DocumentFragment / cloneNode 批量 DOM 操作** | 离线构建 DOM，一次性挂载到真实文档，只触发 1 次重排 |
| 🟠 P1 | **切换 `display: none` 后批量修改** | 修改前先隐藏（1 次重排），修改完成再显示（1 次重排），中间修改不触发 |
| 🟡 P2 | **对频繁变化的元素使用绝对定位脱离文档流** | 让重排影响范围限定在自身，不挤压周围元素 |
| 🟡 P2 | **用 `classList` / `className` 切换样式类** | 一次切换完成多项样式修改，替代逐条设置 `style.xxx` |
| 🟢 P3 | **图片设置显式尺寸** | 在 `<img>` 上声明 `width/height`，避免图片加载完成后挤压布局触发重排 |
| 🟢 P3 | **CSS 中为动画元素开启独立图层** | 合理使用 `will-change` 或 `transform: translateZ(0)`（仅当动画确实卡顿且已确认分层后有效） |

## 第6章 分层合成与 GPU 加速

### 6.1 合成层（Compositing Layer）创建条件

并非所有 Layer Tree 的图层都会成为独立的 **合成层（Compositing Layer）**。浏览器会进一步筛选，满足以下任一条件的图层会被提升为合成层，获得 **独立的 GPU 位图（Graphics Backing / Surface）**：

```
1. 显式 3D 或透视变换
   transform: translate3d(x,y,z) / translateZ(z) / perspective(...)

2. 视频 / Canvas / WebGL
   <video>、<canvas>（硬件加速上下文）、WebGL 画布

3. 动画 / 过渡中的合成属性
   正在进行 opacity / transform 的 transition 或 animation

4. will-change 声明
   will-change: transform / opacity / left / top / filter 等

5. 合成层覆盖 + 层叠顺序要求
   元素 Z 位于两个合成层 A、B 之间，为保持正确层叠顺序会被"被动提升"

6. 滚动容器（独立滚动条）
   overflow: scroll/auto 且内容实际溢出（主文档滚动条始终是合成层）

7. 其他 Chromium 内部规则
   拥有混合模式 mix-blend-mode / 拥有 filter 非 none 等
```

> **重要**：每创建一个合成层都需要分配额外的 GPU 显存。在移动端（显存比桌面端紧张得多），过多合成层会导致 **图层爆炸（Layer Explosion）**，反而引发掉帧。

### 6.2 堆叠上下文（Stacking Context）详解

堆叠上下文是浏览器决定元素 **谁覆盖谁** 的三维概念。创建堆叠上下文的元素会影响其子元素在 z 轴方向的排序规则。

#### 6.2.1 堆叠上下文的创建

以下任一声明会为当前元素创建一个 **新的局部堆叠上下文**：

| 类型 | 具体规则 |
|-----|---------|
| **根级** | `<html>` 文档根元素（天然创建全局堆叠上下文） |
| **定位 + z-index** | `position` 为 `relative/absolute/fixed/sticky` **且** `z-index` 不为 `auto` |
| **Flex/Grid 子项 + z-index** | 作为 flex/grid 容器的子项 **且** `z-index` 不为 `auto` |
| **opacity < 1** | `opacity` 值小于 1（需 Alpha 合成） |
| **transform / perspective** | `transform` / `perspective` 值不为 `none` |
| **filter / backdrop-filter** | `filter` / `backdrop-filter` 值不为 `none` |
| **will-change** | `will-change` 值为 `opacity/transform/filter` 等 |
| **isolation: isolate** | 显式声明隔离（推荐用于手动创建独立层叠上下文） |
| **mix-blend-mode** | 混合模式不为 `normal` |

**关键特性**：堆叠上下文具有 **封装性**。当父元素创建堆叠上下文后，子元素的 `z-index` 只在父级内部比较，不会与父元素外的同级元素直接比较。

```css
/* ❌ 常见陷阱：子元素 z-index 再大也跳不出父级堆叠上下文 */
.box-a { position: relative; z-index: 1; }       /* 堆叠上下文 A */
.box-a .child { z-index: 9999; }                 /* 只在 A 内排序，和 B 无关 */
.box-b { position: relative; z-index: 2; }       /* 堆叠上下文 B */
/* 结果：.box-b 永远覆盖 .box-a，哪怕 .box-a 内部子元素 z-index=9999 */
```

#### 6.2.2 层叠等级顺序

同一个堆叠上下文内部，元素按以下 **从下到上** 的顺序绘制（后绘制覆盖先绘制）：

```
┌──────────────────────────────────────────────────┐ 高（后绘制，覆盖下面）
│  ⑧  z-index > 0 的定位元素（堆叠上下文子元素）   │
│  ⑦  z-index = 0 的定位元素 / inline-level 盒子  │
│  ⑥  浮动盒子（float）                            │
│  ⑤  block-level 盒子（正常流）                   │
│  ④  行盒（display:inline）中的文本与内联内容     │
│  ③  背景与边框（当前堆叠上下文根元素自身）        │
│  ②  z-index < 0 的定位元素（堆叠上下文子元素）   │
│  ①  当前堆叠上下文的 border / background         │
└──────────────────────────────────────────────────┘ 低（先绘制）
```

### 6.3 GPU 加速工作原理

**GPU 加速**（GPU Acceleration）指的是将原本由 CPU 执行的渲染计算，转移到 GPU 的 **并行着色器阵列** 上执行，利用 GPU 海量 ALU 进行矩阵运算、纹理采样、像素合成。

浏览器渲染流水线中 GPU 主要负责两部分：

```
① 光栅化阶段（Rasterize）：
   将 Paint Records 转换为位图（GPU 以 Tile 为单位并行完成，速度是 CPU 的数倍~数十倍）

② 合成阶段（Composite）：
   将多个 Tile / Layer 的位图通过 GPU 纹理混合：
   - 应用 transform 矩阵（位移、旋转、缩放、倾斜、透视）
   - 应用 opacity（Alpha 混合）
   - 应用 filter（着色器实现卷积/模糊/颜色变换）
   - 最终输出到帧缓冲区
```

**为什么 GPU 做这些更快？**

- CPU 核心数少（4~16 核），但单核主频高，擅长串行复杂逻辑
- GPU 核心数极多（移动 GPU 数百核 ~ 桌面 GPU 数千核），虽然单核主频低，但大量简单任务（例如对每个像素执行相同计算）可以 **数据级并行（SIMD）**
- 合成阶段每个像素的计算高度同质化（矩阵乘法 + 纹理采样），完美契合 GPU 架构

### 6.4 `transform` 与 `opacity` 的高效性原理

从渲染流水线角度对比 `left/top` 动画与 `transform` 动画：

```
方案 A：用 left 做位移动画（❌ 低效）
  每一帧修改元素 style.left
    → 布局变化（Reflow）            ← 渲染主线程
    → 重绘（Repaint）               ← 渲染主线程
    → 分块 → 光栅化 → 合成         ← 合成线程 + GPU
  主线程每帧都在工作，JS 运行时会被阻塞导致掉帧

方案 B：用 transform: translateX() 做位移动画（✅ 高效）
  每一帧修改元素 transform
    → 合成阶段直接应用变换矩阵       ← 合成线程 + GPU
    → 主线程完全空闲，可同时执行 JS
  不触发 Reflow / Repaint，只触发最后一步合成
```

**为什么 `opacity` 也高效？**

当元素提升为合成层后，`opacity` 只需在合成阶段对该图层的位图做一次 **Alpha 混合**（每个像素颜色 × opacity 值），不需要重新生成绘制指令。但若元素 **不是合成层**，修改 `opacity` 仍会触发重绘（因为要重新计算该层中半透明区域与下层的混合绘制指令）。

> **最佳实践**：`opacity` 和 `transform` 动画应同时配合 `will-change: transform, opacity` 或任一合成层触发条件，确保元素提前提升为独立合成层，获得最高性能。

### 6.5 `will-change` 的正确使用姿势

`will-change` 的作用是 **提前告知浏览器**："这个元素的某个属性即将频繁变化，请提前优化（如提升合成层、预分配资源）"。

**错误用法**（反模式）：

```css
/* ❌ 滥用：页面所有元素都加 will-change，会导致图层爆炸，内存暴涨 */
* { will-change: all; }

/* ❌ 过度使用：列表 1000 项都加 will-change，移动端可能 OOM */
.list-item { will-change: transform; }

/* ❌ 提前移除太早：在动画开始前才加 will-change，没有预留提升时间 */
.box:hover { will-change: transform; transition: transform .3s; transform: scale(1.1); }
```

**正确用法**：

```css
/* ✅ 仅对"即将发生动画"的少量关键元素声明 */
/* 在父级 hover 时提前为子元素加 will-change，预留 ~200ms 提升时间 */
.card { transition: transform .3s; }
.card-wrapper:hover .card { will-change: transform; }
.card-wrapper:hover .card:hover { transform: translateY(-4px); }

/* ✅ 动画结束后清理 will-change，释放多余图层（通过 JS 动态移除类） */
/* 推荐做法：动画结束后移除 will-change，避免长期占用 GPU 显存 */
```

使用原则：

1. **少而精**：只给真正需要的元素声明，不要全局加
2. **提前声明**：给浏览器预留约 200ms 的图层提升时间
3. **用后清理**：静态页面的临时动画结束后移除类，不要长期保留 will-change
4. **不要迷信**：分层本身有显存开销，只在真实出现掉帧时才加，不要作为默认优化

## 第7章 性能优化实战

### 7.1 HTML / CSS / JS 层面优化

**HTML 层面**：

| 优化项 | 实施方法 |
|-------|---------|
| 精简 DOM 节点 | 首屏 DOM 节点 ≤ 1500 最佳（Chrome 推荐），避免深层嵌套（≤ 32 层） |
| 语义化标签 | 优先 `<nav>`、`<section>`、`<article>`，便于 CSS 选择器匹配优化 |
| 关键脚本位置 | 首屏核心脚本放 `<head>` 并用 `defer`，非关键脚本放 `</body>` 前或 `async` |
| `<img>` 声明尺寸 | `<img width=200 height=120>` 或 CSS aspect-ratio，避免 CLS（累积布局偏移） |

**CSS 层面**：

| 优化项 | 实施方法 |
|-------|---------|
| 内联首屏关键 CSS | 首屏必需样式通过 `<style>` 内联到 `<head>`，非关键 CSS 异步加载 |
| 移除未使用 CSS | 使用 Chrome Coverage 面板、PurgeCSS、UnCSS 工具删除死代码 |
| 避免过深选择器 | `.a .b .c .d .e span` → 改为给目标 span 加类名，减少匹配开销 |
| 避免 `*` 通配符选择器 | `* { box-sizing: border-box }` 开销尚可接受，但 `div *` 嵌套要谨慎 |
| 使用 CSS 变量替代 SASS 变量 | 运行时可切换主题，且现代浏览器对 CSS 变量已做 JIT 优化 |

**JavaScript 层面**：

| 优化项 | 实施方法 |
|-------|---------|
| 代码分割 | 路由级动态 import `() => import('./page.js')`，降低首屏 JS 体积 |
| Tree Shaking | 使用 ESM（`import/export`），避免 CommonJS，生产构建启用 sideEffects 分析 |
| 长任务拆分 | 单个同步任务 ≤ 50ms，超过用 `setTimeout / requestIdleCallback` 切片，避免阻塞输入响应 |
| 虚拟列表 | 长列表只渲染视口 + buffer 区域的 DOM（如 `react-window`、`vue-virtual-scroller`） |

### 7.2 减少重排重绘的技巧

#### 7.2.1 批量 DOM 操作（使用 DocumentFragment / cloneNode）

```javascript
// ❌ 反例：每次 appendChild 都可能触发重排
const list = document.getElementById("list");
for (let i = 0; i < 1000; i++) {
  const li = document.createElement("li");
  li.textContent = "Item " + i;
  list.appendChild(li);   // 1000 次 append，最坏触发 1000 次重排
}

// ✅ 方案一：DocumentFragment（轻量级 DOM 容器，挂载时才合并）
const frag = document.createDocumentFragment();
for (let i = 0; i < 1000; i++) {
  const li = document.createElement("li");
  li.textContent = "Item " + i;
  frag.appendChild(li);   // 离屏操作，不触发重排
}
list.appendChild(frag);   // 仅 1 次重排

// ✅ 方案二：cloneNode（复制现有节点批量更新）
const clone = list.cloneNode(false);  // 深拷贝为 false，只复制容器
for (let i = 0; i < 1000; i++) {
  const li = document.createElement("li");
  li.textContent = "Item " + i;
  clone.appendChild(li);
}
list.parentNode.replaceChild(clone, list);  // 一次性替换，1 次重排
```

#### 7.2.2 切换 `display: none` 隐藏后再批量修改

```javascript
const box = document.getElementById("box");
box.style.display = "none";   // 1 次重排（从文档流移除）
// 中间 100 次样式修改：全部不触发重排
box.style.width = "300px";
box.style.height = "200px";
box.style.padding = "16px";
box.style.margin = "8px";
// ...
box.style.display = "block";  // 1 次重排（重新加入文档流）
// 合计 2 次重排，而不是 100+ 次
```

#### 7.2.3 使用 `classList` 批量切换样式类

```css
/* 将一组样式预定义为一个类 */
.card-active {
  width: 320px;
  padding: 24px;
  border-radius: 12px;
  box-shadow: 0 8px 24px rgba(0,0,0,.12);
}
```

```javascript
// ❌ 逐条修改，理论上最多 4 次重排（虽有合并机制但仍有开销）
card.style.width = "320px";
card.style.padding = "24px";
card.style.borderRadius = "12px";
card.style.boxShadow = "0 8px 24px rgba(0,0,0,.12)";

// ✅ 一次性切换，只触发 1 次样式解析 → 1 次重排
card.classList.add("card-active");
```

#### 7.2.4 脱离文档流（position: absolute / fixed）

```html
<!-- ❌ 拖拽/动画元素在文档流中，每次位置变化都会挤压邻居引起大面积重排 -->
<div class="list">
  <div class="drag-item" style="position: static;">可拖拽卡片</div>
  <div class="item">Item 1</div>     <!-- 每次拖拽都要重排 Item1/2/3 -->
  <div class="item">Item 2</div>
  <div class="item">Item 3</div>
</div>

<!-- ✅ 拖拽元素用 position: absolute / fixed 脱离文档流 -->
<div class="list" style="position: relative;">
  <div class="drag-item" style="position: absolute; left: 0; top: 0;">可拖拽卡片</div>
  <div class="item">Item 1</div>     <!-- 拖拽只重排 drag-item 自身，周围不影响 -->
  <div class="item">Item 2</div>
  <div class="item">Item 3</div>
</div>
```

### 7.3 CSS 动画性能最佳实践

| 原则 | 推荐实现 | 应避免 |
|-----|---------|--------|
| **仅使用合成属性** | `transform`（translate/scale/rotate）、`opacity` | `left` / `top` / `width` / `height` / `margin` 动画 |
| **使用 CSS 动画优先于 JS 动画** | `transition`、`@keyframes`（可运行在合成线程） | `setInterval` 手动插值更新 DOM 样式（阻塞主线程） |
| **声明 will-change** | 在动画前 200ms 左右为容器元素添加 `will-change: transform, opacity` | 永久挂在所有元素上（导致图层爆炸） |
| **尽量使用 requestAnimationFrame** | JS 必须驱动的动画用 `requestAnimationFrame(cb)` 与 vsync 对齐 | `setInterval(cb, 16)`（与显示刷新不同步，易掉帧） |
| **避免频繁布局抖动** | 动画过程中不要读取 `offsetWidth/scrollTop` 等布局属性 | 每帧先写样式再读布局属性（FSL 问题） |

**标准高性能 CSS 动画模板**：

```css
.card {
  width: 200px;
  height: 120px;
  /* 动画前预留 will-change（例如父级 :hover 时提前添加） */
  transition: transform .25s ease, opacity .25s ease;
  will-change: transform, opacity;   /* 仅在确实需要时声明 */
}

/* 只动 transform / opacity */
.card:hover {
  transform: translateY(-6px) scale(1.03);
  opacity: .95;
}

@keyframes float {
  0%   { transform: translateY(0); }
  50%  { transform: translateY(-8px); }
  100% { transform: translateY(0); }
}
.floating { animation: float 3s ease-in-out infinite; }
```

### 7.5 代码示例：低效实现 vs 高效实现

#### 示例 1：表格行高动态调整

```javascript
const rows = document.querySelectorAll("table tr");

// ❌ 低效实现：交替"写-读"，触发强制同步布局
rows.forEach(row => {
  row.style.height = "40px";          // 写：入渲染队列
  const currentH = row.offsetHeight;  // 读：被迫立即重排！每行 1 次 Layout
  console.log(currentH);
});

// ✅ 高效实现：读写分离
// Phase 1：全部写（只入队，不重排）
rows.forEach(row => {
  row.style.height = "40px";
});
// Phase 2：全部读（仅触发 1 次 Layout）
rows.forEach(row => {
  const currentH = row.offsetHeight;
  console.log(currentH);
});
```

#### 示例 2：元素动画（left/top vs transform）

```css
/* ❌ 低效：每帧修改 left → 每帧触发 Reflow + Repaint */
@keyframes move-bad {
  from { left: 0;      }
  to   { left: 400px;  }
}
.box-bad {
  position: absolute;       /* 必须配合定位 */
  animation: move-bad 1s linear infinite alternate;
}

/* ✅ 高效：每帧修改 translateX → 只触发合成阶段 */
@keyframes move-good {
  from { transform: translateX(0);   }
  to   { transform: translateX(400px); }
}
.box-good {
  animation: move-good 1s linear infinite alternate;
  will-change: transform;   /* 提前提升为合成层（可选） */
}
```

在 Performance 面板录制对比：方案 A 的 Main 线程火焰图会看到大量连续的 Layout / Paint；方案 B 的 Main 线程几乎空闲，动画 100% 跑在合成线程。

## 第8章 常见面试题汇总

### 8.1 基础概念题

#### Q1：浏览器是如何渲染一个页面的？请完整描述渲染流水线。

**【参考回答】**

当浏览器网络进程通过 HTTP(S) 获取到 HTML 文档后，将数据交给渲染进程，渲染主线程通过事件循环取出渲染任务，开启完整的 **8 步渲染流水线**：

**第 1 步：解析 HTML（Parse HTML）**
- 渲染主线程使用分词器（Tokenizer）将 HTML 字符串转换为 Token 流，再通过树构建器生成 **DOM 树**。
- 同时，预解析线程提前扫描 `<link>`、`<script>` 等标签，并行下载外部 CSS/JS。
- CSS 被解析为 **CSSOM 树**，包含浏览器默认样式、用户样式、作者样式（外部/内部/内联）。

**第 2 步：样式计算（Recalculate Style）**
- 遍历 DOM 树每个节点，按四步流程计算 **Computed Style**：确定声明值 → 层叠冲突（源重要性 → 优先级 → 次序）→ 使用继承 → 使用默认值。
- 相对单位（em、rem、百分比）、颜色名（red→rgb）等标准化为绝对值。

**第 3 步：布局（Layout）**
- 遍历带样式的 DOM 树，结合 **包含块** 规则，计算每个节点的尺寸（宽高）和位置（x、y 坐标），产出 **Layout Tree**。
- Layout Tree 与 DOM 树不一一对应：`display: none` 的节点被排除，伪元素、匿名盒会被额外生成。

**第 4 步：分层（Layer）**
- 浏览器基于堆叠上下文与启发式策略，将 Layout Tree 拆分为多个 **图层（Layer Tree）**，便于局部更新。
- `transform`、`opacity < 1`、`<video>/<canvas>`、`will-change`、独立滚动条等会触发独立图层的创建。

**第 5 步：绘制（Paint）**
- 渲染主线程为 **每个图层** 生成一份 **绘制指令集（Paint Records / Display List）**，描述该层的背景色、文字、边框、图片该如何画。
- 完成后将图层树 + 绘制指令集通过 IPC 提交给合成线程。

**第 6 步：分块（Tiling）**
- 合成线程将每个图层切分为多个矩形瓦片（通常 256×256 或 512×512px）。
- 视口附近的 Tile 赋予高优先级，远离视口的低优先级，避免首屏等待整页处理。
- 分块由合成线程从线程池调度多个工作线程并行完成。

**第 7 步：光栅化（Rasterize）**
- 合成线程将每个 Tile 的绘制指令提交给 GPU 进程。
- GPU 进程使用 GPU 硬件并行完成光栅化：将绘制指令转换为位图（RGBA 像素矩阵）。

**第 8 步：合成显示（Composite & Display）**
- 合成线程收集每个 Tile 的位图，结合位置、变换矩阵、透明度生成 **Quad（四边形指引信息）**。
- 将 Quad 提交给 GPU 进程，GPU 进程调用图形 API 驱动 GPU 硬件完成最终画面合成，写入帧缓冲区。
- 显示器按固定刷新率（60/120/144Hz）从帧缓冲区读取，最终显示到屏幕。

#### Q2：什么是重排（Reflow）和重绘（Repaint）？它们的关系是什么？

**【参考回答】**

**重排（Reflow / Layout）**：当 DOM 元素的 **几何信息**（尺寸、位置、结构）发生变化时，浏览器需要重新执行 **布局阶段**，重新计算 Layout Tree。
- 典型触发：修改 `width/height/padding/margin/top/left`、增删 DOM 节点、图片加载完成、`window.resize`。
- 成本：极高，需要递归/增量遍历布局树。

**重绘（Repaint / Paint）**：当元素的 **可见样式**（颜色、阴影、边框色、背景色）发生变化，但 **不影响几何信息** 时，浏览器重新执行 **绘制阶段**，生成新的绘制指令集。
- 典型触发：修改 `color/background-color/box-shadow/outline/visibility`。
- 成本：较高，需要遍历该图层重新生成绘制指令，但比重排便宜。

**关系**：
> **Reflow 一定会触发 Repaint**（布局变化后，绘制信息必然需要重新生成）；
> **Repaint 不一定伴随 Reflow**（单纯修改颜色，尺寸/位置不变，无需重新布局）。

为降低重排/重绘频率，浏览器内置 **异步合并策略**：在同一事件循环任务中的多次样式修改会写入渲染队列，任务结束后一次性合并为 1 次 Reflow + 1 次 Repaint。但如果 JS 在修改后 **立即读取布局属性**（如 `offsetWidth`），会触发 **强制同步布局**，打破异步合并。

---

#### Q3：什么是关键渲染路径（CRP）？如何优化？

**【参考回答】**

**关键渲染路径（Critical Rendering Path, CRP）** 是浏览器从收到 HTML、CSS、JS 资源开始，到完成首屏像素绘制（First Paint）所需经过的最短关键路径。核心步骤：`HTML 解析 → DOM 构建 → CSS 解析 → CSSOM 构建 → 样式计算 → 布局 → 绘制 → 合成显示`。

CRP 的两个阻塞特性：
- CSS **不阻塞 HTML 解析**（预解析线程提前下载），但 **阻塞渲染**（必须等 CSSOM 就绪才能样式计算）；
- 默认 `<script>` **同时阻塞 HTML 解析和渲染**（JS 可能修改 DOM/CSS，必须暂停）。

**CRP 优化三板斧**：

| 维度 | 具体方案 |
|-----|---------|
| **① 减少关键资源数量** | ① 首屏 CSS 内联到 `<head>`；② 非关键 CSS 用 `media="print"` + onload 异步加载；③ 非首屏 JS 用 `defer`/`async` 或动态 `import()`；④ 非首屏图片用 `loading="lazy"` |
| **② 减小关键资源体积** | ① 启用 Gzip/Brotli 压缩；② 移除未使用 CSS（Coverage + PurgeCSS）；③ JS Tree-Shaking + 代码分包；④ 字体子集化（font-spider / pyftsubset） |
| **③ 减少往返次数 / 降低 RT 影响** | ① 使用 CDN 缩短物理距离；② `<link rel="preconnect dns-prefetch">` 提前握手；③ 启用 HTTP/2（或 HTTP/3）多路复用；④ `<link rel="preload">` 关键资源高优先级加载 |

### 8.2 深入原理题

#### Q4：为什么 CSS 不会阻塞 HTML 的解析，但会阻塞页面的渲染？

**【参考回答】**

**CSS 不阻塞 HTML 解析的原因**：浏览器启动了 **预解析线程（Preload Scanner）**。在主线程开始逐行解析 HTML 的同时，预解析线程会"预览"整个 HTML 文档，提前扫描 `<link>`、`<script>`、`<img>` 等标签，提前发起外部 CSS 的下载请求。主线程在解析到 `<link>` 时，不需要原地等待 CSS 返回，而可以继续解析后续的 HTML 标签。因此 HTML 解析和 CSS 下载/解析是 **并行的**。

**CSS 阻塞页面渲染的原因**：渲染流水线的 **样式计算阶段** 必须等 DOM 树和 CSSOM 树 **都准备好** 才能开始。如果先渲染出了"没有 CSSOM 的半成品页面"，等 CSS 到达后页面样式又突然全变，会出现严重的 **FOUC（无样式内容闪烁）** 问题，用户体验极差。因此浏览器宁愿延迟一点时间渲染，也要等样式就绪后一次性渲染出正确的页面。

> **间接阻塞**：当 HTML 解析到 `<script>` 且此时 CSSOM 尚未构建完成时，浏览器必须 **先等 CSSOM 构建完成，再执行 JS**。因为 JS 中可能调用 `getComputedStyle` 访问样式，必须拿到最新的 Computed 值。所以 CSS 还会 **间接阻塞 JS 的执行**，而 JS 又会阻塞 HTML 解析，形成 **CSS → JS → HTML** 的链式阻塞链路。

---

#### Q5：为什么 JavaScript 会阻塞 HTML 的解析？

**【参考回答】**

因为 JS 运行期间 **可能修改 DOM 结构和 DOM 的解析过程**，为避免解析结果与实际 DOM 状态不一致，浏览器必须在执行 JS 时暂停 HTML 解析。

具体可能出现的竞态问题：

1. **`document.write()`**：JS 可以在解析过程中调用 `document.write("<div>...")` 向 HTML 流动态插入内容。如果此时 HTML 仍在并行解析，插入的位置无法确定，后续节点的父子关系会错乱。
2. **DOM 结构修改**：JS 可以 `appendChild / removeChild` 修改当前解析中的节点。如果解析器正在构建该节点的子树，结构会被打乱。
3. **样式访问**：JS 可能读取 `getComputedStyle` / 修改内联样式，需要样式计算与 DOM 构建保持一致的快照。

**解除阻塞的两种方案**：

- `<script **async** src="a.js">`：下载不阻塞 HTML 解析；下载完成后 **立即执行**，此时会暂停解析。多个 async 脚本 **执行顺序不保证**（谁先下载完谁先执行）。适合无依赖独立脚本。
- `<script **defer** src="b.js">`：下载不阻塞 HTML 解析；下载完成后 **不立即执行**，等待 HTML 完全解析完成、`DOMContentLoaded` 之前，按出现顺序依次执行。多个 defer 脚本 **顺序保证**。**业务逻辑脚本首选 defer**。

---

#### Q6：为什么 `transform` 的效率比 `left/top` 高？请从渲染流水线角度说明。

**【参考回答】**

从浏览器 8 步渲染流水线的角度，两者在每帧更新时触发的阶段完全不同：

**使用 `left` / `top` 修改位置（低效）**：
```
每一帧：
  修改元素 style.left
    → 触发布局阶段（Reflow）：必须重新计算元素及其邻居节点的尺寸和位置   ← 渲染主线程
    → 触发绘制阶段（Repaint）：重新生成包含该元素的图层的绘制指令集       ← 渲染主线程
    → 提交合成线程 → 分块 → 光栅化 → 合成 → 显示
```
每帧都让渲染主线程做了布局+绘制两件重活。如果主线程同时还在跑 JS、处理事件，就很容易超过 16.6ms 的单帧预算，产生掉帧卡顿。

**使用 `transform: translateX/Y` 修改位置（高效）**：
```
每一帧：
  修改元素 transform
    → 直接进入合成阶段
    → 合成线程对该图层的位图应用一次 2D/3D 变换矩阵（GPU 并行完成）    ← 合成线程 + GPU
    → 显示
```
完全 **跳过了渲染主线程的布局、分层、绘制三个阶段**，也跳过了分块和光栅化（图层位图已存在），只走最后一步合成。渲染主线程可以完全空闲去处理 JS 逻辑和用户输入。

> **额外好处**：主线程再忙也 **不会阻塞 `transform` 动画**。比如 JS 里跑一个耗时 1 秒的 `for` 循环，期间 `left` 动画会彻底停住 1 秒，而 `transform` 动画仍会丝滑流畅，因为它不在同一个线程。

### 8.3 性能优化实践题

#### Q7：如何减少页面的重排和重绘？请列举至少 5 种具体方案。

**【参考回答】**

以下是 7 种业界广泛使用的方案：

**方案一：优先使用合成属性 `transform` / `opacity` 实现动画**
- 用 `transform: translateX()` 替代 `left/top` 做位移动画；用 `transform: scale()` 替代 `width/height` 做缩放。
- 只触发合成阶段，跳过 Reflow + Repaint。

**方案二：批量 DOM 操作，使用 DocumentFragment 或 cloneNode**
- 循环创建 1000 个 `<li>` 时，不要直接对真实 DOM 节点 `appendChild`，而是先 append 到 `document.createDocumentFragment()`，最后一次性把 Fragment 加入真实 DOM，从 1000 次重排减少为 1 次。

**方案三：样式读写分离，避免强制同步布局（FSL）**
- 不要在"改样式"后立刻"读布局属性"（如 `offsetWidth`、`getBoundingClientRect`）。
- 先 **批量写完** 所有样式，再 **批量读** 所有布局属性，让浏览器只合并执行 1 次 Layout。

**方案四：使用 `classList` / 切换 `display: none` 批量修改**
- 将一组样式修改预定义为 CSS 类，用 `el.classList.add("active")` 一次性切换，不要逐条 `el.style.xxx = yyy`。
- 对大量样式修改：先 `el.style.display = "none"` 让元素脱离文档流（1 次重排），中间随便改（0 次重排），改完再恢复显示（1 次重排），合计 2 次。

**方案五：对频繁变化的元素使用 `position: absolute / fixed` 脱离文档流**
- 拖拽、悬浮、轮播图等频繁变化位置的元素，设置绝对/固定定位，让它的重排影响范围限定在自身，不挤压周围的兄弟元素和后续元素。

**方案六：图片声明尺寸 + 使用 CSS `aspect-ratio`**
- `<img width=800 height=450>` 或 `.img-box { aspect-ratio: 16/9 }`，避免图片加载完成后突然撑开布局引起 CLS（累积布局偏移）和额外重排。

**方案七：合理使用 `will-change` 提前提升为独立合成层**
- 对即将开始动画的元素（例如卡片 hover 上浮、模态框弹出）提前 200ms 左右添加 `will-change: transform, opacity`，让浏览器预留图层提升时间。
- **注意不要滥用**：动画结束后移除类，不要挂在所有元素上，否则会引发图层爆炸、显存暴涨。

---

#### Q8：`will-change` 属性有什么作用？使用时有哪些注意事项？

**【参考回答】**

**作用**：`will-change` 是 CSS 提供的 **"开发者向浏览器的提前告知"** 属性，它提示浏览器："该元素的某个属性即将频繁变化，请提前做好优化准备"。浏览器通常的反应包括：

1. **提前提升为独立合成层**：为该元素分配独立的 GPU 位图，避免动画开始时才临时提升导致的"首帧闪烁"；
2. **预分配显存与光栅资源**：让 Tile 光栅化提前完成；
3. **调整渲染调度策略**：对该图层所在区域的重排/重绘采用更激进的局部更新。

**使用时的 5 条注意事项**：

| 注意事项 | 说明 |
|---------|------|
| **① 少而精，不要滥用** | 绝对禁止 `* { will-change: all }`。每个合成层占用额外 GPU 显存，过多会导致"图层爆炸"，移动端可能 OOM 崩溃。 |
| **② 提前声明，给浏览器留准备时间** | 不要等动画触发瞬间才加 `will-change`（比如 `:hover` 同时声明 will-change 和 transition），那样浏览器来不及准备。应在 **动画触发前约 200ms** 的"前置事件"中声明，如父元素 `:hover` 时给子元素加 will-change。 |
| **③ 用后即焚，静态状态下移除** | 临时动画（如弹窗打开、下拉展开）结束后，应移除 will-change 类名。长期保留会持续占用 GPU 显存。 |
| **④ 不要迷信，只在真实掉帧时加** | will-change 是"急救药"不是"保健品"。默认 CSS animation/transition 已经是合成层友好的。仅当用 Performance 面板确认存在合成线程瓶颈、且动画确实掉帧时才使用。 |
| **⑤ 只声明即将真正变化的属性** | 写 `will-change: transform, opacity` 而不是 `will-change: all`。声明不存在的变化是无意义的额外开销。 |

#### Q9：什么是强制同步布局（Forced Synchronous Layout）？如何避免？

**【参考回答】**

**定义**：浏览器为了提升性能，会将一个事件循环任务内的多次样式修改合并为一次 Layout（异步更新策略）。但如果 JS 在 **同一个任务中先修改样式，然后立即读取布局属性**（如 `offsetWidth`、`scrollTop`），浏览器为了返回 **最新的、准确的** 布局值，不得不 **立即中断合并、立刻执行一次 Layout**，这种违反异步合并策略的现象就叫 **强制同步布局（Forced Synchronous Layout, FSL）**，在 Chrome DevTools Performance 面板中会标红警告。

**典型反例**：

```javascript
for (const el of elements) {
  el.style.width = el.offsetWidth + 1 + "px";   // 先写后读，每循环 1 次 FSL
}
```

1000 次循环 → 1000 次 FSL → 主线程卡死。

**避免方法**：

| 方法 | 说明 |
|-----|------|
| **读写分离** | 把所有"写操作"放前半段全部执行完毕，再把所有"读操作"放后半段批量执行。只触发 1 次 Layout。 |
| **使用 `requestAnimationFrame`** | 将"读布局"和"写样式"分别放在两帧。第 N 帧读取上帧的布局值，第 N+1 帧写入。 |
| **缓存布局值，避免重复读取** | 在循环开始前，把需要的 `offsetWidth/scrollTop` 一次性读取到变量中，循环内只用变量。 |
| **将样式修改合并到类切换** | 用 `classList.add()` 一次性应用一组样式，而不是逐条 `style.xxx` 赋值。 |

**读写分离的正例**：

```javascript
// Phase 1：先把所有需要的布局值读出来（1 次 Layout）
const widths = elements.map(el => el.offsetWidth);
// Phase 2：再用读出的值批量写样式（0 次额外 Layout，最后合并 1 次）
elements.forEach((el, i) => {
  el.style.width = (widths[i] + 1) + "px";
});
```

### 8.4 综合场景分析题

#### Q10：一个长列表页面滚动卡顿，请从浏览器渲染原理角度分析可能的原因，并给出优化思路。

**【参考回答】**

长列表滚动卡顿的本质原因是 **单帧耗时超过了 16.6ms**（60FPS 目标）。从渲染流水线的 **5 个关键阶段** 逐一排查：

---

**🔴 原因一：滚动事件回调过重，JS 阻塞主线程**
- 表现：Performance 面板 Main 火焰图中，`scroll` 事件处理器每次耗时 > 10ms，且连续调用。
- 典型问题：`onscroll` 里做大量 DOM 查询/修改、防抖节流失效、每次滚动读取布局属性引发 FSL。
- 优化：
  - 用 `passive: true` 注册滚动监听：`window.addEventListener("scroll", cb, { passive: true })`，告诉浏览器回调里不调 `preventDefault`，不阻塞 GPU 滚动。
  - 配合 `requestAnimationFrame` 或 Lodash `_.throttle(cb, 16)` 降低处理频率。
  - 滚动回调内 **不读布局属性、不改 DOM**，只做"状态收集 + 下一帧更新"的读写分离。

---

**🔴 原因二：滚动引发大面积重排（长列表每一项都参与布局）**
- 表现：滚动时 Main 线程 Layout 长条 > 8ms，Layout 范围覆盖整棵列表。
- 典型问题：列表项高度使用 JS 动态计算、每项都有 margin collapse 递归影响、未脱离文档流。
- 优化：
  - **使用 CSS Sticky 替代 JS 吸顶**：`position: sticky; top: 0;`，吸顶逻辑交给合成线程。
  - **列表项使用固定高度 + `contain: layout paint size`**：告诉浏览器每个列表项的布局、绘制、尺寸与外部无关，浏览器增量更新。
  - **切换 BFC**：`overflow: hidden` 或 `display: flow-root`，避免 margin 塌陷递归传递。

---

**🔴 原因三：滚动引发大面积重绘（Paint 风暴）**
- 表现：Performance 面板 Paint 长条连续且覆盖大量区域，Layers 面板显示"更新区域"覆盖整个视口。
- 典型问题：列表项中使用 `background-attachment: fixed`（每滚动一像素都整页重绘）、半透明渐变背景、未分层独立滚动容器。
- 优化：
  - 移除 `background-attachment: fixed`，改用伪元素 + `position: fixed` + 独立合成层实现视差。
  - 滚动容器显式 `will-change: scroll-position` 或 `transform: translateZ(0)` 提升合成层。
  - 为列表图片占位设置 `background-color`，避免图片异步加载时反复重绘。

---

**🟠 原因四：DOM 节点过多，长列表无虚拟化**
- 表现：Elements 面板中列表项 DOM 上万级；Main 线程每次 Recalculate Style + Layout 时间线性增长。
- 优化：
  - **使用虚拟列表（Virtual Scrolling）**：只渲染视口内 ± buffer（上下各 5~10 项，~100 个节点），其余项用"占位空白"撑高度。技术选型：React（react-window / react-virtuoso）、Vue（vue-virtual-scroller / vue-virtual-scroll-list）、Svelte（svelte-virtual-list），或原生实现基于 IntersectionObserver。
  - 首屏控制 DOM 节点总数 ≤ 1500，深度 ≤ 32 层（Chrome 官方推荐阈值）。

---

**🟠 原因五：图片解码延迟与 CLS（累积布局偏移）**
- 表现：滚动过程中图片加载突然撑开布局 → Layout；图片解码在主线程完成 → Long Task。
- 优化：
  - `<img>` 上声明 `width`/`height` 属性，或 `.img { aspect-ratio: 16/9; }` 预留占位，消除布局偏移。
  - 使用 `loading="lazy"` 非首屏图片懒加载，减少首屏并发请求。
  - 使用 `decoding="async"` 将图片解码让出主线程：`<img decoding="async" loading="lazy" ...>`。

---

**🟡 原因六：图层爆炸或合成层过多**
- 表现：Layers 面板图层数 ≥ 50，每个列表项都是独立合成层；Compositor 线程帧合成耗时 > 5ms。
- 典型问题：每个列表项都加了 `transform: translateZ(0)` / `will-change: transform` / `backface-visibility: hidden`。
- 优化：
  - 移除不必要的图层提升代码，只在真正动画的极少量卡片上保留。
  - 使用 Chrome DevTools Layers 面板的"Layer Explosion"分析，定位批量提升元凶。

---

**排查与验证**：按照 Performance 面板的 **Summary → Main 火焰图（定位具体哪个阶段慢）→ Layers 面板（分层是否合理）→ 逐帧柱状图（是否稳定 ≤ 16.6ms）** 的顺序定位瓶颈，然后对应上述 6 类原因套用优化方案，每次优化后再录制对比数据，量化 FPS 提升和帧耗时下降。
